Guard XPC callbacks with a Sendable source scan

Standing source-scanning guard for issue #0053: `YardKit/Tests/YardKitTests/XPCSendableTests.swift` (4 tests) scans the XPC callback trigger sites in `Sources/YardKit`, `Switchyard/` and `BrokerAgent/` and fails when a callback closure lacks `@Sendable` or an `exportedObject`-bearing `shouldAcceptNewConnection` is hosted by a class that is not `nonisolated`. The runtime half (kill-app-mid-request, interruptionHandler, invalidationHandler against live processes) is #0054's and was not faked.

"Nothing needed fixing" was NOT quite true: three real gaps, all latent rather than live traps under today's target settings. The BrokerAgent target already defaults to nonisolated (so its callbacks could not inherit MainActor), and the YardKit package target has no MainActor default either — but the annotations are the tree's stated convention ("load-bearing, not decoration"), they protect against a future change of a target's default isolation, and they let the guard run exemption-free. The `@unchecked Sendable` on BrokerService is honest: `owner` is immutable, `registry` is a lock-guarded `EndpointRegistry`. Without it the now-`@Sendable` invalidationHandler could not capture the non-Sendable service under the broker's Swift 6 complete checking — verified by the unsigned xcodebuild build below.

`nonisolated` on pure helpers (criterion 2, by eye): `AppXPCServer.repairGate` was already `nonisolated`; `EndpointRegistry`, `ResumeOnce`, `Transferred` are lock-guarded/`@unchecked Sendable`; `AppService`/`ListenerDelegate` in the app were already `nonisolated`. No pure helper needed fixing beyond the two BrokerAgent classes above.

## The guard

`XPCSendableTests.isolationViolations(lines:fileName:)` scans file text (no compile-time check is possible — no `#if` can observe closure isolation). Per non-comment code line (LayeringTests idiom, including the `#expect(!swiftFiles.isEmpty)` vacuity guard and the same symlink-shy recursive walk):

- `remoteObjectProxyWithErrorHandler`, `interruptionHandler`, `invalidationHandler`, or a `reply:` closure literal → `@Sendable` must appear on the trigger line or the next one. Two-line window because the tree uses both shapes: `{ @Sendable [weak self] ...` on the trigger line (AppXPCServer, BrokerConnection now) and `@Sendable error in` on the line after the brace (AppConnection:205).
- An `exportedObject`-bearing `shouldAcceptNewConnection` (method is not a closure literal, so `nonisolated` is the method-level equivalent) → the nearest `class` declaration within 30 lines above must contain `nonisolated`; `exportedObject` must appear within 15 lines below the trigger before the class is held to it.

The matcher itself is proven live: `matcherFlagsEveryTriggerKindMissingItsAnnotation` feeds it five known-bad snippets (the tree's real shapes with the annotation removed) and asserts exactly one violation for each; `matcherAcceptsEveryAnnotatedShapeInTheTree` feeds the five annotated shapes and asserts zero violations. Both pin their snippet dictionary at count 5 so a new trigger kind must arrive with its own known-bad pair. Exemptions: none — no site in the tree needed one.

Outside-package tolerance choice: `Switchyard/` and `BrokerAgent/` are scanned per-directory, tolerated individually when absent (the package is a self-contained SwiftPM tree that must stay testable without the app checkout), with two non-silent bounds — `Switchyard.xcodeproj` beside the package is the anchor for "this repository": with it present, both directories must have been scanned (count asserted == 2) and each scanned directory's file count is asserted non-empty; with it absent (standalone package), the skip asserts no directory was half-found. In this repository both directories exist and both counts are asserted. Walk-up correctness is pinned transitively: the package-side test proves the `#filePath`-derived package root is real, and the repo root is one deletion further.

## Not done / for review

- Runtime scenarios live in #0054's manual script by design; this round did not attempt them.
- Scan scope follows the issue exactly: `Sources/YardKit` + `Switchyard/` + `BrokerAgent/`. A grep across all of `Sources/` found no trigger sites in any other package target, but note `YardUI` compiles with `defaultIsolation(MainActor.self)` and is outside the pinned scope — if XPC callbacks ever move there, the scope should widen.
- The two-line `@Sendable` window is pragmatic: an annotation three lines after the trigger would be flagged (fail-safe direction). Delegate hosting-class lookup walks back at most 30 lines.
