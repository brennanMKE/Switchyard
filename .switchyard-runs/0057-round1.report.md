## The wire

- `ResolveRequest { commonDir, pathspec: String?, timeoutSeconds }` — the
  pathspec is omitted when nil; `matches(path:)` is exact-or-under-the-named-
  directory (`dir` matches `dir/f.txt`, not `dirf.txt`).
- `PathResolution { path, kind: ConflictKind, choice: PathChoice,
  editedContent?, note? }` — nils omitted (#0129 Decision 4). `ConflictKind`
  is the seven porcelain XY pairs (String raw values = the wire keys, so the
  record reads next to porcelain v2 output and transfers from
  `ConflictedFile.Kind` by rawValue). `PathChoice`: useOurs / useTheirs /
  editedContent / keepDeletion / keepModification / renameTakeOurs /
  renameTakeTheirs — the design table's vocabulary, closed.
- `ResolveReply` — enum with exactly one wire shape: `{"resolutions":[…]}`
  or `{"cancelled":true}`. An EMPTY resolutions array is a real wire form
  (Submit with nothing staged) and is deliberately distinct from cancel.
- `ResolveOutcome` — `decided(ResolveReply)` / `timedOut` / `superseded`,
  byte-pinned (`{"decided":…}` / `{"timedOut":true}` / `{"superseded":true}`).
  **Assumption recorded: cancel rides `.decided(.cancelled)`** — "cancel is a
  decided outcome carrying exit 7" — the way a rejected review rides
  `.decided`; there is no separate `.cancelled` outcome case, so the fact can
  never be encoded two ways.

## The store

`PendingResolveStore` mirrors `PendingReviewStore`: keyed by resolved
commonDir, ONE pending per repo, second `resolve --wait` SUPERSEDES (review
semantics — ask's FIFO queue is deliberately not copied), per-request typed
`.timedOut`, `resolve(commonDir:answer:)` / `resolve(id:answer:)`, and the
`onPendingChange` hook for round 2's pane. Locks, not an actor; never AppKit.
One scanner-driven spelling: the resolve methods take `answer:` not `reply:`
(same as `PendingAskStore`) — XPCSendableTests' audit requires `@Sendable`
on any line naming `reply:`, and these parameters are values, not closures.

## The engine apply half (`ResolveApply.apply(resolution:path:at:git:)`)

Runs inside `JournalCheckpoint.around(operation: "resolve", …)` (#0027/#0212
discipline — one entry per apply, `undo`-able; `applyWithoutCheckpoint`
exists for callers composing several applies into one entry). The conflicted
lookup, stage-blob read (`git cat-file blob <stage-oid>`), write, and one
`git add -- <path>` all happen inside the checkpoint body. Per kind:

- useOurs / renameTakeOurs — write ours' stage-2 blob, stage. (renameTakeOurs
  is useOurs' apply form: on a rename the AU record IS ours' new path; kept
  as its own case so the record the choice produced stays distinguishable.)
- useTheirs / renameTakeTheirs — symmetric with stage 3.
- editedContent(text) — write the human's text, stage.
- keepDeletion — remove the working file when it exists, `git add` records
  the deletion; resolves DU, and the DD/UA records of a rename group.
- keepModification — write the surviving side's blob (ours ?? theirs), stage;
  deterministic regardless of what the merge checked out.
- Refusals (typed, all repository-state/exit-class 6): path not conflicted,
  chosen stage absent, no surviving side.

Kinds the fixtures produce (all built with the fixture API, both ref
formats where parametrised): UU (content), AA (add/add), DU/UD (delete/
modify both directions), and rename/rename(1to2) — which surfaces as THREE
records: `DD` at the old path, `AU` at ours' new path, `UA` at theirs' new
path. The round's rename finding: git 2.50.1 rename detection AUTO-RESOLVES
a would-be delete/modify conflict when the deleting side's only other change
is a lone added file (even an empty one — measured), so the fixtures do real
`git rm` deletions and nothing else on the deleting side. The rename group
resolves as per-record cards (renameTake at the chosen path, keepDeletion on
the other two); the grouped three-record presentation is round 2's card.

## The arm and its exits

`resolve --wait [--timeout <s>] [pathspec]`; `--wait` required (non-`--wait`
-> usage 1), timeout default 3600 (judgement), at most one pathspec, empty
pathspec refused. Blocking is #0055's inherited whole: `launchIfNeeded:
false`, await up to `--timeout` + 5 s backstop, store arms exactly
`--timeout`. Exits: 0 all conflicts resolved; 7 cancel (envelope still
`ok:true` carrying `{"cancelled":true}`); 8 conflicts remain after the reply
(`blocked_on_conflicts`, envelope still `ok:true` carrying the reply — the
rejected-review contract); 3 app down; 5 app death (connection error path);
10 typed timeout; 4 superseded or app could not serve. **Assumption
recorded: the design's exit list does not name a superseded code; the store's
supersede semantics need one, so the arm uses review's precedent (4,
`request_failed`).** On a decided non-cancelled reply the arm re-checks via
`app.perform(["conflicts"])` (the CLI does not link the engine) and counts
the result array — ANY remaining conflict in the repository exits 8, not
just the request's pathspec scope, because the repository is what stays
blocked; an unreadable re-check is 4, never a fabricated 0.

## Serving body

`runResolveRequest` resolves the context, enumerates `conflictedFiles`,
filters by the request's scope, reads every stage blob (`readBlob`) plus the
working file's current text (the editor seed), and delivers
`(request, context, details, error?)` to `onPending` BEFORE registration
(the review body's order). Nothing in the serve path writes to the
repository. Blob texts decode lossily as UTF-8 and are never interpreted.

parallel load (PendingAskStoreTests, then AskSheetTests, then
ReviewDecisionNoteTests, then my serving suite; each passes in isolation and
in the green runs). This is the documented Rule 7c contention behavior; my
+68 git-fixture tests add load. My serving suite's registration wait went

may still see a moved flake.
