  `stagePatch(_:at:git:)`: applies an arbitrary patch text to the index

## The amend-application design (the settled contract)

What the app DOES with an amended patch: it writes the edited patch to
the index BEFORE the reply resolves — apply-then-resolve, so a reply
that leaves always refers to an index that was actually amended; the
reply still carries `editedPatch` for the agent's record. The apply
runs at the request's resolved origin (the worktree root, which is what
the diff's paths are relative to) through the engine's staging path:
`git apply --cached` on standard input, one journal entry, atomic like
`stageHunks` (a patch that cannot apply changes nothing).

Failure is a typed outcome to the sheet: a stale patch (context the
index no longer holds) throws git's own message, the model records it
in `applyError`, `decide` returns false, and the pending is NOT
resolved — the human sees the error, edits the patch and sends again,
or cancels back to the three decisions (Cancel clears the error). Never
a crash, never a resolution, never a silent success. An unwired apply
path refuses the same way.

Documented honestly in `stagePatch`'s doc comment: matching is against
the INDEX, so for an already-staged review the seed resent unedited
fails ("does not apply") — the editor is free text exactly so the human
writes the delta they mean. An empty patch applies nothing and resolves
as amend with the patch absent on the wire. Judgement call recorded
here: apply-then-resolve means an apply can land for a pending that
then fails to resolve (raced with a timeout); the index change is real
work the human did and a retry of the same patch then fails with the
same typed error rather than double-applying.

## The per-line decision

The per-LINE affordance exists: inside round 2's per-hunk disclosure,
the free-text "Line (optional)" field is replaced by a Picker of the
hunk body's own new-side lines (`lineChoices(for:)` — context and added
lines numbered from `newStart`; a deleted line occupies no new-side
line and is not offered), default "Whole hunk". Not invasive — same
disclosure, one control swapped — so per-hunk-only was not needed. The
wire is unchanged: the picked number rides `ReviewComment.line` as
round 1 pinned it. Not covered: a rendered-Picker interaction test
(this target's convention asserts the model seam, never rendering).

## scripts/verify-review.md (UNRUN)

10 scenarios in the verify-xpc.md style (preconditions, exact commands,
expected stdout shapes derived from `ReviewArm.swift`/`AppXPCServer.swift`,
exit codes cited by `ExitCode` case name), each UNRUN because the round
that wrote it cannot launch or install the app: 1 app-not-running
(exit 3 appUnavailable, never a launch), 2 approve round-trip (exit 0,
envelope fields), 3 reject (exit 7 humanDeclined, envelope still
ok:true), 4 amend with an edited patch (exit 0 + editedPatch + the
index actually amended via git diff --cached), 5 a stale amend patch
(typed error in the sheet, review still pending), 6 timeout
(--timeout 5 → exit 10 timedOut typed envelope), 7 app quits mid-review
(exit 5 sessionTerminated, never a rejection), 8 no-tab repository
(opens and focuses per #0084), 9 two concurrent reviews on two
repositories (each sheet independent), 10 a minutes-long review
(default timeout — the manual marker for the long-review criterion).
Supersede/usage/non-repo are noted as covered by the package suite
rather than duplicated as scenarios.
