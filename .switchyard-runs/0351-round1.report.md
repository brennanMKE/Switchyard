Widen the review delivery waits that suite load can exceed

## Diagnosis: test deadline, not a code window

The failing observation is `rangeRequestResolvesTheCommitDiffAndDeliversItToTheSheet` dying at
ReviewRequestServingTests.swift:180 with `Expectation failed: registered → nil` — the bounded
poll ran its full 60 s and never saw `onPending` fire.

Ruled out a code window by reading the chain end to end:

- In the test, the delivery chain is strictly sequential inside ONE child task:
  `runReviewRequest` → `WorktreeContext.resolve` (3 async `rev-parse` calls, the #0344
  non-blocking `GitProcess.capture` path) → `reviewDiff` → `commitDiff` → `onPending` →
  `registration.record` → `ReviewServing.handle` → `awaitDecision`. There is no main-actor hop
  (the test injects its own `onPending` closure; `ReviewSheetBridge` is never in the path), and
  no store hook is involved in the observed state (the test's `onPendingChange` is unset; the
  poll watches the test's own `Registration`, an NSLock-protected slot). A completed `record`
  is immediately visible to `registration.value`; there is no window in which a poll can miss
  it. `PendingReviewStore`'s hook firing outside the lock and the round-2 order-independent
  stash are therefore not in the failing observation path at all.
- If `resolve` threw under load, `runReviewRequest` would reply a failure envelope and never
  deliver — but a git-level failure at the observed ~1-in-3-4 rate is implausible, and it would
  fail the staged test in the same file at the same rate, which has never been observed.

What remains is scheduling latency. `GitProcess.capture`'s non-blocking path (#0344) releases
the pool thread while git runs, but `FixtureRepository` (every suite's setup) drives the
SYNCHRONOUS `capture`, holding a cooperative-pool thread for the subprocess's lifetime. With
1463 tests / 112 suites running in parallel on a 12-core pool, continuations queue behind
fixture builds and resumption latency reaches tens of seconds; this repo has already measured a
`Task.sleep(for: 50ms)` returning 24.4 s late under this suite's contention (AppConnection.swift
lines 111-118, and Rule 7c's 2026-08-17 measurement). The delivery chain needs ~6 pool
resumptions (child-task start, 3 resolve awaits, the diff await, and the poll iterations that
must observe the result), so its tail latency exceeds the 60 s deadline at the observed rate.
`AppConnection.poll`'s deadline is wall-clock, so a delivery landing just before the last
delayed iteration is also missed. Filtered runs never flake because the pool is idle. The flake
was live on this tree pre-fix: 5 full-suite runs, 1 failure (run 2, "failed ... with 2 issues";
its per-test output was lost to a truncated log, runs 1/3/4/5 passed).

## Fix: generous deadlines, values only, no production code

- ReviewRequestServingTests.swift (3 tests) and AskRequestServingTests.swift (3 tests) — the
  same family and chain: poll deadlines 60 s → 300 s, request `timeoutSeconds` 60 → 600 so the
  store's own armed timeout (also pool-delayed) can never win the race against the test's
  resolve. `unresolvableWorkingDirectoryIsNeverRegistered` keeps its 1 s (nothing is registered,
  no timeout is armed). No assertions changed; `#require(registered)` still proves delivery.
- ReviewArmTests.appDeathMidReviewExitsFive and AskArmTests.appDeathMidAskExitsFive — the same
  window, different deadline: their `--timeout 2` pins the arm's XPC deadline to 2.5 s. Under
  load, if the arm's exchange is delayed past it, the arm exits 10 (timedOut) instead of 5 —
  the observed neighbour flake. Now `--timeout 60`, and the "request reached the app" wait is
  120 s, strictly more patient than the arm's new 60.5 s deadline, so app death always wins the
  race. A real exit-10 regression still fails the test, only after 60.5 s. The deliberate
  `--timeout 1` timeout tests are untouched (both the store-typed and backstop paths map to
  exit 10 + `timed_out`, so they are insensitive to which timer wins).

Red-run cost of the new shape: a genuine regression burns up to 300 s in the first poll before
failing, and the arm tests up to ~120 s. Green runs are unaffected — the polls return on first
sighting.
