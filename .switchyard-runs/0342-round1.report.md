Decide merge diffs as combined output

Decision — `--cc` wins, implemented as directed and written into guide §11 as decision 26
(docs/switchyard-development-guide.md, after decision 25, before "### Still open"): `commitDiff`
passes `--cc` for every revision because measured byte-identical output for an ordinary commit with
and without it, so the argument vector does not fork on parent count. For merges it shows what the
merge contributed relative to all parents. `-m` (needs a parent-picker UI that does not exist) and
`--first-parent -m` (hides one side) rejected with the reasons recorded in the guide entry.

One measurement contradicted the decision's expectation and I implemented the truth instead:
`FixtureRepository.merged`'s merge ADDS `merge.txt` — a file in neither parent — so under `--cc` it
is NOT empty; it shows exactly `diff --cc merge.txt` with `@@@ -1,0 -1,0 +1,1 @@@` over `++merge`
and `new file mode 100644`. "Empty for a clean merge" holds only for a merge with no contribution of
its own (measured zero bytes for two branches adding their own files and nothing contributed by the
merge). So the replacement for `commitDiffOfAMergeCommitIsEmpty` is two tests:
`commitDiffOfAMergeShowsOnlyItsOwnContribution` (merged fixture: only merge.txt appears — neither
branch's file does, which is what makes --cc honest) and
`commitDiffOfAMergeWithNoChangesOfItsOwnIsEmpty` (empty, reason in the assertion message: honest
verdict, not diff-tree's parent-picking refusal). Guide §11's wording reflects this distinction.

Parser — `HunkParser` now parses `diff --cc` blocks instead of dropping them (#0342 policy):
`HunkBuilder` gained a combined path (`init(combinedHeader:)`) parsing `@@@ -a,b -c,d +e,f @@@` with
one range per parent plus the result, tolerating a trailing section heading (measured:
`@@@ -9,7 -9,7 +9,7 @@@ l`); `Hunk.oldStart/oldCount` carry the first parent column and
`newStart/newCount` the result column, with the full picture verbatim in `header`. Body lines keep
their raw two-character prefixes verbatim (`- ours`, ` -theirs`, `++resolved`). The budget rule that
bounds a combined body was derived from measured output and is exact on every measured shape: a line
with `-` in column k consumes only parent k's budget (other columns are padding); a line with no `-`
consumes the result budget once plus each parent whose column is a space. `wantsMoreBody` also
requires the line's first character to be a status character for combined hunks, so a header can
never be swallowed even if a future git emitted counts the rule did not predict. New
`pathFromDiffCCLine` handles `diff --cc P` (single path, no a/ prefixes, spaces allowed — measured).
`Hunk.patchText` and the `Staging.swift` doc comments updated for the new reality.

Ripple the decision did not name, flagged for review: the same `diff --cc` shape reaches `listHunks`
during a conflict (`git diff` prints unmerged paths as combined blocks), so conflicted paths NOW
APPEAR in unstaged listings as their own FileDiff with stable ids (previously silently dropped).
Staging a conflicted file's hunk id is refused where it used to be impossible — git apply does not
accept combined patches (measured exit 128, "No valid patches in input"), all-or-none preserved, so
conflicted content still cannot reach the index — but the failure is git's own refusal rather than
`StagingError.unknownHunkIDs`. Three pinned tests were updated accordingly
(`combinedDiffBlockDoesNotCorruptAnOpenFile`, `combinedDiffFirstThenNormalFileParses` — rewritten
with real measured bytes; `conflictedFileIsUnaddressableButOthersStage` renamed to
`conflictedFileIsVisibleButItsHunksCannotBeStaged` and extended; `unstagingWorksWhileAnotherPathIsUnmerged`
extraction now targets a.txt by path). If the reviewer wants the old typed refusal back, the place
is `selectPatch`, not the parser — suggested as follow-up, not done.

Also measured: `core.abbrev` leaks into combined `index` lines (4-char with `core.abbrev=4`), and
the already-pinned `--full-index` neutralizes it (full 40-hex regardless) — documented in the
pinnedDiffFlags comment; no new pin needed.
