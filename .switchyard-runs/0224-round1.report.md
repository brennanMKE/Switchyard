Pin the journal cache rewrite staleness constraint

## What changed

**1. `YardKit/Sources/YardGit/JournalMetadataCache.swift` — the constraint, in the cache's own doc
comment** (16 lines added, no code touched). Where a wirer of the read path will read it, it now
says: a `JournalAnchor.updateMetadata` rewrite does NOT update a cached row — it replaces the
entry's `metadata.json` blob and re-points the anchor ref, touching neither this file nor anything
a read of it consults. The `Row`'s `snapshotRef` stores a ref **name**, not an oid, so the name
survives the rewrite untouched; **the staleness is in the embedded `metadata`, never in the ref**,
which is exactly why it is quiet — a reader sees a valid-looking row with the attached mapping
absent, and #0064's rewrite-diff would silently return nothing. Whoever wires the cache into a
read path must either update the cached row whenever `updateMetadata` changes an entry, or detect
the staleness on read. Rebuilding from refs (#0030) plus `rewrite(from:)` recovers from any
staleness, because the refs are the authority.

**2. `YardKit/Tests/YardGitTests/JournalMetadataCacheTests.swift` —
`aMetadataRewriteStalesTheCachedRowUntilUpdatedOrRebuilt`**, the test the re-milestoning note said
was unwritable, written against the cache's own API on a real fixture journal (real
`JournalAnchor.write`, real `updateMetadata`, real `JournalRebuild.rebuild` — no mocks). One test,
three phases:

- Setup/anti-vacuity: writes a real entry, appends its row, then runs the real #0221 path —
  `attachingRewrite` + `updateMetadata` with a mapping of fixture commit oids — and asserts the
  ref really moved and the live blob really carries the mapping, so phase 1's absence below cannot
  pass because nothing was rewritten.
- **Phase 1 (the hazard, pinned):** reading through the cache still shows the PRE-rewrite metadata
  (`rewrite == nil`), while `snapshotRef` still equals the ref name — proving the ref survived and
  the embedded metadata is the stale part.
- **Phase 2 (the wirer's obligation):** after updating the cached row via the cache's own
  `append` (which replaces by id), the mapping is visible through `rows()`.
- **Phase 3 (rebuild-from-refs recovers — confirmed, not assumed):** with a stale row deliberately
  re-planted, `cache.rewrite(from: JournalRebuild.rebuild(in:))` restores the post-rewrite
  metadata, the mapping, and the ref name, with no defects.
