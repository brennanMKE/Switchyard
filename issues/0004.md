# 0004 — Verify the chosen libgit2 build works against a reftable repository

| | |
|---|---|
| **Status** | open |
| **Module** | YardGit |
| **Milestone** | M0 |
| **Platform** | macOS |
| **First seen** | 2026-08-06 |

## Description

Reftable becomes the default reference storage format for newly created repositories in Git 3.0. A
libgit2 build that cannot read reftable will appear to work perfectly and then return *nothing* —
not an error, nothing — on any repo using it. Zed dropped libgit2 for the git CLI in June 2026
partly over this. Reftable support has landed upstream in libgit2, but "merged" and "in a tagged
release you can build against on macOS" are different states, and only a test tells us which we have.

## Expected behavior

- [ ] A repo created with `git init --ref-format=reftable` is used as the fixture.
- [ ] The chosen build can enumerate refs, resolve `HEAD`, and read the reflog in it.
- [ ] The exact libgit2 version tested is recorded, not just "latest".
- [ ] Finding recorded in `docs/engine-findings.md`, including what the fallback costs if negative.

## Notes

Git internals §1. This does not stop the project if it fails, but it **must be settled before M1
starts**: a negative answer moves ref enumeration and graph traversal onto `git for-each-ref` and
`git rev-list`, shifting the hybrid boundary substantially toward the CLI. That is not a retrofit.
