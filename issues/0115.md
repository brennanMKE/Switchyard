## Description

`YardGit` has five public entry points and **not one of them is callable from `switchyard`**:

| function | file | issue that built it |
|---|---|---|
| `whereAmI(...)` | `WhereAmI.swift:102` | #0012 |
| `worktreeList(path:git:)` | `WorktreeList.swift:79` | #0009 |
| `worktreeRemove(at:_:force:git:)` | `WorktreeRemove.swift:100` | #0095 |
| `gitStatus(...)` | `WorktreeStatus.swift:162` | #0113 |
| `yardWhere(path:git:)` | `WorktreeWhere.swift:45` | #0109 |

`runYard` handles exactly three inputs: no arguments, `noop`, and everything else as a usage error.
So the product an agent actually runs cannot do any of the things the engine can do. Each of those
issues was verified by its unit tests and by a driver compiled against the library — never by running
the binary, because there is nothing to run.

This is filed as a **tracking gap, not a task**. It is here so the gap is visible in the queue rather
than discovered at the end of M1.

## Givens — verified on `main` 2026-08-07, treat as true

1. `YardKit/Sources/YardKit/CommandLineRunner.swift` holds `runYard(arguments:) -> (stdout: String,
   stderr: String, exitCode: ExitCode)`. It is the only place a subcommand can be added; `main.swift`
   is argument collection and a write, and cannot be unit-tested because SwiftPM does not allow
   `@testable import` of an executable target.
2. `YardKit` does **not** currently depend on `YardGit` — check `Package.swift` before assuming a
   call is even possible. Adding that dependency is part of the work and belongs in the first
   subcommand's issue, not here.
3. `CommandSpec`, `renderHelp(for:)` and `renderSchema(for:)` exist. `CommandRegistry` does not; #0088
   builds it.
4. Guide §11 settled decision 6: `--help` and `--version` print plain text; every other command emits
   a JSON envelope unconditionally. There is no `--json` flag.

## Expected behavior

This issue is closed by **filing the per-command issues**, not by writing code. One issue per
subcommand, each of which must:

- [ ] Add the `CommandSpec` to `CommandRegistry` so `--help` and `schema` pick it up for free.
- [ ] Add the dispatch arm to `runYard`, returning the engine result inside an envelope.
- [ ] Assert on the **binary's real output** — `swift run switchyard <cmd>` — parsed with
      `JSONSerialization`, not on the engine function in isolation. That is the coverage that does not
      exist today.
- [ ] Regenerate the skill, per the CLAUDE.md rule that a command lands with its documentation
      regenerated or it does not land.

Blocked by #0088, which builds the registry and the `--help` / `schema` arms.

## Re-milestoned to M3 — 2026-08-07

Guide §11 decision 11. This issue was blocked, not on missing work, but on a contradiction between
two settled documents: guide §9 required every M1 command to run from the built binary, while guide
§5 and `CLAUDE.md` require the CLI to marshal over XPC and never link `YardGit` — and XPC is built in
M3.

Brennan's decision is that **M1 claims the engine and its tests; M3 owns the claim that the commands
run.** So this issue moves to M3 unchanged in substance, and stops blocking M1's close.

Nothing here should be dispatched until the XPC layer exists (#0046–#0048). Wiring the CLI to the
engine directly now would be rework, which is precisely the reading that was rejected.


## The pattern, established by #0124 — 2026-08-17. Every remaining command follows it.

#0124 wired the first command end to end and its children can now be filed as mechanical repeats. The
recipe, in the order it is done:

1. **The arm** in `YardKit/Sources/YardCommands/EngineCommands.swift`: a `case "<name>":` in
   `runEngineCommand`, and a private function that resolves `WorktreeContext` for the **passed**
   working directory, calls the engine function, and returns the result in an `Envelope`. Failures
   become `EnvelopeFail(code: .repositoryError, …)` with exit **6**.
2. **`Encodable` on the result type**, with an **explicit `CodingKeys` enum listing every case, using
   the property names unchanged**. The JSON is the agent-facing contract; a property rename must not
   silently change it. Two of #0124's three failed rounds got exactly this wrong, in opposite
   directions — one renamed to snake_case, one deleted the enum and let synthesis satisfy a criterion
   phrased as an absence.
3. **A `CommandSpec` in `CommandRegistry.all`** with a non-empty `summary`, a non-empty `schemaName`,
   and at least exit codes 0 and 6. #0088's registry test asserts all three on every spec.
4. **The `CommandSpec`'s `payload` field (#0194).** A command lands with its payload shape or it does
   not land: one `PayloadField` per wire key the result type encodes, matching `CodingKeys` exactly.
   See `Sources/YardKit/CommandSpec.swift`'s doc comment for the design (flat fields only, absent
   means absent, closed string enums via `enumCases`) and `whereamiSpec` for a worked example.
5. **Regenerate the golden schema** — `SCHEMA_REGENERATE=1`, and commit the new
   `YardKit/Schemas/<name>.json`. `SchemaGoldenTests.noOrphanSchemaFiles` fails without it.
6. **Bind the schema to the type**, the way `WhereAmIWireTests.schemaFieldNamesMatchTheEncodedKeysExactly`
   does: read the generated `<name>.json` off disk, extract `envelope.success.result.fields[].name`,
   and assert that set equals the keys a fully-populated encoded value actually has. This is what
   makes the payload shape true rather than decorative — a hand-written shape and a hand-written wire
   literal can each drift from the type independently, and this test is the one thing that reads both
   off the generated artifact instead of trusting either by hand.
7. **Tests in `YardKit/Tests/YardCommandsTests/`**, asserting values the fixture determines rather
   than shapes, plus a not-a-repository case asserting `error.code == "repository_error"` and exit 6.
8. **Nothing in `main.swift`.** #0124 built the three-way routing — local, known-and-remote, unknown —
   and every new command is picked up by `CommandRegistry.all` automatically.

**Running the real binary end to end is not part of any of these issues.** It needs an installed app
and a registered launch agent; #0054's script owns it, and M3's exit criterion is where the claim
lives.

### The remaining commands, with the engine entry point each one wraps

| command | engine function | file |
|---|---|---|
| `status` | `gitStatus(at:includeIgnored:git:) throws -> WorktreeStatus` | `WorktreeStatus.swift:424` |
| `conflicts` | `conflictedFiles(at:git:) throws -> [ConflictedFile]` | `Conflicts.swift:176` |
| `wt list` | `worktreeList(path:git:) throws -> [WorktreeEntry]` | `WorktreeList.swift:79` |
| `wt where` | `yardWhere(path:git:) throws -> WorktreeWhere` | `WorktreeWhere.swift:45` |
| `hunks` | `HunkParser` and its `FileDiff`/`Hunk` types | `Hunks.swift` |
| `log` | `CommitLogEntry` / `CommitLogOptions` | `CommitLog.swift` |
| `graph` | `LaneAssigner`, `GraphRow`, `RevListParser` | `LaneAssignment.swift` |
| `verify` | `SignatureVerification` | `SignatureVerification.swift` |

The first four have a single top-level function with a `path`-shaped first parameter and are the
smallest; **file and dispatch them first**. The last four need an options surface or a parameterised
call and each needs its own planning pass — do not batch them.

`wt add`, `wt rm`, `wt gc` and `wt repair` mutate, so they follow M2's shape rather than this one and
are not covered by this pattern.

## Resolved — 2026-09-03. Closed by filing the per-command issues, as this issue always said.

The five entry points this issue was filed for:

- `whereAmI` → `switchyard whereami` — wired by **#0124** (the pattern-establishing round).
- `gitStatus` → `switchyard status` — wired by **#0225**.
- `conflictedFiles` → `switchyard conflicts` — wired by **#0226**.
- `worktreeList` → `switchyard wt list` — wired by **#0227**.
- `yardWhere` → `switchyard wt where` — wired by **#0228**.

The remaining read commands named in the table below each have their own filed issue, in the six-step
shape, ready to claim and dispatch:

- `hunks` (`listHunks(at:area:git:)`) → **#0345** — `--staged`/`--unstaged` required, refused
  otherwise (guide §6).
- `log` (`CommitLog.run(path:rangeArguments:options:git:)`) → **#0346** — range arguments pass
  through; option flags refused.
- `graph` (`graphRows(at:limit:revisions:git:)`) → **#0347** — optional `--limit <n>`; `--all` and
  friends refused.
- `verify` (`SignatureVerification.run(revision:in:git:extraEnvironment:)`) → **#0348** — exactly one
  revision required; exit code reports command success, the payload carries the verdict.

That is every read command the table names. `worktreeRemove` (and the other mutating `wt`
subcommands) remain out of scope here by the section above — they follow M2's shape and are owned by
their own issues (#0095, #0271, #0319 and successors). The lump issue that would have batched the
four filings was retired as a duplicate (#0338, `wontfix`), which is what directed them here.
