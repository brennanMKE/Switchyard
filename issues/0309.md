## Description

**Finding of #0160's eleventh umbrella review, 2026-08-18.** `attachRewrite`'s rule *"read the in-flight
file only when the environment carried no id"* is unpinned.

`YardKit/Sources/YardGit/JournalCheckpoint.swift:434-441`, mutated:

```diff
-        let fromFile = entryID == nil
-            ? try inFlightEntryID(in: context, git: git, fileManager: fileManager)
-            : nil
+        let fromFile = try inFlightEntryID(in: context, git: git, fileManager: fileManager)
```

`✔ Test run with 1115 tests in 78 suites passed after 87.128 seconds.` — **full suite.**

**The ternary is not an optimisation.** The production comment at `:434-437` states its purpose — *"a
different, still-open operation's own file (guide §11 decision 24) is never this call's to clear"* — and
`RepositoryLayout.swift:69-70` states the same rule again.

**What the mutation actually breaks.** Entry *selection* stays correct (`entryID ?? fromFile?.id` still
yields the environment id). What changes is that the trailing
`try? fileManager.removeItem(atPath: path)` now fires against **another operation's live slot**, and
`inFlightEntryID`'s own stale-file cleanup fires too. So operation A's conflicted rebase loses its
entry-id file; when A is later continued — a foreign invocation with no environment id — `attachRewrite`
finds neither source and **A's mapping never reaches A's entry.** That is the #0237 failure this whole
file mechanism exists to prevent.

## The test that looks like the pin covers only half of it

`precedenceLandsOnTheEnvironmentEntryNotTheFileEntryWhenBothNameLiveEntries`
(`PostRewriteAttachTests.swift:1817`) already stands the state up perfectly — an environment id and a
live slot file naming two **different** live entries — and asserts which entry received the mapping
(`:1849`) and that the other stayed untouched (`:1852`). **It never asserts anything about the file.**

A scan of all 24 tests in that file found it is **the only one that writes a slot file and makes no
`fileExists` assertion afterwards**. The mirror-image property on the foreign path *is* pinned, by
`aForeignDecisionWithALiveFilePresentAttachesNothing`.

## The comment that hid it — second instance of #0303's defect

The same test's doc comment at `:1811-1813` says that under correct precedence *"the environment id is
read eagerly and the file is never even opened (`??`'s right side is an autoclosure)"*. **The code has
not worked that way since the `try` forced the explicit ternary**: `fromFile` is computed *before* the
`??`, so the autoclosure buys nothing. The comment asserts the file cannot be touched — which is exactly
why asserting its survival looked redundant. The production comment at `:434-435` carries the same stale
`??` framing.

#0303's fourth bullet ordered this class of comment corrected *"even where the assertion survives,
because a comment that misdescribes its own mechanism is how this stayed hidden"*. That applies here
verbatim.

## Notes

**Parent #0160**, bullet 2. Same class and same size as **#0255**, **#0299** and **#0303**: one assertion
on a test that already replays the state.

**Honest limit, as #0303 stated its own.** Nothing can observe this today. It needs an own invocation
carrying an environment id to reach `attachRewrite` while a sequencer that will *survive* the call is
live: an own `amend` during a rebase is filtered by `isMidRebaseAmend`, an own `rebase` cannot start
while one is in progress, and a completing rebase's directory is being torn down anyway. The reachable
route needs `git am` inside an `around` body, and nothing in-tree runs `git am`. **It is latent, and it
is filed for the same reason #0303 was.**

**The reviewer's own observation, worth carrying forward:** this is a *sequential* version of the same
"whose file is this?" question that the concurrent-`around` race raises, which is mild evidence that the
slot's **ownership model** deserves one issue rather than continued case-by-case patching. That is a
proposal for Brennan, not part of this issue.
