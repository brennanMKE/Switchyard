## Description

A pure function turning a `CommandSpec` into a JSON Schema description of that command's response
envelope. Same shape as #0086: spec in, value out, no I/O.

This is what makes the JSON contract documentable and diffable (#0026) rather than implicit.

## Expected behavior

- [ ] New file `YardKit/Sources/YardKit/SchemaEmitter.swift`. Touch nothing else except its test file.
- [ ] `func renderSchema(for spec: CommandSpec) -> String` returning pretty-printed JSON, sorted keys so output is stable across runs.
- [ ] The emitted schema includes `schemaVersion`, the command name, and the declared `schemaName`.
- [ ] A test decodes the output with `JSONSerialization` and asserts it is valid JSON — not a string comparison.
- [ ] A test asserts two calls with the same spec produce byte-identical output.
- [ ] A test proves the key ordering is actually stable: build a spec whose keys would not be in
      sorted order naturally, emit it, and assert the emitted key sequence is sorted. Asserting only
      that two identical calls match does **not** test sorting — an unsorted-but-deterministic
      emitter passes that.
- [ ] Tests use **swift-testing** — `import Testing`, `@Test`, `#expect`. Not XCTest. Every other
      test file in this package uses swift-testing, and `swift test`'s summary line counts only
      swift-testing tests, so an XCTest file passes invisibly.
- [ ] `cd YardKit && swift build` succeeds, and `swift test` prints a `Test run with N tests` line
      you paste. **N must be greater than 92**, the count on `main` before this change. If N is
      still 92, your tests are not in the run being counted.

## Notes

Split out of #0010. Blocked by `#0085`.

Sorted keys and pretty printing are required, not cosmetic: the committed schemas are reviewed in
diffs, and unstable key order makes every diff noise. Use
`JSONSerialization.WritingOptions([.prettyPrinted, .sortedKeys])` or the `JSONEncoder` equivalent —
do not hand-sort.

`CommandSpec` is on `main` at `YardKit/Sources/YardKit/CommandSpec.swift`, along with
`HelpRenderer.swift` from #0086 as a worked example of the same shape: pure function, spec in, String
out, tested from a hand-built spec. Read it before starting; do not modify either file.

**Cover the conjunctions, not just each criterion alone.** #0086 was rejected because its tests
checked "flag with a short name" and "flag with an argument" separately and never both together —
which was exactly the case its code got wrong.

**Target placement:** `yard` is an `executableTarget`, so `@testable import yard` does **not** link in
SwiftPM — anything that needs unit tests must live in the `YardKit` library target. This was found
the hard way on #0085, whose round burned itself discovering the link error. Only `main.swift` and
code that genuinely cannot be unit-tested belong in `Sources/yard/`.

## Review — round 1 was rejected

Round 1 exited 0 after 856s. **The emitter is correct** — I verified independently that a spec with
deliberately out-of-order keys emits sorted top-level keys, sorted nested flag keys, and ordered
arrays. Do not rewrite `SchemaEmitter.swift`'s sorting logic; it works.

**The sorting test proves nothing.** `extractTopLevelKeys` skips any line not starting with four
spaces and a quote, but `JSONSerialization` pretty-prints with **two**. The extractor returns `[]` on
every input, so both assertions reduce to `[] == []` and `0 == 0`. Running a byte-for-byte copy of
that helper against the real output gives `count=0 keys=[]`.

This is the exact evasion this issue's own bullet warned about, arrived at by accident rather than
design — an unsorted emitter would pass that test identically.

Round 2 must:

- [ ] Rewrite the key-order check so it **does not assume an indentation width**. Either scan the raw
      string for `"([A-Za-z]+)" :` at brace depth 1, or assert that the byte offset of each expected
      key within the output increases in sorted order. Do not hardcode two spaces either — that just
      moves the same brittleness.
- [ ] **Assert the extraction is non-empty before comparing it.** `#expect(!keys.isEmpty)` first,
      then compare. An extractor that silently yields nothing is the failure mode here, and a
      non-empty guard converts it from a silent pass into a loud failure.
- [ ] Delete `testSuiteHasSufficientTests` — its body is `#expect(true)`, which passes unconditionally
      and measures nothing.
- [ ] Note that `testFullSpecSorted` compares `Array(decoded.keys).sorted()` against a literal. That
      tests the key *set*, not the order, because it sorts both sides. Keep it if you like, but it is
      not the sorting test and must not be presented as one.
- [ ] `renderSchema` uses `try!` and `!` on line 34-35, so a malformed payload traps rather than
      surfacing an error. Make it throwing or handle the failure.
- [ ] `"argument": flag.argument as Any` relies on Optional-to-NSNull bridging. It works — it emits
      `null` — but write it as `flag.argument.map { $0 as Any } ?? NSNull()` to match how `short` is
      already handled two lines below.
- [ ] `swift test` must still show **more than 92** tests, and state the new count.

The most expensive issue so far, and the reason is worth recording: **round 1's production code was
correct.** The emitter sorted properly from the start. What failed was the test for that criterion,
and it failed silently — `extractTopLevelKeys` skipped any line not starting with four spaces while
`JSONSerialization` pretty-prints with two, so it returned `[]` on every input and both assertions
reduced to `[] == []`.

Round 2 was verified by mutation rather than by reading: removing `.sortedKeys` from the emitter made
both sorting tests fail with real diagnostics, and the file was then restored and hash-checked. The
extractor returns six keys on real output, correctly excludes the nested `code`/`meaning` keys inside
`exitCodes`, and discriminates sorted from unsorted.

`renderSchema` is now `throws` rather than `try!` — a departure from the issue's literal signature
that the review sanctioned, with no other callers in `YardKit/Sources`.

**This round also found a false positive in `scripts/check-tests-assert.sh`.** A `@Test` display name
containing braces — `@Test("encodes via .map { $0 as Any } ?? NSNull()")` — balanced its own braces
on the attribute line, closing the scanned body before the function was reached and reporting a real,
asserting test as inert. The scanner now strips string literals before counting braces. Validated
against a test that has braces in its name *and* asserts (not flagged) and one that has braces and
does not (flagged).

Two latent items, neither blocking: `extractKeysAtDepth` mixes an `NSRange` UTF-16 offset with a
`Character`-count prefix, identical for ASCII output but wrong for non-ASCII; and the tests call
`try! renderSchema(...)` throughout.
