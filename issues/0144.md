## Description

**M1 exit criterion served (guide §9, criterion 5):** "every engine function has tests that can
fail: each has a mutation recorded against a named test that dies under it."

Found by the M1 milestone review, 2026-08-07. `worktreeRemove`
(`YardKit/Sources/YardGit/WorktreeRemove.swift`) has a recorded behavior mutation (#0095: dropping
the `--force` handling) that is stated to fire, but the killing test is recorded only as "the force
test" — not by name. #0137's named wire tests (`uncleanEncodesCodeMessageAndPaths`, …) pin the
result type's encoding, not the removal behavior.

## Expected behavior

The #0095 mutation is re-applied, the exact test name(s) in
`YardKit/Tests/YardGitTests/WorktreeRemoveTests.swift` that go red are recorded in this issue's
work log, and the mutation is reverted with the suite green.

## Mutations recorded — run by the reviewer 2026-08-07

Applied to `YardKit/Sources/YardGit/WorktreeRemove.swift`, full suite run each time, file restored,
tree verified clean.

| # | mutation | verdict | named test that died |
|---|---|---|---|
| W1 | drop `--force` from the retry arguments | **RED** | *"removes a dirty worktree when forced"* |
| W2 | the dirty-stderr guard never matches, so no paths are extracted | **RED** | *"refuses to remove a dirty worktree without force"* |

Both are clean one-mutation/one-named-test pairings, and together they pin the two halves of the
design that matter: that `--force` is **not** passed up front — guide-level behaviour, since the engine
must never force on an agent's behalf — and that the refusal path actually parses git's
`use --force to delete it` stderr rather than assuming it.

W2 is the sharper of the two. Without the guard the function returns an empty path list, so the
refusal still happens but names nothing, and only a test that asserts the *paths* catches it.
