## Description

The app has no test of its own that would have caught #0123 — it crashed in dyld on every launch and
both suites stayed green, because the package tests never launch the app and the stock UI test never
runs here.

Brennan's constraint, and it shapes the whole issue: **a simple launch test pointing at a folder with
a git workspace is sufficient.** No long UI tests. Nothing that drives the interface, steals focus for
minutes, or makes the machine unusable while it runs.

## Givens — verified on `main` 2026-08-07, treat as true

1. **UI tests cannot run under CLI-driven `xcodebuild` on this machine.** CLAUDE.md records it: the
   runner times out enabling automation mode without Accessibility rights. So an `XCUIApplication`
   test is not runnable by an agent — only by Brennan, from Xcode, after granting those rights.
   Anything that must run unattended has to avoid `XCUITest`.

2. `SwitchyardUITests/` contains the stock template tests — `SwitchyardUITests.swift` and

   `runsForEachTargetApplicationUIConfiguration = true` and takes a screenshot attachment. That is
   exactly the disruptive shape this issue rules out.

3. `SwitchyardTests/SwitchyardTests.swift` is the stock swift-testing placeholder — one `@Test func
   example()` with an empty body. It is a **unit** target, so it runs under CLI `xcodebuild` without
   automation rights.

4. Launching the built app as a **subprocess** and checking it survives works today and needs no
   permissions. Measured while verifying #0123: build unsigned, run
   `"$APP/Contents/MacOS/Switchyard" &`, sleep, `kill -0`. It stayed alive and LaunchServices
   registered it. Six seconds end to end.

5. `Switchyard/ContentView.swift` is the stock template — a globe and `Hello, world!`. **The app
   accepts no arguments and opens no repository.** So "points at a git workspace" cannot mean anything

6. The app build command is
   `xcodebuild build -project Switchyard.xcodeproj -scheme Switchyard -destination 'platform=macOS'
   CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO -quiet`.

7. **The package suite's count on `main` is 924**, measured 2026-08-17 at `HEAD`. (This Given
   originally carried the 2026-08-07 figure, which is superseded.) This issue does not change the

## Scope — what "points at a git workspace" can mean today

Nothing in the app reads a repository yet, so a test that opens one would be asserting against a
feature that does not exist. **This issue builds the harness and the launch assertion now**, with the
repository as a fixture the test creates and passes, so the assertion can tighten the moment the app
does something with it.

Concretely: create a real git repository in a temp directory, pass its path as an argument, assert the
process survives. When the app grows a repository-opening path, the same test gains an assertion about
what it opened — without restructuring.

## Expected behavior

- [ ] A new smoke test in **`SwitchyardTests/`** — the unit target, not `SwitchyardUITests/` — that:
      builds nothing itself, locates the built app via `BUILT_PRODUCTS_DIR`, creates a temporary git
      repository with one commit, launches `Contents/MacOS/Switchyard` as a subprocess with that path
      as an argument, asserts the process is **still alive after a bounded wait**, and terminates it.
- [ ] **The wait is at most 5 seconds** and the process is always killed, including on failure. A test
      that can leave a window on screen is a failed test.
- [ ] On failure it reports the process's stderr, so a dyld error is visible in the test output rather
      than requiring a manual launch. #0123's message would have named the missing library.
- [ ] **Delete `SwitchyardUITests/SwitchyardUITestsLaunchTests.swift`** and the stock
      `SwitchyardUITests.swift`. They cannot run here and the screenshot-per-configuration shape is
      what Brennan ruled out. Leave the target in place; it will be used when there is a UI worth
      driving, and #0054's manual XPC script is the model for anything that needs a human.
- [ ] Replace the stock `SwitchyardTests.example()` placeholder rather than adding beside it.
- [ ] The app test run is scoped, per CLAUDE.md:
      `xcodebuild -project Switchyard.xcodeproj -scheme Switchyard -destination 'platform=macOS'
      -only-testing:SwitchyardTests test` — paste the result.
- [ ] `cd YardKit && swift test` still reports the count on `main` — see the planning refresh below.
      This issue touches no package code.

## Tests must be able to fail

**The test must fail when the app cannot launch.** That is the entire point, and it is checkable
without breaking anything permanently:

**Mutation**: temporarily point the launch at a path that does not exist, or at
`/usr/bin/false` — the test must fail with a clear message, not hang and not pass. Report the failure
text. Restore.

**Second mutation, the real one**: `git stash` the #0123 fix on a scratch branch — restoring the
`Clibgit2` dependency — rebuild, and confirm this test **fails with the dyld error in its output**.
That is the regression it exists to catch. If that cannot be arranged cheaply, say so and rely on the
first mutation, but do not claim coverage that was not demonstrated.

Do **not** assert on a screenshot, a window title, or any accessibility query. Those need automation
rights, which this machine does not grant to a CLI-driven run.

### The second mutation is no longer available, and that is not a reason to skip the first

The issue asks for the #0123 regression to be reproduced by restoring the `Clibgit2` dependency on a
scratch branch. `Package.swift` on `main` has no `Clibgit2` target and no libgit2 dependency at all —
#0103 is the open issue that would reintroduce one. **Do not reconstruct it**: fabricating a dyld
failure by hand-editing the manifest proves the harness works against a failure you invented, which is
not the same claim.

Do the **first** mutation instead, and report it honestly as the only one run:

1. Point the launch at `/usr/bin/false` (or a nonexistent path). The test must **fail within the
   bounded wait**, with the launched process's stderr in the failure message. It must not hang.
2. Restore, re-run, confirm green.

Then state plainly in the report that the dyld regression itself was not reproduced and why.

### One addition to the criteria

- [ ] The subprocess is terminated on **every** exit path, including when an expectation fails. Use a
      `defer` that terminates and waits — an orphaned `Switchyard` process left running after a failed
      test is the failure mode Brennan's "nothing that makes the machine unusable" rules out, and it is
      exactly what a test that returns early produces.
