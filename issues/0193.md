## Description

**Filed by the M1 milestone review, 2026-08-17, against M1 exit criterion 3** — *"Every failure mode
returns a structured error carrying the exit code from §6 — not a trap, and **not a success value with
empty fields**."* The other two halves of that criterion are met; this is the third.

`WorktreeStatusParser.parse(_:)` — `YardKit/Sources/YardGit/WorktreeStatus.swift:228` — is declared
`throws` and contains **zero `throw` statements**. `WorktreeStatus.swift` declares **no error type at
all**, and it is the only one of the engine's four porcelain parsers without one.

Two of its five `continue` guards discard real malformed input rather than a structural artifact:

- `:238` `guard let expectedFields else { continue }` — drops any record whose leading token is not in
  `fieldCount`, so a record type a future git adds **vanishes from `status`**.
- `:251` `guard tokens.count > expectedFields else { continue }` — drops a truncated record.

In both cases `gitStatus` returns `WorktreeStatus(entries:)` with the entry simply absent and the call
reported successful. That is criterion 3's named forbidden shape, exactly.

**The asymmetry is decision-free.** `ConflictParser` throws `.unrecognizedKind(xy:path:)`
(`Conflicts.swift:126`) for the analogous case on the same `-z` byte stream; `HunkParser` has eight
throw sites and `RevListParser` throws at `:160`. All three failures carry
`ExitClass.repositoryError`. Nothing in `issues/` records a reason for status to differ.

**Why it survived.** The two issues that own criterion 3 split it and neither covered this: #0140 owns
the success-value half and scoped itself to *"One deliverable: `whereAmI` throws … on a
non-repository"*, auditing the other reads only for the non-repository case — true, and orthogonal to
malformed output. #0141/#0146/#0147 own only *"the exit-code half"*. And `ExitClassCoverageTests`
**structurally cannot see it**: it enumerates conformers of `ExitClassCarrying`, so a parser with no
error type produces no line containing the protocol name and the guard stays green.

## Expected behavior

- [ ] `WorktreeStatusParser.Failure` (or equivalent) with at least `unrecognizedRecordType(leading:)`
      and `truncatedRecord(_:)`, thrown from `:238` and `:251` instead of `continue`.
- [ ] `extension WorktreeStatusParser.Failure: ExitClassCarrying { var exitClass: ExitClass
      { .repositoryError } }`, matching `ConflictParser.Failure`.
- [ ] A row in `DescriptionCoverageTests` and in the `ExitClassCoverageTests` registry.
- [ ] Two tests feeding a hand-built `-z` buffer — one with an unknown leading token, one with a
      token-short record — each asserting the specific error is thrown. Build the buffer by hand;
      do not try to make real `git status` emit malformed output.
- [ ] A mutation recorded as **observed**: turn each new `throw` back into `continue` and confirm the
      named test dies. If a test does not die, it is asserting on the wrong thing.
- [ ] `cd YardKit && swift test` prints a `Test run with N tests` line where N is
      **greater than** the count in `docs/test-baseline.txt` by exactly 2. The delta is the criterion;
      read the baseline file rather than trusting any absolute written here.

## Notes

**M1 does not close until this resolves** — it is a stated exit criterion, and two consecutive clean
milestone reviews are required after it.

`CommitLog.parse` (`CommitLog.swift:199`, guards at `:224` and `:227`) has the same shape and also no
error type. The review flagged it as a second instance **with lower confidence**, because `:217`
legitimately skips the trailing fragment after the final NUL and the other two guards are harder to
reach. Decide whether it belongs here or in its own issue once the status half is understood — do not
widen this issue's scope on a guess.

The structural blind spot is worth fixing separately and is **not** part of this issue:
`ExitClassCoverageTests` can only see error types that already conform, so it can never catch the next
error type that forgets to.
