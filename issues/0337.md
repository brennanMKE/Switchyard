## Description

**Nothing in this repository can be run by a human today, and the reason is one 67-line file, not the
size of the remaining work.**

The state, measured 2026-08-18:

- The engine is real — 1146 tests, seven criterion-1 functions plus the whole `wt` group, driving 28
  `git` subcommands against real repositories.
- `YardKit/Sources/YardCommands/EngineCommands.swift` is the adapter layer. It depends on `YardGit`
  and `YardKit`, and its `switch` has **exactly one case**: `whereami`.
- **No executable links `YardCommands`.** The shipping `switchyard` target depends on `YardKit` only —
  correctly, per guide §5, because it is meant to marshal over XPC to the app — and the app target is
  still a stock SwiftUI template.

So the engine has no caller, and guide §11 decision 11 is the reason: it moved CLI reachability to M3,
on the correct architectural grounds that the CLI must not link `YardGit`. **What it did not provide
was any other way to run the engine in the meantime**, and #0115 is the standing precedent for what
that costs — forty-two M1 issues resolved with nothing anyone could run.

**This issue adds that other way, without touching the shipping architecture.** A second executable,
for development and demonstration only, that links `YardCommands` directly and runs engine commands
in-process. `switchyard` keeps its XPC-only dependency exactly as it is.

## Expected behavior

- [ ] A new executable target **`yard-engine`** in `YardKit/Package.swift`, `dependencies: ["YardCommands", "YardKit"]`,
      with sources at `YardKit/Sources/yard-engine/`. **Do not change the `switchyard` target's
      dependencies** — the whole point is that it stays XPC-only.
- [ ] `YardKit/Sources/yard-engine/main.swift`, modelled on the existing
      `YardKit/Sources/switchyard/main.swift` (18 lines): read `CommandLine.arguments.dropFirst()`,
      take `FileManager.default.currentDirectoryPath`, call `runEngineCommand(arguments:workingDirectory:)`,
      fall back to `runYard(arguments:)` when it returns `nil`, write stderr then stdout, `exit` with
      the `ExitCode`'s raw value.
- [ ] **It must print the header explaining what it is** on `--help`, before anything else: that this
      is a development harness which links the engine in-process, that `switchyard` is the real CLI
      and talks to the app over XPC, and that the two will not always agree once the app exists.
- [ ] A test in `YardKit/Tests/YardCommandsTests/` asserting the composition rule — `runEngineCommand`
      returning `nil` falls through to `runYard`, and a known engine command does not. Assert the
      **exit code and the `schemaVersion` in the payload**, not merely that something was printed.
- [ ] `cd YardKit && swift build` succeeds and **`swift run yard-engine whereami` prints a
      `schemaVersion: 1` envelope for this repository.** Paste the actual output into the report.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, above the count in `docs/test-baseline.txt`.

## Notes

**Milestone M3.** **Sibling #0338 wires the remaining commands into `runEngineCommand`** — this issue
only makes the one that already exists reachable, so that "can a human run it" and "how many commands
are wired" fail independently rather than as one lump.

**Paste the manifest edit rather than describing it.** #0129's precedent: a ten-line `Package.swift`
edit pasted literally was transcribed byte-identically first round, while #0124 spent three rounds
*designing* one and never wrote a test.

**This is a demo harness, not a product surface.** It does not need `--json` parity, does not need the
skill regenerated, and must not acquire commands of its own — everything it can do comes from
`runEngineCommand` and `runYard`.
