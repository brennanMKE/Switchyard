## Description

Commit ▸ Create Branch… makes a branch; Edit ▸ **Undo New Branch** is then offered and, when
chosen, **the branch is still there**. The same holds for Add Tag… and Undo New Tag. Nothing else
in the repository changes either, so from the user's side the Undo item does nothing.

This is not an accident. Guide §11 decision 20 (Brennan, 2026-08-17, #0231): *a restore deletes
only refs its snapshot recorded.* The checkpoint before Create Branch has no `made-here`, so the
restore leaves it. #0506 (question 3) and #0507 already noted that Undo of Check Out as Local
Branch and Undo New Branch behave this way, and assumed it acceptable.

**Measured in the VM** (planner's run `20261005-142949-90030`, `main` at 7ff8d880): #0598's spike
created `made-here` at "hist main three" from the Commit menu, chose Edit ▸ Undo New Branch, and
compared git state. Every branch, tag, HEAD, HEAD's tree and the status were back — except:

```
--- expected                                   --- actual
refs/heads/ff-topic 211ec3c3…                  refs/heads/ff-topic 211ec3c3…
                                               refs/heads/made-here 9b73b99e…
refs/heads/main b91560a5…                      refs/heads/main b91560a5…
```

and identically for `refs/tags/v-made-here` after Undo New Tag.

## Question for Brennan

Decision 20 exists so a restore does not silently delete a ref **a sibling worktree** created after
the checkpoint. It also catches the ref **the undone operation itself** created, which is the one
ref the user expects Undo to remove. Should it?

- **A — keep decision 20 as is.** Then the Edit menu should not promise what it does not do: Undo
  New Branch / Undo New Tag would be relabelled or disabled ("Can't Undo New Branch" — the #0459
  pattern for Push). Small, UI only.
- **B — delete the refs the undone entry's own operation created.** The entry knows its operation
  (`branch-create`, `tag-create`, `switch-track`) and the name it created; a restore of that entry
  would delete exactly that ref when it still names the oid the operation wrote, and nothing else.
  Decision 20's protection for sibling-created refs stands. Engine change in `JournalRestore` plus a
  metadata field; this is the GitUp-like behaviour (undo removes the branch).

**Assumed meanwhile:** A's behaviour is what ships. #0598's spike asserts everything except the
created ref is restored, and wraps "the ref is gone" in `XCTExpectFailure("#0600: …")`, so the
spike stays green today and **fails the moment B lands** (an expected failure that stops failing is
reported as a failure), which is the signal to delete those two `XCTExpectFailure` wrappers.

**Recommendation:** B, because a menu item named "Undo New Branch" that leaves the branch reads as a
bug, and B leaves decision 20's actual concern (other agents' refs) untouched. Not decided here: it
changes journal semantics Brennan set.

## Expected behavior

Brennan picks A or B; the chosen one is planned as its own issue down to the code.
