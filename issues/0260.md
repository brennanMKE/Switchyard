## Description

**Review finding on #0251, 2026-08-17.** #0251 narrowed step 6's object-existence check from the
recorded snapshot to the snapshot actually applied:

```swift
// YardKit/Sources/YardGit/JournalRestore.swift:384
let missing = try missingObjects(in: toApply, at: base, git: git)
```

That is the right call — an object a **left-alone** branch recorded is not something the restore is
about to write, so a missing one must not be able to refuse an operation that was never going to
touch it. But **nothing pins it.** Measured, during review of #0251:

| mutation | result |
|---|---|
| `missingObjects(in: toApply, …)` → `missingObjects(in: applied, …)` | `Test run with 1052 tests in 78 suites passed after 46.165 seconds` — **full suite, unfiltered, SURVIVED** |

The two mutations either side of it die immediately, which is what makes this one worth filing rather
than shrugging at: `toApply.restore(…)` → `applied.restore(…)` reddens
`restoreLeavesALiveSiblingsCheckoutAloneAndReportsIt` and `aSecondUndoPastTheSiblingsCommitAlsoSucceeds`,
and ignoring `prunable` in `leavingLiveDisturbances` reddens `aPrunableHoldersBranchIsStillRestoredNotLeftAlone`.
Step 6 is the one line of #0251's change with no test behind it.

**Why it is reachable.** Step 6 exists because a refusal *after* `HEAD` has already moved is worse than
no restore at all (see the type comment). Under the un-narrowed version, a live sibling holding a branch
whose recorded oid has since been garbage-collected — a stale entry, a repository that was maintained
between capture and undo — refuses the caller's whole restore over an object the restore had already
decided not to write. The caller's own undo becomes impossible for a reason that has nothing to do with
the caller, which is the exact family guide §11 decision 23 exists to end.

## Expected behavior

- [ ] A named test in `YardKit/Tests/YardGitTests/JournalRestoreTests.swift`: a live sibling holds
      `refs/heads/agent-branch`; the entry's snapshot records an oid for that branch which **no longer
      exists** in the object database; restore **succeeds**, reports the branch in `leftAlone`, and does
      **not** throw `Error.unrestorableObjects`.
- [ ] Reaching "recorded but gone" needs care. `RefSnapshot` capture records real oids, so the fixture
      must make one unreachable and then actually remove it — the surrounding tests never do this, so
      **measure what works rather than assuming**: a commit created, recorded, then made unreachable and
      expired is one route (`git reflog expire --expire=now --all` then
      `git gc --prune=now`), and `git cat-file -e <oid>` must be shown failing before the restore runs.
      **`switchyard` itself never runs `git gc`** (CLAUDE.md) — a *test fixture* doing so to construct a
      state is not that rule, but say in the test why it is there.
- [ ] **Mutation:** `missingObjects(in: toApply, …)` → `missingObjects(in: applied, …)`. The new test
      must redden. Confirm it landed on the line you meant — there is exactly one call site.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.
