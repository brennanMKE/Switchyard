## Description

**Filed by #0167's review on 2026-08-08.**

#0167 decision 5 claims that a checkpoint failing between the object writes and the anchor `create`
leaves nothing behind: the anchor-ref `create` is the single commit point, everything before it is
unreferenced loose objects, invisible to `JournalAnchor.list` and reclaimed by ordinary
maintenance. It is the mirror of #0033's invariant — *the cache may under-report the journal, never
over-report it.*

**The claim is argued from construction and never exercised.** No test injects a failure between
the blob writes and the anchor create. The file's only `#expect(throws:)` is the lock-contention
case, which fails *before* any object is written, so it does not reach the path in question.
`aTagPointingAtABlobDoesNotBreakTheCheckpoint` proves only the happy path.

## What this issue must deliver

A test that drives a checkpoint to fail *after* the refs blob and snapshot commit exist but
*before* the anchor ref is created, then asserts:

- `JournalAnchor.list` does not report the entry;
- `JournalRebuild.rebuild` reports neither an entry nor a **defect** for it — a half-written
  checkpoint must be invisible, not merely broken;
- the written objects are unreferenced, so ordinary maintenance would reclaim them. Assert
  reachability rather than running `gc` — **`switchyard` never runs `git gc`**.

## The injection point is the design question

The failure has to be induced without contorting production code into a test seam. Options worth
measuring before choosing:

- make the anchor `create` fail for real by pre-creating the ref, or by pointing the namespace at
  something `update-ref` refuses;
- an unwritable `$GIT_DIR` at the moment of the ref transaction;
- an existing-entry-id collision, which #0028 already refuses.

The first is likely cleanest — `JournalAnchor.write` refuses an existing entry id, and that
refusal happens after the objects are written.
