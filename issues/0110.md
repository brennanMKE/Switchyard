## Description

#0012's Description asks for a **conflict count**. What landed is `hasConflicts: Bool`.

The difference matters to the caller. An agent deciding whether to attempt an automatic resolution
cares whether there is one conflicted file or forty; a human deciding whether to open the merge UI
cares too. A boolean forces a second call to find out.

## Givens — verified on `main`, treat as true

1. The file is `YardKit/Sources/YardGit/WhereAmI.swift`, which already reports `hasConflicts`.
2. **Unmerged paths come from `git diff --name-only --diff-filter=U`**, or from stage entries in
   `git ls-files -u`. Do not parse `git status` porcelain for this — it reports conflicts in a
   different vocabulary and is harder to count exactly.
3. **`FixtureRepository.conflicted()` — `Sources/YardGit/FixtureRepository.swift:296` — already
   builds a conflicting merge**, but with **one** file (`f.txt`). Read it and follow its shape; you
   need the two-file variant, so add a sibling helper rather than reinventing the mechanism.
   The shape is: `build` a `base` commit, `build` divergent `ours` and `theirs` from it that edit the
   same paths, `checkoutDetached(repo.oids["ours"]!)`, then `merge --no-commit` the other.
4. **`repo.oids` is populated only by `build(_:)`** (line 134). `branch(_:at:)` at line 150 creates a
   ref and writes nothing. Force-unwrapping `oids` for anything `build` did not create traps and
   aborts the entire suite — that cost #0112 a round.
5. Every shell-out goes through `GitProcess` — a concrete struct, `GitProcess()`, `run(_:at:)` /
   `capture(...)`. There is no runner protocol.

## Measured on `main` before writing this — treat as verified

Built a two-file conflicting merge and ran both candidate commands:

```
$ git ls-files -u                       $ git diff --name-only --diff-filter=U
100644 4b48dee 1  f.txt                 f.txt
100644 b19a1e9 2  f.txt                 g.txt
100644 950b81b 3  f.txt
100644 4b48dee 1  g.txt                 → 2 lines, one per path
100644 b19a1e9 2  g.txt
100644 950b81b 3  g.txt
→ 6 lines for 2 paths
```

Then a **delete/modify** conflict, where the deleted side contributes no stage entry:
`diff --name-only --diff-filter=U` returned 3 paths; `ls-files -u` returned 8 lines. **So dividing
the `ls-files -u` line count by three is also wrong** — the stages-per-path is not a constant.

Also verified `--diff-filter=U` still lists a path whose worktree content happens to match a stage,
so it does not silently drop a hand-edited conflict.

**Use `git diff --name-only -z --diff-filter=U` and count NUL-terminated fields.** `-z` because the
non-`-z` form quotes paths containing special characters, and this project counts NUL-terminated
fields everywhere else for the same reason.

The existing comment at `WhereAmI.swift:222` describes the entry format as
`"<mode> <sha>\t<stage>\t<name>"`. **That is wrong** — the real format is
`<mode> <sha> <stage>\t<name>`, one tab, verified above. If that comment survives it must be
corrected; if `ls-files -u` stops being used, delete it.

## Expected behavior

- [ ] `conflictCount: Int` is reported alongside the existing flags.
- [ ] Zero in a clean repository, and exactly the number of unmerged paths in a conflicted one.
- [ ] Keep `hasConflicts` or derive it from the count — do not report two facts that can disagree.
- [ ] Counts each conflicted **path** once, not once per stage. `ls-files -u` lists up to three
      entries per path; that is the trap here.
- [ ] Tests use **swift-testing** — `import Testing`, `@Test`, `#expect`. Not XCTest.
- [ ] Tests are `throws` and use `try` — **never `try!`**. A trap in a test destroys the whole run
      summary; that cost #0012 a round.
- [ ] New tests go in **`YardKit/Tests/YardGitTests/`**. `Tests/YardGit/` is not a declared target
      path in `Package.swift`; a file placed there is silently never compiled, the suite stays green,
      and the count does not move. That cost #0095 a round.
- [ ] `cd YardKit && swift build` succeeds and `swift test` prints a `Test run with N tests` line you
      paste. **`main` reported 216 on 2026-08-07.** Run `swift test` on the branch *before* your
      change to get its own baseline, paste that number too, and N must exceed it.

## Tests must be able to fail

Build a fixture with **two** conflicted files and assert the count is exactly 2. A one-file test
passes for `hasConflicts ? 1 : 0` and for a stage-entry count, so it proves nothing.

**Run these three mutations and report each result individually.** A green suite is not evidence —
every rejected round in this project had a green suite.

| # | mutation | required |
|---|---|---|
| 1 | make the count `hasConflicts ? 1 : 0` | the two-file test FAILS (expects 2, gets 1) |
| 2 | count `ls-files -u` lines instead of unique paths | the two-file test FAILS (expects 2, gets 6) |
| 3 | make the count a constant `0` | the two-file test FAILS |

Restore after each and confirm the suite is green again and `git diff` is unchanged.

Also assert **zero** in a clean repository — mutation 3 must not be the only thing distinguishing
those two states.

**The planning update is what made this a one-round issue.** Before dispatching, both candidate
commands were run against a real two-file conflict rather than reasoned about: `ls-files -u` gives
six lines for two paths, and — the part that mattered — eight lines for the *three* paths of a
delete/modify conflict, where the deleting side contributes no stage entry. That single measurement
ruled out both plausible wrong implementations, including the divide-by-three workaround the original
issue text implicitly invited by saying `ls-files -u` "lists up to three entries per path".

`<mode> <sha>\t<stage>\t<name>`. It is `<mode> <sha> <stage>\t<name>` — one tab. The comment went
with the implementation that used it.
