## Description

**Found by the M1 milestone review, 2026-08-17**, as the structural reason its criterion-3 finding
(#0193) could exist at all.

`ExitClassCoverageTests` enumerates **conformers of `ExitClassCarrying`** — it scans source for lines
containing the protocol name and checks each conformer is registered. So it answers *"does every type
that carries an exit class do so correctly?"* and **cannot** answer *"does every error type carry
one?"* An error type that conforms to nothing produces no line containing the protocol name, and the
guard stays green.

That is exactly how `WorktreeStatusParser` came to have no error type at all (#0193) while every
mechanical check passed. The guard is not wrong; it is looking at the wrong set.

Concretely, and verified: **`FixtureRepository.Error` is the one engine error type with no exit
class**, and it ships in the `YardGit` product — `Package.swift` has no `exclude` for it. It *is*
registered in `DescriptionCoverageTests:94`, so the omission reads as an oversight rather than a
decision.

- [ ] The new test lives in `YardKit/Tests/YardWireTests/ExitClassCoverageTests.swift`, beside the
      scan it extends, and reads sources under `YardKit/Sources/YardGit/` and
      `YardKit/Sources/YardKit/`. It enumerates **every type declared as an error in
      `YardKit/Sources`** — the discovery
      rule is the design question here: `: Error`, `: Swift.Error`, `enum …Error`, `enum Failure`, and
      whatever else the codebase actually uses — and asserts each one conforms to `ExitClassCarrying`.
      Read the existing scan in `ExitClassCoverageTests` first and extend that machinery rather than
      inventing a second one.
- [ ] `FixtureRepository.Error` either gains an exit class or is excluded from the product with a
      recorded reason. Decide which and say why in the issue; do not do both.
- [ ] The new test must **fail** against a deliberately unconformed error type. Add one temporarily,
      observe red, remove it, and record that as the mutation — otherwise this is another guard that
      cannot see what it was written to catch, which is the third one this project has shipped.
- [ ] `swift test` prints a `Test run with N tests` line exceeding the count in
      `docs/test-baseline.txt` by exactly 1.

## Notes

`docs/review-failures.md` records three inert guards already — a staleness check that suppressed its
own stderr, a preflight check placed after `exit 9`, and a guard that computed the right answer and
wrote it where no artifact read it. The lesson each time was the same: **a control that only looks for
the absence of failure proves nothing.** This issue is not done until the new test has been seen red.

**The round hit this issue's own failure class inside its first draft, and said so.** Swift's `Regex`
word boundary follows Unicode text segmentation (UAX #29), which does not break a word between two
letters joined by a period — so `Regex("\bError\b")` matches `.Error` but **not** `Swift.Error`.
Scanning for the single token missed roughly **20 of the 35** declared error types, including
`WorktreeContext.Error` and `RepositoryIdentity.Error`, **and the suite stayed green**. A guard that
sees two-fifths of its subject and reports success is precisely the thing this issue was filed to end,
and it very nearly shipped as the fix for itself. Measuring the boundary behaviour directly, rather
than trusting what `\b` "obviously" means, is what caught it.

**Two further gaps surfaced and were allow-listed rather than quietly conformed**: `RepositoryIdentity.Error`
has no call site in `Sources` yet, and `RepositoryRegistry.Error` lives in `YardKit`, which does not
depend on `YardGit` and so cannot import `ExitClassCarrying` at all — its §6 mapping has to happen at
M3 wiring time. An allow-list entry with a written reason is the right shape for both: the guard stays
total, and the exceptions are visible instead of absent.
