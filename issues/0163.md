## Description

Filed from #0037's planning pass, which dropped the old criterion "a gpg-agent prompt cannot hang
the CLI indefinitely — a timeout produces exit 9" as untestable, so the concern is not lost.

The facts, measured or read from source on 2026-08-08:

- `GitProcess.environment(adding:)` pins `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS=""`,
  `SSH_ASKPASS=""`, `GIT_EDITOR=false`, and `GIT_PAGER=cat` — git itself cannot prompt.
- **None of those governs a signing helper's own UI.** gpg launches pinentry (a GUI dialog on
  macOS) for a passphrase-protected key, and `ssh-keygen` can read `/dev/tty` directly (#0036
  recorded its prompt behavior as unverified for the same reason).
- `GitProcess.launch` calls `process.waitUntilExit()` with **no timeout of any kind**. A helper
  that blocks on a prompt blocks the engine, and eventually whatever agent called it.

**This cannot be verified or exercised in this project's environment**: reproducing the hang
requires a passphrase-protected signing key, and creating signing keys is absolutely forbidden
(CLAUDE.md, Code signing). Any fix would therefore ship with a fake-helper test (a script that
sleeps — the #0037 fake-gpg pattern) rather than a real-key reproduction.

## The decision needed — this is a design question, not yet an implementation issue

Whether to add a bounded wait to `GitProcess`, and if so where and what the default is:

1. **No timeout (wontfix).** Position: a GUI pinentry is the user's own configuration doing its
   job; killing git mid-commit to dodge it is worse. The CLI's XPC layer may grow its own
   deadline instead (RemoteControl precedent).
2. **Opt-in timeout parameter on `run`/`capture`**, used only by signing-adjacent call sites,
   classified as `ExitClass.signingFailed` (9) when signing was in effect.
3. **Blanket default timeout on every invocation.** Almost certainly wrong — clones and fetches
   legitimately run for minutes — listed only to be rejected explicitly.

Do not dispatch this issue as written. It needs Brennan's pick among 1–3 (it changes what gets
built), then an Opus 5 planning pass to author the chosen option to code level — including the
measured behavior of `Process` termination on a blocked child and the fake-helper test.

## Preparatory measurement — 2026-08-17. The termination semantics, so whichever option is picked is cheap.

**Still open and still Brennan's pick** — options 1–3 change what gets built, so this is not being
decided here. What follows removes the one unknown a planning pass would otherwise have to establish,
and it needed no signing key: a `sh -c 'sleep 60'` child stands in for a blocked helper.

Measured on this machine, 2026-08-17, Foundation `Process`:

| child | what worked | `terminationStatus` | `terminationReason` | elapsed against a 1s deadline |
|---|---|---|---|---|
| ignores `SIGTERM` (`trap '' TERM`) — a pinentry-like case | needed `SIGKILL` | **9** | `uncaughtSignal` | 2.02s |
| ordinary | `terminate()` alone | **15** | `uncaughtSignal` | 1.01s |

Three consequences for option 2, if it is chosen:

1. **`terminate()` alone is not sufficient.** A helper that ignores `SIGTERM` — which is exactly the
   shape of the case this issue is about — survives it. The pattern that works is `terminate()`, a
   short grace period, then `kill(pid, SIGKILL)`, and it cost 1.0s of grace in the measurement above.
2. **`waitUntilExit()` returns promptly once the child is actually dead**, so the bounded wait belongs
   *around* the wait rather than replacing it: a `terminationHandler` plus a semaphore with a deadline,
   then escalate, then `waitUntilExit()` to reap. `GitProcess.launch` can keep its
   `waitUntilExit()` exactly where it is.
3. **The status is a signal number, not an exit code** (`terminationReason == .uncaughtSignal`), so a
   timeout must be classified explicitly rather than by reading `terminationStatus`. Note the trap:
   **a `SIGKILL`ed child reports status 9, and `ExitClass.signingFailed` is also 9** — a classifier
   that infers the exit class from the status would call every killed helper a signing failure and
   every signing failure a timeout. They must be distinguished by *how the process ended*, not by the
   number.

The fake-helper test the issue calls for is therefore buildable with no key and no signing at all:
point `GitProcess` at a script that sleeps, set a short timeout, and assert on the classified error.

## Decided as guide §11 decision 18, and planned to code level — 2026-08-17

**Option 2.** Taken in Brennan's absence on decisions 14–17's terms: reversible (a parameter deletion),
flagged in the guide, and decided on the measurements already in this issue. The guide entry carries
the reasoning; it is not repeated here.

### The change — `YardKit/Sources/YardGit/GitProcess.swift`

`capture` and `run` gain a `timeout: Duration? = nil` parameter, forwarded to the private launch path.
`nil` means what happens today: `waitUntilExit()` with no bound. **Do not give it a default value** —
a blanket timeout is option 3 and is ruled out.

The bounded wait goes **around** `waitUntilExit()`, not in place of it. The measured shape:

```swift
// Measured 2026-08-17 on this machine, Foundation Process:
//   child ignoring SIGTERM (`trap '' TERM`): terminate() alone does NOT end it.
//     terminate(), 1s grace, then kill(pid, SIGKILL) -> status 9, .uncaughtSignal, 2.02s
//   ordinary child: terminate() alone -> status 15, .uncaughtSignal, 1.01s
```

so: a `terminationHandler` plus a semaphore with the deadline, then `terminate()`, then a short grace,
then `kill(process.processIdentifier, SIGKILL)`, then `waitUntilExit()` to reap. `waitUntilExit()`
returns promptly once the child is actually dead, which is why it can stay where it is.

### The classification trap, and it is the one thing that must not be got wrong

**A `SIGKILL`ed child reports `terminationStatus == 9`, and `ExitClass.signingFailed` is also 9.** A
classifier that reads the number will call every killed helper a signing failure and every signing
failure a timeout. Distinguish by **how the process ended**:

```swift
process.terminationReason == .uncaughtSignal   // killed, not exited
```

Add a case to `GitProcess.Failure`:

```swift
/// The child was still running when its deadline expired, and was
/// terminated. Distinct from `.exited`: nothing about its status is a git
/// exit code -- a SIGKILLed child reports 9, which collides with
/// ExitClass.signingFailed's raw value.
case timedOut(after: Duration, arguments: [String])
```

`CommitCreate` maps it to `ExitClass.signingFailed` **only where signing was in effect** — reuse
`signingInEffect(_:in:git:extraEnvironment:)`, which already exists for exactly this question. Where
signing is not in effect a timeout is `.repositoryError`.

### Where the timeout is passed

**Only the signing-adjacent call sites**, which is the whole point of option 2 over option 3:
`CommitCreate.run`'s `git commit` invocation, and the `git rebase` in `Fixup`'s `autosquashRebase`
when `signing` is not `.noSign`. Everything else keeps `nil` and today's behaviour. Name a constant —
`GitProcess.signingTimeout` — rather than sprinkling a literal, and say in its comment that the value
is a guess about human patience, not a measurement.

### Tests — `YardKit/Tests/YardGitTests/GitProcessTimeoutTests.swift`

**No signing key, and no real gpg.** The fake helper is a shell script that sleeps, which is the
technique this issue's own text predicted:

- **A child that exits normally within its deadline is unaffected** — `git --version` with a 30-second
  timeout returns its output.
- **A sleeping child is terminated and reported** as `.timedOut(after:arguments:)`, not as `.exited`.
  Point `gpg.program` at `#!/bin/sh\nsleep 60` and commit with signing on.
- **A child that ignores `SIGTERM` is still killed** — `#!/bin/sh\ntrap '' TERM\nsleep 60`. This is the
  case `terminate()` alone does not handle and the reason the grace-then-`SIGKILL` exists.
- **Classification**: with signing in effect the failure carries `ExitClass.signingFailed` (9); with
  signing off it carries `.repositoryError` (6). Assert the exit class, not the raw termination status.

**Rule 7c applies with force here.** Do **not** assert how long anything took. Assert that the call
*returned* and *what it returned*. A test that checks elapsed seconds will pass alone and fail in the
full suite — that is measured, and it cost a round today. Keep every timeout in a test generous
(seconds, not milliseconds) and make the child's sleep much longer than the deadline so the ordering
is not in question.

## Work log

- **Round 1 — 2026-08-17, Sonnet subagent, 176,133 tokens, rejected.** The escalation and the
  classification were right; the delivery was not. It replaced `GitProcess`'s synchronous stdout read
  with a `DispatchQueue.global()` drain plus a blocking semaphore **on every invocation**, and the
  full suite went from 38 seconds to over ten minutes at ~0% CPU. The round stalled twice waiting on
  a background test run it had started, ending two turns with no report — it could not tell slow from
  hung. Logged in `docs/review-failures.md`.
- **Round 2 — 295,994 tokens, accepted.** The `nil` path is restored exactly and the drain is confined
  to `timeout != nil`, on a `Thread.detachNewThread` rather than a pooled queue — the comment on
  `StdoutDrain` records why, and it is worth reading: a pool thread blocking on work queued to its own
  exhausted pool is the deadlock, and it only appears once enough callers compete.
- **A second defect the round found on its own:** both call sites were passing a timeout whenever
  `signing` was *shaped* like it might sign — and `.config` is the default, so nearly every commit and
  rebase in the suite took the expensive path. They now resolve `signingInEffect` once, cheaply, and
  pass a deadline only when a signature will actually be attempted.
- **Review.** 1021 green twice with `main` merged in, ~39s both — the same neighbourhood as `main`.
- **One gap, filed rather than spent a third round on: #0239.** Under the mutation
  (`terminate()` alone, no `SIGKILL`) `childIgnoringSigtermIsStillKilled` **passes**, in 60 seconds
  instead of 2, because the fake child's own `sleep 60` eventually ends it. Nothing asserts that the
  escalation reached `SIGKILL`, and Rule 7c rightly forbids asserting the elapsed time.
- `signingTimeout` stays at **30 seconds** — a guess about human patience at a pinentry prompt, not a
  measurement, and labelled as such in the source.
