## Description

**Found by the third #0044 umbrella review, 2026-08-17, and measured.** An ordinary restore **deletes
a branch or tag a sibling worktree created**, with no refusal, no omission in the `Report`, and
nothing in `detachedFrom`.

Measured with a probe in `JournalRestoreTests`' own fixture style:

```
main worktree checkpoints; linked worktree "agent" runs `git branch sibling-wip <oid>`
while standing on agent-branch; main restores its own checkpoint.

PROBE before: exit=0 f4bd7e80…
PROBE restore succeeded, restored: [refs, head, index, worktree, untracked]
PROBE after:  exit=128  fatal: Needed a single revision
```

`refs/heads/sibling-wip` is gone. The same probe with `git tag sibling-tag` deletes the tag.

**The mechanism, in two places:**

- `RefSnapshot.restore` plans `delete <name>` for **every** current direct ref absent from the
  snapshot (`RefSnapshot.swift:198-200`). A ref created after the checkpoint is by definition absent.
- `WorktreeDisturbance.disturbances` skips every worktree entry without a `branch` attribute
  (`WorktreeDisturbance.swift:111`) — it protects what a sibling has **checked out**, and a branch a
  sibling merely created is not that.

## This needs Brennan's pick, and here is why it is not mine

#0044's premise sentence is *"Getting the shared/per-worktree split wrong loses someone's work —
silently"*, and this is literally that. But decision 2's operative sentence is scoped to *"every
sibling worktree whose **checked-out branch** the snapshot would move, delete, or re-create"*, so
**by its letter the criterion is met**. The review marked it a proposal for exactly that reason.

It is the same interpretive shape as #0211 — which I decided in your absence as guide §11 decision 16
— and I am not deciding this one the same way, because the three readings differ in what gets built
rather than in how carefully:

**A — restore stops deleting refs it did not record.** Delete only refs the snapshot itself carried,
leaving anything created since untouched. Safest, and it changes what "restore" means: the repository
would no longer match the snapshot exactly, which is the promise `RefSnapshot.restore`'s own type
comment makes.

**B — extend the disturbance check to refs, not just checkouts.** Refuse when the snapshot would
delete any ref a live sibling created since. Keeps restore exact, costs a refusal the caller must
resolve, and needs a force path — which does not exist until M3's flag surface.

**C — record it as designed.** Restore is repository-wide over refs on purpose; a sibling's
uncommitted-to-a-worktree branch is out of scope until there is a force surface to talk about. Cheapest,
and it leaves a silent deletion in place.

**My recommendation is B**, with the refusal naming the ref and the worktree that created it, deferred
until the force surface exists — and **A as the interim**, because a restore that leaves a stranger's
branch alone is closer to what a user expects than one that deletes it silently. But B and C produce
materially different milestones, so this is your call.
