## Description

**Found by the third #0044 umbrella review, 2026-08-17, and measured.** An ordinary restore **deletes
a branch or tag a sibling worktree created**, with no refusal, no omission in the `Report`, and
nothing in `detachedFrom`.

Measured with a probe in `JournalRestoreTests`' own fixture style:

```
main worktree checkpoints; linked worktree "agent" runs `git branch sibling-wip <oid>`
while standing on agent-branch; main restores its own checkpoint.

PROBE before: exit=0 f4bd7e80…
PROBE restore succeeded, restored: [refs, head, index, worktree, untracked]
PROBE after:  exit=128  fatal: Needed a single revision
```

`refs/heads/sibling-wip` is gone. The same probe with `git tag sibling-tag` deletes the tag.

**The mechanism, in two places:**

- `RefSnapshot.restore` plans `delete <name>` for **every** current direct ref absent from the
  snapshot (`RefSnapshot.swift:198-200`). A ref created after the checkpoint is by definition absent.
- `WorktreeDisturbance.disturbances` skips every worktree entry without a `branch` attribute
  (`WorktreeDisturbance.swift:111`) — it protects what a sibling has **checked out**, and a branch a
  sibling merely created is not that.

## This needs Brennan's pick, and here is why it is not mine

#0044's premise sentence is *"Getting the shared/per-worktree split wrong loses someone's work —
silently"*, and this is literally that. But decision 2's operative sentence is scoped to *"every
sibling worktree whose **checked-out branch** the snapshot would move, delete, or re-create"*, so
**by its letter the criterion is met**. The review marked it a proposal for exactly that reason.

It is the same interpretive shape as #0211 — which I decided in your absence as guide §11 decision 16
— and I am not deciding this one the same way, because the three readings differ in what gets built
rather than in how carefully:

**A — restore stops deleting refs it did not record.** Delete only refs the snapshot itself carried,
leaving anything created since untouched. Safest, and it changes what "restore" means: the repository
would no longer match the snapshot exactly, which is the promise `RefSnapshot.restore`'s own type
comment makes.

**B — extend the disturbance check to refs, not just checkouts.** Refuse when the snapshot would
delete any ref a live sibling created since. Keeps restore exact, costs a refusal the caller must
resolve, and needs a force path — which does not exist until M3's flag surface.

**C — record it as designed.** Restore is repository-wide over refs on purpose; a sibling's
uncommitted-to-a-worktree branch is out of scope until there is a force surface to talk about. Cheapest,
and it leaves a silent deletion in place.

**My recommendation is B**, with the refusal naming the ref and the worktree that created it, deferred
until the force surface exists — and **A as the interim**, because a restore that leaves a stranger's
branch alone is closer to what a user expects than one that deletes it silently. But B and C produce
materially different milestones, so this is your call.

## One thing worth knowing before you pick — added 2026-08-17

**Option A also fixes #0232**, the two-agent undo deadlock, and no other option does.

`RefSnapshot.restore` deletes every direct ref absent from the snapshot, so "the refs a restore
touches" is every ref in the repository — which is why the cross-tool guard has to be repository-wide,
and why a sibling's ordinary commit refuses the caller's traversal from step two onward. Scope the
deletion to recorded refs and the touched set becomes `applied.refs` plus `HEAD`; the guard can then be
scoped to that set without weakening it, and both problems go away together.

That is not an argument that A is *right* — it changes what restore promises, and "the repository
matches the snapshot" is a real property to give up — but it is the strongest single fact about the
choice, and it was not visible when this issue was filed.

## Decided — option A, guide §11 decision 20. Planned to code level 2026-08-17.

**Brennan picked A.** The guide entry carries the reasoning and what is given up; it is not repeated.
This section is the shape.

### The change — `YardKit/Sources/YardGit/RefSnapshot.swift`

`restore` currently plans a deletion for every current direct ref absent from the snapshot:

```swift
// RefSnapshot.swift:198-200
for current in try Self.listDirectRefs(at: base, git: git) where !wanted.contains(current.name) {
    commands += "delete \(current.name)\n"
}
```

**Delete that loop.** A restore writes `update` for every ref the snapshot carries and touches nothing
else. Update the type's own doc comment in the same change: it currently promises the repository will
match the snapshot, and after this it matches it **except** for refs created since the capture. A
comment that overstates what the code does is how the next reader gets it wrong.

**One thing that must not change with it:** the journal's own namespace was already excluded from
deletion planning for a reason recorded at `RefSnapshot.swift:36-46` — deleting an anchor ref makes the
snapshot that anchor keeps alive unreachable. That exclusion becomes redundant rather than wrong. Leave
the comment; it explains a hazard that would otherwise be re-introduced by someone restoring the loop.

### The second half — scoping the cross-tool guard, which is #0232

With deletion scoped, "the refs a restore touches" is `applied.refs` plus `HEAD` rather than every ref
in the repository. That is what makes `CrossToolGuard.diff` scopeable, and scoping it is what fixes
#0232's deadlock. **Do that in #0232, not here** — this issue is one deliverable, and #0232 already
exists with the measurement in it. Say in the report that you left it.

### Tests — `YardKit/Tests/YardGitTests/JournalRestoreTests.swift`

The issue's own probe is the first test, and it is the criterion:

- **A sibling's newly created branch survives a restore.** Main worktree checkpoints; a linked
  worktree runs `git branch sibling-wip <oid>` while standing on its own branch; main restores its own
  checkpoint. Assert `refs/heads/sibling-wip` still resolves to the same oid afterwards. Measured
  before the fix: `exit=128 fatal: Needed a single revision`.
- **The same for a tag** — the probe showed `git tag sibling-tag` is deleted identically.
- **A ref the snapshot *does* carry is still restored to its recorded value**, including one that moved
  since the capture. This is the assertion that stops the fix from becoming "restore stopped writing
  refs".
- **The journal namespace is still never deleted**, which the existing tests cover — say which ones you
  checked rather than adding another.

**Mutation to run and report:** put the deletion loop back and confirm the sibling-branch test reddens.
