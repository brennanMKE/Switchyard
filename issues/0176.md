## Description

**Filed by #0167's review on 2026-08-08, from a mutation the planner did not write.**

#0167 decision 7 requires `JournalLock.withLock` to wrap the *entire* checkpoint flow — capture →
blob write → `list`/`generate(after:)` → anchor write — not merely the final write. The shipped
code does exactly that, verified by reading it.

**But no test can tell the difference.** #0167's row M7 removes the lock entirely, which the
contention test catches. Review then applied a row the table did not have: hoist the capture, the
blob write and the id generation *outside* the lock, leaving only `JournalAnchor.write` inside.
**The suite stays green.**

So the property decision 7 exists to guarantee — that another process cannot read the same newest
id and mint a colliding entry between our read and our write — is unwitnessed. The contention test
observes a `JournalLockError` thrown from the write step and finds nothing written, which is true
of both the correct and the incorrect scoping.

## What this issue must deliver

A test that fails when the lock is narrowed to the final write. That needs genuine concurrency —
two threads, or two processes, interleaving at the read-then-write window — rather than the
sequential contention the current test uses.

- **Prefer a second process** over a second thread. `withLock` is synchronous and polls with
  `usleep`, and #0168's planning pass measured that macOS `flock` returns `EWOULDBLOCK` on a
  second fd **in the same process** — so an in-process attempt may prove something other than what
  it appears to.
- The failing case is two checkpoints minting the **same id** or one silently overwriting the
  other's anchor. Assert on the surviving entry list, not on whether an error was thrown.
- The test must be deterministic. A race that reproduces "usually" is worse than no test: it will
  be quarantined the first time it flakes.

## Why this is its own issue

Witnessing a race is separate work from the flow that has one, and #0167 was already two rounds.
`JournalPrune` and #0168's restore take the same lock and will want the same guarantee, so the
harness for it is shared.

## Notes

`docs/review-failures.md` records the general lesson: a mutation table drifts toward the lines that
are easy to perturb, and the claim lives in the design. M7 removing the lock is the easy
perturbation; narrowing its scope is the one that matters, and only a reviewer writing a row the
table lacked found it.
