## Description

**Review finding on #0254, and then measured by a probe rather than argued.** #0254 made `around`'s
in-flight slot claim **first-writer-wins**: if the slot already names a still-live journal entry, the
catch clause does not overwrite it. That fixed a real orphaning bug. It also opened a worse one,
because **a journal entry outlives its operation** — entries persist until pruned — so "the slot names
a live entry" and "the slot is held by the operation that is live right now" are not the same claim.

The round's own justification was *"a worktree can only hold one resumable sequencer at a time, so the
two coincide."* They coincide only while one sequencer stays up continuously.

**Reproduced end to end, measured 2026-08-18** by a throwaway probe in `PostRewriteAttachTests`, run in
the foreground and then deleted:

| step | measured |
|---|---|
| 1. `Fixup.run` conflicts | slot = entry **A** (`slotAfterA == entryA.id.string`) |
| 2. caller runs `git rebase --abort` **directly**, not through `Fixup` | `isMidRebase` false; **slot untouched, still A** — nothing switchyard-side ran to clear it |
| 3. before operation B starts | `SequencerSnapshot.capture(in:git:)` returns **nil** — no operation is live at this instant |
| 4. operation B conflicts, leaving its **own** rebase live | 2 entries exist, but `slotNamesALiveEntry` sees A still live and **refuses to let B claim the slot** |
| 5. B's `git rebase --continue` fires the real `post-rewrite` hook | `attachRewrite(entryID: nil)` finds A live *and* an operation in progress (B's), so #0253's gate passes |

**Result:** `attached?.id == entryA.id`. **Entry A's `rewrite` went from absent to populated with B's
mapping — an operation A never ran — and entry B's `rewrite` stays nil, so B's own rewrite is recorded
nowhere.** That is #0241's symptom, reached from the write side, and it is a corrupted journal rather
than a missing one: a later undo of A would consult a mapping describing a different operation.

## Expected behavior

- [ ] `around` clears a **stale** slot at the **start** of the call — before `body` runs — when the
      slot exists and **no operation is live**:

      ```swift
      let context = try WorktreeContext.resolve(path: path, git: git)
      // #0261: a slot left by an operation that has since ended -- an
      // out-of-band `git rebase --abort` is the reachable case -- names a
      // live ENTRY long after its operation is gone, and #0254's
      // first-writer-wins check would then refuse THIS call the slot and
      // divert its rewrite onto the older entry (measured). Nothing is live
      // yet at this point in the call, so an existing slot here is stale by
      // construction.
      if try SequencerSnapshot.capture(in: context, git: git) == nil {
          let pendingPath = try context.path(
              for: RepositoryLayout.inFlightEntryIDRelativePath, git: git)
          try? fileManager.removeItem(atPath: pendingPath)
      }
      ```

      Place it **after** `WorktreeContext.resolve` and **before** `checkpoint(...)`. The exact
      placement is the whole fix; put it after `body` runs and it does nothing.

- [ ] **#0254's protection must survive unweakened.** In the two-failing-calls case #0254's test
      covers, the second call's `around` *starts while the first operation's rebase is still live*, so
      `SequencerSnapshot.capture` is **non-nil** at the start and this clear does not fire.
      `aSecondConflictingFixupCannotClobberTheFirstsInFlightSlot` must keep passing — **say that you
      ran it.**
- [ ] The probe above becomes a **permanent** named test in
      `YardKit/Tests/YardGitTests/PostRewriteAttachTests.swift`: conflicting `Fixup.run`, out-of-band
      `git rebase --abort`, a second unrelated conflicting operation, its continue — and B's mapping
      lands on **B's own entry**, with entry A's `rewrite` still nil.
- [ ] **Mutation 1:** delete the new clear. The new test must redden.
- [ ] **Mutation 2:** move the clear to *after* `checkpoint(...)` — it still runs, but this call's own
      entry now exists. State what happens and whether any test notices; if nothing does, say so
      rather than leaving it unsaid.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.

## Notes

Parent **#0254**, and the third issue in the family whose root is *the slot's lifetime is not bound to
an operation* — #0253 fixed the read side, #0254 the write side's claim, and this is the write side's
**release**. The three together are what guide §11 decision 19 as amended actually requires.

**Why not simply clear the slot on a successful `around`?** Because the operation that leaves the slot
behind is one that **threw** — there is no successful call to hang the release on. Clearing at the
*start* of the next call is the only point where the "nothing is live" fact is knowable, which is what
step 3 above measures.
