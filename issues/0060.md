## Description

GitUp wrote its own rebase engine because stock libgit2's is not sufficient for interactive-style
history rewriting. M5's commands need something similar — but how much of one, and can `absorb` and
`split` be built on narrower primitives instead?

This is an open question in guide §11 and needs a written decision before the M5 commands are built,
not during.

## Expected behavior

- [ ] The minimum primitive set M5 actually requires is enumerated.
- [ ] Options compared: stock libgit2 rebase, shelling out to `git rebase`, a purpose-built engine.
- [ ] Decision recorded in `docs/` with reasoning, including what it costs each M5 command.
- [ ] Guide §11 updated to move this from open to settled.

## Planning pass — 2026-09-09, to code level. One round.

**The decision to evaluate and record** (hypothesis from `docs/clean-room/rebase-engine-scope.md`,
written 2026-08-06 before this issue; GitUp's rebase implementation was not consulted and must not
be): **do not write a rebase engine. Build a rewrite pipeline over git's non-interactive
primitives** — `commit-tree` (make a modified copy of a commit), `cherry-pick` (replay onto a new
base, structured conflict reporting), `update-ref --stdin` (move the branch once, transactionally),
all wrapped in `JournalCheckpoint.around` so undo reverses the whole rewrite as one step. The
evidence bar for ever growing more machinery: a specific M5 command demonstrably failing under this
pipeline, not an assumption up front.

**The minimum primitive set, per command (the enumeration criterion):**

| command | primitives it needs | replay? |
|---|---|---|
| `reword` | `commit-tree` + descendant replay | yes, trivial (no tree change) |
| `drop` | the same walk, commit list minus one | only where the gap conflicts |
| `reorder` | the same walk, reordered list | conflicts only where the new order actually conflicts |
| `split` | #0016 hunk IDs + index manipulation + two `commit-tree` calls | no replay beyond the split point's own descendants |
| `absorb` | #0018 range-limited blame + `cherry-pick` replay of descendants | yes — the one genuine replay consumer |

**The comparison (record all three, with the costs):**

1. *Stock libgit2 rebase* — not linked at all since #0123/#0103's re-milestone; adopting it would
   resurrect the vendoring question for an insufficient engine. Rejected.
2. *Shell out to `git rebase -i`* with a scripted `GIT_SEQUENCE_EDITOR`: the intent lives in a
   temporary todo file whose format is not a stable contract; failures surface as half-finished
   sequencer state rather than typed errors; `GIT_SEQUENCE_EDITOR` is already pinned to `false` in
   `GitProcess` as a hazard guard. Rejected as the general mechanism (Fixup's `--autosquash`
   without `-i` remains the measured exception it is).
3. *Purpose-built engine* (GitUp's route): the most code, and it reimplements conflict semantics
   git already owns. Rejected absent a demonstrated need.

**What the decision costs each command** (goes in the recorded doc): every rewritten commit is
created through `CommitCreate`'s signing path, so signed commits stay signed by construction
(#0061/#0062/#0063's criterion); conflicts surface as `cherry-pick`'s structured state, mapping to
the exit-8 resumable contract; the risk to watch is rerere replay (#0065) diverging from `git
rebase` expectations — that is the concrete finding that would justify more machinery.
