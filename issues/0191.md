## Description

**Split out of #0153 on 2026-08-17.** #0153 builds the store — `JournalObserved.record`, writing a
foreign transaction's ref updates into `refs/switchyard/observed/` (guide §11 decision 12). Nothing
calls it. This issue is the call, from the `reference-transaction` hook's `committed` state, and the
two invariants that make it safe to call from there.

Both invariants already exist in #0042's decision core; this issue proves they survive the store.

## Expected behavior

- [ ] A committed **foreign** transaction's updates land as one observed entry, end to end through
      the hook path — not by calling `JournalObserved.record` directly, which #0153 already covers.
- [ ] **The journal's own ref writes produce no entry.** `switchyard` sets an environment marker and
      the hook skips its own transactions; #0042 decided this and the store must not undo it. Without
      it the journal records itself recording itself, once per entry, forever.
- [ ] **A failure to persist never produces a non-zero hook exit.** #0042's totality invariant: the
      hook returns 0 in every state that is not `committed`, and a `committed` state whose recording
      throws still returns 0. A hook that fails aborts the user's ref transaction — measured in
      CLAUDE.md's gotchas as `fatal: ref updates aborted by hook`, exit 128 — so a journal defect
      must never become a repository defect.
- [ ] `cd YardKit && swift test` prints a `Test run with N tests` line greater than the count on main
      when the round starts; state the delta at planning time.

## Notes

**Blocked by #0153.** Read `docs/switchyard-git-internals-and-undo.md` §4 and `ReferenceTransaction`
(`YardKit/Sources/YardGit/ReferenceTransaction.swift`) — `decide` already returns the exit code and
the updates, so this issue wires an existing decision to an existing store rather than deciding
anything new.

The states git 2.50.1 actually emits are `prepared`, `committed`, `aborted` — measured; there is no
`preparing`. Do real work only on `committed` and return 0 immediately in every other state, so a
future git that adds a state cannot break a repository.

To be planned to code level when #0153 resolves.

## Planning update — 2026-08-17. #0153 landed; this is the composition.

Both halves now exist on `main` and neither needs changing:

- **`ReferenceTransaction.decide(stateArgument:environment:markerVariable:readStandardInput:)`**
  (`ReferenceTransaction.swift:134`) already enforces every invariant this issue is about. Read its
  body: `exitCode` is hard-coded `0` on all three paths; a state other than `committed` returns before
  `readStandardInput` is ever called; a non-empty marker returns before it too. **Do not re-implement
  any of that** — the totality and the marker skip are decided there, and this issue's job is not to
  undo them.
- **`JournalObserved.record(_:in:now:git:)`** (`JournalObserved.swift`) writes one entry under
  `refs/switchyard/observed/`.

So the deliverable is the seam between them, and the one thing neither can do alone: **swallow a
persistence failure so a journal defect never becomes a repository defect.**

## Change 1 — `YardKit/Sources/YardGit/ReferenceTransaction.swift`, append

```swift
extension ReferenceTransaction {

    /// What one `reference-transaction` hook invocation did.
    public struct HookOutcome: Equatable, Sendable {
        /// What the hook must exit with. **Always 0**, including when
        /// recording failed — a non-zero exit from this hook aborts the
        /// user's ref transaction (`fatal: ref updates aborted by hook`,
        /// exit 128, measured), so a journal defect must never become a
        /// repository defect.
        public let exitCode: Int32
        /// The observed entry written, when one was.
        public let recorded: JournalAnchor.Entry?
        /// Why recording failed, when it did. Present *and* `exitCode == 0`
        /// is the normal shape of a swallowed failure; a caller that wants to
        /// surface it may, but the hook does not.
        public let recordingFailure: String?
        /// Malformed stdin lines dropped while parsing.
        public let malformedLineCount: Int
    }

    /// Runs one hook invocation end to end: decide, then persist.
    ///
    /// The decision core owns the invariants (exit 0 always; only `committed`
    /// reads stdin; our own transactions are skipped via the marker). This
    /// adds persistence and **catches everything it can throw**, which is the
    /// whole reason it is a separate function rather than a call site.
    public static func runHook(
        stateArgument: String,
        environment: [String: String] = ProcessInfo.processInfo.environment,
        in context: WorktreeContext,
        markerVariable: String = GitProcess.markerVariable,
        git: GitProcess = GitProcess(),
        readStandardInput: () -> Data
    ) -> HookOutcome {
        let decision = decide(
            stateArgument: stateArgument,
            environment: environment,
            markerVariable: markerVariable,
            readStandardInput: readStandardInput)

        guard !decision.updates.isEmpty else {
            return HookOutcome(
                exitCode: decision.exitCode, recorded: nil,
                recordingFailure: nil,
                malformedLineCount: decision.malformedLineCount)
        }

        do {
            let entry = try JournalObserved.record(
                decision.updates, in: context, git: git)
            return HookOutcome(
                exitCode: decision.exitCode, recorded: entry,
                recordingFailure: nil,
                malformedLineCount: decision.malformedLineCount)
        } catch {
            // Deliberately total. Every failure mode of the store -- a git
            // that cannot run, a ref that already exists, a full disk --
            // lands here and still exits 0.
            return HookOutcome(
                exitCode: decision.exitCode, recorded: nil,
                recordingFailure: String(describing: error),
                malformedLineCount: decision.malformedLineCount)
        }
    }
}
```

**`exitCode: decision.exitCode` rather than a literal `0` on purpose**: it keeps a single source for
the invariant, so a mutation to `decide` that breaks it fails this layer's tests too.

## Change 2 — `YardKit/Tests/YardGitTests/ReferenceTransactionHookTests.swift`, new file

Four tests in a `struct ReferenceTransactionHookTests`:

1. `aForeignCommittedTransactionIsRecordedAsOneObservedEntry` — stdin with two update lines, an
   environment with **no** marker, state `committed`. Assert `exitCode == 0`, `recorded != nil`, and
   that `JournalObserved.list(in:)` returns exactly one entry whose metadata decodes to those two
   updates, `refName` included.
2. `theJournalsOwnTransactionsAreNotRecorded` — the same stdin, but the environment carries
   `GitProcess.markerVariable` set to a non-empty value. Assert `recorded == nil` and that
   `JournalObserved.list` is **empty**. Assert too that `readStandardInput` was **never called** — use
   a captured `var read = false` and check it, because "no entry was written" is also true if the
   parse silently produced nothing.
3. `aPreparedTransactionRecordsNothingAndReadsNoInput` — state `prepared`, same assertions on the
   read flag and an empty listing. **`prepared` and `aborted` are the only other states git 2.50.1
   emits — there is no `preparing`** (measured 2026-08-07; CLAUDE.md records it, and guide §9's M2
   criterion was corrected on 2026-08-17 to say "every state that is not `committed`"). Use a
   nonsense state string as well, in the same test, to prove the default path is do-nothing rather
   than case-by-case.
4. `aFailureToPersistStillExitsZero` — the totality invariant, and the point of this issue. Pass
   `git: GitProcess(executablePath: "/usr/bin/false")`, which the suite already uses for exactly this
   (`YardKit/Tests/YardGitTests/FailingGitFixture.swift:69`). Assert `exitCode == 0`,
   `recorded == nil`, and `recordingFailure != nil`. **Resolve the `WorktreeContext` with a real
   `GitProcess` first**, then hand the failing one to `runHook` — `/usr/bin/false` fails
   `rev-parse` too, so resolving the context with it throws `WorktreeContext.Error` before the hook
   is ever reached, which would make this test pass for the wrong reason.
