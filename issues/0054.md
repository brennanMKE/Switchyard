## Description

UI tests will not run under CLI-driven `xcodebuild` in this environment — the runner times out
enabling automation mode because it lacks Accessibility rights. RemoteControl hit exactly this and
solved it with a documented manual script, which is the approach to carry forward.

## Expected behavior

- [ ] Script covers: broker ping with the app closed, on-demand activation, live data from the running app, app-pushed events, streaming progress.
- [ ] Failure scenarios covered: app quits mid-session, CLI killed mid-session, broker restarted under the app, two concurrent sessions, nothing registered at all.
- [ ] Each scenario states the expected output and exit code so a human can tell pass from fail.
- [ ] Referenced from `issues/Issues.md` as the verification path for XPC issues.

## Planning update — 2026-08-17. What the script can cover, and what it must drop.

**Half the scenarios in the Expected behavior list describe features Switchyard has not chosen to
build.** "App-pushed events" and "streaming progress" are RemoteControl's session model — long-lived
sessions with the app streaming back to an attached CLI. Guide §11 decision 15 settles Switchyard's
wire as **argv in, a rendered envelope out**, and #0213 has not yet established that sessions are
needed at all. Writing scenarios for them now would document a design nobody has adopted.

So the script covers what exists at the end of the #0045→#0218 chain, and **says explicitly** which
original scenarios were dropped and why. Do not silently omit them.

### Deliverable — `scripts/verify-xpc.md`, not a shell script

A `.sh` cannot check "the app launched and its window appeared", and the point of this artifact is
that a **human** runs it and reads the results. Prose with copy-pasteable commands, each scenario
stating: preconditions, the exact command, the expected stdout, and the expected exit code.

`../../RemoteControl/docs/` has the model to follow; read it before writing.

### The scenarios that are real today

1. **Nothing registered at all.** Fresh machine state, app never launched:
   `switchyard noop` → exit **2** (`broker_unreachable`), and the JSON envelope carries
   `"code":"broker_unreachable"`.
2. **Broker ping with the app closed.** After the app has been launched once (so the launch agent is
   registered) and then quit: the broker answers on demand — launchd starts it — and the app stays
   closed. This is the acceptance probe `BrokerProtocol.brokerPing` was written for (#0046).
3. **On-demand app launch.** A command that needs the app, with the app closed, launches it and
   succeeds; `--no-launch` in the same state exits **3** (`app_unavailable`) and launches nothing.
   Check with `pgrep -x Switchyard` before and after.
4. **Live data from the running app.** With the app open, a command returns a result that reflects the
   repository the CLI was invoked in, **not** the app's own working directory — the check that
   `workingDirectory` is being marshalled (guide §11 decision 15).
5. **App quits mid-request.** Start a command, quit the app, expect exit **5**
   (`session_terminated`) and no hang.
6. **Broker restarted under the app.** `launchctl kickstart -k gui/$UID/co.sstools.Switchyard.broker`,
   then a command: the app re-registers its endpoint via `interruptionHandler` (#0047) and the command
   succeeds. This is the only scenario that exercises re-registration, and it is the reason #0047
   wrote it.
7. **Two concurrent CLIs**, in two different repositories, at once. Both get their own answers.
8. **The `@Sendable` failure paths from #0053** — kill the app mid-request, and restart the broker
   under it — confirming the handlers run **without a `SIGTRAP` crash**. #0053's planning update
   assigns these here explicitly; they cannot be reached from `swift test`.

### The one measurement this script owns

**Cold-start latency**, which #0048 lists as a criterion and cannot measure. With the app closed and
the agent registered, time a command that needs the app:
`/usr/bin/time -p switchyard <cmd>` — record the real seconds, three runs, and note the machine.
#0048's report is expected to point here rather than to a fabricated number.

### Criterion 4 of the original list

Reference the script from `issues/Issues.md` under the XPC issues, so a future issue claiming "XPC
verified" has a named place to point at. An issue that claims XPC verification without naming a
scenario number from this file has not verified anything.

## Verification

This issue produces a document, so its verification is that **a human can follow it**: every command
in it must be pasteable, and every expected exit code must come from `ExitCode`
(`YardKit/Sources/YardKit/ExitCode.swift`) rather than from memory. Run every command that does not
require the app to be installed, and mark the ones you could not run as unrun — do not write expected
output you did not observe.
