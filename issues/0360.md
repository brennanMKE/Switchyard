## Description

Two single-commit replay operations from GitUp's commit-node context menu (see #0359's capture)
that Switchyard does not have in any form: **Revert Against Current Branch** (apply the inverse of
a commit onto the current branch as a new commit) and **Cherry-Pick Against Current Branch**
(replay a commit from another branch onto the current branch).

The engine half is small — both are `git cherry-pick` (or `cherry-pick --no-commit` + inverse
apply for revert) against a known target, which #0060's decision already measured for structured
conflict reporting (exit 1, `CHERRY_PICK_HEAD`, `# Conflicts:` list, `--abort` verified clean).
The new work is the typed wrapper, the CLI verbs, and the journal discipline.

## Expected behavior

- [ ] `yard revert <commit>` applies the inverse commit to the current branch through
      `CommitCreate`'s signing path; `yard cherry-pick <commit>` replays it. Both non-interactive.
- [ ] Both auto-checkpoint and are exactly undoable; conflicts exit 8 leaving git's own resumable
      state (the measured cherry-pick shape).
- [ ] Refusals typed before mutation: reverting a merge (needs `-m`, refused with a reason),
      picking a commit already reachable from the current branch, unknown commit.
- [ ] Signed commits stay signed per the #0060 explicit-`-S` rule.
- [ ] Both appear as #0359 context-menu items when the node permits (the disabled states mirror
      the typed refusals).

## Notes

The menu's disabled-state logic is the UI half of the engine's refusal knowledge — the same
pattern #0359 established.

### Items, titles, shortcuts

Add `CommitAction.revert` and `.cherryPick`. They form a new menu group after #0359's Delete group:

| Item | Title | Shortcut |
|---|---|---|
| revert | `Revert on “main”` — detached: `Revert on HEAD` | ⌥⌘R |
| cherryPick | `Cherry-Pick onto “main”` — detached: `Cherry-Pick onto HEAD` | ⌥⌘C |

#0359 allocated both shortcuts. **Titles now depend on the branch**, so move `title` from
`CommitAction` onto `CommitActionState`, filled in by `CommitActionRules.states(for:)` from
`context.branchName`. #0359's seven titles stay static strings. Naming the branch in the item tells
the user where the new commit will land before they choose it. **No ellipsis on either**: both
commit at once with git's default message, and neither asks for input.

### Availability

These go in `CommitActionRules.reason`, **after** the shared busy and in-progress checks and
**outside** `rewriteReason`. Neither action rewrites `HEAD`'s history, so the "only commits in
“main”’s own history" guard must not apply.

| Action | Disabled when | Reason text | Mirrors |
|---|---|---|---|
| revert | the node is a merge (`parents.count > 1`) | "Reverting a merge commit isn’t supported" | the typed merge refusal in Expected behavior |
| cherryPick | the node is reachable from `HEAD` in the window | "Already in “main”" | the typed already-reachable refusal |
| cherryPick | the node is a merge | "Cherry-picking a merge commit isn’t supported" | **UI-conservative**: git needs `-m` for it too. Keep it only if the engine planning pass adds the matching refusal; otherwise let the engine answer. |

Add `isReachableFromHead: Bool` to `CommitActionContext`, computed in `make` as
`LocalReachability.oids(in: rows, from: [whereAmI.rawHead]).contains(oid)` (#0368). It is bounded
by the loaded window. A commit that *is* reachable from `HEAD`, but only through history older than
the window, reads as not reachable. The item then stays enabled and the engine's typed refusal
arrives through `CommitActionFailure`. That is the correct fallback, not a bug to chase.

### Invocation and result

- **Immediate, no confirmation.** Both add one new commit on top of `HEAD`, and the journal records
  it. Same reasoning as #0359's Move Up/Down.
- **Progress label**: "Reverting…" / "Cherry-picking…", in #0359's header slot, with the same busy
  disabling.
- **After success**: select the new `HEAD` commit, the refreshed `WhereAmI.rawHead`, and scroll it
  into view through #0359's `ScrollViewReader`. The user sees the commit they just made, at the top,
  on the current branch's lane.
- **Failure titles**: "Couldn’t Revert Commit" / "Couldn’t Cherry-Pick Commit", added to
  `CommitActionFailure.make`'s `verb` switch. The conflict sentence applies unchanged to exit
  class `.blockedOnConflicts`.

### A conflicted revert is invisible to the header today (*measured*)

`WhereAmI` probes `MERGE_HEAD` and `CHERRY_PICK_HEAD` through `rev-parse --git-path`
(`YardKit/Sources/YardGit/WhereAmI.swift`, both the sync and async paths). It never probes
`REVERT_HEAD`. So after a conflicted **revert**, #0369's `operationInProgress` returns `nil`: the
header shows no warning, and #0359's rules leave every rewrite enabled over a half-finished revert.

**Blocked by #0376.** Brennan, 2026-09-12: `WhereAmI` gains an `isMidRevert` state (engine and
schema), so the alternative this section used to offer — mapping the revert's conflict onto a state
`WhereAmI` already reports — is withdrawn. Once #0376 lands, #0369's `operationInProgress` returns
"A revert is in progress", in the same position as the other three, and #0359's rules disable every
rewrite over a conflicted revert like any other in-progress operation. This issue's UI leg lands
after #0376.
