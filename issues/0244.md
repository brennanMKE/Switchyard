## Description

**Found by #0232's round while building its two-agent test, 2026-08-17, and reported as out of scope
rather than fixed there.** `WorktreeDisturbance.disturbances` — `JournalRestore` step 5, which runs
unconditionally and is #0044's decision 2 — **treats a target snapshot that never recorded a ref name
the same as one that deletes it.**

That was accurate before **guide §11 decision 20**. It is stale now: restore leaves an unrecorded ref
alone, so "the snapshot does not mention this branch" no longer means "the snapshot would remove this
branch". A sibling worktree standing on a branch the target snapshot simply never captured is now
refused for a disturbance that cannot happen.

The round hit it directly: constructing a two-agent test with a **real checked-out sibling worktree**
refused independently of the guard it was fixing. It kept its own test's `agent-branch` as a plain
uncontested branch to avoid conflating the two, documented that in the test's doc comment, and left
`WorktreeDisturbance.swift` alone because step 5 is outside #0232's named scope.

## Expected behavior

- [ ] `disturbances` distinguishes **"the snapshot would move or delete this branch"** from **"the
      snapshot never recorded it"**. Only the first can disturb a sibling now.
- [ ] The existing disturbance tests still pass unchanged — `restoreRefusesToDisturbASiblingsCheckout`,
      `aPrunableWorktreeStillRefusesAndSaysHowToRelease`,
      `aDetachedSiblingHoldsNoBranchAndIsNeverDisturbed`,
      `theCallersOwnCheckedOutBranchIsNotADisturbance`, and the two #0203/#0210 tests that pin the check
      running under `bypassGuard` and under the cross-worktree override. **Say that you ran them**,
      because they are the reason to be careful here.
- [ ] A new test: a live sibling checked out on a branch the target snapshot **never recorded** does
      **not** refuse the restore, and that branch is untouched afterwards.
- [ ] Mutation: treat an unrecorded name as a deletion again, and confirm the new test reddens while
      the existing refusal tests stay green.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, **N greater than 1036**.

## A second instance, in step 4 — noted 2026-08-17 while reviewing #0232

The same staleness appears in `CrossToolGuard` for a ref **neither** the belief nor the target
records. After #0232, such a name is still reported as a divergence — `anotherToolsMoveRefusesRestore
WhileTheChainStandsOnAnEntry` pins that for `rogue` — even though the restore, post-decision-20, will
never touch it.

That is defensible as a general "the world changed under you" signal and it is **deliberately pinned**,
so it is not being changed on my say-so. But it is the same question this issue asks about step 5, and
whoever answers one should answer both: **is a ref the restore cannot touch grounds for refusing?**

If the answer is no in both places, that test changes with it. If it is yes for step 4 and no for
step 5, the difference should be written down, because the two now behave inconsistently.
