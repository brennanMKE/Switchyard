## Description

**Found by the third #0044 umbrella review, 2026-08-17, and measured.** In a two-agent repository —
the usage #0044 exists to support — agent A's **second** undo is refused, and stays refused, because
of an ordinary commit by agent B in B's own worktree on B's own branch.

```
PROBE first undo ok
PROBE sibling commit exit=0 [agent-branch e9bdaa8] sibling work
PROBE second undo FAILED: repository changed since capture:
  refs/heads/agent-branch was 75644410…, now e9bdaa8b…
```

A's **first** undo succeeds only because its scoped cursor is nil, so the cross-tool guard is skipped
entirely. Once A is mid-traversal the cursor is non-nil, the guard runs against a
**repository-wide** snapshot diff, and every further step of A's walk is refused with a divergence
naming a ref A does not control and cannot act on. There is no non-force way out, and `bypassGuard`
has no CLI surface until M3.

## Why this is filed as a consequence rather than a violation

Decision 1 says the chain is per-worktree precisely so that one agent's work does not disturb
another's traversal. Decision 3 **explicitly endorses** the guard catching a sibling's move ("is
caught from any worktree"). So the umbrella records both halves and does not say what happens when
they meet — which is this. No stated criterion is violated; the criteria are jointly incomplete.

## The shape of an answer

Two candidates, and the choice is a design decision rather than a bug fix:

- **Scope the guard's diff to what the applied snapshot would actually write.** A divergence in a ref
  the restore will not touch is not evidence that the caller's world changed under it. This preserves
  the guard's purpose — catching a tool that moved something the journal is about to restore — while
  letting siblings work.
- **Keep the guard repository-wide and make the refusal actionable**: say which divergences belong to
  a sibling worktree, name that worktree, and say what to do. Weaker, but it does not narrow a safety
  check on the strength of one measurement.

The first is the better shape and also the riskier change, because the guard is what stands between
the journal and a tool that moved refs behind its back.

- [ ] Whichever way: a test in the two-agent shape — A undoes twice while B commits in between — that

## This is the same root cause as #0231 — analysed 2026-08-17, and it changes who decides it

I set out to plan the first candidate above — scope the guard's diff to what the applied snapshot
would actually write — and it does not stand on its own. Read `RefSnapshot.restore`:

```swift
// RefSnapshot.swift:198-200
for current in try Self.listDirectRefs(at: base, git: git) where !wanted.contains(current.name) {
    commands += "delete \(current.name)\n"
}
```

**A restore deletes every direct ref absent from the snapshot.** So "the refs the restore would touch"
is *every ref in the repository*, and the guard's repository-wide diff is already scoped exactly to
what restore touches. There is nothing to narrow. `CrossToolGuard.diff`'s own doc comment —
*"Empty means no other tool moved anything restore would touch"* — is accurate today for that reason.

So the deadlock is not a defect in the guard. It is the second consequence of restore being
repository-wide over ref **deletion**, and #0231 is the first:

- **#0231**: a sibling's newly created branch is deleted, because it is absent from the snapshot.
- **#0232** (this): a sibling's ordinary commit refuses the caller's traversal, because the guard must
  be repository-wide for the deletion to be safe.

**#0231 option A — restore stops deleting refs it never recorded — fixes both.** With deletion scoped
to recorded refs, the touched set becomes `applied.refs` plus `HEAD`, and the guard can be scoped to
that set without weakening it. Under options B or C the deadlock stays and needs its own answer.

**So this issue is blocked by #0231**, which is Brennan's pick, and its own two candidates should not
be decided before that one. Recording the dependency rather than building against a shape that may
not survive the decision.

## Unblocked — #0231 took option A, 2026-08-17

Brennan picked **A** on #0231 (guide §11 decision 20): a restore deletes only refs its snapshot
recorded. That is the half this issue was waiting on, and it is what makes the fix here possible —
with deletion scoped, **"the refs a restore touches" is `applied.refs` plus `HEAD`** rather than every
ref in the repository, so the cross-tool guard can be scoped to that set without weakening it.

**This issue is now the second half, and it is small:** `CrossToolGuard.diff` compares the believed
snapshot against the whole repository. Scope it to the refs the applied snapshot will actually write,
and a sibling's ordinary commit on its own branch stops refusing the caller's traversal.

**Sequence after #0231**, not alongside it — the scoping is only correct once deletion is scoped, and
doing them together produces a diff in which neither half can be reviewed on its own.

The measurement to turn into a test is already in this issue: agent A undoes twice while agent B
commits in between, and the second undo currently fails with
`repository changed since capture: refs/heads/agent-branch was 75644410…, now e9bdaa8b…`.

**The assertion that must survive the fix**, and it is the reason to be careful: a divergence in a ref
the snapshot **does** write must still be refused. Narrowing a safety check without pinning what it
still catches is how it stops catching anything.

## Planned to code level — 2026-08-17, after #0231 landed

#0231 is merged, and its round established that the consequence is **broader than this issue's title**:
the guard now refuses the next traversal after **any** foreign ref creation, not only a sibling
worktree's. Six existing tests in `JournalUndoTests` had to be rewritten around it, and three of them
now pin the refusal deliberately with a comment naming this issue. **Those three are the acceptance
test for this work** — they must go back to asserting the traversal succeeds.

### The change — `YardKit/Sources/YardGit/CrossToolGuard.swift` and one call site

`diff` compares two whole snapshots:

```swift
public static func diff(recorded: RefSnapshot, current: RefSnapshot) -> [Divergence]
```

Give it a scope — the set of ref names the restore will actually write:

```swift
/// Divergences limited to `scope`, the ref names the caller is about to
/// write. A ref outside it cannot be disturbed by this restore, so a change
/// to one is not evidence that the caller's world moved under it (#0232).
/// `HEAD` is always in scope: restore always writes it.
public static func diff(
    recorded: RefSnapshot, current: RefSnapshot, scope: Set<String>
) -> [Divergence]
```

Keep the two-argument form, delegating with the full name set, **only if something still needs it** —
check, and if nothing does, delete it rather than leaving an unscoped overload for someone to reach
for by accident. Say which you found.

The single call site is `JournalRestore.swift:320`, inside step 4. The scope it passes is the names
`applied` will write — `Set(applied.refs.map(\.name))` — and `applied` is already in scope at that
point, computed a few lines above at step 3.5. **Pass `applied`, not `recorded`**: the two differ
under the cross-worktree override and after #0211's head detach, and the guard must be scoped to what
will actually be written.

### The property that must survive, and the test that pins it

**A divergence in a ref the snapshot *does* write is still refused.** Narrowing a safety check without
pinning what it still catches is how it stops catching anything — and
`anotherToolsMoveRefusesRestoreWhileTheChainStandsOnAnEntry` exists for exactly that. It must keep
passing unchanged; say that you checked it rather than assuming.
