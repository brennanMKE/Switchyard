## Description

Git can record how a conflict was resolved and replay that resolution when the same conflict
reappears. For agents this is directly valuable: a human resolves a merge conflict once in
Switchyard's three-way UI, and every subsequent rebase of that branch resolves it without asking.

Surface it in the app so recorded resolutions are **visible and editable** rather than invisible
magic — a replayed resolution that nobody can inspect is indistinguishable from a bug.

## Expected behavior

- [ ] `yard rerere status --json` reports what is recorded.
- [ ] Recorded resolutions are visible in the app as a **sidebar section** (#0081) alongside branches, worktrees, and stashes, and can be deleted or edited.
- [ ] Selecting one shows the recorded resolution in the Detail pane.
- [ ] Resolving via #0057 records a resolution when `rerere` is enabled.
- [ ] A replayed resolution is reported in command output, never applied silently.

## Planning pass — 2026-09-09, to code level. Two rounds.

**Scope split**: round 1 is the engine + CLI (`yard rerere status --json`, the replay-reporting
rule); round 2 is the app sidebar section + detail pane. The split keeps the engine testable
headless and the UI round focused on #0081's section idiom.

**Round 1 — the engine and the CLI arm:**
- `YardKit/Sources/YardGit/Rerere.swift` (NEW) — probe git's rerere surface in a fixture FIRST and
  paste output: `git rerere status` (conflicted paths rerere knows about), `git rerere diff`
  (recorded resolutions as diffs), `git rerere remaining`, and the `.git/rr-cache` layout. Then
  build: `Rerere.status(at:git:)` → recorded resolutions (path, conflict id, whether a resolution
  is recorded vs merely known), `Rerere.enabled(at:git:)` (config `rerere.enabled`), typed errors.
  Read-only — this round never invokes `git rerere` mutating subcommands.
- **The replay-reporting rule** (the criterion that matters): a replayed resolution must be
  reported, never applied silently. Wire it where conflicts are already surfaced: the resolve
  serving path (#0057) and the conflicts command gain a `rerereReplayed: [path]` field when git's
  output/status shows a replayed resolution during the operation. Probe what `git merge`/`git
  cherry-pick` print on replay ("Resolved 'f.txt' using previous resolution") in the fixture and
  parse that shape.
- **Recording on resolve** (#0057 criterion): when `rerere.enabled` is true, a resolution staged
  through the resolve flow is recorded by git itself at the next `git rerere`-aware operation —
  verify what actually records it (the merge machinery, not us) and assert the recorded state
  appears in `Rerere.status` after a resolve. If enabling is required, the resolve arm documents
  that `rerere.enabled` is the repository's choice, never set by Switchyard.
- `YardKit/Sources/YardCommands/RerereServing.swift` (NEW) + `EngineCommands.swift` case +
  `YardKit/Schemas/rerere-status.json` + golden/registry updates.
- `YardKit/Tests/YardGitTests/RerereTests.swift` (NEW) — fixture-driven: enable rerere, resolve a
  conflict, re-raise it, assert status shows the recorded resolution and the replay is reported;
  disabled-rerere shape; refusals.
