## Description

A plain double-clicked app cannot publish a named Mach service — `NSXPCListener(machServiceName:)`
only works when launchd owns the name, and launchd only learns a name from a launchd property list.
So a small launch agent embedded in the bundle declares the name and acts as a bootstrap broker.

The broker holds the app's anonymous listener endpoint so the CLI can find it. `NSXPCListenerEndpoint`
is a live Mach right — it can be passed over an existing XPC connection and nowhere else, never
written to disk — which is the entire reason a broker must exist rather than the app leaving its
endpoint somewhere readable.

## Expected behavior

- [ ] Publishes `co.sstools.Switchyard.broker` via its launchd plist and `MachServices`.
- [ ] Accepts and stores the app's endpoint; hands it to CLI clients on request.
- [ ] `yard ping` reaches it with the app never launched — launchd starts it on demand.
- [ ] Restarting the broker mid-session does not disturb an attached CLI, verified manually.
- [ ] Holds no traffic after the handoff — it is out of the data path.

### The shape, read from the source

```swift
@objc public protocol BrokerProtocol {
    /// Liveness check that does not depend on the app running at all.
    func brokerPing(reply: @escaping @Sendable (String) -> Void)
    /// Called by the app after it creates its anonymous listener.
    func registerAppEndpoint(_ endpoint: NSXPCListenerEndpoint)
    /// Called by the CLI. Replies `nil` when no app has registered.
    func appEndpoint(reply: @escaping @Sendable (NSXPCListenerEndpoint?) -> Void)
}
```

Three details from RemoteControl's implementation that are load-bearing and easy to lose in a port:

1. **The endpoint registry is guarded by a lock, not an actor.** XPC invokes each connection's methods
   on its own queue, so the registry is reachable from several queues concurrently. Its own comment
   says why a lock rather than an actor.
2. **Only the connection that registered may clear the endpoint.** RemoteControl tracks whether *this*
   connection is the registering one; without that, any client could clear another's registration.
3. **`@Sendable` on every reply closure.** CLAUDE.md's gotcha: XPC invokes these off the main queue, and
   under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` an unmarked closure inherits main-actor isolation
   and **crashes with `SIGTRAP` at runtime with no compiler warning**. #0045 set the BrokerAgent target
   to `SWIFT_DEFAULT_ACTOR_ISOLATION = nonisolated`, which reduces the risk in *this* target — but the
   app side, which #0047 writes, is MainActor by default, so the protocol must carry `@Sendable`
   regardless.

## Where the protocol goes

**`YardKit`, not `YardGit`.** It is an XPC/app identifier concern, the same category as `ServiceNames`,
and `YardGit` must not grow app-layer surface (guide §11 decision 13's reasoning applies unchanged).
Put it in `YardKit/Sources/YardKit/XPCProtocols.swift`, matching RemoteControl's file name.

**The broker executable is not a package target**, so it cannot `import YardKit` unless #0045's Xcode
target is given the product dependency. **Check first**: if `BrokerAgent` has no `YardKit` product
dependency, adding one is in scope for this issue and is the same four-line pbxproj edit #0045 made —
and **Xcode must be closed**, per Rule 5d and #0045's precondition. If it is already there, say so.

## Review of round 1 — 2026-08-17. Accepted in substance; one stated criterion is not met.

The port is right and the fresh work is better than the port. `BrokerProtocol` carries `@Sendable` on
all three reply closures; the listener reads `ServiceNames.machServiceName` rather than a literal; the
`YardKit` product dependency was added to the `BrokerAgent` target after confirming Xcode was closed;
the build succeeds and both files are embedded, proven by `file` on the executable rather than a green
build. **916 tests**, exactly the predicted +7.

**`EndpointRegistry` is the part worth keeping.** Making it generic over the value and an
`Owner: Hashable & Sendable` token, and moving the ownership check *inside* `clear(owner:)` rather than
tracking a bool on the service, turns the one piece of real logic into something testable without XPC
at all — seven tests including clear-by-a-different-owner and reassignment. That is the difference
between porting 150 lines and understanding them.

### The criterion that is not met

> *"The service name in the plist and the one the listener uses come from the same source of truth, or a
> test pins that they agree. They are in different files and nothing currently connects them."*

The round reported this satisfied by the existing `ServiceNamesTests.derivedNamesShareTheBundleIdentifier`.
It is not. That test asserts relationships **among the Swift constants only**:

```swift
#expect(ServiceNames.machServiceName == "\(ServiceNames.bundleIdentifier).broker")
#expect(ServiceNames.agentPlistName == "\(ServiceNames.machServiceName).plist")
```

Verified: **nothing in `YardKit/Tests` reads `Support/co.sstools.Switchyard.broker.plist`.** `grep -rn
'broker.plist\|Support/' YardKit/Tests` returns nothing. So the file on disk — which is what launchd
actually reads — is pinned by no test, which is precisely the gap the criterion was written to close.

This is the same shape as several findings today: **a test whose name suggests coverage it structurally
cannot provide.** The consequence here is specific and bad: if the plist's `MachServices` key and
`ServiceNames.machServiceName` ever diverge, launchd reserves one name while the listener publishes
another, and the broker silently never receives a connection. This issue's own Notes say `ping` is the
highest-value diagnostic in the system — a silent mismatch defeats it.

### Round 2 — one test

Add to `YardKit/Tests/YardKitTests/ServiceNamesTests.swift`:

- Locate `Support/co.sstools.Switchyard.broker.plist` **relative to the source file** — `#filePath` is
  the reliable anchor; the package's working directory during tests is not. Walk up to the repository
  root and read it from there, and if the file is missing **fail** rather than skipping, or the test
  becomes a no-op the day someone moves it.
- Parse it with `PropertyListSerialization`.
- Assert three things, each of which can break independently: `Label == ServiceNames.machServiceName`;
  the `MachServices` dictionary has **exactly one** key and it equals `ServiceNames.machServiceName`;
  and the file's own name equals `ServiceNames.agentPlistName`.
- Measured, so you can assert against something real — `plutil -p` today prints:
  `Label => co.sstools.Switchyard.broker`, `MachServices => { "co.sstools.Switchyard.broker" => true }`,
  `BundleProgram => Contents/MacOS/BrokerAgent`, `ProcessType => Interactive`, `RunAtLoad => false`.

**Mutation, and it must be observed:** change the `MachServices` key in the plist to
`co.sstools.Switchyard.broker2`, confirm the new test goes red, and restore it. A test that reads a file
and asserts nothing falsifiable is worse than none.

Expected delta: **+1**, from a baseline of 912 on `main` — not the 909 round 1 measured, because #0209
landed in between. Merge `main` into the branch first, then predict.
