## Description

**Finding of #0160's fifth umbrella review, 2026-08-18, reproduced by two probes against pristine
`main`.** The in-flight slot now has a claim rule (#0254), a release rule (#0261) and a read rule
(#0253), written by three separate rounds. **All three ask a question about the *worktree* — "is any
rebase live?", "does the slot name a live entry?" — and none asks about *this call*.** They compose
correctly only when every rebase in the worktree was started inside an `around`. A rebase started
outside one — **a user or an agent running `git rebase` directly, which is the ordinary case this whole
mechanism exists for** — is invisible to all three.

`around` already probes the sequencer *before* running the body, at `JournalCheckpoint.swift:310`, and
throws that answer away.

### Route 1 — an empty slot is claimed on behalf of a foreign rebase

1. A **foreign** rebase (raw `Process`, no `SWITCHYARD_*` marker) stops on a conflict. `rebase-merge`
   is live, the slot is absent, `JournalAnchor.list` is empty — no switchyard code has run.
2. An unrelated switchyard operation runs and throws. Its catch finds `SequencerSnapshot.capture != nil`
   — **the foreign rebase** — the slot is empty so `slotNamesALiveEntry` is false, and it claims the slot.
3. switchyard concludes that rebase. `attachRewrite(entryID: nil, stillInProgress: true)` attaches the
   **foreign rebase's mapping to the unrelated operation's entry.**

```
PROBE slot after unrelated failing operation: 01M09YXM0FHHGAN17W44C2Z6M2  unrelated=01M09YXM0FHHGAN17W44C2Z6M2
PROBE final invocation: source=rebase entryID=nil resumable=true
PROBE attached: 01M09YXM0FHHGAN17W44C2Z6M2
✘ (attached?.id) != (unrelated.id)
✘ (after.rewrite → RewriteMapping(source: "rebase", …)) == nil
```

### Route 2 — a stale slot survives, because #0261's clear only fires when *nothing* is live

1. A conflicting `Fixup.run` leaves slot = entry A, rebase A live.
2. Out-of-band `git rebase --abort`. Slot = A is stale, nothing live.
3. **Before any further switchyard operation runs**, an unrelated **foreign** rebase goes live.
4. An unrelated switchyard operation fails during it. #0261's clear does not fire (a sequencer *is*
   live) and #0254's first-writer-wins refuses to claim (A is still a live entry). Slot stays A.
5. switchyard concludes the foreign rebase → **its mapping lands on entry A**, aborted long ago.

**The stored mapping is wrong, not missing**, and the documented safe degradation everywhere else in
this mechanism is no-attach.

## Expected behavior

Two independent changes; **route 1 needs the first, route 2 needs both.**

- [ ] **Bind the pre-body sequencer answer and require it.** `around` at `JournalCheckpoint.swift:310`
      already computes it:

      ```swift
      let sequencerWasLiveBefore = try SequencerSnapshot.capture(in: context, git: git) != nil
      ```

      In the catch, require `!sequencerWasLiveBefore` before claiming the slot. **A body can only have
      left a resumable operation behind if none was live when it started.** That is the statement about
      *this call* that all three current rules lack.

- [ ] **Decide what happens to `slotNamesALiveEntry` (#0254) and say why.** The new condition subsumes
      it: in #0254's own two-failing-calls scenario the second call's `around` starts while the first
      rebase is live, so `sequencerWasLiveBefore` is true and it never reaches the claim.
      `aSecondConflictingFixupCannotClobberTheFirstsInFlightSlot` must keep passing either way — **say
      that you ran it.** If you keep the helper, it must still be pinned: a mutation removing it has to
      redden something, or it is dead protection.

- [ ] **Stamp the slot with the operation it is waiting for**, so the read side can tell "the operation
      this slot was written for" from "some other operation that happens to be live". **Measured, git
      2.50.1: both backends write an `orig-head` file** — `rebase-merge/orig-head` and
      `rebase-apply/orig-head`, each holding the pre-rebase oid (verified in both layouts; the file
      lists are in this issue's Work log). `SequencerSnapshot` already knows both layouts
      (`SequencerSnapshot.swift:20-24`).

      Write `<entry-id> <orig-head-oid>` into the slot, and have `inFlightEntryID` require that the
      **currently live** operation's `orig-head` matches the recorded one. A slot whose stamp does not
      match the live operation is stale by construction: treat it exactly as the existing stale paths do
      — remove it, return nil, no attach.

      **Keep reading it through `WorktreeContext.path(for:)`** — `worktrees/<name>/rebase-merge/orig-head`
      — never by concatenating onto `.git/`.

- [ ] **A slot written before this change has no stamp.** Decide and state what happens to it: treating
      an unstamped slot as stale is the safe direction and costs one missed attach, once. Say which you
      chose.

- [ ] **Both probes become permanent named tests** in
      `YardKit/Tests/YardGitTests/PostRewriteAttachTests.swift`: a foreign rebase plus an unrelated
      failing operation attaches **nothing**; and the stale-slot-plus-foreign-rebase route attaches to
      neither entry. The foreign rebase must be driven through a raw `Process` with the `SWITCHYARD_*`
      marker removed — a `GitProcess` invocation is own-marked and does not reproduce it.
- [ ] **Mutations:** (1) drop `!sequencerWasLiveBefore` from the claim — the route-1 test must redden.
      (2) drop the `orig-head` comparison from the read — the route-2 test must redden. Confirm each
      landed on the line you meant; `JournalCheckpoint.swift` has several similar `SequencerSnapshot.capture`
      call sites and one was mis-mutated earlier today for exactly that reason.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.

## Notes

Parent **#0160**, bullet 2 — the same criterion #0253, #0254 and #0261 were each filed against, in a
quadrant none of them covers. #0254's doc comment at `:283-292` explicitly reasons about a *second
switchyard call* throwing during a *first switchyard call's* rebase; **the quadrant where the live
rebase belongs to nobody switchyard knows about appears in none of the three rounds' comments.**

**This is the fourth issue against one root cause** — *the slot's lifetime is not bound to an
operation*. The first three bound it to a worktree instead. If this fix also turns out not to close it,
the next step is not a fifth patch: it is to ask whether the slot should exist at all, or whether the
hook should carry the entry id itself (#0217's arm has the environment available).
