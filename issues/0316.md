## Description

**Proposed by the M1 milestone review's twelfth pass, as the concrete half of its answer to "is criterion
5 closable?".** Two of the five classes every M1 finding falls into can be **enforced inside the suite**
rather than left to a reviewer noticing — and this project already has the machinery.

`ExitClassCoverageTests`, `DescriptionCoverageTests` and `ConformanceScan.swift` are exactly this shape:
a source scan compared against a runtime registry, in both directions, so a type added without its
assertion turns a test red. **That is why nobody has found an unpinned `description` in twelve passes.**

Two more classes deserve the same treatment.

### (a) Enum vocabulary parsed out of git output

Every case of every enum the engine parses from git's output should appear in a **table-driven test fed
the real git bytes for that case**, with the case count asserted so a newly added case fails until its
row exists.

**Findings this would have caught mechanically:** #0311 (`UD`, `AU`, `UA` — three of seven conflict kinds
unpinned), #0310 (`C` in the status alphabet), #0304 (`rebase-apply`), #0306 (`gpgsig-sha256`).

### (c) Hand-written conformances

Every hand-written `==`, `encode(to:)` and `description` should be checked against its type's **stored
member list**, so omitting a member fails a test rather than passing silently.

**Finding this would have caught:** #0312 — `WorktreeEntry.==` omits `prunableReason` *today*, and no
mutation was needed to expose it; a scan would simply have failed.

## Expected behavior

- [ ] **Read `ConformanceScan.swift` and `ExitClassCoverageTests` first** and follow their shape. They
      already solved the hard part — comparing a source scan against a runtime registry in both
      directions — and a second, differently-shaped scanner is how the two drift apart.
- [ ] **(c) first: a stored-member-vs-`==` scan.** It is the smaller of the two, it has a live defect to
      prove itself against (#0312), and it needs no git fixtures. **Land it and confirm it fails on
      `WorktreeEntry` before #0312 is fixed** — a scan that goes green on arrival has proved nothing.
- [ ] **(a) second: enum vocabulary coverage.** Start with `ConflictedFile.Kind` and
      `WorktreeStatusEntry`'s status alphabet, the two the pass measured. **Say how you decided which
      enums are "parsed out of git output"** — that boundary is the whole design, and a scan that
      over-reaches will be disabled by the first person it annoys.
- [ ] **Each scan must fail for the right reason and say so in its message.** `ExitClassCoverageTests`'s
      messages are the standard: they name the missing type and what to add.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, above the count in `docs/test-baseline.txt`.

## Sequencing

**Do (c) before #0312 is fixed** so the scan demonstrably catches a real, live omission. If #0312 has
already landed, **reintroduce the omission temporarily** to prove the scan, then restore it — and say so
in the report.

## The files

The existing scans live in **`YardKit/Tests/YardWireTests/`**:
`ConformanceScan.swift`, `ExitClassCoverageTests.swift`, `DescriptionCoverageTests.swift`. **Read all
three before writing anything** — `ConformanceScan.swift` is the shared source-scanning helper the other
two are built on, and the whole point of this issue is to extend that mechanism rather than start a
second one.

**Create:**

- **`YardKit/Tests/YardWireTests/EqualityCoverageTests.swift`** — deliverable (c), the
  stored-member-vs-`==` scan.
- **`YardKit/Tests/YardWireTests/EnumVocabularyCoverageTests.swift`** — deliverable (a), the enum
  vocabulary table.

**Edit only if the shared helper genuinely needs it:** `YardKit/Tests/YardWireTests/ConformanceScan.swift`.
If you extend it, say what you added and why the existing two scans still pass unchanged.

**Verification count:** `N` must be **greater than 1115**, the count on `main` before this change
(`docs/test-baseline.txt`).
