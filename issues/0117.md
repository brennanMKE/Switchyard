## Description

`CommitLog.parse` splits each record on `\u{01}` — the field delimiter — and then takes **only**
`parts[5]` as the message. A commit body containing that byte produces more than six fields, and
everything after the embedded delimiter is silently discarded.

Measured against `main` on 2026-08-07, with a fixture commit whose message is
`"has \u{01} delimiter inside\n\nbody\n"`:

```
PROBE log oid=701c4e2c9644 subject=[unicode 日本語 café 🚂]        ← fine
PROBE log oid=7a07a02c650c subject=[has]                            ← truncated at the delimiter
PROBE log oid=5550efad5097 subject=[subject one]                    ← fine
```

The subject should be `has <SOH> delimiter inside`. Everything from the embedded delimiter to the end
of the body — including the trailer block — is gone, and the entry still reports success.

The same probe confirmed the rest of the parser is sound: multi-paragraph bodies, blank lines, CJK,
accents, emoji, merge parents, trailers, and `-1`/range arguments all round-trip correctly. **This is
one line.**

## Givens — verified on `main`, treat as true

1. The file is `YardKit/Sources/YardGit/CommitLog.swift`. The defect is at **line 180**:

   ```swift
   let message = parts.count > 5 ? String(parts[5]) : ""
   ```

2. **The comment three lines above says what the code should have done and does not:** *"split with
   limit 6 so the trailing field gets everything after the 5th separator."* `split(separator:
   omittingEmptySubsequences:)` takes no limit here, so `parts` has as many elements as there are
   delimiters. Fix the comment along with the code — a comment describing behaviour the code does not
   have is worse than none, per #0111.

3. The format string is
   `"--format=%H\u{01}%P\u{01}%an\u{01}%G?\u{01}%D\u{01}%B%x00"` at line 109. `%B` is last and the
   record is NUL-terminated, so **rejoining is safe**: everything from index 5 onward is body, by
   construction. Do not change the format string — #0014 spent four rounds settling it.

4. `CommitLog.run` and `CommitLog.parse` are `static` on `public enum CommitLog`. `parse` is internal
   and tested through `@testable import`, so a test can call it with a literal string — no fixture
   needed for the framing case.

## Expected behavior

- [ ] The message is `parts[5...]` rejoined with `\u{01}`, so an embedded delimiter round-trips.
- [ ] The comment at lines 172-179 describes what the code actually does.
- [ ] Nothing else changes. `git diff --stat` shows one file and a handful of lines.
- [ ] Tests use **swift-testing** — `import Testing`, `@Test`, `#expect`. Not XCTest.
- [ ] New tests go in **`YardKit/Tests/YardGitTests/`**. `Tests/YardGit/` is not a declared target
      path; a file there is silently never compiled, the suite stays green, and the count does not
      move. That cost #0095 a round.
- [ ] `cd YardKit && swift build` succeeds and `swift test` prints a `Test run with N tests` line you
      paste. **`main` reported 225 on 2026-08-07.** Paste the branch's own pre-change baseline too,
      and N must exceed it.

## Tests must be able to fail

Two tests, and the second is the one that matters:

1. **Unit**, calling `CommitLog.parse` with a literal record string containing an embedded `\u{01}`
   in the body. Assert the full message, not a prefix — `#expect(entry.message.contains("delimiter
   inside"))` would pass on a half-truncated body. Compare the whole string.
2. **End to end**, building a real commit through `FixtureRepository.Commit(_:message:)` with the same
   body and reading it back through `CommitLog.run`. This is what proves git actually emits the byte
   rather than rejecting or escaping it.

**Mutation**: restore `String(parts[5])` and confirm **both** tests fail. If only the unit test
fails, the end-to-end test is not exercising the path — say so rather than moving on.

Also assert a body **without** an embedded delimiter is byte-identical before and after, so the
rejoin does not introduce a stray separator into ordinary messages. That is the regression this fix
could plausibly cause.
