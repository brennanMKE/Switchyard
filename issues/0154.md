## Description

The thin process wrapper the installed `reference-transaction` hook script execs:
read argv[1] (the state), call `ReferenceTransaction.decide` (#0042) with the process
environment and a stdin closure, and exit with `Decision.exitCode` — which is 0 by the #0042
totality invariant. Per #0042 Givens 5, the process spawn (~8 ms) dominates the handler cost,
so this arm must stay a straight-line exec with no XPC wait and no journal I/O of its own
(#0153 owns persistence; forwarding to the app is M3).

## Expected behavior

- [ ] The arm checks its state argument and environment **before** draining stdin — #0042's
      `readStandardInput` closure contract, preserved at the process boundary.
- [ ] Exit status is 0 for every input, including garbage stdin on `committed` — a non-zero
      exit in `prepared` aborts the user's transaction (#0042 Givens 3).
- [ ] A test exercises the built binary as a real hook in a real repository, both ref formats —
      an in-process approximation cannot satisfy this criterion.
- [ ] `swift test` prints a `Test run with N tests` line; N must exceed the pre-change baseline
      (re-measure at planning time; state the delta).

## Milestone corrected to M3 — 2026-08-09

This is a **CLI arm**, and guide §11 decision 11 (2026-08-07) settled that **CLI reachability is an
M3 criterion, not an M1 one** — the CLI reaches the engine over XPC, which M3 builds. #0115 and
#0124 were re-milestoned M1 → M3 for exactly this reason at the time; this issue was filed before
that decision and kept its original label.

Its engine half is already done: #0042 merged the `reference-transaction` decision core, which is
the part that can exist without the CLI. What remains here is the arm that calls it, and that
cannot land before M3's XPC surface.

## Blocked on #0217 — 2026-08-17

This issue's own Notes say where the arm lives "is a planning-time decision that must be settled with
the M3 XPC design, not improvised by a round". Working the M3 queue reached that decision and it does
not have one defensible answer: routing a `reference-transaction` hook over XPC means a background
`git fetch` launches a GUI app, and refusing to launch means the journal silently loses entries
whenever the app is closed.

**#0217 states the three readings and recommends one.** Not dispatched until it is answered.

## Acceptance criterion inherited from #0160 — 2026-08-17

#0160's umbrella review established that its bullet 4 — *"failure to persist never surfaces as a
non-zero hook exit"* — is met by nothing today, because **there is no `PostRewrite.runHook`**. The
only `runHook` in `Sources/` is `ReferenceTransaction.runHook`
(`ReferenceTransaction.swift:217-260`), which catches every throw, returns `exitCode: 0`, and carries
a `recordingFailure` string.

That invariant belongs to the **process arm**, which is this issue. So it is recorded here:

- [ ] `PostRewrite.runHook` exists in the same shape as `ReferenceTransaction.runHook`: it catches
      every throw from persistence, returns exit **0**, and carries the failure as a string rather
      than as a status.
- [ ] Tested with a `GitProcess` that cannot write — an executable path that does not exist is the
      technique #0220 already uses — asserting the hook's own exit code is 0 while the write failed.
      **Not** by asserting a stored property the persistence call cannot reach; that is the vacuous
      shape #0160's test had.

`#0042` Givens 3 is why this matters at all: a non-zero exit in `prepared` aborts the user's
transaction. A journal that cannot write must never be able to break a commit.

## Unblocked — #0217 decided as option C, 2026-08-17

**Guide §11 decision 22.** The arm goes over XPC like every other command: `AppConnection.connect`
with **`launchIfNeeded: false`** and a short timeout, then `perform`. No second binary and no spool
file, so this issue no longer needs a layering exception — and it is now dispatchable, since #0218
landed the transport and #0048 the client.

**Three constraints the decision carries into this issue:**

1. **Exit 0 in every case.** #0042's totality invariant is unchanged by an unreachable app: a journal
   that cannot record must never break somebody's commit. That is also the criterion inherited from
   #0160 (see the section above) — `PostRewrite.runHook` in the same shape as
   `ReferenceTransaction.runHook`, tested with a `GitProcess` that cannot write.
2. **`launchIfNeeded: false`, always.** The hook fires on every ref update by any tool; a background
   `git fetch` in a terminal must never launch a GUI application. This is the whole reason C is
   liveable.
3. **A short timeout.** #0043 Givens 5 measured the process spawn (~8 ms) already dominating the
   handler cost, so an unreachable app must cost a ref update nothing measurable. Say what value you
   chose and why; it is a judgement, not a measurement, and should be labelled as one.

**And the consequence, which belongs in the arm's own doc comment so nobody rediscovers it as a bug:**
ref transactions made while the app is closed are **not journalled**. Journal completeness is a
function of whether Switchyard.app is running. That was decided knowingly; it should not read as an
oversight to the next person.

## Planning update — 2026-09-03. The arm at code level.

**The invocation is already fixed by #0041's script** (`HookInstall.script(for:)`): the installed
wrapper runs `switchyard hook <handlerName> "$@" <payload>` with stdout/stderr discarded and `|| :`,
so the arm is the `hook` subcommand of the switchyard CLI, handler name `reference-transaction`.

- `YardKit/Sources/YardKit/CommandLineRunner.swift` — `hook` is a **local** arm (like `--help`): it
  must NOT enter `CommandRegistry.all` (it is not a remote command and must never be offered to the
  app), and `route` must classify it local so it never goes over the remote path. The arm: check the
  state argument and the environment BEFORE draining stdin (#0042's closure contract at the process
  boundary), read stdin to EOF, then `AppConnection.connect(launchIfNeeded: false)` with a short
  timeout and `perform` the decision request; exit `Decision.exitCode` — 0 in every case, including
  unreachable app and garbage stdin on `committed`.
- The decision core (`ReferenceTransaction.decide`, YardGit) runs app-side; the CLI does not link
  YardGit (layering), so the arm ships state + stdin bytes + the environment values the decision
  needs over the existing `AppServiceProtocol` (extend it if no hook method exists — both sides are
  in this repo; #0048's client, #0218's transport).
- The short timeout is a **judgement, labelled as one**: pick a value that keeps an unreachable app
  unmeasurable next to the ~8 ms spawn (#0043 Givens 5) — say the value and the reasoning in the doc
  comment.
- `PostRewrite.runHook` (the #0160-inherited criterion): if `PostRewrite` does not exist in the tree
  yet, that bullet is recorded as NOT APPLICABLE here — it lands with #0160's machinery; the exit-0
  invariant itself is implemented and tested for THIS arm.
- Tests (`YardKit/Tests/YardKitTests/` or `YardGitTests/` — where the built-binary harness lives):
  the built binary as a real hook in a real repository, both ref formats (`files` and `reftable`):
  install the #0041 script with a temp bin dir on PATH holding a symlink to the built `switchyard`,
  make a ref update, assert the transaction succeeds (exit 0 — the hook must never abort it) and
  that no app was launched. Plus: garbage stdin on `committed` → exit 0; missing state argument →
  exit 0 (totality) with the refusal logged, never a non-zero.
- Verification: `cd YardKit && swift test` prints `Test run with N tests` with **N greater than
  1318**, the count on main before this change. State the delta.
