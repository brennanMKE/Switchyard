## Description

`GitProcessAsyncTests.cancellingAsyncCaptureTerminatesTheChildAndThrows`
(`YardKit/Tests/YardGitTests/GitProcessAsyncTests.swift`) keeps failing intermittently under parallel
load after #0408 fixed a real production race in the same path (`onCancel` now finishes the gate
before terminating). **This remaining failure is not a production race. It is the test's own child,
`/bin/sleep 30`, which is a 30-second wall-clock deadline.** The test launches the capture, sleeps
100 ms "long enough that the child is launched", then cancels. Under parallel load the test's
resumption after that `Task.sleep` is delayed — the cooperative pool is saturated by other suites'
synchronous `git` calls — and when the delay exceeds 30 s the child has already exited 0, the
capture has **succeeded before any cancellation existed**, and `task.cancel()` lands on a finished
task. Nothing throws, and the test fails at `#require(thrown, …)`.

### Evidence (measured 2026-09-29, planning worktree `../sy-plan-cancel` at `8782a3ad`, 12-core host)

1. **Natural reproduction on `main`.** `swift test --skip-build --filter 'YardGitTests\.'` with 24
   `yes > /dev/null` CPU hogs (load average reached 152), run 1 of 4:

   ```
   ✘ Test cancellingAsyncCaptureTerminatesTheChildAndThrows() recorded an issue at GitProcessAsyncTests.swift:196:25: Expectation failed: thrown
   ✘ Test cancellingAsyncCaptureTerminatesTheChildAndThrows() failed after 204.077 seconds with 1 issue.
   ✘ Test run with 1059 tests in 48 suites failed after 250.165 seconds with 1 issue.
   ```

   `:196:25` is `let error = try #require(thrown, "expected the cancelled capture to throw")` — the
   capture returned **successfully**. The test ran for **204 s**, nearly seven times the child's
   30-second lifetime. That is the whole mechanism: the only way `sleep 30` produces a successful
   capture is by running to completion.

2. **Deterministic reproduction of the mechanism.** A scratch test (not to be committed) that is the
   `main` test verbatim plus one step — after the 100 ms sleep, block every cooperative-pool thread
   for 33 s with `activeProcessorCount` detached `sleep(33)` tasks, then `Task.sleep(1 ms)` before
   `cancel()` — fails every time, with the identical message:

   ```
   REPRO main-shape thrown=nil
   ✘ Test starvedCancelOnMainShape() recorded an issue at StarvedCancelReproTests.swift:26:25: Expectation failed: thrown
   ```

   The same starvation applied to the fixed test below (35 s of blocked pool between "child is
   running" and `cancel()`) **passes**: `✔ Test starvedCancelFixedShape() passed`.

3. **Loops that do *not* reproduce it**, recorded so nobody re-runs them hoping they will:
   `--filter cancellingAsyncCapture` 50× under 24 hogs, 50 pass / 0 fail;
   `--filter GitProcessAsyncTests` 20× under 24 hogs, 20 pass / 0 fail. CPU contention alone does
   not starve the pool for 30 s; it takes the full target's synchronous `git` traffic on top.

### Production code was re-read for a remaining race; there is none

Read `GitProcess.capture(_:workingDirectory:standardInput:extraEnvironment:timeout:)` (async),
`ResumeOnce` and `AsyncCaptureState` in `YardKit/Sources/YardGit/GitProcess.swift`:

- **Cancel before `withTaskCancellationHandler` is entered** (task cancelled while still in
  `prepare` or before `process.run()`): Swift runs `onCancel` immediately on entry, *before* the
  operation. `onCancel` finishes the gate with `CancellationError` (stored as `pending`, `finished =
  true`) and terminates the already-launched child; the operation's `gate.attach` then delivers the
  pending `CancellationError`. Correct.
- **Cancel while suspended**: `onCancel` finishes the gate first (#0408), so the SIGTERM'd child's
  exit + EOF cannot win. Correct.
- **Cancel after the child exited on its own**: the capture has already returned its `Output`;
  there is nothing to cancel. This is correct behaviour and it is exactly what the test hits.

So the fix is test synchronisation, and it removes the clock rather than lengthening it.

## Expected behavior

One deliverable: **the cancel test's child cannot finish on its own while the test intends to cancel
it, and the test cancels only once the child is known to be running** — no `sleep` duration decides
the outcome.

## Fix — the literal change

File: `YardKit/Tests/YardGitTests/GitProcessAsyncTests.swift`. Replace the whole body of
`cancellingAsyncCaptureTerminatesTheChildAndThrows` from `let sleeper = …` through `task.cancel()`
(lines 181–188 on `8782a3ad`), and add the child script above it. The tail of the test — from
`var thrown: (any Error)?` to the `#expect(error is CancellationError, …)` — is **unchanged**.
Nothing else in the file changes; the existing `waitForRelease` helper is not touched.

(DIFF — filled in below once measured)

Why each piece:

- **The child creates the marker, then runs until the marker is removed.** Only the test's `defer`
  removes it, and the `defer` runs after `task.value` has returned — so on a correct implementation
  the child is SIGTERM'd by `onCancel`, and on a broken one the child is still released and the run
  ends. One file, created and removed per run; no temp litter.
- **The bounded marker poll replaces `Task.sleep(100 ms)`.** "The child is running" becomes a fact
  the test observes, not a guess. The poll is the same shape as the starvation test's (18 000 × at
  least 10 ms), and `#require` turns a child that never started into a named failure.
- **The 12 000-poll backstop (≥ 600 s)** exists only so a mutation that stops cancellation reaching
  the child entirely still ends (AGENTS.md Rule 14). It is not a deadline the test races on a
  correct implementation — `onCancel` kills the child long before — and each poll forks a `sleep`,
  so it stretches with the load that delays the test. 600 s is three times the 204 s measured above.
- **No production change.** See "Production code was re-read" above.
