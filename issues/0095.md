## Description

Remove a worktree, releasing its lock and any attached agent session. Refuses when the worktree is
unclean unless `--force`, matching `git worktree remove`'s own behavior.

## Givens — verified on `main`, treat as true

1. `YardKit/Sources/YardGit/WorktreeContext.swift` provides `WorktreeContext.resolve(...)` plus
   `topLevel: String?` (nil in a bare repo), `gitDir`, `commonDir`, `worktreeName: String?`,
   `isLinkedWorktree`, `isBare`, and `path(for:git:)`. Use it; do not resolve paths yourself.
2. **`WorktreeContext` does not expose the main worktree's path.** If you need it, take the **first**
   `worktree <path>` line of `git worktree list --porcelain` — that entry is the main worktree from
   any worktree in the repo. Verified from inside a linked worktree. Do not derive it by trimming
   `/.git` off `commonDir`; that breaks on bare repos and on a `.git` file pointing elsewhere.
3. `YardKit/Sources/YardGit/FixtureRepository.swift` provides
   `addWorktree(named:branch:) throws -> URL`, `build(_:)`, `branch(_:at:)`, `checkout(_:)`,
   `destroy()`, and `RefFormat.supported()`. Tests build a **real** linked worktree with it rather
   than simulating one.
4. **Every shell-out goes through `GitProcess`** (`YardKit/Sources/YardGit/GitProcess.swift`). Do not
   construct `Process` directly — the boundary is centralised there so it stays testable, and
   libgit2 does not run hooks.
5. **Never build a path by concatenating onto `.git/`.** Resolve through `git rev-parse --git-path`
   or `WorktreeContext`. Reftable repositories have no `.git/refs/**` at all and return nothing
   rather than erroring.

## Tests must be able to fail

- Assert any extraction is non-empty before comparing it. A helper that silently returns nothing

- No `#expect(true)` or any assertion whose operands are literals.
- Exercise the real failure path, not only the happy one. Say how you confirmed the test fails when

### Verified `git worktree` behaviour — probed 2026-08-06, treat as fact

Run against a real repo with a linked worktree, not read from the man page.

- **`git worktree remove <path>` refuses a dirty worktree with exit `128`** and the message
  `fatal: '<path>' contains modified or untracked files, use --force to delete it`.
  `--force` then succeeds. "Dirty" includes untracked files, not just modifications.
- **`git worktree prune -v`** prints one line per reaped entry:
  `Removing worktrees/<name>: gitdir file points to non-existent location`, and the entry disappears
  from `git worktree list --porcelain`.
- **`git worktree repair <path>`** prints `repair: gitdir incorrect: <path-to-admin-gitdir-file>`.

**The counter-intuitive one, and the reason it is written down:** after a linked worktree is *moved*
on disk, `git -C <new-path> status` **still exits 0**. The worktree keeps working from the inside,
because its own `.git` file still points at the administrative directory. What breaks is the
*reverse* pointer — the `worktrees/<name>/gitdir` file in the main repository still names the old
location. So a test asserting "status fails before repair" would be **wrong**, and would pass or fail
for reasons unrelated to the code under test. Assert on the administrative state, or on an operation
run from the main repository, not on `status` from inside the moved worktree.

## Review — the implementation is good, the tests were never compiled

**`WorktreeRemove.swift` works.** Exercised against real `FixtureRepository` worktrees, all four
scenarios behave correctly:

```
CLEAN         success=true                                     stillExists=false
DIRTY-MOD     refusal=true  "refusing to remove dirty worktree a.txt"          stillExists=true
UNTRACKED     refusal=true  "refusing to remove dirty worktree untracked.txt"  stillExists=true
FORCE         success=true  forced=true                        stillExists=false
```

Untracked-only dirt is correctly refused and names the file — that was the case most likely to be
missed, and it is right. Keep this file; round 2 needs only the two small fixes below.

### The blocking defect: the tests live outside every declared target

Round 1 wrote `YardKit/Tests/YardGit/WorktreeRemoveTests.swift`. `Package.swift` declares only
`Tests/YardGitTests` and `Tests/YardKitTests`. **`Tests/YardGit/` is not a target path, so SwiftPM
never compiled the file** — and the round reported `Test run with 216 tests` as proof of success. 216
is exactly the pre-change baseline.

**Move it to `YardKit/Tests/YardGitTests/WorktreeRemoveTests.swift`** and delete the stray directory.

### The tests do not compile even once relocated

Copied into the right target, they produce 20+ errors. Every one is an API assumption:

| what round 1 wrote | reality |
|---|---|
| `worktree.path` | the binding is named `worktreePath` |
| `WorktreeContext.resolve(forPath:)` | the signature is `resolve(path:git:)` |
| `fixture.git` | `FixtureRepository.git` is **private**; `@testable` does not cross `private` |
| `canonicalize(...)` | also `private`, in `WorktreeRemove.swift` |
| `context.repositoryPath` | **no such member.** `WorktreeContext` has `topLevel`, `gitDir`, `commonDir`, `worktreeName` |
| `result.error is WorktreeRemoveError.unclean == false` | not valid Swift |
| `URL(...)` | no `import Foundation` |

**Use `fixture.url.path` as the repository path**, call `worktreeRemove(at:_:force:)` and let it
default its own `GitProcess`, and assert with `FileManager.default.fileExists` on the worktree
directory before and after. That is all the tests need.

### Two small fixes in the source

1. **`WorktreeRemove.swift:203`** — `extractDirtyPaths` constructs a fresh `GitProcess()` instead of
   using the injected `git`, so a caller-supplied process is bypassed on the refusal path.
2. **`WorktreeRemove.swift:165-172`** — the force retry uses `git.run(...)`, which **throws** on
   non-zero, so the following `guard forced.exitCode == 0 else { throw .unknownFailure }` is
   unreachable. A forced removal that fails for an unrelated reason escapes as `GitProcess.Failure`
   rather than a structured `WorktreeRemoveError`.

Also delete the dead `nestedPath.appendingPathComponent(".git")` at test line 184 — the project does
not build paths onto `.git/`.
