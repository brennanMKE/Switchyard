## Description

The repo is currently a stock SwiftUI template. M3 needs the real structure: the app target, a
`BrokerAgent` executable target, the `YardKit` package as a local dependency, and `Support/` holding
`Info.plist`, entitlements, and the launch agent's launchd plist.

## Expected behavior

- [ ] `BrokerAgent` target added and produces an executable.
- [ ] `Switchyard.xcworkspace` references both `Switchyard.xcodeproj` and `YardKit`. **Already
      done** — verify it still resolves rather than recreating it.
- [ ] `YardKit` referenced as a local package dependency **in `Switchyard.xcodeproj`**, with both
      `YardKit` and `YardGit` products added to the app target.
- [ ] The app imports and uses a real symbol from each — a reference that is declared but never
      imported proves nothing. `ServiceNames.cliName` and `YardGit.libgit2Version` are enough.
- [ ] `otool -L` on the built product shows libgit2 linked. **Check
      `Switchyard.app/Contents/MacOS/Switchyard.debug.dylib`, not the `Switchyard` binary** — under
      Xcode 26 the latter is a thin stub and inspecting it shows nothing at all.
- [ ] Build copies the agent to `Contents/MacOS/BrokerAgent` and its plist to `Contents/Library/LaunchAgents/`.
- [ ] Unsigned build passes: `CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO`.
- [ ] `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` retained on the app target.
- [ ] Settings verified with `xcodebuild -showBuildSettings`, not by reading `project.pbxproj`.

## The integration is proven — 2026-08-06

Brennan noticed that `Switchyard.xcodeproj` references nothing from `YardKit`: the three
`packageProductDependencies` arrays in `project.pbxproj` are empty, and the app imports only SwiftUI.
That is accurate, and it is this issue's job.

**The wiring was tested first, on a scratchpad copy**, because leaving it until M3 meant every issue
in M1 and M2 rested on an unverified assumption. It works — build succeeds, and the built dylib
carries `YardKit`/`YardGit` symbols and calls `git_libgit2_init`. Details in
`docs/engine-findings.md`.

So this issue is now mechanical rather than exploratory, and it moves to **M1**. It is out of order
otherwise: the package has 124 tests and the app cannot see any of it.

### Follow Batty's structure — `../../Batty` is the reference

Brennan's Batty app solves exactly this and Switchyard should match it. Verified by reading it:

1. **`Batty.xcworkspace/contents.xcworkspacedata` holds two `FileRef`s** — `group:Batty.xcodeproj`
   and `group:BattyKit`. That is the whole file. It puts the app and the package in one Xcode window,
   so the package is editable alongside the app rather than being an opaque dependency.
2. **The `.xcodeproj` *also* carries the package reference** — `XCLocalSwiftPackageReference` with
   `relativePath = BattyKit` in the project's `packageReferences`, an `XCSwiftPackageProductDependency`
   with `productName = BattyKit`, and a `PBXBuildFile` putting that product in the target's Frameworks
   phase.

Both halves. The workspace alone does not make the app link the package; the project reference is
what does that.

**The workspace earns its place for testing.** With the package in the workspace, its tests appear in
Xcode's test navigator alongside `SwitchyardTests`, so the whole suite — currently 124 package tests
plus whatever the app target grows — runs in one action instead of splitting between `swift test` in
a terminal and ⌘U in Xcode. It also makes the package's sources editable in the same window rather
than read-only inside a dependency node.

**`Switchyard.xcworkspace` already exists** — created 2026-08-06, identical in shape to Batty's,
referencing `Switchyard.xcodeproj` and `YardKit`. Confirmed working:
`xcodebuild -workspace Switchyard.xcworkspace -list` resolves the package graph and reports
`YardKit: …/Switchyard/YardKit`. **This issue's remaining job is half 2, the project reference.**

**Build commands do not change.** Batty's own `CLAUDE.md` still builds with
`-project Batty.xcodeproj`, and that is correct: because the project carries the package reference,
`-project` and `-workspace` both work. Do not rewrite the documented build commands in `CLAUDE.md`.

**Do half 2 by hand in Xcode, not by editing `project.pbxproj`.** File → Add Package Dependencies →
Add Local → select `YardKit`, then add both `YardKit` and `YardGit` to the app target's Frameworks.
`CLAUDE.md` records that Xcode rewrites the file underneath hand edits and has silently dropped build
configurations mid-edit — the spike only edited a throwaway copy for that reason.

**Licensing note:** Batty is Brennan's own MIT-licensed project, not GitUp. Reading it and copying its
structure is fine. The clean-room rules in `CLAUDE.md` are about GitUp specifically.

**Known consequence, not a blocker for this issue:** the resulting binary links
`/opt/homebrew/opt/libgit2/lib/libgit2.1.9.dylib` by absolute path, so the app runs only where
Homebrew has libgit2 at that path. Fine for development, fatal for distribution. That is #0103.

## Half done — 2026-08-07

Brennan added `YardKit` to `Switchyard.xcodeproj`. The **package reference** is there:

```
XCLocalSwiftPackageReference "YardKit"   relativePath = YardKit
```

But **the products are not linked to the app target**, and that is the half that matters. Verified
rather than inferred — on a scratchpad copy, with `import YardKit` added to `ContentView.swift`:

```
error: unable to resolve module dependency: 'YardKit'
** BUILD FAILED **
```

`packageProductDependencies` on the `Switchyard` target is `()`, and the file contains no
`XCSwiftPackageProductDependency` section at all — that section only exists once a product is
attached to a target.

### The remaining step, in Xcode

Select the **Switchyard** target → **General** → **Frameworks, Libraries, and Embedded Content** →
**+** → add **`YardKit`** and **`YardGit`**.

(The Add Package dialog offers this as its final step — "Add to Target" — and it is easy to dismiss
past. Adding the package and adding its products are two separate actions.)

### How to know it worked

Not by the build succeeding — it already succeeds, because nothing imports the package yet. Add
`import YardKit` to a source file in the app target and confirm it compiles, or check that
`packageProductDependencies` is no longer empty.

The rest of this issue — the `BrokerAgent` target and the `Support/` layout — is untouched and still
open.

## Blocking finding — the package is referenced but no product is linked

Verified 2026-08-07, and **the build being green is not evidence** — nothing in the app imports
`YardKit`, so nothing forces the link.

`project.pbxproj` has the local package reference:

```
/* Begin XCLocalSwiftPackageReference section */
    26BA44803025CBFE00DDB2E9 /* XCLocalSwiftPackageReference "YardKit" */ = {
        isa = XCLocalSwiftPackageReference;
        relativePath = YardKit;
    };
```

and **`packageProductDependencies = ( )` is empty on all three targets**, with every
`PBXFrameworksBuildPhase` holding `files = ( )`.

Proved rather than inferred: added a two-line `Switchyard/LinkProbe.swift` containing
`import YardKit`, built unsigned, and got

```
LinkProbe.swift:2:8: error: unable to resolve module dependency: 'YardKit'
** BUILD FAILED **
```

The probe was deleted immediately. So the app target cannot use a single line of the engine today.

### Resolved 2026-08-07

Brennan added both products through Xcode. `project.pbxproj` now carries two
`XCSwiftPackageProductDependency` entries on the app target:

```
packageProductDependencies = (
    26BA44843026752800DDB2E9 /* YardGit */,
    26BA44863026752800DDB2E9 /* YardKit */,
);
```

and the `PBXFrameworksBuildPhase` has two files where it had none.

Verified the same way it was proved broken, and in both directions. A `Switchyard/LinkProbe.swift`
importing **both** products and touching one real symbol from each — `ServiceNames.cliName` and
`whereAmI(path:)` — compiles:

```
SwiftCompile normal arm64 Compiling LinkProbe.swift (in target 'Switchyard')
** BUILD SUCCEEDED **
```

Negative control, so a green build is not mistaken for a linked one: changing that symbol to
`ServiceNames.noSuchMember` fails with `type 'ServiceNames' has no member 'noSuchMember'` — the probe
is genuinely compiled against the module, not skipped. The probe was deleted after each run.

**The app can now use the engine.** The remaining app-side issues — #0046 through #0051 — are
unblocked.

### Why this was not fixed by me in the same pass

**Xcode is open on the project.** Hand-editing `project.pbxproj` while Xcode holds it is the
documented way to lose the edit — it has silently dropped hand-added build configurations mid-edit
before. The fix is 20 seconds in the GUI and belongs to whoever has the window:

> Switchyard target → General → **Frameworks, Libraries, and Embedded Content** → **+** → add
> **YardKit** and **YardGit**.

Then re-run the probe above; it must compile. `xcodebuild -showBuildSettings` is the check, not the
file — per the CLAUDE.md gotcha, trusting the written file is what fails here.
