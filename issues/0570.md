# 0570 — ⌘Z right after ⌘↩ does nothing: the message editor swallows Undo Commit

| | |
|---|---|
| **Status** | open |
| **Module** | YardUI, UI tests |
| **Milestone** | — |
| **Platform** | macOS |
| **First seen** | 2026-09-30 |
| **Parent** | #0569 (hardening pass 2026-09-30) |
| **Severity** | high — the most common undo in the app silently does nothing |
| **Related** | #0393 / #0448 (Edit ▸ Undo forwards to a focused text view), #0445 (⌘↩ commits), #0466 (Amend) |

## Description

The everyday flow is: type a message, press ⌘↩, notice a typo, press ⌘Z. **Nothing happens.** The
commit stays, the header still reads "1 ahead", and no alert or beep says why. Edit ▸ Undo even
reads **Undo Commit** (or **Undo Amend**) and is enabled — and clicking it does nothing either.

**Why.** `JournalCommands` (`YardKit/Sources/YardUI/JournalMenu.swift`) forwards `undo:` down the
responder chain whenever the key window's first responder is an `NSText` (`JournalMenu.routesToText`),
so text editing keeps its own undo stack (#0448). After ⌘↩ the focus is still in the message
editor, so the journal is never asked. The text undo does nothing visible because the editor
was reset to empty (or to the template) when the commit succeeded. But the typing steps stay on
the window's undo manager, so `NSApp.sendAction(undo:)` still returns `true`.

The two existing VM spikes that undo a commit or amend (#0466 and #0448) work around this. Each
clicks a Changes row first "to move focus off the message editor", so neither tests what a person
does.

### Measured (VM, 2026-09-30, throwaway hardening spikes)

- **Switch fixture.** Stage `notes.txt`, type `audit commit`, then ⌘↩. The header reads
  `On branch switch-main · 1 ahead of origin/switch-main`. ⌘Z (focus still in the editor) was
  followed by a 3 s wait. The header **still** reads `… 1 ahead of origin/switch-main` and the
  editor is empty with its caret showing. Screenshot:
  `issues/0569/0570-cmd-z-after-commit-does-nothing.png`.
- **Changes fixture.** Commit `harden first commit`, then Amend to `harden amended commit` with
  the Amend button. Edit ▸ **Undo Amend** was present and enabled, and was clicked. History still
  showed `harden amended commit` (`981e0d6`) and the first commit never came back. The next menu
  lookup for **Undo Commit** found nothing, because the title still read Undo Amend.
- **Host, `swift test`, a scratch test in a throwaway worktree.** An `NSTextView` in an `NSWindow`
  with `allowsUndo = true` was measured at each step:
  - fresh: `canUndo == false`
  - after `insertText("hello")`: `true`
  - after `string = ""` (a programmatic reset, which is what the editor gets on commit): **still
    `true`**
  - after `undoManager.removeAllActions()`: `false`

  So resetting the draft does not clear the text undo stack. Both halves of the fix below are
  needed.

## The change — two files

### 1. `YardKit/Sources/YardUI/JournalMenu.swift` — route to text only when text has something to undo

Replace `routesToText` (currently `firstResponder is NSText`) with:

```swift
    /// #0448: whether Undo (or, with `redo`, Redo) belongs to text editing
    /// rather than the journal — true only while an `NSText` view (a field
    /// editor, a `TextEditor`) is the key window's first responder.
    /// #0570: and only while that view has a step to take. A focused editor
    /// with nothing to undo — the one ⌘↩ just emptied — must not swallow
    /// Undo Commit.
    @MainActor
    public static func routesToText(_ firstResponder: NSResponder?, redo: Bool = false) -> Bool {
        guard let text = firstResponder as? NSText, let undoManager = text.undoManager else {
            return false
        }
        return redo ? undoManager.canRedo : undoManager.canUndo
    }
```

In `JournalCommands.body`, replace the single `editingText` with one flag per item:

```swift
        let responder = NSApp.keyWindow?.firstResponder
        let editingUndo = JournalMenu.routesToText(responder)
        let editingRedo = JournalMenu.routesToText(responder, redo: true)
```

- The Undo button's action tests `JournalMenu.routesToText(NSApp.keyWindow?.firstResponder)`
  (unchanged) and its `.disabled` reads `!editingUndo`:
  `.disabled(!(target?.undoEnabled ?? false) && !editingUndo)`.
- The Redo button's action tests
  `JournalMenu.routesToText(NSApp.keyWindow?.firstResponder, redo: true)` and its `.disabled`
  reads `!editingRedo`.

### 2. `YardKit/Sources/YardUI/ContentView.swift` — `runWorkingChange` clears the editor's undo steps after a commit or amend

The typing is committed. Its undo steps would now edit the next draft, and ⌘Z should mean Undo
Commit. Clear them **after** the refresh: by then SwiftUI has pushed the reset draft into the
text view, so nothing re-registers behind the clear. The body becomes:

```swift
        Task {
            defer { runningWorkingChange = nil }
            var committed = false
            do {
                try await performWorkingChange(change, at: repositoryPath)
                switch change {
                case .commit, .amend:
                    commitDraft = CommitDraft(template: commitTemplate)
                    draftStore.save("", for: repositoryPath)
                    committed = true
                default: break
                }
            } catch {
                actionFailure = change.failure(for: error)
            }
            await refreshAfterMutation { _, _ in nil }
            // #0570: the message is committed; its typing steps must not
            // swallow ⌘Z, which now means Undo Commit (or Undo Amend).
            if committed, let editor = NSApp.keyWindow?.firstResponder as? NSText {
                editor.undoManager?.removeAllActions()
            }
        }
```

Nothing else changes. Focus stays in the editor, so the next message can be typed straight away.

## Verification

### Unit tests — `YardKit/Tests/YardUITests/JournalMenuRoutingTests.swift`

The existing `#expect(JournalMenu.routesToText(NSTextView()))` asserts the old rule. A bare text
view has no window, so it has no undo manager. Replace that line with
`#expect(!JournalMenu.routesToText(NSTextView()))`, and add:

```swift
@MainActor
@Test func textRoutesOnlyWhileItHasAStepToTake() {
    let window = NSWindow(contentRect: NSRect(x: 0, y: 0, width: 200, height: 100),
                          styleMask: [.titled], backing: .buffered, defer: true)
    let text = NSTextView(frame: NSRect(x: 0, y: 0, width: 200, height: 100))
    text.allowsUndo = true
    window.contentView!.addSubview(text)
    window.makeFirstResponder(text)
    #expect(!JournalMenu.routesToText(text))
    text.insertText("hello", replacementRange: NSRange(location: NSNotFound, length: 0))
    text.undoManager?.endUndoGrouping()
    #expect(JournalMenu.routesToText(text))
    #expect(!JournalMenu.routesToText(text, redo: true))
    text.string = ""                     // the commit's reset leaves the steps behind…
    #expect(JournalMenu.routesToText(text))
    text.undoManager?.removeAllActions() // …which #0570's clear removes
    #expect(!JournalMenu.routesToText(text))
}
```

Each step's value is the one measured on the host above (fresh `false`, typed `true`, reset
`true`, cleared `false`).

### VM spike — `SwitchyardUITests/0570UndoAfterCommitUITests.swift`, new

```swift
// 0570UndoAfterCommitUITests.swift
//
// #0570: ⌘Z straight after ⌘↩, with the focus still in the message editor,
// takes the commit back. No click elsewhere first — that is the workaround
// #0466's and #0448's spikes use, and what a person never does.

import XCTest

final class Spike0570UndoAfterCommitUITests: XCTestCase {
    @MainActor
    func testCommandZAfterCommandReturnUndoesTheCommit() {
        let app = XCUIApplication()
        app.launchWithChangesFixture()
        XCTAssertTrue(app.changesRow(UITestChangesFixture.staged, staged: true).waitForExistence(timeout: 30),
                      "staged.txt is not listed as staged")
        let editor = app.textViews["commit-message"]
        XCTAssertTrue(editor.waitForExistence(timeout: 30), "no message editor")
        editor.click()
        editor.typeText("0570 commit to take back")
        editor.typeKey(.return, modifierFlags: .command)
        let row = app.historyRows(containing: "0570 commit to take back").firstMatch
        XCTAssertTrue(row.waitForExistence(timeout: 30), "⌘↩ did not commit")

        editor.typeKey("z", modifierFlags: .command)
        XCTAssertTrue(app.waitUntilDisappears(row, timeout: 30),
                      "⌘Z after ⌘↩ left the commit in History: the editor swallowed Undo Commit")
        XCTAssertTrue(app.changesRow(UITestChangesFixture.staged, staged: true).waitForExistence(timeout: 30),
                      "Undo Commit did not put staged.txt back in Staged Changes")
        let shot = XCTAttachment(screenshot: app.windows.firstMatch.screenshot())
        shot.name = "0570-undone"
        shot.lifetime = .keepAlways
        add(shot)
    }
}
```

`scripts/run-ui-tests-vm.sh`: add `run_spike_if_selected 0570 Spike0570UndoAfterCommitUITests` after
the two `0568` lines.

1. Keep the `redo:` parameter but change `routesToText`'s body back to `firstResponder is NSText`.
   Both tests go red, **measured 2026-09-30** in a throwaway worktree:
   - `undoRoutesToTextOnlyWhileATextViewIsFirstResponder` at `!JournalMenu.routesToText(NSTextView())`
   - `textRoutesOnlyWhileItHasAStepToTake` at its first `#expect(!JournalMenu.routesToText(text))`

   The spike fails too.

   With the new body, the same two tests passed: `Test run with 2 tests … passed`.

   green, but the spike fails: after the reset the typing steps are still there, which is the
   measured `string = ""` → `canUndo == true` step.

## Expected behavior

- ⌘Z (or Edit ▸ Undo Commit / Undo Amend) straight after ⌘↩ takes the commit or amend back.
- With a draft half-typed, ⌘Z in the editor still undoes typing (#0448 is unchanged).
