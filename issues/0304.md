## Description

**Finding 1 of the M1 milestone review, eleventh pass, 2026-08-18.** `whereami` never detects the
**`rebase-apply`** backend.

`YardKit/Sources/YardGit/WhereAmI.swift:206`, `["rebase-merge", "rebase-apply"]` → `["rebase-merge"]`:
`Test run with 1110 tests in 78 suites passed` — **full suite**.

**Measured on git 2.50.1**: a repository stopped in `git rebase --apply` has `rebase-apply` present and
**`rebase-merge` absent**. So `isMidRebase` — a field of `whereami`'s result — silently flips from
`true` to `false` for a repository `git status` itself describes as `HEAD (no branch)` with `UU f.txt`.

**Why nothing catches it:** the only mid-rebase test drives `rebase --exec false`, which uses the
**merge** backend. Same class as #0288 — a real state the fixture cannot reach.

This is the fourth place the `--apply` backend has been the blind spot: #0263 (`WorktreeDisturbance`),
#0273 round 2 (the entry-id file's layout), #0291 (`isMidRebaseAmend`), and now `whereAmI`.

## Expected behavior

- [ ] A named test in `YardKit/Tests/YardGitTests/WhereAmITests.swift` for a repository stopped in
      `git rebase --apply`, asserting `isMidRebase == true`.
- [ ] **Verify the fixture reached the intended backend** — `rebase-apply` present and `rebase-merge`
      absent, resolved through `WorktreeContext.path(for:)`. `#0263`'s test is the model; a fixture that
      quietly produced `rebase-merge` would pin nothing.
- [ ] **Mutation:** drop `"rebase-apply"` from the list at line 206. The new test must redden while the
      existing merge-backend test stays green — that pairing is the criterion.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, above the count in `docs/test-baseline.txt`.
