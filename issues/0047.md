## Description

The app side of the transport: create an anonymous `NSXPCListener`, register its endpoint with the
broker on launch, serve requests, and support the long-lived session shape where the app calls back
into an attached CLI.

## Expected behavior

- [ ] Anonymous listener created and its endpoint registered with the broker at launch.
- [ ] Re-registers after a broker restart.
- [ ] Request/reply works; sessions survive minutes with heartbeats.
- [ ] Session teardown handled on every path: CLI exits, CLI killed, app quits, broker restarts, connection interrupted.
- [ ] Orphaned sessions are reaped rather than accumulating.

## Planning update — 2026-08-17. Scoped to the listener and registration; sessions split out.

**Five criteria, and the last three are a different deliverable.** Sessions surviving minutes with
heartbeats, teardown on every path, and orphan reaping are the *session lifecycle* — RemoteControl's
`AppXPCServer.swift` is **571 lines** and most of that is session machinery specific to its own
`BridgeRequest` shape. Splitting rather than porting wholesale: **#0213 owns sessions and teardown.**

**This issue: the anonymous listener, registration with the broker, and re-registration after a broker
restart.** That is what makes `yard ping` possible (#0048) and nothing beyond it.

#0046 landed the broker, `BrokerProtocol` and `XPCInterfaces.broker` in `YardKit`, so the app side has
a protocol to talk to and a Mach service to find.

### The trap this issue exists to get right, and it is a crash rather than a bug

**`@Sendable` on every XPC callback closure.** From RemoteControl's own comment on the line that
matters:

> Foundation types this parameter as a plain `(any Error) -> Void`, so a closure written inside this
> `@MainActor` method inherits main-actor isolation and Swift emits an isolation assertion at its entry.
> XPC then calls it on its own queue and the process dies with **`SIGTRAP` in
> `_swift_task_checkIsolatedSwift`**.

The app target has `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (verified in `project.pbxproj`), so this
applies to **every** closure in this file: `remoteObjectProxyWithErrorHandler`, `interruptionHandler`,
`invalidationHandler`. There is **no compiler warning**. CLAUDE.md lists it first among the gotchas, and
#0053 exists to audit it — this issue must not create work for #0053.

### Two details worth copying rather than re-deriving

- **Reuse the existing broker connection on re-registration.** After an *interruption* the connection
  object is still usable, and recreating it loses the invalidation-handler wiring.
- **`registerAppEndpoint` is one-way.** No reply block, so it returns immediately whether or not the
  broker received it; failures arrive at the error handler, not at the call site. Do not write code that
  assumes a successful return means registration happened.

## Expected behavior

- [ ] `Switchyard/AppXPCServer.swift` — a `@MainActor` type holding `NSXPCListener.anonymous()` and a
      strong reference to its delegate (`NSXPCListener.delegate` is **weak**; a delegate that is only
      locally owned is deallocated and connections are silently refused).
- [ ] `registerWithBroker()` connects to `ServiceNames.machServiceName`, obtains a `BrokerProtocol`
      proxy, and calls `registerAppEndpoint(listener.endpoint)` — reading the constant, never retyping
      the string.
- [ ] `interruptionHandler` re-registers; `invalidationHandler` clears the cached connection so the next
      attempt rebuilds it. Both `@Sendable`.
- [ ] The app calls `start()` and `registerWithBroker()` at launch — `SwitchyardApp.swift` or an
      `AppDelegate`, whichever fits the existing app; say which you chose.
- [ ] `xcodebuild build -scheme Switchyard … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` prints
      `** BUILD SUCCEEDED **`.
- [ ] Every XPC callback closure in `Switchyard/AppXPCServer.swift` is marked `@Sendable`. Report the
      count `grep` finds and name what each one is; three or more is expected — the error handler and
      both connection handlers.
- [ ] `cd YardKit && swift test` still prints **`Test run with 924 tests`** — the current baseline in
      `docs/test-baseline.txt`, measured on `main` at `HEAD`. This issue adds no package code, so a
      changed count means something moved that should not have.

## What cannot be verified here, and must not be faked

**There is no CLI to connect** (#0048) and **launchd will not start the broker on demand until the agent
is registered** (#0049). So "the endpoint actually reached the broker" is **not** provable in this round.
Do not write a test that claims it, and do not try to launch the app to check.

What *is* provable: the code compiles under MainActor isolation with the closures marked, the app builds,
and the `@Sendable` count. The behavioural proof is #0048's `yard ping`, which is the first thing that
exercises this end to end — and #0054 owns the manual verification script.
