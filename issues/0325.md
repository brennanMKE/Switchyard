## Description

**Finding 2 of the M1 milestone review, fourteenth pass, 2026-08-18 (second half).** Under
`log.showSignature`, **`CommitLogEntry.oid` becomes an English sentence.**

`YardKit/Sources/YardGit/CommitLog.swift:195` invokes `git log` without `--no-show-signature`. The
config prepends a verification line **even with a custom `--format`**. Measured through the engine
against a real signed commit:

```
log default:        oid=[27a977e1a8ad5c5d8e1c5231d24358db9d32c21f]  sig=good
log showSignature:  oid=[Good "git" signature for t@t with ED25519 key SHA256:aqNIt…\n27a977e1…]
```

**`oid` is a wire payload field an agent feeds back to git.** An agent that reads it and passes it to
another command gets a failure it cannot diagnose.

## Expected behavior

- [ ] `CommitLog.run` passes `--no-show-signature`.
- [ ] A named test setting `log.showSignature=true` and asserting `oid` is a bare oid — assert it
      **matches an oid shape** (40 hex characters, or `count == 40` plus hex membership), not merely that
      it is non-empty, since the failure mode is prose that is also non-empty.
- [ ] **Verify the config bites first**: plain `git log --format=%H` under it must emit the prose line.
- [ ] **Mutation:** drop `--no-show-signature`. The new test must redden.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, above the count in `docs/test-baseline.txt`.

## Notes

**Milestone M1**, criterion 5 — **class 2**. **#0324 is the same config on `verify`**, where the
consequence is a validly signed commit reported as unverifiable. Separate files, separate fixtures.

**The signed-commit fixture is the shared cost.** `installFakeGpg` (see #0270) needs no key material —
prefer it. If #0324 lands first, look at what it built before writing a second one.

**The signed-commit fixture, measured 2026-08-18 — use SSH signing, not gpg.** `installFakeGpg`
(`CommitCreateGPGTests.swift:39`) is `private` to that file **and** a fake gpg cannot produce a
signature git will call *good*, which is what this issue needs. SSH signing needs no key material
beyond a throwaway keypair and no external tool beyond `ssh-keygen`. Verified end to end:

```sh
ssh-keygen -q -t ed25519 -N "" -C t@t -f "$repo/k" </dev/null
git config gpg.format ssh
git config user.signingkey "$repo/k.pub"
printf "t@t $(cat "$repo/k.pub")\n" > "$repo/allowed"
git config gpg.ssh.allowedSignersFile "$repo/allowed"
git commit -S -m ...
```

Measured output on that fixture (git 2.50.1):

```
git log -1 --format=%H                          -> 64f4916d3b19c0a81e151971c3c4a04b55f3349e
git -c log.showSignature=true log -1 --format=%H -> Good "git" signature for t@t with ED25519 key
                                                    SHA256:KEn7up2tM8A1el4fRI4gkUtSp8nv+lBLTVIa4A5q0zc
                                                    64f4916d3b19c0a81e151971c3c4a04b55f3349e
git -c log.showSignature=true log -1 --no-show-signature --format=%H

```

**The key fingerprint differs per run** — it is a fresh keypair — so never assert on it.
