## Description

**A design question, not an implementation task.** Written 2026-08-17 after Brennan pointed out that
GitUp is available as a reference and that a thing already working there is a path forward.

It is — but not for the problems M2 has been solving. The full note is in
`docs/clean-room/snapshot-and-undo.md`'s addendum; the short version:

**GitUp has no worktree concept at all** (`grep -i worktree GitUpKit/Core/*.h` returns nothing), so a
sibling holding a branch, two agents undoing past each other, and a rebase continued by a foreign
process are problems it never had. Nothing to borrow, because a single-process client with exclusive
ownership does not meet them.

**But its snapshot API has two shapes Switchyard lacks**, and one of them matters a lot:

1. **Restore is scoped by ref class** — an options set selecting which kinds of reference participate,
   used for both restore and snapshot comparison.
2. **There is a delta operation alongside restore** — "apply the difference between snapshot A and
   snapshot B", not only "make the repository match snapshot B".

## Why the delta shape is worth a decision rather than a note

Four issues resolved today are all consequences of *"apply this whole snapshot"* being the primitive:

| issue | what it fixed |
|---|---|
| **#0231** | a restore deleted a ref it never recorded |
| **#0232** | the guard refused over refs the restore would not touch |
| **#0248** | the same, for refs neither side recorded |
| **#0251** | a sibling's held branch clobbered, or the whole operation refused |

**Under a delta primitive, none of those questions arise.** A ref neither snapshot mentions is
untouched by construction — no rule, no scope set, no guard clause. And "which refs does this restore
write", which #0232 had to answer by threading a third snapshot through `CrossToolGuard.diff`, is just
the delta's own key set.

The current fixes are correct and are staying. This issue asks whether the **primitive underneath
them** is the right shape, given that four separate issues have now been spent papering over the same
seam.

## What answering it looks like

- [ ] Decide whether `RefSnapshot` grows a delta application — `apply(from:to:)` — alongside `restore`,
      or stays snapshot-only. Recorded in guide §11 either way.
- [ ] If yes: which of the current rules become **unnecessary** rather than reimplemented? Name them.
      #0231's non-deletion, #0248's skip, and #0232's three-snapshot scope are the candidates, and a
      change that keeps all three has not bought anything.
- [ ] If yes: what happens to the journal entries already written, which record whole snapshots? A
      delta between two recorded snapshots is computable from what exists, so this may be additive —
      **check rather than assume**.
- [ ] If no: say why in the guide, so this is settled rather than rediscovered by whoever hits the
      fifth instance of the seam.
