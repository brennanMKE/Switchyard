## Description

The same canonical skill, packaged for OpenCode. Same rule: one source, per-client wrappers, no
parallel copies.

## Planning verdict, 2026-09-29: not worth building. Recommend `wontfix`, folded into #0068

The planning pass for #0066-#0069 (guide §11 decision 31) found nothing left to package:

- **OpenCode already reads the file as it is.** OpenCode's skills documentation (opencode.ai/docs/skills,
  checked 2026-09-29) discovers `SKILL.md` at `.opencode/skills/<name>/`,
  `~/.config/opencode/skills/<name>/`, and the Claude-compatible `.claude/skills/<name>/` and
  `~/.claude/skills/<name>/`. Its front-matter rules (`name` matching the folder and
  `^[a-z0-9]+(-[a-z0-9]+)*$`, a description of 1-1024 characters) are already met by
  `skills/switchyard/SKILL.md`: `name: switchyard`, a 430-character description. #0066's
  `frontMatterNamesTheSkill` test holds the description to 1024 so it stays that way.
- **The install is one line, and #0068 documents it.** #0068's README section gives
  `switchyard skill > ~/.config/opencode/skills/switchyard/SKILL.md` for OpenCode and any other
  agent that reads `SKILL.md` files, and `switchyard skill` itself (#0067) for an agent with no skill
  system. That covers the original "plain-markdown fallback" criterion.
- **Nobody can verify an OpenCode package.** The original last criterion — load it in OpenCode and run
  a command from an agent turn — needs OpenCode installed and configured with a model. OpenCode was
  retired from this project's workflow on 2026-08-16 (`CLAUDE.md`, "Implementation is delegated"), so
  there is no configured instance here, and an unverifiable package is exactly what the verification
  rules forbid shipping.
- **Brennan set the scope:** the goal is that Claude Code can install and use the skill today, with
  OpenCode minimal. The README line is that minimum.

If OpenCode support ever needs more than the README line (for example an `opencode.json` plugin entry
or an npm package), reopen this with that concrete requirement.
