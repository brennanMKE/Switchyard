## Description

After a `fixup`, `absorb`, or rebase, the question a reviewer actually has is "what changed in the
changes." `git range-diff` answers it, and the `post-rewrite` mapping (#0043) tells you exactly
which ranges to compare.

**This is the feature that makes the journal feel trustworthy rather than merely present.** A
reviewer who can see the delta accepts an agent's history rewrite; one who cannot undoes it
defensively.

## Expected behavior

- [ ] `yard rewrite-diff <journal-entry>` computes the ranges from the stored mapping.
- [ ] Many-to-one squash mappings produce a sensible comparison, not a broken range.
- [ ] Structured JSON output, not raw `range-diff` text.
- [ ] Works for rewrites performed by `git` directly, since #0043 captures those too.

## Planning pass — 2026-09-09, to code level. One round.

**`replacements(of:)` IS the helper** — this issue is its production consumer. No new mapping
grouping is written; the many-to-one view it already produces (new oids in first-appearance order,
old oids grouped in git's processing order) is what makes a squash mapping a sensible comparison
rather than a broken range.

**The mechanism:** `yard rewrite-diff <journal-entry-id>` —

1. **Resolve the entry**: read the journal entry's metadata. Two shapes carry a mapping, and both
   must work (the "git directly" criterion): an **own** entry's `JournalEntryMetadata.rewrite`
   (`RewriteMapping`, composed per #0234) and an **observed** entry whose
   `JournalObserved.Metadata` is kind `.rewrites` (source + rewrites, #0220). An entry with neither
   is a typed refusal (`noRewriteMapping`), not an empty diff.
2. **Compute the ranges**: old tip = the newest old oid in the mapping, new tip = the newest new
   oid, base = the parent of the oldest old oid (empty-tree root handled — Split measured the
   shape). Probe `git range-diff`'s three-arg form (`<base> <old-tip> <new-tip>`) in a fixture
   BEFORE relying on it, including the many-to-one case (two old commits squashed into one new):
   paste the output into the report. If the three-arg form misbehaves on a squash, fall back to
   the two-range form and record why.
3. **Parse structured**: `git range-diff --no-color` output is line-oriented (`<n> <old> <new>
   <summary>` with `=`/`!` markers); parse it into typed rows — pair status (identical/modified),
   both sides' oids and subjects — never raw text passthrough.
4. **Render**: JSON payload (schema `rewrite-diff.json`) carrying the entry id, source, the ranges
   used, and the rows. Exit 0/1/4; no conflict class (read-only command).
