## Description

non-interactive replacement for `git add -p`, which agents cannot use because it demands a
terminal. This issue owns the criterion #0016 explicitly deferred: **staging a stale hunk id must
get a structured error**, never a silently wrong hunk.

## The design, in one paragraph

The id is the only thing that crosses calls; patch text never does. `stageHunks` re-lists the
unstaged hunks *inside* the call, resolves every requested id against that fresh listing, rebuilds
the patch from the fresh `FileDiff.headerText` + `Hunk.patchText` (#0016 Given 7), and feeds it to
**one** `git apply --cached` invocation. An id that resolves against nothing — stale because the
hunk's lines changed, or never valid — is refused **by name, before anything is applied**. It has
to be refusal-by-resolution: measured below, `git apply` is no detector, because a patch with a
stale header still applies.

### 1. The #0016 stability fact, re-measured

The two-hunk fixture (20-line file; a line inserted after `line 03`, `line 17` replaced). Staging
only the first hunk — file header + first hunk piped to `git apply --cached` — leaves the second
hunk's **body byte-identical while its header moves** `@@ -14,7 +15,7 @@ line 13` →
`@@ -15,7 +15,7 @@ line 13`, and `git diff --cached` shows the first hunk under its original
header. So the id (SHA-256 over path + body, header excluded, 12 hex) survives staging in both
listings, and a *fresh* listing always carries an applyable header for it.

### 2. `git apply` cannot detect staleness — measured, it applies a stale patch

With hunk 1 already staged, the **pre-staging** patch for hunk 2 — header `@@ -14,7 +15,7@@` and
the now-wrong `index 036b411..0aea296` line — was fed to `git apply --cached`: **exit 0, applied.**
git offset-searches for the context and ignores the stale index line. This is why a stale id must
be refused by resolution against a fresh listing: relying on apply failure would let a stale
listing stage something silently. It also settles the ordering question: two ids staged in two
calls both work, because each call rebuilds from a fresh listing (pinned by
`secondCallWithTheSurvivingIdStillApplies`).

### 3. One `git apply --cached` invocation is atomic

A single patch stream touching two files, with the second file's context corrupted:
`error: patch failed: b.txt:1`, exit 1, and the first file's hunk was **not** staged
(`git diff --cached` empty). All-or-none therefore needs no rollback code: resolve every id first
(refusing unknowns before any apply), then apply everything in one invocation.

### 4. `git apply` on an empty patch is an error, not a no-op

`printf '' | git apply --cached` → exit 128, `error: No valid patches in input (allow with
"--allow-empty")`. So an empty id list must return before invoking git; the guard is load-bearing
(mutation M6).

### 5. Conflicted files are structurally unaddressable, and staging others still works

A merge conflict (3 unmerged index entries) plus an ordinary worktree edit in another file. Plain
`git diff` with the listing flags prints the unmerged path as a **combined diff** —
`diff --cc m.txt`, `@@@` headers — and, measured with two different path orderings, every
`diff --cc` block prints **ahead of** every `diff --git` block. `HunkParser` opens files only on
`diff --git `, so a conflicted path yields no `FileDiff`, no hunks, and no ids: any id aimed at it
is `unknownHunkIDs`. And `git apply --cached` on the ordinary file's patch succeeded with the
unmerged entries still in the index — staging touches only its own paths, so conflicts elsewhere
do not block it. (The `git write-tree` refusal on unmerged indexes is the journal's problem, not
staging's; nothing here calls `write-tree`.)

### 6. The listing side of these facts is already on `main`

`listHunks(at:area:git:)`, `FileDiff` (`path`, `headerText`, `hunks`), `Hunk` (`id`, `patchText`),
and `HunkParser.hunkID(path:body:)` are in `YardKit/Sources/YardGit/Hunks.swift` exactly as #0016
specifies — read that file's doc comments, not the issue history. `GitProcess.run` throws
`GitProcess.Failure` on non-zero exit and writes `standardInput` to stdin then closes it; its full
signature is pasted in #0016's Givens. `ExitClass`/`ExitClassCarrying` are in
`YardKit/Sources/YardGit/ExitClass.swift`. `FixtureRepository` provides
`init(refFormat:)`, `build(_:)`, `writeUntracked(_:)`, `checkoutDetached(_:)`, `oids`,
`destroy()`, `url` (realpath-resolved), and `RefFormat.supported()`. No other collaborators exist
and none need inventing.

## The deliverable — `YardKit/Sources/YardGit/Staging.swift`, in full

```swift
// Staging.swift — stage hunks by their stable content-derived ids (#0040)

import Foundation

/// Why staging or unstaging by hunk id could not proceed.
public enum StagingError: Error, Equatable, CustomStringConvertible, Sendable {
    /// Ids that do not appear in a fresh listing of the given area. An id
    /// goes stale the moment the hunk's own lines change — the id is a hash
    /// of path and body (#0016) — so a stale id is simply absent from the
    /// fresh listing and is refused by name here rather than guessed at.
    /// `git apply` itself cannot be the detector: measured, a patch whose
    /// `@@` header and `index` line are both stale still applies (git
    /// offset-searches for context), so relying on apply failure would let
    /// a stale id stage the wrong thing silently.
    case unknownHunkIDs(ids: [String], area: DiffArea)

    public var description: String {
        switch self {
        case let .unknownHunkIDs(ids, area):
            "unknown hunk id(s) in the \(area.rawValue) listing: "
                + ids.joined(separator: ", ")
                + " — stale (the hunk changed since it was listed) or never valid"
        }
    }
}

/// Stages the hunks with the given ids: index gains exactly those changes.
///
/// Ids come from `listHunks(at:area:git:)` over the **unstaged** area. The
/// listing is re-taken inside this call, so headers are always fresh — an id
/// survives an earlier hunk being staged (its `@@` line shifts, its body does
/// not), and the patch fed to git is rebuilt from the current listing, never
/// from whatever listing the caller decided from.
///
/// All-or-none: every id is resolved before anything is applied, and the
/// selected hunks go to git as **one** `git apply --cached` invocation, which
/// is atomic — measured: a two-file patch whose second file fails leaves the
/// first unstaged. An unknown or stale id therefore stages nothing.
///
/// Conflicted files are unaddressable: git prints unmerged paths as combined
/// diffs (`diff --cc`), which carry no stable ids, so no id can name a hunk
/// of a conflicted file — staging one fails with `unknownHunkIDs`. Other
/// files stage normally while the index holds unmerged entries (measured).
///
/// An empty `ids` array is a no-op: nothing to resolve, and `git apply` on
/// an empty patch is an error (`No valid patches in input`, exit 128), so
/// git is not invoked at all.
public func stageHunks(
    ids: [String],
    at path: String,
    git: GitProcess = GitProcess()
) throws {
    let files = try listHunks(at: path, area: .unstaged, git: git)
    let patch = try selectPatch(ids: ids, from: files, area: .unstaged)
    guard !patch.isEmpty else { return }
    try git.run(["apply", "--cached"],
                workingDirectory: path,
                standardInput: Data(patch.utf8))
}

/// Builds the patch text for the requested hunk ids: for every file owning
/// at least one requested hunk, its `headerText` followed by the requested
/// hunks' `patchText` in **listing order** — hunks inside one file patch must
/// stay in file order whatever order the caller passed the ids in. Duplicate
/// ids in the request select the hunk once. Throws `unknownHunkIDs` (in
/// caller order, deduplicated) when any id matches nothing; returns "" for
/// an empty request.
func selectPatch(ids: [String], from files: [FileDiff], area: DiffArea) throws -> String {
    var wanted = Set(ids)
    var patch = ""
    for file in files {
        let selected = file.hunks.filter { wanted.contains($0.id) }
        guard !selected.isEmpty else { continue }
        for hunk in selected { wanted.remove(hunk.id) }
        patch += file.headerText + selected.map(\.patchText).joined()
    }
    var missing: [String] = []
    for id in ids where wanted.contains(id) {
        missing.append(id)
        wanted.remove(id)
    }
    guard missing.isEmpty else {
        throw StagingError.unknownHunkIDs(ids: missing, area: area)
    }
    return patch
}

// MARK: - §6 exit class (#0141)

/// A stale or unknown id is a repository-state failure — the state the id
/// referred to no longer exists — guide §6 code 6. Not conflicts (8): a
/// conflicted file's hunks are unlisted, so an id for one lands here too,
/// and the caller's recovery is the same either way: re-list.
extension StagingError: ExitClassCarrying {
    public var exitClass: ExitClass { .repositoryError }
}
```

// MARK: - Fixture helpers (same two-hunk shape HunksTests measures)

/// `line 01` … `line 20`, one per line, trailing newline.
private func base20() -> String {
    (1...20).map { String(format: "line %02d", $0) }.joined(separator: "\n") + "\n"
}

/// A line inserted after `line 03`, and `line 17` replaced — far enough
/// apart that git keeps them as two hunks at -U3.
private func edited20() -> String {
    var lines = (1...20).map { String(format: "line %02d", $0) }
    lines[16] = "line 17 CHANGED"
    lines.insert("inserted after 03", at: 3)
    return lines.joined(separator: "\n") + "\n"
}

private func twoHunkRepo(_ format: FixtureRepository.RefFormat) throws -> FixtureRepository {
    var repo = try FixtureRepository(refFormat: format)
    try repo.build([.init("base", files: ["f.txt": base20()])])
    try repo.writeUntracked(["f.txt": edited20()])
    return repo
}

/// The two hunks of the one changed file, in listing order.
private func listedHunks(in repo: FixtureRepository, area: DiffArea) throws -> [Hunk] {
    try listHunks(at: repo.url.path, area: area).flatMap(\.hunks)

@Test(arguments: FixtureRepository.RefFormat.supported())
func conflictedFileIsUnaddressableButOthersStage(format: FixtureRepository.RefFormat) throws {
    // A conflict in m.txt plus an ordinary edit in a.txt. Unmerged paths
    // print as combined diffs (`diff --cc`, `@@@` headers) ahead of every
    // `diff --git` block — measured — and carry no stable ids, so no id can
    // address a conflicted file's content.
    var repo = try FixtureRepository(refFormat: format)
    defer { repo.destroy() }
    try repo.build([.init("base", files: ["m.txt": "original\n", "a.txt": "a1\na2\na3\n"])])
    try repo.build([.init("ours", parents: ["base"], files: ["m.txt": "ours\n"])])
    try repo.build([.init("theirs", parents: ["base"], files: ["m.txt": "theirs\n"])])
    let ours = try #require(repo.oids["ours"])
    let theirs = try #require(repo.oids["theirs"])
    try repo.checkoutDetached(ours)
    _ = try? GitProcess().run(["merge", "--no-commit", theirs],
                              workingDirectory: repo.url.path)
    let unmerged = try GitProcess().run(["ls-files", "-u"], workingDirectory: repo.url.path)
    #expect(unmerged.lines.count == 3)   // guard against vacuity: a real conflict
    try repo.writeUntracked(["a.txt": "a1 CHANGED\na2\na3\n"])

    // The conflicted path never appears in the listing.
    let files = try listHunks(at: repo.url.path, area: .unstaged)
    #expect(files.map(\.path) == ["a.txt"])

    // Staging the ordinary file works over an unmerged index (measured:
    // `git apply --cached` touches only its own paths).
    let hunk = try #require(files.first?.hunks.first)
    try stageHunks(ids: [hunk.id], at: repo.url.path)
    let staged = try listHunks(at: repo.url.path, area: .staged)
    #expect(staged.map(\.path) == ["a.txt"])

    // Any id aimed at the conflicted file's content fails typed.
    let bogus = "111111111111"
    let error = try #require(throws: StagingError.self) {
        try stageHunks(ids: [bogus], at: repo.url.path)
    }
    #expect(error == .unknownHunkIDs(ids: [bogus], area: .unstaged))
}

// MARK: - selectPatch (pure)

private func hunk(path: String, header: String, body: [String]) -> Hunk {
    Hunk(id: HunkParser.hunkID(path: path, body: body), path: path,
         oldStart: 1, oldCount: 1, newStart: 1, newCount: 1,
         header: header, body: body)
}

@Test func selectPatchKeepsListingOrderWhateverTheRequestOrder() throws {
    let h1 = hunk(path: "f.txt", header: "@@ -1 +1 @@", body: ["-a", "+A"])
    let h2 = hunk(path: "f.txt", header: "@@ -9 +9 @@", body: ["-b", "+B"])
    let file = FileDiff(path: "f.txt", oldMode: nil, newMode: nil, isBinary: false,
                        headerText: "HEADER\n", hunks: [h1, h2])
    // Request in reverse order: the patch must still put h1 first, because
    // hunks inside one file patch must be in file order for git to apply.
    let patch = try selectPatch(ids: [h2.id, h1.id], from: [file], area: .unstaged)
    #expect(patch == "HEADER\n" + h1.patchText + h2.patchText)
}

@Test func selectPatchEmitsEachFileHeaderOnceAndSkipsUnselectedFiles() throws {
    let h1 = hunk(path: "one.txt", header: "@@ -1 +1 @@", body: ["-x", "+y"])
    let one = FileDiff(path: "one.txt", oldMode: nil, newMode: nil, isBinary: false,
                       headerText: "ONE\n", hunks: [h1])
    let h2 = hunk(path: "two.txt", header: "@@ -1 +1 @@", body: ["-p", "+q"])
    let two = FileDiff(path: "two.txt", oldMode: nil, newMode: nil, isBinary: false,
                       headerText: "TWO\n", hunks: [h2])
    let patch = try selectPatch(ids: [h1.id], from: [one, two], area: .unstaged)
    #expect(patch == "ONE\n" + h1.patchText)
    #expect(!patch.contains("TWO"))
}

@Test func selectPatchReportsMissingIdsInCallerOrderDeduplicated() {
    let h1 = hunk(path: "f.txt", header: "@@ -1 +1 @@", body: ["-a", "+A"])

    }
}

## Notes

**Scope moved out of the original issue, deliberately:**

- **`unstage` is #0162**, blocked on this issue and on #0161 (a parser hardening this planning
  pass found by measurement: `git diff --cached` prints `* Unmerged path <p>` at the unmerged
  path's sorted position, which poisons a neighbouring file's `headerText` — it breaks *reverse*
  apply during conflicts, and does not affect this issue).
- **The auto-checkpoint is the command layer's, not this function's.** The journal write path
  (#0027–#0034) does not exist yet; when `switchyard stage` is wired (M2 command work, alongside
  #0038's `commit --hunk`, which consumes this same engine surface), the wiring takes the
  checkpoint — under #0032's `JournalLock` — before calling `stageHunks`. Putting a checkpoint
  inside the engine function would deadlock the callers that already hold the lock.
- **CLI wiring is deliberately absent** — same boundary as #0016: no `CommandSpec`, no `runYard`
  arm, no `--json` shape.

**Design decisions, so nobody relitigates them mid-round:**

- **Refusal-by-resolution, not refusal-by-apply.** Given 2: git applies stale patches. The fresh
  listing is the only honest oracle for what an id currently names.
- **One apply invocation per call** buys atomicity with zero rollback code (Given 3).
- **Recorded limitations, deliberate:** untracked files have no unstaged hunks (`git diff` does
  not list them) and so cannot be staged by id — whole-file staging is a different command;
  binary and mode-only `FileDiff`s have no hunks, so no id can select them, and requesting one is
  `unknownHunkIDs`; a worktree edit racing between the internal listing and the apply surfaces as
  `GitProcess.Failure` (already `ExitClassCarrying`, code 6), not as a typed staging error.
- `@testable import YardGit` in the tests: the fixture tests exercise `stageHunks` as a public
  caller; `@testable` exists only for the internal `selectPatch`, which is pure and worth pinning
  directly (#0116's public-surface concern is covered at wiring time, when the CLI compiles
  against the public API).
