## Description

**Finding 1 of #0160's second umbrella review, 2026-08-17.** A `fixup` that stops on a conflict stores
**no rewrite mapping at all** — neither attached to its journal entry nor as an observed entry.

The mechanism is a hole between #0160's two children:

1. `Fixup.run` throws `.blockedOnConflicts` and **deliberately leaves the rebase in progress**, so
   `JournalCheckpoint.around` unwinds. The scoped `GitProcess` — the only carrier of
   `SWITCHYARD_JOURNAL_ENTRY` — stops existing while the operation is still half-done.
2. Whatever finishes the rebase (`git rebase --continue`, or a `switchyard` command that does) runs
   through an **unscoped** `GitProcess`, which still exports `markerVariable`. So the resulting
   decision is `isOwnInvocation == true` **with no entry id**.
3. Both halves then refuse it: `attachRewrite` returns `nil` because there is no id, and
   `JournalObserved.record` returns `nil` because the invocation is our own.

**The `(own, no id)` quadrant is a hole**, and it is exactly the case an interrupted operation lands
in. Established by probe in a scratch copy: c1/c2/c3 all touching `f.txt`, staged `X`,
`Fixup.run(target: c2)` throws `blockedOnConflicts`, then resolve and continue. Hook log:

```
=I= amend   =E= (empty)  =M= 1
=I= rebase  =E= (empty)  =M= 1
```

`entry.rewrite` after the continue is `nil`; `JournalObserved.list` is empty. The journal entry count
stays 1 throughout — **the entry exists and is simply never completed**.

## The design question, and it is the substance of this issue

An interrupted operation's continuation has to find its entry id, and the scoped `GitProcess` is gone.
Three shapes:

**A — persist the id where the sequencer lives.** A rebase in progress already has state on disk under
the path `git rev-parse --git-path rebase-merge` reports; write the in-flight entry id beside it when
`around` unwinds with the operation incomplete, and have the hook read it back when no environment id
is present. Survives the process boundary, which is the actual problem. Costs a file and its cleanup.

**B — fall back to the newest entry for this worktree.** No new state: with no id in the environment,
an own invocation attaches to the newest entry recorded by this worktree. Cheap, and wrong the moment
anything else has checkpointed since — which in a two-agent repository is normal.

**C — record it as an observed entry instead.** Treat "own, but we cannot say which entry" as foreign.
Loses the connection to the entry but keeps the mapping, and it is one condition to change. It also
makes `undo` never offer to revert it, which for a half-finished operation may be the honest answer.

**A is the only one that is correct in a two-agent repository**, and it is the most work. Whichever is
chosen, say why in the code, and make the probe above a test.

## Decided as guide §11 decision 19 — option A. Planned 2026-08-17.

The guide entry carries the reasoning and why B and C were rejected; it is not repeated here. What
follows is the shape.

### The file

Resolved through **`WorktreeContext.path(for:)`** — which is `git rev-parse --path-format=absolute
--git-path` — so it lands in the **per-worktree** `$GIT_DIR`, which is correct: an in-flight operation
belongs to the worktree running it, and `HEAD` and the sequencer are per-worktree for the same reason.
**Never build this path by concatenating onto `.git/`** (CLAUDE.md).

Put it under the repository's existing `switchyard/` directory rather than at the top of `$GIT_DIR`:
`RepositoryLayout` already owns those relative paths (see `journalMetadataRelativePath`, and #0199,
which migrated the literals). Add the new one there and say what you named it.

Contents: the entry id's `description`, nothing else. One line, no JSON — a second format for one
field earns nothing.

### The lifecycle, and the failure mode each step is for

- **`JournalCheckpoint.around` writes it** right after it mints the entry, before running the body.
- **`around` removes it** when the body returns normally. The common case leaves nothing behind.
- **`around` leaves it** when the body throws. That is the whole point: `Fixup.run` throwing
  `.blockedOnConflicts` is a *deliberate* mid-flight state, not a failure to clean up.
- **`attachRewrite` reads it** when the environment carries no id, and **removes it after a successful
  attach** — the operation is over at that point.
- **The environment wins when both are present.** A scoped `GitProcess` means the operation is running
  right now; the file is the fallback for when it is not.

### The part that must not be got wrong

**A stale file must degrade to today's behaviour — attach nothing — rather than attach to an unrelated
entry.** A crash between writing the file and finishing the operation leaves one behind, and the next
rewrite in that worktree would otherwise pick it up and attach its mapping to a months-old entry.

Guard it: the id in the file must name an entry that still exists (`JournalAnchor.list` or a
`rev-parse --verify` of its ref). If it does not, remove the file and attach nothing. **Test that
case** — write a file naming a pruned or fabricated id, run a rewrite, assert nothing attached and the
file is gone.

- [ ] `JournalCheckpoint.around` writes it on entry, removes it on normal return, leaves it on throw.
- [ ] `attachRewrite` falls back to it, prefers the environment, and removes it after attaching.
