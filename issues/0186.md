## Description

**Filed by #0152's planning pass on 2026-08-08, from measurements on git 2.50.1 (Apple Git-155).**

`docs/switchyard-git-internals-and-undo.md` §3 says the worktree is captured with `git stash
create` and restored with `git stash apply <oid>` (or `read-tree` + `checkout-index`). Both halves
are now measured wrong for the case M2's exit criterion names:

1. **`git stash create` fails on a conflicted worktree** — the stage lines plus `Cannot save the
   current index state`, exit **1**. It also fails on an intent-to-add entry (`error: Entry
   'ita.txt' not uptodate. Cannot merge.`), and prints nothing at exit 0 on a clean or
   untracked-only worktree. So the mechanism the doc prescribes cannot capture the unmerged state
   *"undo round-trips every mutating command, including with an unmerged index"* depends on.
2. **`git stash apply` cannot be the restore path.** #0152's snapshot is a parentless
   worktree-state commit; `stash apply` on it is `fatal: '…' is not a stash-like commit`, exit
   128 — and no applyable commit can exist for the unmerged case, because a true stash commit's
   index-commit parent is exactly what `write-tree` refuses to build there (#0151 Given 1).

The mechanism that does work, measured in #0152's Givens: `git add -u` against a temporary *copy*
of the index (against the real index it silently **resolves the user's conflict** — 3 unmerged
entries collapse to stage 0 at exit 0), then `write-tree` + `commit-tree` with pinned
identity/dates; untracked files staged into a fresh temporary index from
`ls-files --others --exclude-standard -z`; restore via a temporary union index
(`read-tree <commit>`, `update-index -z --index-info` fed `ls-tree -r -z` output, then
`checkout-index -a -f`) plus an explicit deletion pass.
