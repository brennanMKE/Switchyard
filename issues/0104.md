# 0104 — Cut YardGit out of the CLI's dependency chain

| | |
|---|---|
| **Status** | in-progress |
| **Module** | YardKit |
| **Milestone** | M1 |
| **Platform** | macOS |
| **First seen** | 2026-08-06 |

## Description

`switchyard` is a remote control for Switchyard.app. The app owns the engine; the CLI marshals
arguments over XPC and prints the reply. Guide §4, corrected 2026-08-06.

`Package.swift` still encodes the old, wrong premise that the CLI runs the engine in-process:

```swift
.target(name: "YardKit", dependencies: ["YardGit"], …)
.executableTarget(name: "yard", dependencies: ["YardGit", "YardKit"], …)
```

So the CLI links `YardGit` directly **and** transitively through `YardKit` — meaning it links libgit2
twice over, for a job it does not do. This blocks #0103: vendoring libgit2 for the app is one
problem, and vendoring it into a CLI that never opens a repository is pointless work.

## Givens — verified on `main`, treat as true

1. **Exactly one thing forces the dependency.** `YardKit/Sources/YardKit/CommandLineRunner.swift`
   line 4 is `import YardGit`, and line 14 is:
   ```swift
   let version = YardGit.libgit2Version
   ```
   used to build the version string `"switchyard 0.0.1 (libgit2 1.9.6)"`. Nothing else in
   `Sources/YardKit/` references `YardGit` — verified by grep over the whole directory.
2. The correct chain afterwards:
   - `switchyard` → `YardKit`
   - `YardKit` → nothing (envelope, `ServiceNames`, `CommandSpec`, XPC protocol types)
   - the app → `YardKit` + `YardGit`
   - `YardGit` → `Clibgit2`
3. `YardKit/Tests/YardKitTests/LayeringTests.swift` already asserts `YardGit` does not import
   `YardKit`. The inverse now needs asserting too, and it did not before.

## The version string

The CLI cannot report libgit2's version without linking libgit2. Report the CLI's own version only —
`"switchyard 0.0.1"` — and leave the engine's version to be reported by whatever asks the app. Do not
hardcode a libgit2 version string in the CLI; a hardcoded version that drifts from the linked library
is worse than no version at all.

## Expected behavior

- [ ] `Package.swift`: the `YardKit` target has **no** dependencies, and the CLI executable target
      depends on `YardKit` alone.
- [ ] `CommandLineRunner.swift` no longer imports `YardGit`. The version string is the CLI's own.
- [ ] A layering test asserts **`YardKit` does not import `YardGit`**, in the same style as the
      existing `yardGitDoesNotImportYardKit` — scan the source files, do not just rely on the
      manifest, because a manifest change and a stray import fail differently.
- [ ] Tests use **swift-testing** — `import Testing`, `@Test`, `#expect`. Not XCTest.
- [ ] `cd YardKit && swift build` succeeds, and `swift test` prints a `Test run with N tests` line
      you paste. **N must be greater than or equal to 124**, the count on `main` before this change.
- [ ] `swift run switchyard` still emits a valid success envelope, exit 0. Paste it.
- [ ] **Prove libgit2 is gone from the CLI**: `otool -L .build/*/debug/switchyard | grep -i git2`
      returns nothing. Paste the full `otool -L` output. This is the criterion that matters — the
      build succeeding proves nothing, since it already succeeds today with libgit2 linked in.

## Tests must be able to fail

The layering test must fail if someone adds `import YardGit` back to a file in `Sources/YardKit/`.
Say how you confirmed that — the honest way is to add the import temporarily, watch the test fail,
then remove it.

## Notes

Do **not** implement the XPC transport here. This issue only removes a dependency that should never
have been there. The CLI keeps doing exactly what it does today, minus libgit2.

Blocks #0103, which should not vendor libgit2 for a target that does not need it.

This exists because an invented requirement — "the CLI must work without the app, for CI and SSH" —
was recorded as settled and then shaped the manifest. See guide §4's correction note.
