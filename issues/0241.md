## Description

**Finding 1 of #0160's third umbrella review, 2026-08-17, and it is a defect in guide §11 decision 19
— which I made.** The in-flight entry-id file #0237 introduced is an **unkeyed single slot** with no
lifetime tied to the operation that wrote it.

`JournalCheckpoint.around` writes `RepositoryLayout.inFlightEntryIDRelativePath` for **every** wrapped
operation and removes it only on a normal return. `inFlightEntryID` validates only that the id still
names a **live** journal entry — which it almost always does, since entries persist until pruned.
Nothing records *which* operation is in flight, or whether one still is.

Two symptoms, both measured by the review in a scratch copy:

**1. An abandoned operation captures a later, unrelated rewrite.**

```
conflicting Fixup.run -> .blockedOnConflicts, file names entry A
git rebase --abort                  (git fires no post-rewrite on abort)
...file survives...
a later unrelated own `amend`, no environment id -> attaches to A

attached=01M099HPK7BZ9MF2SA1EES4FN4  abandonedEntry=01M099HPK7BZ9MF2SA1EES4FN4
operation=fixup  rewrite=RewriteMapping(source: "amend", …)
```

An `amend` mapping landed on an abandoned `fixup` entry. **And this is not only a user path**:
`Fixup.autosquashRebase` / `classifiedRebaseFailure` run `git rebase --abort` **themselves** on the
timeout, signing-failure and plain-failure arms (`Fixup.swift:183, 259, 267`) and then throw through
`around` — so `switchyard` leaves a file for an operation it just cancelled.

**2. Any succeeding command in between erases the mapping.** A conflicting fixup leaves the file naming
A; one successful `around(operation: "unrelated", …)` in the same worktree overwrites it and then
removes it on its normal return; the eventual `rebase --continue` attaches nothing —
`fileExistsAfterUnrelatedCommand=false attached=nil fixupEntryRewrite=nil`. The reciprocal also holds:
a throwing non-rewrite body leaves a file that only a future rewrite will consume.

This is **#0234's last-write-wins defect one layer down** — at the file rather than in the metadata.

## What a fix has to establish

The file must identify **an operation that is still in progress**, not merely an entry that still
exists. Two halves, and both are needed:

- **Write it only when the body leaves a resumable git operation.** A body that throws having cleaned
  up — every `rebase --abort` arm in `Fixup` — must leave nothing behind.
- **Validate against live sequencer state before trusting it.** `SequencerSnapshot` and the
  `rebase-merge` path already answer "is a rebase in progress"; a file whose operation is no longer
  running is stale, whatever the entry's liveness says.

Both halves are testable, and the review's two probes are the tests: an aborted fixup followed by an
unrelated rewrite attaches **nothing**, and a conflicting fixup followed by an unrelated successful
command still attaches to its own entry when continued.

## The files

- `YardKit/Sources/YardGit/JournalCheckpoint.swift` — `around`'s write/remove, and `inFlightEntryID`.
- `YardKit/Sources/YardGit/Fixup.swift` — the three arms that run `git rebase --abort` and then throw.
- `YardKit/Sources/YardGit/SequencerSnapshot.swift` — read it for the in-progress probe rather than
  writing a second one.
- `YardKit/Tests/YardGitTests/PostRewriteAttachTests.swift` — both new tests.

## Expected behavior

- [ ] The file is written only for an operation that leaves resumable state, and cleaned up by the
      arms that abort.
- [ ] `inFlightEntryID` refuses a file whose operation is no longer in progress, and removes it.
- [ ] Test: abandoned fixup (`rebase --abort`) then an unrelated own rewrite → **nothing attached**,
      and the file is gone.
- [ ] Test: conflicting fixup, an unrelated successful `around` in between, then continue → the mapping
      still lands on the **fixup's** entry.
- [ ] Mutations, each run and reported: drop the sequencer validation and confirm the first test
      reddens; keep writing the file on the abort arms and confirm it reddens too.
- [ ] `cd YardKit && swift test` twice in the **foreground**, both green, **N greater than 1026**.
- [ ] Guide §11 decision 19 is amended to say the file names an in-progress operation, not just an
      entry — the decision as written is what produced this.

## Work log

- **Round 1 — 2026-08-17, Sonnet subagent, 186,026 tokens, 17m15s, accepted.** It reproduced **both**
  symptoms first, and how it built the first is worth recording: a fake gpg that succeeds once and then
  fails puts `Fixup` into `classifiedRebaseFailure`'s signing branch, which runs `git rebase --abort`
  and throws — the abandoned-operation state, produced by `switchyard` itself rather than by a user.
- **The fix is smaller than the plan expected, and better.** Rather than adding conditions to the
  write, `around` now writes **only on a throw, and only when `SequencerSnapshot.capture` confirms a
  rebase is still live**. A successful operation never touches the file at all, which is what stops one
  operation clobbering another's slot; an aborted one writes nothing, because the sequencer is already
  gone when the throw arrives. One change, both symptoms.
- **The round proved its own second guard redundant and said so.** `Fixup.clearInFlightFile`, called
  from the three abort arms, is defence-in-depth: disabling it leaves the new tests green. I confirmed
  that independently — with the sequencer gate mutated **and** `clearInFlightFile` disabled, the
  failure is identical to mutating the gate alone. **Kept**, with its doc comment saying plainly that
  it is a second independent guard. Documented-redundant is a different thing from
  believed-load-bearing, and only the second is a problem.
- **Review.** 1029 green with `main` merged in. Replacing the sequencer gate with an unconditional
