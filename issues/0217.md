# 0217 — Decide how the reference-transaction hook arm reaches the engine

| | |
|---|---|
| **Status** | open |
| **Module** | yard |
| **Milestone** | M3 |
| **Platform** | macOS |

## Description

**A decision, not an implementation.** Two M3 issues are blocked on the same question and neither can
be planned to code level until it is answered: **#0154** (the `hook ref-txn` arm) and, in a weaker
form, **#0124** (the first ordinary command).

CLAUDE.md's Layering section is unambiguous about ordinary commands:

> **`YardGit` and libgit2 live in the app only. The CLI does not link them, and does not open a
> repository itself.** … **The CLI marshals arguments over XPC and prints the reply.**
> … **If the app is not running, the CLI launches it.**

Applied to a `reference-transaction` hook, that produces a result nobody would choose:

- The hook fires on **every ref update by any tool** — `git commit`, `git fetch`, a rebase's dozens of
  individual updates. #0042 Givens 5 measured the process spawn (~8 ms) already dominating the handler.
- "Launch the app if it is not running" means **a background `git fetch` in a terminal launches a GUI
  application**. That is not a defensible behaviour, and an agent running git in a container would pay
  a launch timeout on every ref write.
- The hook must exit **0 for every input** (#0042), so a failure to reach the app is silent — the
  journal would simply lose entries whenever the app happens to be closed, which is exactly when an
  agent is most likely to be working.

So one of three things is true, and they produce materially different code.

## The three readings

**A — the hook arm links the engine.** `switchyard hook ref-txn` calls `ReferenceTransaction.decide`
and writes the journal in-process, with no XPC and no app. Fastest and always correct, but it means the
CLI binary links `YardGit`, which the Layering section forbids. Could be narrowed by shipping a
**second, tiny executable** (`switchyard-hook`) that links the engine, leaving `switchyard` itself
thin — the rule keeps its meaning for every ordinary command, and the exception is visible in the file
list rather than hidden in a flag.

**B — the hook spools, the app drains.** The arm appends one line per transaction to a spool file
resolved through `git rev-parse --git-path`, and the app (or the next `switchyard` invocation that does
reach the app) turns spooled lines into observed journal entries. No engine link, no app dependency,
~1 ms. Costs: a second on-disk format, an ordering guarantee to design, and observed entries appearing
late — which matters because `undo` reads them.

**C — the hook goes over XPC like everything else**, but with `launchIfNeeded: false` and a short
timeout, accepting that ref transactions made while the app is closed are simply not journalled. The
smallest amount of new machinery, and it makes the journal's completeness a function of whether a GUI
app happens to be running.

## Recommendation

**A, in its two-binary form.** The journal's value is that it is complete; B and C both trade
completeness for adherence to a rule whose stated purpose ("the CLI stays small", "the app owns the
engine") is about the *interactive command surface*, not about a hook that is not a user-facing command
at all. A second executable keeps the rule literally true for `switchyard` and puts the exception
somewhere a reader will find it.

B is a real alternative if hook latency measurements later say otherwise, and it is the only option
that survives the app being uninstalled.
