## Description

Carried out of **#0213** (closed wontfix 2026-09-03): its planning gate asked whether any M3 command
needs a long-lived session, and the answer is no — the interactive commands that would need one
(`review --wait`, `ask`, `resolve --interactive`, `watch`) are **M4** (guide §4, "M4 — Human-in-the-loop").
M3's XPC surface is request/reply (`AppService.perform`), which needs no session. So the session
criteria move here, to the milestone that owns the commands that would use them.

## Description (from #0213, unchanged in substance)

- Sessions survive minutes with heartbeats. Do not port RemoteControl's heartbeat cadence without
  checking it against guide §4 — its cadence was tuned for its own long-running operations.
- Teardown handled on **every** path: the CLI exits, the CLI is killed, the app quits, the broker
  restarts, the connection is interrupted. Several are not unit-testable; the manual script (#0054,
  or its M4 successor) owns those.
- Orphaned sessions are reaped rather than accumulating, with a stated policy: what makes a session
  orphaned, how often it is checked, and what is logged when one is reaped.

## What has to be settled first

**What a Switchyard session *is*.** RemoteControl's sessions exist because its app streams progress
back to an attached CLI. Switchyard's CLI marshals a command and prints a reply — guide §5. Before
any code, name exactly which M4 commands need a session and what each one streams; `review --wait`
and `ask` are the clear candidates, `resolve --interactive` and `watch` need checking.

## Planning pass — 2026-09-03, answered from the landed M4 code.

**Which M4 commands need a session: only `watch` (#0058).** `review --wait`, `ask` and
`resolve --interactive` block on a pending registration whose lifetime the store's own timeout owns —
that is a request/reply with a long deadline, not a session. Their pending stores
(`PendingReviewStore`/`PendingAskStore`/`PendingResolveStore`) already implement the session-shaped
state: registration, supersede, typed timeout, and the sheet outliving the CLI. No heartbeat: the
blocking XPC call holds the connection for the deadline's duration, and a heartbeat would only
re-assure a connection that either works or has already fired its invalidation handler.

**This issue's deliverable is the teardown audit + the stated reaping policy:**

- **The five teardown paths, audited against the three pending stores** (tests where unit-testable):
  1. *CLI exits cleanly* — the connection closes; the pending stays registered (the human may still
     decide; #0059 records the note either way). Stated policy: a decision after the CLI's death is
     still recorded — the note outlives the agent.
  2. *CLI is killed* — same path as 1 (connection invalidation). The sheet stays until the human
     decides or the timeout fires; the timeout is the reaper.
  3. *The app quits* — everything dies with the process; the CLI's blocking call gets
     `sessionTerminated` (exit 5) via the connection error path. Tested in #0055 round 1.
  4. *The broker restarts* — re-registration via #0047's `interruptionHandler`; the pending store is
     app-side and unaffected. Manual scenario (verify-xpc.md scenario 6 covers the shape).
  5. *The connection is interrupted* — same as 3/4 by the invalidation path.
- **The reaping policy, stated where a reader will find it** (the stores' doc comments): an orphaned
  pending is one whose CLI connection is gone; it is reaped when its own `timeoutSeconds` fires
  (typed `.timedOut` to nobody, sheet banner, note still recordable). No background reaper needed —
  the per-pending timer IS the reaper, and it cannot accumulate because each pending carries its own
  deadline.
- **The gap to fill**: when the CLI's connection dies, the pending currently waits out its full
  timeout before the sheet shows anything. Add a connection-death hook — the store resolves the
  pending as a typed `.abandoned` outcome the moment the connection invalidates (the sheet banner
  changes from "waiting" to "the asking agent went away — you can still decide, it will be recorded
  as a note"), instead of silently counting down. Tested with a killed listener.
- **`watch` is #0058's**, and its session design (a real stream) is that issue's to plan; this issue
  hands it the policy above as the base.
- **Manual scenarios** append to `scripts/verify-xpc.md`'s successor set: CLI killed mid-review, app
  quit mid-resolve, broker restart under a pending review.
