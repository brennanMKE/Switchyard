## Description

`try!` traps. A trap in a library kills the host process with a signal, so `switchyard` exits with no
envelope at all — an agent sees a signal where the contract promises
`{"schemaVersion":1,"ok":false,…}`, and a test run loses its entire summary rather than reporting one
failure. This project has already paid for that twice, in #0012 and #0112, both in test code.

There are **nine**, verified 2026-08-07 by
`grep -rn 'try!\|as! \|(using: .utf8)!\|encoding: .utf8)!' YardKit/Sources/`. This issue removes all
nine. Four of them arrived with #0088's `schema` command, after this issue was first written — which
is itself the argument for fixing the class rather than the instances. Fixing them one at a time is how #0014's hand finish guarded two subscripts
and left nine — name the class, not the instance.

## Givens — verified on `main`, treat as true

1. The five sites, with the correct fix for each:

   | file:line | expression | fix |
   |---|---|---|
   | `YardKit/Sources/YardGit/WhereAmI.swift:209` | `try! git.capture(["ls-files", "-o", "--exclude-standard"], …)` | `try?` and return **0**, matching the neighbouring `stashCount` closure at line 199 which already does `guard let out = try? …, out.exitCode == 0 else { return 0 }` |
   | `YardKit/Sources/YardGit/WhereAmI.swift:218` | `try! git.capture(["diff-index", "--name-status", "HEAD"], …)` | same |
   | `YardKit/Sources/YardGit/WhereAmI.swift:226` | `try! git.capture(["diff-index", "--name-status", "--cached", "HEAD"], …)` | same |
   | `YardKit/Sources/YardKit/CommandLineRunner.swift:30` | `try! JSONEncoder().encode(value)` inside `jsonString` | return a **hand-written literal** failure envelope string |
   | `YardKit/Sources/YardKit/Envelope.swift:241` | `try! JSONEncoder().encode(self)` inside `EnvelopeFail.write()` | same |
   | `YardKit/Sources/YardKit/CommandLineRunner.swift:63` | `.data(using: .utf8)!` in `runSchema` | `guard let` → literal envelope |
   | `YardKit/Sources/YardKit/CommandLineRunner.swift:64` | `JSONSerialization.jsonObject(with: raw) as! [String: Any]` | `as?` with `guard let` → literal envelope |
   | `YardKit/Sources/YardKit/CommandLineRunner.swift:72` | `String(data: data, encoding: .utf8)!` in `runSchema` | same |
   | `YardKit/Sources/YardKit/CommandLineRunner.swift:85` | `String(data: data, encoding: .utf8)!` in `jsonString` | same |

   The `as!` at line 64 is the sharpest of them: `JSONSerialization` returns `Any`, and a schema
   payload that is not a top-level object crashes the process rather than producing a failure
   envelope.

2. **`YardKit/Sources/YardGit/WhereAmI.swift` already contains the pattern to copy**, in the `stashCount` and `hasConflicts`
   closures. Follow it; do not invent a third shape.

3. `EnvelopeFail(code:message:)` and `EnvelopeErrorCode` are in
   `YardKit/Sources/YardKit/Envelope.swift`. **There is no
   `internalError` case.** The ten cases, verified by reading `Envelope.swift:84`, are: `ok`,
   `usage`, `brokerUnreachable`, `appUnavailable`, `requestFailed`, `sessionTerminated`,
   `repositoryError`, `humanDeclined`, `blockedOnConflicts`, `signingFailed`.

   **Use `.requestFailed`, and do not add a case.** Adding one means touching `ExitCode`,
   `codeLabel`, the `init(from:)` decoding switch, and the exit-code contract that CLAUDE.md says
   must not be renumbered.

4. `runYard` returns `(stdout: String, stderr: String, exitCode: ExitCode)` — three elements.

5. `EncodableResult` (`YardKit/Sources/YardKit/Envelope.swift:62`) wraps `any (Encodable & Sendable)`, which is why the
   encoding failure is reachable in principle even though no command triggers it today. The first
   command whose payload carries a non-string dictionary key, a non-finite `Double`, or a throwing
   custom `encode(to:)` crashes the process.

6. `YardKit/Sources/YardGit/FixtureRepository.swift` contains **no** traps and needs no change.
7. **`runSchema` is #0088's code and has tests** — `CommandRegistryTests.swift` asserts the parsed
   command count and that malformed JSON fails at the parse step. Those must still pass unchanged;
   `swift run switchyard schema` output must be byte-identical before and after.

## The literal failure envelope

The whole point is a path that runs when encoding fails, so it **cannot itself encode**. Write the
bytes:

```swift
private let encodingFailureEnvelope =
    #"{"schemaVersion":1,"ok":false,"error":{"code":"request_failed","message":"Failed to encode the response."}}"#
```

A second `JSONEncoder().encode(...)` in the failure path is the same bug one level down.

## Tests must be able to fail

Every one of these paths is currently unreachable in normal operation, so **a happy-path test proves
nothing** — it passed before the change too.

| # | what to construct | assert |
|---|---|---|
| 1 | an `Encodable & Sendable` type whose `encode(to:)` throws, wrapped in `EncodableResult` | `jsonString` returns the literal envelope, and `runYard` reports a non-zero exit code |
| 2 | the same, through `EnvelopeFail.write()` | the literal envelope reaches stdout |
| 3 | a `GitProcess` pointed at a non-existent executable path, passed to `whereAmI` | `untrackedCount`, `unstagedCount` and `stagedCount` are all `0` and **nothing traps** |

Test 3 is the one that matters, and **it was verified against `main` on 2026-08-07 rather than
assumed** — pointing `GitProcess(executablePath:)` at a path that does not exist makes both `capture`
and `run` throw:

```
PROBE capture THREW: could not launch git: The file "git" doesn't exist.
PROBE run     THREW: could not launch git: The file "git" doesn't exist.
```

So the failure is real and needs no mocking. Two neighbouring behaviours were measured at the same
time and are worth knowing before you write the test:

- **`capture` does not throw on a non-zero exit.** `git config --get nonexistent.key` returns
  `exitCode == 1` with no error. Only a launch failure throws. That is why `try?` with a `0` fallback
  is the right shape for the three `WhereAmI` counts.
- **`run` does throw on a non-zero exit**, as `GitProcess.Failure.exited`, carrying stderr.
- A non-existent working directory is *not* a launch failure: `capture` returns `exitCode == 128` with
  `fatal: cannot change to '/no/such/dir'` on stderr. **Do not use a bad working directory to provoke
  the throw** — it will not. Before this change that test crashes
the whole run; after it, it passes. **Run it against the unmodified source first and report what
happens** — that is the proof the test can fail.

**Then mutate**: put one `try!` back at `YardKit/Sources/YardGit/WhereAmI.swift:209` and confirm test 3 crashes the suite
rather than failing it. Restore, confirm green.

## Review round 1 — the production diff is right; three of my own criteria were unbuildable

**All nine traps are gone.** `grep -rn 'try!\|as! \|(using: .utf8)!\|encoding: .utf8)!' YardKit/Sources/`
returns nothing, and each fix matches the table above. Keep the source diff.

The tests failed, and **two of the three causes are defects in this issue**, not in the round. The
third is the round's: it never ran the suite and reported success anyway — *"the tests themselves take
too long to execute for us to get a count"*. `AGENTS.md` Rule 3 covers that.

### My defect 1 — test 3 as written cannot pass

I measured that `GitProcess(executablePath:)` pointed at a missing file makes `capture` and `run`
throw, and then asserted what `whereAmI` would do with such a process. **I never ran it through
`whereAmI`.** Line 129 is an *uncaught* `try git.capture(["symbolic-ref", …])`, so an unlaunchable git
rethrows there and the count closures at 209/219/228 are never reached. Verified:

```
PROBE missing-git THREW: could not launch git: The file "git" doesn't exist.
```

That is the #0093 mistake in a new costume: verify the part, assert the composite.

**The working vector is a git that LAUNCHES and always fails** — `/usr/bin/false`. `capture` does not
throw on a non-zero exit, so line 129 returns cleanly and every count closure runs. Measured through
`whereAmI` this time:

```
PROBE /usr/bin/false -> untracked=0 unstaged=0 staged=0 conflicts=0 branch=nil head=[]
```

### My defect 2 — the `try!` mutation is not observable, so the criterion asked for the impossible

Because `capture` does not throw on a non-zero exit, restoring `try!` at line 209 changes **nothing**
under `/usr/bin/false` — and under a missing git the closure is never reached. So "put one `try!` back
and confirm the suite crashes" cannot be satisfied by any input.

**Use an observable mutation instead.** Change the fallback in one count closure from `return 0` to
`return 99` and confirm the test fails. That proves the test actually binds to those closures, which
is what the mutation was for.

### My defect 3 — byte-identical stdout is unachievable

Envelope key order is **nondeterministic per process**. Six runs of the same binary produced three
distinct orders:

```
{"ok":true,"result":"switchyard 0.0.1","schemaVersion":1}
{"result":"switchyard 0.0.1","schemaVersion":1,"ok":true}
{"schemaVersion":1,"ok":true,"result":"switchyard 0.0.1"}
```

**Compare parsed JSON, not bytes.** Decode both sides with `JSONSerialization` and compare the
resulting objects. (The nondeterminism is itself a defect — filed as **#0122** — but it is not this
issue's to fix.)

### The round's own defect — a test that deadlocks the whole suite

`YardKitTests/TryTrapScenarios.swift:54` `dup2`s stdout and stderr into `Pipe()`s and then calls
`readDataToEndOfFile()`. The write ends stay open, EOF never arrives, and the test blocks forever —
`sample` shows it parked in `read`. It also hijacks the runner's own stdout, so **the suite emitted no
`Test run with N tests` line at all**: 10m50s and 2,030 bytes before being killed, against a 12s
baseline.

That is the exact failure this issue exists to prevent — a whole run's result destroyed — reintroduced
by the fix's own tests.

**Never capture stdout in a test.** Both encoding paths are reachable without it:

- `jsonString` is `private` in `CommandLineRunner.swift`. **Make it internal**, so `@testable import`
  can call it directly with a payload that fails to encode.
- `EnvelopeFail.write()` writes to `FileHandle.standardOutput`. Do not test it. Test the literal it
  emits by asserting on `encodingFailureEnvelope` — also make that `internal` — and assert `write()`
  exists without invoking it.
