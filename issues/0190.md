## Description

**Filed by #0153's planning on 2026-08-17, as the explicit cost of guide §11 decision 12.**

Observed foreign ref transactions are written under `refs/switchyard/observed/`, deliberately outside
the journal's ref space, so `undo` cannot offer them structurally rather than by four call sites
agreeing. `JournalRebuild` scans `JournalAnchor.refPrefix`, so **a rebuild does not recover observed
entries** — it does not lose them either (they are still in their own refs), but the rebuilt cache
does not mention them.

This issue is the deliberate decision that §11 decision 12 says must be taken rather than discovered:
either the rebuild learns the second namespace, or it is documented that observed entries are outside
its remit.

## Expected behavior

- [ ] A decision recorded in `docs/switchyard-development-guide.md` §11, in the same shape as
      decision 12: what a rebuild does about observed entries, and why.
- [ ] If the answer is "learn the namespace": `JournalRebuild` scans both prefixes and the cache
      distinguishes them, with a test that a rebuild after deleting the cache lists an observed entry.
- [ ] If the answer is "out of remit": a test that pins the *current* behaviour so it cannot drift
      silently, plus a line in the rebuild's doc comment saying so.
- [ ] Either way, `swift test` prints a `Test run with N tests` line where N is greater than the
      count on main at the time.

## Notes

Blocked by #0153 — there is nothing to rebuild until observed entries exist.

The related question, if the answer is "learn the namespace": what a rebuild should do about an
observed entry whose refs were deleted by `git gc` or by hand. The journal's answer is that anchors
keep objects alive; observed entries have no anchor, by design.

## Decision and plan — 2026-08-17. Out of rebuild's remit, and pinned.

**Decided: (b), the rebuild does not recover observed entries — and it should not.** Taken in
Brennan's absence under the standing instruction, reversible, and flagged for his confirmation like
decision 12 itself. The reasoning is structural rather than a preference, which is why it did not wait:

**`JournalRebuild` reconstructs the undo/redo chain**, and observed entries are by design not on it.
Read the type comment (`JournalRebuild.swift:5-24`): it rebuilds *"the journal, recovered from the
repository alone"* from `JournalAnchor.refPrefix`, and its whole purpose is that *"the repository
always suffices and everything outside it is derived"*. An observed entry is not derived state and it
is not a journal entry — teaching rebuild to collect it would mean either putting foreign activity on
the chain, which decision 12 exists to prevent, or returning it in a second list that nothing consumes.

**Nothing is lost by this.** Observed entries live in their own refs and `JournalObserved.list` reads
them directly; a rebuild neither deletes nor hides them. The word "recover" in this issue's title
overstated the risk — there is nothing to recover, only a question of who enumerates them.

**What is worth pinning is the failure mode next door.** `JournalRebuild` records a ref in the journal
namespace whose last component is not an id as a `Defect` — `.foreignRef(name:)`, tested at
`JournalRebuildTests.swift:227`. If rebuild's scan were ever widened to `refs/switchyard/**`, every
observed entry would surface as a defect, and the defect list is *"how an agent knows it got a partial
journal rather than a complete one"*. That would make a healthy repository report itself broken, once
per foreign transaction. Nothing prevents that widening today except that nobody has done it.

## Change 1 — `YardKit/Sources/YardGit/JournalRebuild.swift`, doc comment only

Append to the type comment, after the failure-policy paragraph:

```swift
/// **Observed entries are out of scope, deliberately** (#0190, guide §11
/// decision 12). They live in `JournalObserved.refPrefix`, outside the
/// namespace this scans, because they are a record of *foreign* ref activity
/// and never undo targets. Rebuild reconstructs the chain; they are not on
/// it. Widening the scan to all of `refs/switchyard/` would report every one
/// of them as a `Defect` — a healthy repository declaring itself partial,
/// once per foreign transaction.
```

## Change 2 — `YardKit/Tests/YardGitTests/JournalRebuildTests.swift`, append one test

Inside the existing type, matching the surrounding style (`writeEntry`, `threeIds`, `context(of:)` are
that file's own helpers):

```swift
    /// #0190: a rebuild neither recovers nor trips over observed entries. The
    /// second assertion is the load-bearing one — observed refs sit outside the
    /// journal namespace, so if the scan were ever widened they would surface
    /// as `.foreignRef` defects and a healthy repository would report itself
    /// partial, once per foreign transaction.
    @Test func rebuildIgnoresObservedEntriesEntirely() throws {
        let repo = try FixtureRepository.linear()
        defer { repo.destroy() }
        let ctx = context(of: repo)
        let good = try writeEntry(#"{"op":"good"}"#, id: threeIds().a, in: repo)

        try JournalObserved.record(
            [.init(oldValue: String(repeating: "0", count: 40),
                   newValue: String(repeating: "a", count: 40),
                   refName: "refs/heads/topic")],
            in: ctx)
        try #require(try JournalObserved.list(in: ctx).count == 1)

        let result = try JournalRebuild.rebuild(in: ctx)
        #expect(result.entries == [good])
        #expect(result.defects.isEmpty)
    }
```
