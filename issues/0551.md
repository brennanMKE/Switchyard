## Description

Switchyard is meant to be a daily driver for someone coming from GitUp, whose defining property
was speed on big repositories. Measured on the git/git fixture
(`/Users/brennan/Developer/brennanMKE/Git/git`, 5,000 loaded commits, 1,017 refs) on 2026-09-30,
with a throwaway probe test in a planning worktree:

- **The loads are fast** — `loadCommitHistory` 0.17 s, `loadCommitGraph` 0.06 s, the sidebar 0.13 s,
  `BranchMapLayout.make` 3 ms, the per-row geometry under 0.1 ms. Paging and lazy rows are not the
  problem.
- **`CommitHistoryView.body` is.** Every evaluation rebuilds each commit's ref chips against the
  whole ref list — **42-46 ms release, 731-770 ms debug** — and, while a filter query is typed,
  matches every commit with Foundation's case-insensitive search — **118-154 ms more**. Both on the
  main actor, and `body` re-runs whenever `ContentView.body` does (fresh closures defeat SwiftUI's
  diffing), so a click, an arrow key and every filter keystroke paid it.
- **Opening a repository and refreshing after every mutation awaits six independent reads one
  after another**: 0.62-0.68 s, against 0.20-0.21 s when they run together.

**Guide §11 decision 44 is the design**: a `HistoryIndex` value (chips, commits by oid, folded
search text) built once per load, off the main actor, inside one concurrent window loader, and read
by `CommitHistoryView`; the filter becomes a folded byte search (1-2 ms per query on git/git).

## Questions for Brennan (the plan assumed an answer to each; none blocks a child)

1. **`ß` in the History filter.** The filter used Foundation's case-insensitive search, which
   matches `ß` against a lone `s` ("Signed-off-by" matched `ß`, measured). The folded search matches
   `ß` against `ss` only. The other 19 queries tried on git/git gave identical results. Assumed:
   the folded answer is the right one, and a test pins it.
2. **Every pane appears together on open.** The header used to appear before History when the
   later reads were slow; now all six reads land at once, about 0.2 s after the spinner on git/git.
   Assumed fine; the alternative (assign each as it arrives) gives back the same wall time in
   pieces.
3. **History still loads the newest 5,000 commits** (#0405). Paging past them (scroll to the
   bottom, load more) is not in this plan; decision 44 records it as the next performance step if
   5,000 is not enough.
4. **Not measured in-app: frames while scrolling a 5,000-row map.** The rows are a `LazyVStack` of
   per-row `Canvas` strips and the geometry is cheap (above); the spike records the open and filter
   timings but asserts none. If scrolling itself stutters on your machine, say which repository —
   that is an Instruments session, not something the VM can measure.
5. **⌘G and ↓/↑ did not move the selection on the large fixture** in the planning VM runs, before
   and after this work alike — filed as #0556 (observed, not diagnosed), and #0555's spike does not
   drive them. Not a performance defect, so not a child here.
6. **Out of scope:** the sidebar's per-render sort of 1,000 tags (not measured slow), the Whole
   File diff of a very large file (#0534 question 4), `BranchStatus`'s merged read, and a debug
   build's general slowness.
