## Description

Stable hunk IDs are what make precise agent-driven staging possible. `git add -p` is interactive and
therefore unusable by an agent, which is why agents today either stage whole files or generate
patches by hand and get them wrong.

The ID has to survive the round trip that matters: list hunks, decide, stage a subset by ID. That
means it must be derived from content and position in a way that does not change just because an
adjacent hunk was staged first.

## Expected behavior

- [ ] Unstaged and staged hunks both listed, each with an ID, path, old/new ranges, and the patch text.
- [ ] IDs remain valid across a staging operation on a different hunk in the same file.
- [ ] IDs are invalidated — detectably, with a clear error — when the underlying file changes.
- [ ] Binary files and mode-only changes are represented, not skipped silently.
- [ ] Tests cover: two adjacent hunks, staging the second by ID, then re-listing.
