## Description

**Filed by #0044's planning pass on 2026-08-08 as a backlog gap: no issue owns this, and #0035
will hit it.**

`RefSnapshot` captures and restores refs and `HEAD`, and #0044 established that `refs/rewritten/*`
is *already* captured and restored in the correct per-worktree scope. That is enough to put the
refs back where they were. **It is not enough to leave an interrupted rebase resumable.**

An in-progress rebase keeps its state in the sequencer files under `$GIT_DIR` — the todo list, the
done list, the stopped-sha, the original head. Refs alone do not reconstruct them. So after an undo
that crosses a rebase boundary, the refs can be correct while `git rebase --continue` has nothing
to continue, or worse, continues against a stale plan.

## Why this is not folded into #0151 or #0152

#0151 is the index; #0152 is the worktree. The sequencer is neither — it is control state for an
operation in flight, and it has its own lifetime, its own directory, and its own failure mode
(a half-restored sequencer is more dangerous than an absent one, because `git rebase --continue`
will act on it).

## What this issue must settle

- **Which files constitute the sequencer state**, resolved through `git rev-parse --git-path`
  and never by concatenating onto `.git/` — measured, not assumed. Both `rebase-merge` and
  `rebase-apply` layouts, and whether `CHERRY_PICK_HEAD`/`REVERT_HEAD`/`MERGE_HEAD` belong here
  or with the index.
- **Whether capture is byte-for-byte or structured.** The index precedent (#0151) says a raw
  byte snapshot is correct when the file *is* the state; the same argument likely applies, and
  the same caveat about a second referenced file applies too.
- **Whether restore is all-or-nothing.** A partially restored sequencer should be impossible;
  say how that is guaranteed.
- **What happens on undo when no rebase is in progress but the entry recorded one, and the
  reverse.** Both are ordinary, not exotic.
- **What `captured` records**, so `undo` keeps reporting honestly what it did and did not
  restore (#0034 Decision 3, #0155's `captured` map).

## Sequencing

Blocked by nothing structural — the primitive can be built and tested standalone against a real
interrupted rebase fixture. It must land before **#0035** can claim the M2 exit criterion *"undo
round-trips every mutating command"*, because a rebase is a mutating command and an unresumable
rebase is not a round trip. Consumers are #0167 (capture) and #0168 (restore); #0171 is the
sibling that wires index and worktree in.

## Notes

Do not re-derive git's behaviour from memory here. Build a real repository, start a rebase that
stops on a conflict, and look at what is actually on disk — #0044's pass found that
`git update-ref` silently moves a branch checked out in another worktree at exit 0, which
contradicted the reasonable assumption everyone had been carrying.

## Planning update — 2026-08-08, authored in-context, all facts measured

Measured on git 2.50.1 in a scratch repository: a three-commit `main`, a `side` branch rebased onto
it, stopping on a conflict.

### Given 1 — the sequencer is one self-contained directory

`git rev-parse --path-format=absolute --git-path rebase-merge` resolves it. During an interrupted
rebase it holds **15 files, 44K total**:

```
author-script  done  drop_redundant_commits  end  git-rebase-todo
git-rebase-todo.backup  head-name  interactive  message  msgnum
no-reschedule-failed-exec  onto  orig-head  patch  stopped-sha
```

`grep -rlE '\.\./|/objects/|sharedindex'` over the directory finds **nothing** — unlike the split
index (#0151 Given), it references no second file. A byte-for-byte capture of this directory is
therefore self-sufficient.

`rebase-apply` is the other layout (`git rebase --apply`, `git am`); capture whichever exists.

### Given 2 — several files are ZERO BYTES and their existence IS the state

`drop_redundant_commits`, `interactive`, `no-reschedule-failed-exec` are empty, and
`git-rebase-todo` is empty once the todo list is exhausted. **A capture that skips empty files, or a
restore that omits them, changes the rebase's behaviour without changing any content.** This is the
single most likely way to get this wrong.

### Given 3 — restoring the directory alone restores resumability. Measured end to end.

1. With the rebase stopped, `rm -rf` the `rebase-merge` directory → `git status` reports
   `HEAD detached`, and no rebase is in progress.
2. Copy the directory back byte-for-byte → `git rebase --continue` runs to completion:
   `Successfully rebased and updated refs/heads/side.`

So the capture unit is the directory, and the restore is the directory. No reconstruction from refs
is needed or sufficient.

### Given 4 — `AUTO_MERGE` is outside the directory and points at an unreachable tree

`git rev-parse --git-path AUTO_MERGE` resolves to a 41-byte text file next to `HEAD`, containing a
**tree** oid (`git cat-file -t` confirms). `CHERRY_PICK_HEAD`, `MERGE_HEAD` and `REVERT_HEAD` are
**absent** during a rebase conflict — they belong to other operations.

**That tree is reachable from no ref.** Capturing only the file text preserves the pointer while
ordinary maintenance may reclaim the object, so the entry would restore a dangling reference. The
tree oid must join the anchor's **keep-alive** set, exactly as #0167 does for captured refs.

## What this issue must deliver

**One deliverable: capture and restore the sequencer state.** A new `SequencerSnapshot` primitive in
`YardKit/Sources/YardGit/`, mirroring `IndexSnapshot` (#0151) and `WorktreeSnapshot` (#0152) — read
both before writing; yours is the same shape of thing.

- **Capture** the whole directory as a git **tree** (each file a blob, empty files included), plus
  the `AUTO_MERGE` oid when present. A tree dedupes against the ODB and is diffable; a tarball blob
  is neither.
- **Restore** the directory byte-for-byte and atomically — a partially restored sequencer is more
  dangerous than an absent one, because `git rebase --continue` will act on it.
- Resolve every path through `WorktreeContext`, **never** by concatenating onto `.git/`. The
  sequencer is **per-worktree** state, so #0184's lesson applies to both capture and restore: put a
  mutation row on each side.
- Report the keep-alive oids to the caller, so #0167 can anchor them.
- `captured.sequencer` must become honest — #0168's `Report` currently names it `.notCaptured`
  unconditionally.

## Verification the issue must require

- A fixture that builds a **real interrupted rebase** (the recipe above), captures, wrecks, restores,
  and then runs `git rebase --continue` to completion — Given 3 made executable. Asserting the files
  match is weaker than asserting the rebase actually resumes.
- **A wreck-took-effect guard**: after the wreck, assert no rebase is in progress. Without it the
  test passes on an unwrecked repository. #0151 carries four such guards, each proven load-bearing
  by fixture mutation.
- Both `rebase-merge` and `rebase-apply` layouts, or an explicit statement of which is deferred.

## Mutation rows the table must contain

it is the one a careful reading would miss.
