# 0382 — Spike: do context-menu key equivalents fire while the menu is closed

## Description

**Child of #0380.** **Question:** a `Button` with `.keyboardShortcut` inside
`.contextMenu(forSelectionType:)` — does its key equivalent fire while no menu is open? And when the
same key equivalent is also on a menu-bar `Button`, does one key press run the action once or twice?

**Why it matters:** #0359 renders one `CommitActionMenuItems` view in both the context menu and the
menu-bar Commit menu, so every shortcut is registered twice.

### Build

Tab **0382 context keys** of #0380's spike app, plus **Spike ▸ Shared ⌥⌘J** in the menu bar.

### Observe

1. Click row "one" so the list has focus, with no menu open. Press ⌥⌘K and count the new log lines.
2. Press ⌥⌘J. Count the new log lines and note each one's source ("menu bar" or "context menu").
3. Right-click a row to open the context menu, press ⌥⌘J while it is open, and count the lines.

### Pass or fail, and what changes

- **Pass** — ⌥⌘J logs **exactly one line** in steps 2 and 3. #0359 is unchanged.
- **Fail** — ⌥⌘J logs **two lines** in any step. #0359 must stop putting `.keyboardShortcut` on the
  context-menu copy: `CommitActionMenuItems` gains a flag so only the menu-bar copy registers key
  equivalents. The context menu then shows no shortcut hints; record that as the cost.
- **Step 1 is informational.** If ⌥⌘K fires, a closed context menu still registers key equivalents;
  #0359 keeps the Commit menu anyway, for discoverability. If it does not fire, the Commit menu is
  required, which is already planned.

- [ ] #0359 is updated per the outcome.
