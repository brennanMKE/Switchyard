## Description

The second journal snapshot primitive (git internals §3): the index, captured as a real git
object and restored exactly — including the unmerged case, which is the one place in the project
where reading a git file directly is correct, because the file *is* the state.

**Structured stub, split from #0027 on 2026-08-07** (three primitives in one round is the
oversized shape that has timed out before). Re-authored to code level at its own planning pass
before dispatch, per CLAUDE.md. The facts below were measured on this machine, git 2.50.1
(Apple Git-155), 2026-08-07, and are what the planning pass builds on.

## Measured facts — run on this machine, 2026-08-07

1. **`git write-tree` refuses an unmerged index**, verbatim, exit 128:

   ```
   f.txt: unmerged (4b48deed3a433909bfd6b6ab3d4b91348b6af464)
   f.txt: unmerged (b19a1e93bec1317dc6097229e12afaffbfa74dc2)
   f.txt: unmerged (950b81b7eee953d050aa05a641f8e056c85dd1bd)
   fatal: git-write-tree: error building trees
   ```

   The three stage entries came from `git ls-files --unmerged` after a real conflicting merge.
   `FixtureRepository.conflicted()` already builds exactly this state — reuse it, do not
   reconstruct it (that reconstruction cost #0112 a round).

2. **The normal case works through a copied temporary index**: copying the index file and running
   `write-tree` against it via `GIT_INDEX_FILE` printed a tree oid and exit 0 without touching
   the real index. `GitProcess` passes environment via `extraEnvironment:`.

3. **The unmerged fallback round-trips byte-identically**: the index file resolved through
   `git rev-parse --path-format=absolute --git-path index` (never by concatenating onto `.git/` —
   in a linked worktree the index is under `$GIT_DIR`, and `WorktreeContext.path(for: "index")`
   is the existing engine affordance), stored with `git hash-object -w`, read back with
   `git cat-file blob <oid>`, compared with `cmp`: identical, 262 bytes on the probe repo.

## Expected behavior (to be authored to code level)

- [ ] `YardKit/Sources/YardGit/IndexSnapshot.swift`: capture returns either a tree oid (normal)
      or a blob oid of the index file (unmerged), as a two-case enum; restore applies whichever
      was captured, and the unmerged restore is byte-for-byte.
- [ ] A conflicted index (via `FixtureRepository.conflicted()`) round-trips: `ls-files
      --unmerged` output identical before and after restore.
- [ ] A normal index round-trips, including staged-but-uncommitted changes.
- [ ] Restore is verified by round-trip, not by inspection.
- [ ] `YardKit/Tests/YardGitTests/IndexSnapshotTests.swift` gains the tests; the diff lists
      exactly two files.

## Notes

- The tree-vs-blob decision point: `git ls-files --unmerged` non-empty, or just attempt
  `write-tree` and fall back on its measured refusal — the planning pass decides and measures
  both.
- Blob capture must record enough to know the restore target is the *index file*, and restore
  must go through the same `WorktreeContext.path(for: "index")` resolution.
- Independent of #0027 (ref snapshot) and #0152 (worktree snapshot). #0028 consumes all three.
