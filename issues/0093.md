# 0093 — Verify the stdout and exit-code contract from a subprocess

| | |
|---|---|
| **Status** | open |
| **Module** | YardKit |
| **Milestone** | M1 |
| **Platform** | macOS |
| **First seen** | 2026-08-06 |

## Description

The contract is that a failure emits JSON **on stdout** and sets a **specific exit code**. Neither can
be proven by encoding a struct in-process — only by running the binary and inspecting what a caller
actually receives.

Both #0011 rounds substituted an encoder round-trip for this. Round 2's test was even *named*
`envelopeFailWriteEmitsJsonToStdout` while never calling `write()`.

## Givens — verified on `main`, treat as true

1. The new test file is **`YardKit/Tests/YardKitTests/YardBinaryContractTests.swift`**. Create it;
   do not add these cases to an existing file.
2. **`swift test` builds the `yard` executable.** This was checked: deleting `.build/debug/yard` and
   running `swift test` recreates it. You do not need to shell out to `swift build` first.
3. **The binary sits in the same directory as the test bundle.** Both the executable and
   `YardKitPackageTests.xctest` are in `$(swift build --show-bin-path)`. Locate it by anchoring on a
   type defined in the test target — this exact form was probed inside a running test bundle and
   works:

   ```swift
   private final class BundleAnchor {}

   var yardBinary: URL {
       Bundle(for: BundleAnchor.self)
           .bundleURL                       // …/debug/YardKitPackageTests.xctest
           .deletingLastPathComponent()     // …/debug
           .appendingPathComponent("switchyard")
   }
   ```

   **`Bundle.allBundles` must not be used here, and the reason is worth knowing** — it is
   order-dependent, which is worse than simply not working. Probed directly:

   - Called first, on its own: `allBundles count=1`, no `.xctest` entry, and
     `Bundle.main` is `…/XcodeDefault.xctoolchain/usr/libexec/swift/pm`. Under `swift test`,
     swift-testing runs through `swiftpm-testing-helper`, so the test bundle is not in the registry.
   - Called *after* any `Bundle(for:)` on a type in the test target, `allBundles` **does** contain
     `YardKitPackageTests.xctest` — because `Bundle(for:)` registers it.

   So `allBundles` can appear to work depending on what ran before it in the same process, which is a
   flake waiting to happen rather than an honest failure. Anchor on `Bundle(for:)` and never read
   `allBundles`. An earlier version of this issue prescribed the `allBundles` form and it cost a full
   30-minute round.

   Do not build a path from `#filePath` and `.build/debug` either — the real directory is
   triple-specific (`.build/arm64-apple-macosx/debug`), and hard-coding either form breaks on the
   other.
4. If the binary is missing, the test must **fail with a message saying so**. It must not skip
   quietly — a subprocess test that silently does nothing is exactly the failure this issue exists
   to prevent.
5. `ExitCode.usage` is `1`. #0092 wired the binary up, and these are its verified behaviours —
   confirmed by running it with the streams captured separately:

   | invocation | exit | stdout |
   |---|---|---|
   | `yard` | 0 | `{"result":"yard 0.0.1 (libgit2 1.9.6)","schemaVersion":1,"ok":true}` |
   | `yard bogus-command` | 1 | `{"error":{"code":"usage","message":"Unknown subcommand 'bogus-command'."},"schemaVersion":1,"ok":false}` |
   | `yard noop` | 0 | `{"schemaVersion":1,"ok":true}` |

   Assert against the **shape** — valid JSON, `ok` false, `error.code` equal to `usage` — not against
   these exact byte strings, which include a version number that will change.
6. stderr is currently **empty** on every path, including failures. That is a known gap tracked by
   #0100, not something for this issue to fix. Do not assert anything about stderr's contents beyond
   what you actually observe.

## Expected behavior

- [ ] A test spawns the built `yard` binary as a subprocess — `Process`, with pipes on stdout and stderr.
- [ ] It asserts stdout parses as JSON via `JSONSerialization`, not by string matching.
- [ ] It asserts `terminationStatus` equals the documented exit code for that failure.
- [ ] It asserts stdout contains **no** non-JSON prefix or suffix.
- [ ] A second case asserts a success path exits 0 with a valid envelope.
- [ ] Tests use **swift-testing** — `import Testing`, `@Test`, `#expect`. Not XCTest. `swift test`'s summary line counts only swift-testing tests, so an XCTest file passes invisibly.
- [ ] `cd YardKit && swift build` succeeds, and `swift test` prints a `Test run with N tests` line
      you paste. **N must be greater than 105**, the count on `main` before this change.

## Notes

Split out of #0011. Blocked by #0092 — there must be a binary that emits envelopes before a
subprocess test can check one.

**A test that does not spawn a process cannot satisfy this issue**, however it is named. Neither
`EnvelopeFail.write()` called in-process nor an encoder round-trip counts, no matter how the test
function is named — both #0011 rounds substituted exactly that. If spawning
proves impossible in the test environment, say so and stop rather than substituting an in-process
approximation.

## Review — round 1 was rejected

Round 1 was killed by the harness at the full 1800s cap (exit 143) without converging. The test file
it produced is structurally correct — a real `Process`, two `Pipe`s, `waitUntilExit()`,
`terminationStatus`, `JSONSerialization`, and it fails loudly rather than skipping when the binary is
missing. It just never managed to find the binary, and burned the entire budget trying.

**Defect 1 was in this issue, not in the work.** Given 3 prescribed
`Bundle.allBundles.first { $0.bundlePath.hasSuffix(".xctest") }`, which matches nothing under
`swift test`. It was written as a verified fact and was not one — what had actually been verified was
that the binary and the bundle are siblings on disk, which is true, and the lookup snippet was
reasoned from that rather than executed. Given 3 above is now the probed form.

**Defect 2 is the one thing to fix in the code.** The helper does:

```swift
var arguments = args
arguments.insert(url.path, at: 0)   // wrong
```

Foundation's `Process.arguments` **excludes argv[0]** — it derives argv[0] from `executableURL`.
Inserting the binary's own path makes it the first subcommand, so the binary reports
`Unknown subcommand '/…/debug/switchyard'` and every success-path case fails. **Delete that line.**

With Given 3's locator and that one line removed, the suite goes green: `Test run with 10 tests in 1
suite passed`. Verified during review. Keep the rest of the file as delivered.

Also note: the binary is now named `switchyard`, not `yard` (#0102). Use `ServiceNames.cliName`
rather than a literal if that reads cleanly; otherwise the literal `"switchyard"` is fine in a test.
