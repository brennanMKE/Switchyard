## Description

**Two independent sightings on 2026-08-17**, from rounds working on unrelated issues (#0238 and #0239),
both reporting the same thing: a test in the **`AppConnection and BrokerConnection`** suite
(`YardKit/Tests/YardKitTests/AppConnectionTests.swift`) failed once under heavy parallel load and
passed on every other run of the same tree. Neither round could attribute it to its own change, and
both final runs were clean.

Two sightings is a pattern rather than a coincidence, and an intermittently red suite is corrosive in a
specific way: **every milestone's exit criteria include "`swift test` is green"**, and a suite that is
green four times out of five cannot establish that. It also trains everyone to re-run rather than
investigate, which is how a real failure gets waved through.

## What is already known

This suite has been here before. #0048 round 1 asserted **wall-clock elapsed time** — 300 ms — and the
full suite reported **24.4 seconds** for it, reproducibly, because seventy suites shelling out to `git`
starve the cooperative thread pool. That produced `AGENTS.md` **Rule 7c**. The fixes since:

- the poll test asserts termination and a computed invocation bound rather than elapsed time;
- `BrokerConnection` gained an injectable `defaultTimeout`, and the tests use **60 seconds** while
  production keeps 5;
- `AppConnection.connect`'s tests pass `launchTimeout: .milliseconds(200)`.

**That last one is the obvious suspect** and it is worth checking first: those tests assert that
`connect` throws `AppConnectionError` — `.appUnavailable` — but under enough load a broker call inside
`connect` can exceed **its** deadline first and throw `CLIError.timedOut` instead, which is a different
type and fails the expectation. That is a hypothesis, not a diagnosis; the round should establish which
test fails and why before changing anything.

Before running, read the code path the issue's hypothesis names
(`AppConnection.connect(broker:launchIfNeeded:requireApp:launchTimeout:)`) and it does not hold as
stated for the two tests that pass `launchTimeout: .milliseconds(200)`:

- `launchIfNeededFalseDoesNotLaunch` passes `launchIfNeeded: false`, so `connect` never reaches the
  `poll(timeout: launchTimeout)` call — the `if launchIfNeeded` branch is skipped entirely and it falls
  straight to `guard let endpoint else { throw .appUnavailable }`.
- `requireAppFailsFastWithoutLaunching` passes `requireApp: true`, which throws `.appUnavailable`
  *before* the `launchIfNeeded` check is even reached.

In both tests the only network call that executes is the first `try await broker.appEndpoint()`, which
runs against the in-process `FakeBroker`, whose `BrokerConnection` is constructed with
`defaultTimeout: testTimeout` (60 seconds) — not the 200 ms `launchTimeout`. So `launchTimeout:
.milliseconds(200)` is dead in both of these tests as the code stands today; it cannot be the deadline
that races and produces a stray `CLIError.timedOut`. The issue's hypothesis is refuted for the current
source, not confirmed.

```
✘ Test aNilResultRightAfterLaunchIsNotAFailure() recorded an issue at AppConnectionTests.swift:262:9: Expectation failed: (result → nil) == "registered"
✘ Test aNilResultRightAfterLaunchIsNotAFailure() failed after 75.411 seconds with 1 issue.
✘ Suite "AppConnection and BrokerConnection" failed after 75.428 seconds with 1 issue.
✘ Test run with 1025 tests in 77 suites failed after 75.764 seconds with 1 issue.
```

**Mechanism, confirmed:** `AppConnection.poll` slept for `interval` *before* every `fetch`, including the
first. The test's fetch closure returns `nil` on the first two calls and succeeds on the third, so
reaching success required three real `Task.sleep` completions inside a 60s deadline. Each sleep is
independently exposed to this suite's cooperative-thread-pool contention — #0048 measured a single 50ms
sleep delayed to ~25s under one full suite running solo — and under two full suites at once a whole run
takes ~75s instead of ~39s, so three stacked delayed sleeps routinely exceeded the 60s deadline before the
successful third attempt ever ran, and `poll` returned `nil`, which the test read as failure. The
coordinator's hypothesis was correct.

**First fix attempt (reordering only) was insufficient.** Moved the `fetch()` call ahead of `Task.sleep`
in `poll`, so reaching a given attempt costs one fewer sleep, and reduced the test to one nil before
success (needing only one real sleep instead of three). Verified against the paired-load setup three
times: pairs 1 and 2 passed, but pair 3 failed the same test the same way — one delayed sleep alone can
still exceed a 60s deadline under this contention level. Recorded here rather than presented as done,
per the round's own standard: an unverified fix is not a fix.

**Actual fix: decouple the test from real time entirely**, per the coordinator's framing that the
criterion is "a nil result is not treated as a failure" — logic, not timing. `poll` gained an injectable
`sleep` parameter (`sleep: @Sendable (Duration) async throws -> Void = { try await Task.sleep(for: $0) }`),
mirroring the existing injectable `clock`. Production and every other test keep the real default;
`aNilResultRightAfterLaunchIsNotAFailure` now passes `sleep: { _ in }`, so the loop's actual logic (keep
going on `nil`, return the value once `fetch` provides one) is exercised for real while nothing about the
result depends on `Task.sleep` actually completing in any bounded time. Restored the original "two nils
then success" shape now that it costs nothing in wall-clock exposure. Kept the fetch-before-sleep reorder
— it is a genuine improvement (an available value is returned without paying for a wasted wait) — and
gave it its own deterministic test, `aValueAvailableOnTheFirstAttemptNeedsNoWait`, which asserts fetch is
called exactly once via an invocation counter, not elapsed time.

No `.serialized`, no retry, no added `sleep` call, and no assertion reads a clock — `pollIsBoundedByItsTimeout`
(the one existing test whose bound *is* a real timing computation) was left untouched and still passes
(it is inherently robust to scheduling delay: delay only reduces the invocation count, and the assertion
is an inequality).
