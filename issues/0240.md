## Description

**Two independent sightings on 2026-08-17**, from rounds working on unrelated issues (#0238 and #0239),
both reporting the same thing: a test in the **`AppConnection and BrokerConnection`** suite
(`YardKit/Tests/YardKitTests/AppConnectionTests.swift`) failed once under heavy parallel load and
passed on every other run of the same tree. Neither round could attribute it to its own change, and
both final runs were clean.

Two sightings is a pattern rather than a coincidence, and an intermittently red suite is corrosive in a
specific way: **every milestone's exit criteria include "`swift test` is green"**, and a suite that is
green four times out of five cannot establish that. It also trains everyone to re-run rather than
investigate, which is how a real failure gets waved through.

## What is already known

This suite has been here before. #0048 round 1 asserted **wall-clock elapsed time** — 300 ms — and the
full suite reported **24.4 seconds** for it, reproducibly, because seventy suites shelling out to `git`
starve the cooperative thread pool. That produced `AGENTS.md` **Rule 7c**. The fixes since:

- the poll test asserts termination and a computed invocation bound rather than elapsed time;
- `BrokerConnection` gained an injectable `defaultTimeout`, and the tests use **60 seconds** while
  production keeps 5;
- `AppConnection.connect`'s tests pass `launchTimeout: .milliseconds(200)`.

**That last one is the obvious suspect** and it is worth checking first: those tests assert that
`connect` throws `AppConnectionError` — `.appUnavailable` — but under enough load a broker call inside
`connect` can exceed **its** deadline first and throw `CLIError.timedOut` instead, which is a different
type and fails the expectation. That is a hypothesis, not a diagnosis; the round should establish which
test fails and why before changing anything.

## Round 1 — 2026-08-17. Did not reproduce, 0 of 10, and the hypothesis is refuted.

Ten consecutive full-suite runs in a clean worktree, nothing else running: **all green, 1023 tests,
38.6–41.2 seconds**. No failure in `AppConnection and BrokerConnection` or anywhere else.

**The issue's hypothesis is refuted for the source as it stands**, by tracing rather than by running:
neither test that passes `launchTimeout: .milliseconds(200)` ever reaches the `poll(timeout:)` call
inside `connect`.

- `launchIfNeededFalseDoesNotLaunch` passes `launchIfNeeded: false`, so the branch containing the poll
  never runs; it falls through to `guard let endpoint else { throw .appUnavailable }`.
- `requireAppFailsFastWithoutLaunching` throws `.appUnavailable` before the `launchIfNeeded` check is
  reached at all.

In both, the only call exercised is the initial `broker.appEndpoint()` against `FakeBroker`, whose
`BrokerConnection` carries the **60-second** `testTimeout`, not the 200 ms one. So the 200 ms deadline
is not live in either test.

**What the round could not establish, and it is the important part:** the two original sightings both
happened while **two rounds were running full suites at once** — which is how this orchestrator works,
not how the round reproduced. Ten clean solo runs is evidence against a flake under normal load; it is
not evidence about the load the sightings occurred under.

**Next step is an experiment, not a fix:** run two full suites concurrently and see whether it appears.
If it does, the fragility is real and worth fixing, because CI (#0076) may well run under contention.
If it does not, this closes as unreproduced with the analysis kept.

The round changed **no source or test file**, which was the right call.

## Round 2 — 2026-08-17. Reproduced under paired load; fixed; fix corrected after review.

Ran the concurrent experiment Round 1 proposed: two full `swift test` invocations at once, one in this
worktree and one in a scratch worktree (`../switchyard-0240-load`, detached at `main`) standing in for a
second checkout. Reproduced on the second paired attempt, before any change:

```
✘ Test aNilResultRightAfterLaunchIsNotAFailure() recorded an issue at AppConnectionTests.swift:262:9: Expectation failed: (result → nil) == "registered"
✘ Test run with 1025 tests in 77 suites failed after 75.764 seconds with 1 issue.
```

**Mechanism:** `AppConnection.poll` slept for `interval` *before every* `fetch`, including the first. The
failing test's fetch returns `nil` twice then succeeds, so reaching success cost three real `Task.sleep`
completions inside a 60s deadline. Each sleep is independently exposed to this suite's thread-pool
contention (#0048: a single 50ms sleep measured delayed to ~25s under one full suite); under two full
suites at once a whole run takes ~75s instead of ~39s, so three stacked delays routinely exceeded 60s
before the successful third attempt ever ran.

**First fix (reorder only) was insufficient — measured, not assumed.** Moved `fetch()` ahead of the sleep
in `poll` (a genuine improvement: an available value returns without paying for a wasted wait), and cut
the test to needing one real sleep instead of three. Verified with three paired runs: 2 passed, the 3rd
failed the same way — one required real sleep can still occasionally exceed 60s at this contention level.

**Fix: decouple the test from real time.** The criterion is logic ("a nil result is not a failure"), not
timing, so `poll` gained an injectable `sleep` parameter mirroring the existing injectable `clock`
(`sleep: @Sendable (Duration) async throws -> Void = { try await Task.sleep(for: $0) }`). Production and
every other call site keep the real default; `aNilResultRightAfterLaunchIsNotAFailure` passes
`sleep: { _ in }`, so `poll`'s actual retry logic runs for real while the result depends on nothing about
wall-clock scheduling. Restored the original two-nils-then-success shape (free now that sleep costs
nothing). Added `aValueAvailableOnTheFirstAttemptNeedsNoWait` for the reorder itself.

Verified with three more paired runs, all six suite runs green (1024/1025 tests, pre-merge counts,
~75–78s each).

**Review correction (same day):** the coordinator caught that `aValueAvailableOnTheFirstAttemptNeedsNoWait`
pinned nothing — with an injected no-op `sleep`, moving `sleep` back above `fetch` in `poll` still left the
test green, because either ordering calls `fetch` exactly once for a first-try success; a fetch-count
assertion cannot see the ordering. Fixed by counting **sleep** invocations instead (also via the injected
closure) and asserting `sleepCount == 0`. Verified by mutation: moved `sleep` above `fetch` in `poll` and
reran `swift test --filter AppConnectionTests` — the mutated build failed exactly this test
(`Expectation failed: await sleepCount.count == 0`), 18 others still green; reverted the mutation and
confirmed green again. Kept the fetch-count assertion alongside it, since it still pins something real
(exactly one fetch on a first-try success), just not the ordering.

`main` was merged into this branch between rounds (`163ffb4`), moving the baseline from 1024/1025 to
**1026**. Foreground `swift test` after the correction: `Test run with 1026 tests in 77 suites passed
after 39.228 seconds`. No paired run was needed for the correction — the coordinator had already verified
the merged fix under paired load separately, and the correction here is test-only, pinned instead by the
mutation above.
