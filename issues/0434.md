## Description

Measured 2026-09-27 on the host. On `main` at `997fb348`, the command below builds successfully and
`codesign --verify --deep --strict` passes, but `open`-ing the app dies in dyld.

```
xcodebuild build -project Switchyard.xcodeproj -scheme Switchyard -destination 'platform=macOS' \
  -derivedDataPath build/dd CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO
```

The crash, from `~/Library/Logs/DiagnosticReports/Switchyard-2026-09-27-191946.ips`:

```
Library not loaded: @rpath/Switchyard.debug.dylib
... code signature in '.../Contents/MacOS/Switchyard.debug.dylib' not valid for use in process:
mapping process and mapped file (non-platform) have different Team IDs
```

Cause: #0418's `scripts/adhoc-seal-app.sh` re-signs the main executable ad-hoc with
`--options runtime`, which turns on hardened-runtime library validation. It does not re-sign
`Contents/MacOS/Switchyard.debug.dylib`, the debug-dylib split Xcode makes for Debug builds. That
dylib keeps only its linker signature, and library validation rejects it. The Release build
(`make-release.sh`) has no debug dylib, and it launches fine.

**Why the VM missed it.** `run-ui-tests-vm.sh` builds with `xcodebuild test` and launches through
XCUITest, and every spike passed with this bug on `main`. No VM step launches the plain Debug product
with `open`, which is what a person does. Why the XCUITest launch tolerated the dylib has not been
determined; the planner should find out.

## Expected behavior

- [ ] `adhoc-seal-app.sh` signs every Mach-O under `Contents/MacOS` (including `*.dylib`) and
      `Contents/Frameworks`, inside-out, before the bundle. Alternatively, it drops
      `--options runtime` for Debug; the planner decides which, with evidence.
- [ ] A test in `AdhocSealScriptTests` builds a fixture bundle containing a nested dylib and fails
      without the fix.
- [ ] A new VM step, part of `run-ui-tests-vm.sh` by default, builds the Debug `Switchyard` scheme
      unsigned exactly as above, `open`s it in the guest with a fixture repository, and asserts the
      process is still alive after 10 s and that no new crash report exists. This is the check that
      would have caught this bug.

Needs an Opus planning pass before dispatch.
