## Description

A structured superset of `git worktree list --porcelain -z`, plus what agents actually need: dirty
state, ahead/behind, in-progress operation, attached agent session, and journal depth.

Always parse the `-z` porcelain form. Agent-created worktree paths are machine-generated and will
eventually contain a newline or something equally awkward; the NUL-terminated form is documented as
stable across git versions and independent of user configuration.

### Verified `git worktree list --porcelain -z` behaviour — probed 2026-08-06

Run against a real repo with two linked worktrees, one locked with a reason and one without.

- **`--porcelain -z` is supported and exits 0.** The issue's requirement to parse it rather than the
  human form is sound.
- **In `-z` form, every attribute line is NUL-terminated** — not newline-terminated. A record ends
  with an *additional* NUL, so records are separated by `\0\0`. Splitting on newline gets nothing;
  splitting on single NUL merges records unless the empty field is treated as the boundary.
- **Attribute lines seen:** `worktree <path>`, `HEAD <oid>`, `branch <ref>`, `locked`, `bare`,
  `detached`, `prunable`.
- **`locked` appears in both forms**, and the parser must handle each:
  - with a reason → `locked agent session 42`
  - without one → bare `locked`, label-only

  So the lock reason *is* surfaced by porcelain, which is what #0021 depends on for agent sessions.
  Do not shell out a second time to read it.
- The **first** `worktree` record is always the main worktree, from any worktree in the repo.

### 1. `-z` is never passed — the headline requirement

Line 135 is:

```swift
git.capture(["worktree", "list", "--porcelain"], workingDirectory: path)
```

The doc comments claim `-z` three times. The argument vector omits it. So production receives
newline-terminated output containing **zero NUL bytes**, the NUL parser finds no boundaries, and
against a real 5-worktree fixture the function returned an **empty array**.

Fix: `["worktree", "list", "--porcelain", "-z"]`, **and add a test asserting the argument vector
contains `-z`**. A doc comment is not a call site.

### 2. The record-boundary scan aborts on the first single NUL

In `parsePorcelain`, when a NUL is not followed by another NUL, the `else` branch sets
`pos = bytes.count`, permanently ending the scan. The first NUL in any real output terminates
`worktree <path>` and is single — so exactly one boundary is ever found and the whole remainder
collapses into one record whose fields overwrite each other.

Fed genuine `-z` bytes for 5 worktrees, it produced **1 entry**: the last worktree's path carrying a
lock reason belonging to a different worktree, with the main worktree and the newline-path worktree
gone entirely.

**Replace the scan; do not patch it.** The whole algorithm is:

> Split the entire buffer on single NUL into fields. **A record boundary is an empty field.**

That is it. No position arithmetic, no lookahead.

### 3. Decode as UTF-8, not per-byte

Around line 196, `Character(UnicodeScalar(byte))` is per-byte Latin-1 and mojibakes any non-ASCII
path. Decode the whole field with `String(decoding:as: UTF8.self)`.

### 4. `mainWorktreeIsMarkedFirst` asserts nothing

It builds a porcelain string, calls nothing, and contains no `#expect` — just a comment describing
what it would have tested. The inert-test detector flags it. Implement it or delete it.

The marking logic it was supposed to cover is separately wrong: it marks **every** entry whose path
equals the first path, rather than index 0.

### 1. Path canonicalization — settled here, do not re-decide

Six of the seven failures are one mismatch. `WorktreeContext.canonicalize` calls
`resolvingSymlinksInPath()`, which collapses `/private/var` → `/var`. `worktreeList` returns **git's
raw path**, which is `/private/var/…`. So every lookup of the form
`$0.path == WorktreeContext.canonicalize(repo.url.path)` finds nothing.

**The production behaviour is correct: a parser reports what git said and does not rewrite paths.**
A caller that wants a canonical path can canonicalize; a caller that wants to compare against git's
own output — `worktree remove`, for instance — needs the raw form, and silently normalising it would
break that.

**So fix the tests: canonicalize both sides.** Compare
`WorktreeContext.canonicalize(entry.path)` to `WorktreeContext.canonicalize(expected)`. Do not add
canonicalization to `worktreeList`.

### 2. The newline fixture passes the newline as a *branch* name

`newlineInPathRoundTrips` calls `addWorktree(path: "has\nnewline", branch: "has\nnewline")` and git
rejects the ref outright. **Only the directory may contain a newline**; a branch name must be a valid
ref. Use a normal branch name — `nlbranch` works — and put the newline only in the path. That is what
the independent probe did, and it worked first try.

### 3. `parserUsesNulTerminatedPorcelain` does not test the parser

It shells out to `git … -z` itself and asserts the output contains NUL bytes. That is an assertion
about **git**, not about our argument vector — it passes with `-z` removed from line 81, which is the
exact defect it was added to prevent. The review asked for a test binding the argument vector and got
one that binds nothing.

Either make it call `worktreeList` against a real repository and assert the entries parse correctly —
which fails if `-z` is dropped, because the parser then sees no NULs — or delete it and rely on the
fixture tests. **A test that passes when the thing it names is broken is worse than no test**, because
it occupies the slot.

### 4. `bareRepositoryReturnsOneEntryMarkedBare` crashes instead of failing

It does `let e = entries[0]` after a plain `#expect(entries.count == 1)`. When the count is wrong the
subscript traps — `Fatal error: Index out of range`, signal 5 — and takes down the whole run,
destroying the summary. Use `try #require(entries.count == 1)` before subscripting, or
`#require(entries.first)`.

This is the same class that cost #0012 a round: **a trap is a lost round; a failed assertion is just
a failing test.**

### The finding worth keeping

Round 3 was told to add a `#require` guard before subscripting, and it fixed
`bareRepositoryReturnsOneEntryMarkedBare` — **the one test the review named by title** — leaving the
identical shape at seven other sites. The `-z` mutation proved that mattered: the run trapped with
`Index out of range` and signal 5 instead of reporting failures.

**Name the class, not the instance.** A review that says "fix X in test Y" gets X fixed in Y. If the
defect is a pattern, say it is a pattern and say how to find every occurrence — here,
`grep -n 'entries\[' plus every force-unwrap`.

The same applies to my own verification: I ran `swift build`, saw it succeed, and moved on. `swift
build` compiles the **library**, not the test target — two tests were missing `throws` and the suite
would not compile at all. A build that does not include the thing you changed proves nothing about
it, which is the same error as trusting a test count that did not move.
