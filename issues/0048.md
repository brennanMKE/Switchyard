# 0048 — Implement the switchyard XPC client with launch, poll, and exit codes

## Description

The CLI side: connect to the broker by Mach service name, request the app's endpoint, launch the app
by bundle identifier if the endpoint is nil, poll until registration completes (app registration
races app launch), then open a direct connection.

**Degradation must be explicit.** An interactive command with no app running fails with exit 3 and a
message naming what is missing. It never silently falls back to a non-interactive path, because an
agent would then proceed without the human approval it was told to obtain.

## Expected behavior

- [ ] The bounded poll loop is bounded — a broken app cannot hang the CLI forever.
- [ ] A nil endpoint immediately after launch is treated as normal, not as failure.
- [ ] Exit codes 2 (broker unreachable), 3 (app unavailable), 4 (request failed), 5 (session terminated) all reachable and correct.
- [ ] `--no-launch` fails instead of launching the app.
- [ ] `--require-app` fails fast when the app is not available.
- [ ] Cold-start latency measured and recorded.

## Planning update — 2026-08-17. The client only; the app's side of the direct connection is #0215.

#0047 landed the app's anonymous listener and its registration with the broker, but its listener
delegate **declines every connection** — exporting a service interface to an accepted CLI was out of
its scope. So this issue builds the client, defines the protocol both sides will speak, and tests it
against an **in-process** listener. #0215 makes the app accept and export. Neither needs the other to
land first, and neither can be proven end to end until #0049 registers the launch agent.

### Where the code goes, and why not in the executable target

**`YardKit/Sources/YardKit/BrokerConnection.swift`** and **`YardKit/Sources/YardKit/AppConnection.swift`**
— the library, not `Sources/switchyard/`. A test target cannot import an executable target, so
connection logic living in `main.swift`'s target is logic `swift test` cannot reach, and the bounded
poll is the single most important thing in this issue to have a test for. `XPCProtocols.swift` is
already in `YardKit` for the same reason. The executable stays thin (guide §5).

`Package.swift` needs **no change**: `switchyard` already depends on `YardKit`
(`Package.swift:40`), and `YardKitTests` already depends on `YardKit` (`:48`).

### Add to `YardKit/Sources/YardKit/XPCProtocols.swift`

```swift
/// What the app exposes to a CLI over the direct connection.
@objc public protocol AppServiceProtocol {
    /// Liveness check on the app itself, distinct from `brokerPing`: this one
    /// only answers when the direct connection is live.
    func appPing(reply: @escaping @Sendable (String) -> Void)
}
```

and a second factory beside `XPCInterfaces.broker`:

```swift
public static var appService: NSXPCInterface {
    NSXPCInterface(with: AppServiceProtocol.self)
}
```

Nothing more. `perform`/`startSession` shapes belong with the command wiring (#0115, #0124) and the
session work (#0213); adding them now would pin a payload format before #0194 is answered.

### Port from RemoteControl — MIT, same author, copying is correct here

`../../RemoteControl/BridgeKit/Sources/remotectl/BrokerConnection.swift` (163 lines) and
`AppConnection.swift` (223 lines). **Retain the copyright notice**, exactly as
`XPCProtocols.swift:1-7` already does. Take these four pieces essentially verbatim, renaming
`ServiceNames.broker` → `ServiceNames.machServiceName` and `appBundleIdentifier` →
`bundleIdentifier`:

- **`ResumeOnce<T>`** — an `NSLock`-guarded box that resumes a `CheckedContinuation` exactly once
  from whichever of the reply block, the error handler, or the timeout arrives first, and that
  stashes a reply which beat `attach`. Do not simplify it: every branch in it is a real ordering.
- **`Transferred<Value>`** — `@unchecked Sendable` wrapper carrying a non-`Sendable`
  `NSXPCListenerEndpoint` out of a reply block. Keep it one named type so the unchecked-ness stays
  auditable.
- **The `call(timeout:_:)` pattern** — a `withThrowingTaskGroup` racing the reply against
  `Task.sleep(for: timeout)`, where the timeout branch **invalidates the connection first**. That
  invalidation is load-bearing: it makes the in-flight call's error handler fire and resume the
  continuation, and without it the losing task abandons a checked continuation and the runtime
  reports a leak.
- **`pollForEndpoint`** — with the bound, the 250 ms interval, and the attempt counter.

Every closure XPC invokes is `@Sendable`. `YardKit` is not `MainActor`-isolated by default, so the
trap that bit the app target does not apply the same way here — but #0053 audits this file too, and
the annotation is correct regardless.

### The bounded poll, extracted so it can be tested

The one piece **not** taken verbatim. RemoteControl's poll closes over a `BrokerConnection`, which a
test cannot supply. Split the loop from its source:

```swift
/// Polls `fetch` until it returns a value or `timeout` elapses.
///
/// A nil result immediately after launching the app is normal, not a failure:
/// app registration races app launch. The bound is what matters — without it a
/// broken app hangs the CLI forever.
public static func poll<Value: Sendable>(
    timeout: Duration,
    interval: Duration = .milliseconds(250),
    clock: ContinuousClock = ContinuousClock(),
    _ fetch: @Sendable () async throws -> Value?
) async rethrows -> Value?
```

`AppConnection.connect` calls it with `{ try await broker.appEndpoint() }`; tests call it with a
counter.

### Exit codes — the criterion, and what each one is reachable from

`ExitCode` already exists (`YardKit/Sources/YardKit/ExitCode.swift`). Declare the mapping on the error
types themselves, as RemoteControl does, and **switch exhaustively** — no `default`, so a new case is
a compile error rather than a silently-wrong code:

| error | `ExitCode` | reachable when |
|---|---|---|
| `CLIError.brokerUnreachable` | `.brokerUnreachable` (2) | the Mach service is not registered |
| `CLIError.timedOut` | `.brokerUnreachable` (2) | the broker accepted but never replied |
| `CLIError.protocolMismatch` | `.requestFailed` (4) | the two sides' interfaces are out of sync |
| `AppConnectionError.appUnavailable` | `.appUnavailable` (3) | broker is fine, no app endpoint registered |
| `AppConnectionError.appNotInstalled` | `.appUnavailable` (3) | LaunchServices knows no such bundle id |
| `AppConnectionError.appTerminated` | `.sessionTerminated` (5) | the app went away mid-call |
| `AppConnectionError.undecodableResponse` | `.requestFailed` (4) | the app replied with something unparseable |

`--no-launch` and `--require-app` are **parameters here, not flags**: `connect(launchIfNeeded:)` false
throws `.appUnavailable` instead of launching, and `requireApp` fails before attempting a launch.
Parsing the flags is the command registry's job (#0124), and this issue must not add a second
argument parser.

### Tests — `YardKit/Tests/YardKitTests/AppConnectionTests.swift`

Three of these are real XPC and were **measured during planning** with a compiled probe, so they are
known to work in a plain test process with no app, no broker, and no launchd registration:

- **Broker unreachable → code 2.** `NSXPCConnection(machServiceName:)` against a name that cannot
  exist (embed a `UUID`), resume, call. Measured: the error handler fires in **0.000s** with
  `NSCocoaErrorDomain Code=4099 "… Connection init failed at lookup with error 3 - No such process."`
  It does not hang, so this needs no special timeout handling. Assert `.brokerUnreachable` and
  `ExitCode.brokerUnreachable`.
- **Request/reply over an anonymous endpoint.** Stand up `NSXPCListener.anonymous()` **inside the
  test**, with a delegate that sets `exportedInterface`/`exportedObject` and returns true, then
  connect with `NSXPCConnection(listenerEndpoint:)`. Measured working in-process: `reply: pong:hi`.
  This is how `AppConnection`'s call path is exercised without the app.
- **App terminated → code 5.** Same in-process listener, then `listener.invalidate()` and call again.
  Measured: the error handler fires with `NSCocoaErrorDomain 4097`. Assert `.appTerminated` and
  `ExitCode.sessionTerminated`.
- **The poll is bounded.** `poll(timeout: .milliseconds(300), interval: .milliseconds(50)) { nil }`
  returns nil, and the elapsed time is at least the timeout and comfortably under a second. This is
  the criterion "a broken app cannot hang the CLI forever" and it must be asserted with a real clock
  reading, not by inspection.
- **A nil result is not a failure.** A fetch returning nil twice and then a value returns that value
  — proving the nil-right-after-launch case is treated as normal.
- **`launchIfNeeded: false` does not launch.** Assert `.appUnavailable` is thrown. Do **not** write a
  test that launches an app.
- **The exit-code table above, exhaustively**, one assertion per row. Not a loop with a `continue` in
  it — that shape has landed twice as a test asserting nothing (`AGENTS.md` Rule 7).

### What cannot be measured here

**Cold-start latency.** It needs an installed app whose launch agent is registered — #0049 and #0050.
Do not fabricate a number and do not tick that box; #0054's manual script is where it gets recorded.
Say so in the report.
