# 0344 — GitProcess blocks a cooperative-pool thread for each subprocess

## Description

**The structural cause #0272 diagnosed, which that issue's named files could not fix — and it reaches
the shipping app, not just the test suite.**

`GitProcess.capture` runs, at `YardKit/Sources/YardGit/GitProcess.swift:286-287`:

```swift
outData = outPipe.fileHandleForReading.readDataToEndOfFile()
process.waitUntilExit()
```

Both are **synchronous and blocking**. When called from an `async` context they block whichever
**Swift-concurrency cooperative-pool thread** is running that task for the entire lifetime of the `git`
subprocess. The pool has a small fixed size — roughly the core count — so enough concurrent calls
leave it with no free thread to resume *anything*, including work that is already complete and merely
waiting to be scheduled.

**Measured, #0272:** with two full suites running concurrently, every test in `AppConnectionTests` took
**46-79 seconds of wall-clock** from "started" to "passed" — including
`brokerUnreachableMapsToExitCodeTwo`, which is documented as doing 0.000 s of work and shells out to
nothing. It was starved by the other eighty suites, not by anything it awaited.

**Why this is not only a test problem.** `YardUI`'s five loaders are all `@concurrent`
(`RepositoryLoader.swift`), which puts them on that same cooperative pool, and each one calls straight
into the engine. So in the running app, **every repository load blocks a pool thread for the duration
of its `git` subprocess** — today that is one window doing a handful of calls, and it is fine. It stops
being fine when the graph pane pages (#0052's deferred windowing), when tabs load several repositories
at once (#0079), or when a background refresh lands (#0217).

## Expected behavior

- [ ] `GitProcess.capture` and `run` gain a path that **does not block a cooperative-pool thread** for
      the subprocess's lifetime. The shape is an `async` overload backed by
      `withCheckedThrowingContinuation` plus `Process.terminationHandler` and asynchronous pipe reads
      (`readabilityHandler`), so the thread is released while `git` runs.
- [ ] **Keep the synchronous entry points.** Most callers are synchronous engine code and must not be
      forced to become `async`; this adds a path, it does not replace one.
- [ ] **`YardUI`'s five loaders adopt the async path**, since they are the ones on the cooperative pool.
- [ ] **A test that demonstrates the improvement rather than asserting a time.** `AGENTS.md` Rule 7c
      forbids asserting wall-clock elapsed time, and this issue is *about* timing — so assert a
      **property**: that N concurrent calls all complete, that a `Task.sleep` scheduled alongside them
      fires before they finish, or that a bounded loop terminates. Say what you chose and why it
      demonstrates the fix.
- [ ] **Do not lower `AppConnectionTests`' 180 s deadline in this issue.** If the fix works, that is a
      separate, later change made once the new behaviour has been observed under load — lowering it in
      the same commit removes the evidence.
- [ ] `cd YardKit && swift test` twice, foreground, 900000 ms timeout, both green, at or above
      `docs/test-baseline.txt`.

## The files

`YardKit/Sources/YardGit/GitProcess.swift`, `YardKit/Sources/YardUI/RepositoryLoader.swift`, and tests
in `YardKit/Tests/YardGitTests/`.

## Notes

**Milestone M3.** Comes from **#0272**, which raised the deadline to 180 s as the in-scope mitigation
and filed this as the cause.

**This is a larger change than it looks and the pipe handling is where it will go wrong.** The existing
synchronous path has a documented deadlock guard around `readDataToEndOfFile` (`GitProcess.swift:260`)
— read it before touching anything. **Do not start this without re-reading `#0239`'s timeout work
either**; `waitWithDeadline` and its `SIGTERM`/`SIGKILL` escalation already exist and the async path
must not lose them.

**Measure before and after with the same two-concurrent-suites method #0272 used**, and put both
numbers in the work log. Without them nobody can tell whether this issue achieved anything.
