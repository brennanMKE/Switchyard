## Description

`CommitLog.parse` opens each record with

```swift
let trimmed = String(record).trimmingCharacters(in: .whitespacesAndNewlines)
```

at `YardKit/Sources/YardGit/CommitLog.swift:151`. That eats leading and trailing whitespace from the
**whole record**, and the record ends with the body — so the trailing newline `git log --format=%B`
emits is removed from every commit message in the repository.

`%B` was chosen precisely because it is verbatim. #0014 spent four rounds settling that format string,
and the value it produces is then trimmed one line into the parser.

## Why it matters, and why it is small

A commit message is `"subject\n\nbody\n"`. `CommitLog` reports `"subject\n\nbody"`. Anything that
writes the message back — `switchyard commit --reword`, a rebase that reuses a message, the journal
storing one — round-trips a different byte sequence than git produced. Trailing blank lines a user
deliberately wrote are gone too.

It is one line, and its risk is entirely in what the trim is *also* doing: the record's leading field
is an OID, and several downstream fields do their own trimming already (`parts[0]`, `parts[1]`,
`parts[3]` each call `trimmingCharacters`). So the record-level trim is very likely redundant for
everything except the body, where it is harmful.

## Givens — verified on `main` 2026-08-07, treat as true

1. The file is `YardKit/Sources/YardGit/CommitLog.swift`. The trim is at line 151; the
   `guard !trimmed.isEmpty else { continue }` on the next line depends on it for skipping the empty
   tail record that NUL-termination produces.
2. **The format string at line 109 must not change.** `%H\u{01}%P\u{01}%an\u{01}%G?\u{01}%D\u{01}%B%x00`
   — #0014 spent four rounds on it.
3. `parts[0]` (oid), `parts[1]` (parents) and `parts[3]` (signature flag) each already call
   `trimmingCharacters` on their own value. `parts[2]` (author) and `parts[4]` (refs) do not.
4. The message is now `parts[5...].joined(separator: "\u{01}")` — #0117.
5. `FixtureRepository.Commit(_:parents:files:message:)` writes the message through
   `git commit -m`, and **git's own `commit` applies cleanup**: it strips trailing whitespace and
   collapses consecutive blank lines by default. So a fixture built with `-m` cannot prove byte-exact
   preservation of arbitrary trailing newlines — see "Tests must be able to fail".

## Tests must be able to fail

**The unit test is the one that proves it.** Call `CommitLog.parse` directly with a literal record
string ending `"subject\n\nbody\n\u{0}"` and assert `entry.message == "subject\n\nbody\n"` —
byte-exact, whole-string comparison. A `.contains` or `.hasPrefix` assertion passes on the truncated
value and proves nothing.

For the end-to-end case, git's own `commit` cleanup means `-m` will not carry an arbitrary trailing
newline through. Use `git commit --cleanup=verbatim` (or `-F` with a file) so the message reaches the
object store unmodified, and say which you used. **If you cannot make git preserve it, say so and rely
on the unit test** — do not adjust the assertion to match whatever comes back. #0117's round made
exactly that mistake in the opposite direction: it hit this trim, diagnosed it as git normalising the
message, and changed its test to match. The diagnosis was wrong and the test got weaker.

**Mutation**: restore `trimmingCharacters(in: .whitespacesAndNewlines)` on the record and confirm the
new test fails. Then check the empty-tail-record path still works — parse a two-commit output and
assert exactly two entries, not three.

## Review round 1 — the trim was doing two jobs, and this issue only named one

The suite is red: `✘ Test run with 276 tests in 19 suites failed after 5.478 seconds with 6 issues.`
The count rose 272 → 276, so the tests are real; three of them fail in both ref formats.

**The intended behaviour is correctly tested and correctly implemented.** The unit assertion is
byte-exact and whole-string —

```swift
#expect(entry.message == "\(body)\n", "trailing newline must be preserved verbatim")
```

— and restoring `trimmingCharacters(in: .whitespacesAndNewlines)` makes exactly that test fail. Keep
both.

### What broke: the record separator is `\0\n`, not `\0`

Measured with `od -c` on the project's own format string:

```
… s   e   c   o   n   d  \n  \0  \n   9   b   4   4   6   5   8   d …
                          ↑   ↑   ↑
                          |   |   the separator `git log` adds between records
                          |   the %x00 terminator in the format
                          the trailing newline of %B — the one this issue preserves
```

Splitting on `\0` therefore yields `["rec1", "\nrec2", "\nrec3", …, "\n"]`. **Every record after the
first begins with a newline that belongs to the separator, not to the record.**

The old record-level trim was silently doing double duty: stripping `%B`'s trailing newline — the bug
— *and* stripping that leading separator. Removing it fixed the first and broke the second.
`parts[0]`'s own trim is `.whitespaces`, which is space and tab only, so `oid` came back as
`"\n<sha>"` for every commit after the first. Hence:

- `runFillsOidsForEachEntry` — `entries[1].oid` carries a leading newline
- `runIncludesParentsForCommitWithOne` — `parents[0]` no longer equals `entries[1].oid`
- `runAgentOnlyReturnsFilteredEntries` — same cause

**This issue is at fault for framing it as "one line at :151".** The trim had two responsibilities and
the issue named one.

### The fix: strip exactly one leading newline per record, at the framing layer

After splitting on `\0`, drop a single leading `\n` from each record if present. **Do not** widen
`parts[0]`'s trim to `.whitespacesAndNewlines` — the separator is not part of the oid field, and
fixing it there leaves the next field that grows a leading newline broken in the same way.

Do not restore any trailing trim. The empty final record is correctly handled by the existing
`contains("\u{01}")` guard, which is a genuine improvement over the trim and stays.

### The empty-tail test never sees the byte that breaks production

`parseSkipsEmptyTailRecordWithoutSoh` concatenates its two records with **no separator**
(`…body1\u{0}oid2\u{01}…`). Real output is `…body1\n\u{0}\noid2\u{01}…`. That is why it passed while
production was broken, and why it also survives the mutation — it is not load-bearing.

**Build the fixture with the real `\0\n` shape.**

### The two edited assertions are right, and were arrived at wrongly

`CommitLogTests.swift:216` (`message == multiLine` → `multiLine + "\n"`) and
`FixtureRepositoryTests.swift:193` (`entry.message == body` → `body + "\n"`) are **correct** — git's
`commit -m` stores exactly one trailing newline, and the parser now preserves it, so the old
assertions encoded the bug. Keep them.

But they were changed to match observed output, not because the new value was derived. That is
#0117's failure mode. **Round 2 must state, for each, why the new value is what git actually stores.**

**Round 1's failure was mine.** I framed this as "one line at `:151`", and that line had two jobs.
`git log` emits `<record>\n\0\n` — `%B`'s trailing newline, the `%x00` from the format string, and
then its own separator between records. Splitting on NUL leaves every record after the first beginning
with that separator, and `parts[0]`'s trim is `.whitespaces`, which does not absorb a newline. The
record-level trim was the only thing removing it. Checklist item 30: **before specifying a deletion,
ask what else that line is the only thing doing.**

**Round 2 is a failure mode not seen before: a context compaction that fabricated its own history.**
The summary claimed rounds 1–3, a round 4, and a list of test names that do not exist, and the model
worked from it — importing round 1's `/tmp` sandbox incident into round 2 as a live instruction. The
sharp part is that the summary *contained the correct fix* — `hasPrefix("\n") ? dropFirst() : self` —
and it discarded that, re-read `CommitLog.swift` for a fourth time, and re-derived the diagnosis
**wrongly**, concluding the oid was empty rather than newline-prefixed. 3,028 output tokens, no
`write` or `edit` call at all.

The mechanism was context pressure it created itself: two full `swift test` runs piped into context
before doing any work, plus a 470-line test file read whole. **It never needed to run the suite** —
the issue already carried the `od -c` bytes and the failing test names.

I hand-finished rather than spending round 3. The fix is one expression against a measured target that
two rounds had already characterised; a third round had poor odds against two minutes of certain work,
and round 3 is better spent on something that needs a model.

The empty-tail test now builds its records with the real `\0\n` shape and asserts the oids and the
messages, not just the count. Round 1's version concatenated with **no** separator, so it passed while
production was broken and survived the mutation — it was never load-bearing.
