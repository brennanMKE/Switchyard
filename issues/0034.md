## The model — settled at this planning pass, binding on the children

### 1. The journal is a timeline; every entry is a full state snapshot

Every journal entry snapshots repository state at its own capture moment (guide §7: undo restores
a snapshot, never computes an inverse). Two kinds of entry, distinguished in metadata:

- **Normal** entries: explicit `checkpoint [label]`, the pre-operation capture every mutating
  command writes, and the pre-restore capture `restore` writes.
- **Traversal** entries: written by `undo` and `redo`, each recording which entry it restored
  (`restored`) and where the cursor stood afterwards (`resultingPosition`, nil = present).

Both kinds capture state identically and both are anchored (#0028) — so the chain state is
derived purely from the entry list and survives a process exit, a reboot, and a deleted
`journal.json` exactly as well as the journal itself. **No cursor file exists anywhere.**

### 2. Undo chain semantics — implemented and verified as `JournalChain` (#0166)

- The **cursor** names the entry whose snapshot the repository currently matches; nil = present.
  It is replayed from the entry list: a normal entry resets it to present; a traversal entry
  moves it to its recorded `resultingPosition`.
- **Undo** restores the newest *normal* entry below the cursor (from present: the newest normal
  entry), then appends a traversal entry recording it. Undo steps back through *operations* —
  never through past undo/redo entries, whose snapshots are duplicates of states already visited.
- **Redo** restores the oldest normal entry above the cursor. At the topmost normal entry, redo
  restores the snapshot captured by the **active run's first traversal entry** — the present
  state as it was when undo first left it — and the cursor returns to present. That is what makes
  "redo after undo returns to the exact post-operation state" true: the first undo captured that
  state, and the final redo restores those bytes.
- **A new normal entry resets the cursor to present and truncates the redo tail — logically,
  never physically.** The former tail stays listed, restorable by explicit `restore <id>`, and
  prunable by #0033; plain `redo` no longer reaches it and reports nothing-to-redo.
- Targets are computed by **order comparison, not adjacency**, so a journal with pruned holes
  still resolves (verified: a cursor naming a pruned id undoes to the newest surviving normal
  entry below it).

All of the above is running code with 12 passing tests and 8 mutations observed red — see #0166,
which carries the source in full.

### 3. What restore restores today — and the honesty contract

A snapshot has up to four pieces. Their real status:

| piece | capture | restore | status |
|---|---|---|---|
| refs + `HEAD` | `RefSnapshot.capture` | `RefSnapshot.restore` | **on `main`** (#0027, merged) |
| refs blob bytes | `serialized()` / `init(serialized:)` | same | **on `main`** (#0165, merged) |
| index (incl. unmerged) | `IndexSnapshot.capture` | `IndexSnapshot.restore` | **on `main`** (#0151, merged) |
| worktree + untracked | `WorktreeSnapshot.capture` | `WorktreeSnapshot.restore` | **on `main`** (#0152, merged) |
| sequencer (mid-rebase) | `SequencerSnapshot.capture` | `SequencerSnapshot.restore` | **on `main`** (#0174 built it, #0188 wired it, #0189 gave it a wire value) |

**Status refreshed 2026-08-17 by the second umbrella review.** The paragraph that stood here described
a transitional state that is over, and a planner reading it today would have read something false. For
the record, it said: *"Until #0151/#0152 land, checkpoint captures refs and `HEAD` only… #0171 wires

of #0151, #0152, #0171 and #0035 are merged and the flags are flipped, exactly as that text predicted.
The table also predated the sequencer entirely; it is a **fifth** piece now.

What still holds, unchanged: **restore restores exactly what `captured` says was captured and returns a
`Report` naming each piece as restored or not-restored-with-reason.**

**One amendment, 2026-08-17 (third umbrella review), and it is the only case where the sentence above
is not literally true.** Since #0205, restore also **removes** a sequencer directory the target never
captured, and reports `.sequencer` in `restored` when it does — so for that one piece `restored` means
*"brought into line with the snapshot"* rather than *"put back"*. Guide §11 decision 14 records the
behaviour and why it is safe (step 7's pre-restore entry has already captured the live sequencer, so
the mid-rebase state stays recoverable); this note exists because decision 3 is where the honesty
contract lives, and a planner reading it otherwise would believe restore never removes anything an
entry does not hold. The M2 exit criterion *"undo
round-trips every mutating command, including with an unmerged index"* **is met** — #0035's suite
asserts it with real fixtures, and #0200 extended full capture to the entries the restore flow itself
writes, which is what makes redo return the index and worktree rather than refs alone.

### 4. The cross-tool guard runs inside the restore flow, before anything mutates

Every restore path — explicit `restore`, `undo`, `redo` — runs in this order, inside
`JournalLock.withLock` (#0032):

1. Read the entry's metadata and refs blob; decode `RefSnapshot(serialized:)`.
2. **The guard, against the *cursor's* snapshot — not the target entry's.** Corrected
   2026-08-17 by the umbrella review; this step originally read
   `CrossToolGuard.requireUnchanged(since: recorded, in: context)`, with `recorded` being the
   target entry from step 1, and **that design was rejected by #0168 decision 1** — it would refuse
   *every* legitimate restore, because the diff between a checkpoint and the present is exactly the
   history the caller asked to revert. `checkpoint → work → restore` would throw
   `repositoryChanged`, and an agent has no force path. #0168 said so and left the correction to a
   docs pass; this is that pass.

   What the code does (`JournalRestore.swift:271-280` — the block moved when #0200 added its four captures): resolve the scoped chain **cursor**, read
   that entry's refs blob as `believed`, and call `CrossToolGuard.diff(recorded: believed,
   current: current)` — the union comparison (recorded ∪ current ref names plus `HEAD`, never the
   recorded subset alone), throwing `repositoryChanged` with every divergence named, exit class 6
   (`.repositoryError`, #0141) — not the internals doc's stale "exit 4". Two degradations are
   deliberate: a **nil cursor** (at present, nothing is believed) and a cursor naming a **pruned**
   entry both skip the guard, because there is no believed state to compare against.

   `CrossToolGuard.requireUnchanged` has **no production call site** and exists for callers that do
   hold a specific reference snapshot.
3. Only then the pre-restore checkpoint (#0167), then `RefSnapshot.restore`.

**When the guard refuses, nothing has been written** — no checkpoint entry, no ref moved. The
engine exposes `bypassGuard: Bool = false`; whether and to whom that surfaces (`--force`, human
only, never a scripted caller — guide §7) is M3's CLI decision, not the engine's.

The guard compares `RefSnapshot`s, which exclude `refs/switchyard/` by construction (#0027), so
the journal's own anchor writes between capture and restore can never trip it.

### 5. Worktree scoping

The entry records its worktree (#0155). `HEAD` is per-worktree; restoring another worktree's
snapshot from here would move this worktree's `HEAD` to a position it never held. So restore and
undo **refuse when the entry's recorded worktree is not the calling context's**, with a typed
error naming both (exit class 6), behind `allowDifferentWorktree: Bool = false`. With the
override, refs restore globally and `HEAD` applies to the calling worktree — documented, not
hidden. (CLI `--worktree` is M3.)

**Correction, 2026-08-17 (umbrella review).** The `allowDifferentWorktree` override described above
**does not exist in `YardKit`** — no such parameter anywhere. It is **#0175's** deliverable, split out
of #0168 deliberately because the override is unsafe without #0044 decision 4's per-worktree ref
filtering, and #0175 is still `open` with a design question recorded in it: whether the cross-tool
guard's reference (the cursor's snapshot, per decision 4 above) still holds across worktrees. Until it
resolves, **#0168's gate refuses a foreign entry unconditionally**, which is what the code does and what
the tests assert (`anotherWorktreesEntryRefusesRestoreNamingBothWorktrees`,
`aDeadRecordedWorktreeIsReportedAsGone`). Read this section as the intended design, not as shipped
behaviour.

### 6. What #0033 must treat as protected

`JournalChain.State.protectedIDs` = **every entry id at or above the cursor** — the cursor
entry, everything between it and the topmost normal entry, and the active traversal run whose
first entry holds the present-state capture. Empty when the cursor is at present (where only
#0033's own newest-entry rule applies). Pruning any protected id would sever the redo path or
the cursor itself; the composition that calls `JournalPrune.prune(protected:)` with this set is
#0170's.

### 7. Metadata: two additions #0155 must carry — binding cross-issue requirement

The #0155 shape needs, beyond its sketch:

- **`label: String?`** — the optional human label of `checkpoint [label]`.
- **`traversal: { restored: <id>, resultingPosition: <id>? }?`** — present exactly on undo/redo
  entries. **Kind is decided by this field's presence, never by matching the `operation`
  string.** `resultingPosition` is stored explicitly rather than derived from `restored`'s kind
  because the referent may be pruned (#0166's replay stays correct over holes only because the
  field is explicit).

This issue may not edit #0155 (planning-scope rule); recorded here as binding and flagged in the
planning report so #0155's own pass picks it up.
