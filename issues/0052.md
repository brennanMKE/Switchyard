## Description

The **middle pane** of the three-pane Git View, rendering the DAG and lane assignment from `YardGit`
(#0015) for the tab's active repository and worktree. Read-only at first — mutation arrives with M4
and M5.

Selection here drives the Detail pane (#0082): selecting a commit shows its diff, and selecting the
working-tree row shows staged and unstaged changes. The sidebar (#0081) drives what this pane shows —
switching worktree or clicking a ref re-scopes the graph without touching the tab.

## The data, which already exists

`graphRows(at:limit:revisions:git:)` (`LaneAssignment.swift:184`) returns `[GraphRow]`, each carrying:

```swift
public let oid: String
public let parents: [String]
public let lane: Int            // 0-based column; lane 0 is leftmost
public let parentLanes: [Int]   // parentLanes[i] is the lane of the edge toward parents[i];
                                // parentLanes[0] == lane always; empty for a root
```

**`parentLanes[0] == lane` always** and the array is empty for a root — those two invariants are what
the edge drawing keys off, and they are stated in the source, not inferred.

## Expected behavior

- [ ] A **lane gutter** to the left of each row in `CommitHistoryView`, drawn from `[GraphRow]`:
      a node marker in the commit's own `lane`, and an edge for each entry in `parentLanes`.
- [ ] **Join `graphRows` to the commit list by `oid`.** They are two engine calls returning two
      collections; a commit with no matching `GraphRow` must render **without** a gutter rather than
      crashing or shifting the row. Say what you did for that case.
- [ ] A `@concurrent` loader beside the four in `RepositoryLoader.swift`, bounded the same way
      `loadCommitHistory` is (`limit: 100`) so the two collections cover the same commits.
- [ ] **The gutter's width is a function of the maximum lane in the loaded rows**, so a linear history
      does not reserve space for lanes it never uses.
- [ ] **A pure, testable lane-geometry helper** — something like
      `laneGutterWidth(maxLane:)` and the x-offset for a lane — living in its own file with unit tests.
      That is what "no engine logic in the view layer; anything worth testing lives in the package"
      means here. `import Foundation` in the test file if it touches `CGFloat` (AGENTS.md Rule 8c).
- [ ] A `YardUITests` test that a **merge commit's row reports two parent edges** and a root's reports
      none — assert against a `FixtureRepository.merged()` fixture, by value.
- [ ] Light and dark both correct; no hardcoded colours.
- [ ] `cd YardKit && swift test` twice, foreground, 900000 ms timeout, both green, above
      `docs/test-baseline.txt` (1162), and the unsigned `xcodebuild build` from #0339 exits 0.

## Placement — settled 2026-08-07

Every view and everything around it goes in **`YardKit/Sources/YardUI/`**, the package target created
by **#0126**. Not in the Xcode project.

The Xcode project keeps only the `@main` `App` type, the asset catalog, `Info.plist`, entitlements,
`SMAppService` registration, and the embedded `switchyard` binary.

**Why it matters for this issue specifically:** a view in the app target can only be exercised by a UI
test, and UI tests cannot run under CLI-driven `xcodebuild` on this machine — the runner times out
enabling automation mode without Accessibility rights. Anything built here would ship untested. In
`YardUI` it is reachable from `swift test`.

`YardUI` sets `.defaultIsolation(MainActor.self)`, so views are main-actor isolated exactly as they
are in the app target today.

Tests go in `Tests/YardUITests` and import **without** `@testable`, so they see what the app sees.
