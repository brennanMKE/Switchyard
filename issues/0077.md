## Description

Tab chrome comes from [SlidingTabs](https://github.com/brennanMKE/SlidingTabs) — MIT, same author,
macOS 15+. `SlidingTabBar` is generic over `Identifiable` and takes a chip `ViewBuilder`, so
reordering and the "+" affordance come with it rather than being rebuilt.

Depend on it **by tag**, not by local path. Batty uses `.package(path: "../../SlidingTabs")`, which
is frictionless while both repos sit on one machine but means a public clone of Switchyard cannot
build. Switchyard is public and MIT, and #0076 puts it in CI.

## It must not go in `YardKit/Package.swift` — corrected 2026-08-06

The original wording said "in the package manifest". That would be wrong, and the reason is the
project's most important constraint.

`Package.swift` declares `.executableTarget(name: "switchyard", dependencies: ["YardGit", "YardKit"])`
— **the CLI links `YardKit`.** So a SlidingTabs dependency added to `YardKit` is inherited by the
headless CLI, which would then link a SwiftUI tab-bar package it can never use. `CLAUDE.md`:
*"`yard` must work without the app running. This is the most important architectural constraint in
the project. If the CLI needs Switchyard.app, it is useless in CI, over SSH, and in headless agent
runs."* Linking SwiftUI chrome into it is a step toward exactly that.

**SlidingTabs is a dependency of the app target**, added to `Switchyard.xcodeproj` as a remote package
— which is where `WindowView` lives per guide §4's tree. Pin it by tag there; an Xcode package
reference takes a version rule just as a manifest does, so nothing about "by tag, not by path" is
lost.

`Package.resolved` for an Xcode-managed dependency lives under
`Switchyard.xcworkspace/xcshareddata/swiftpm/Package.resolved` (or the project's equivalent path).
**Commit it** — that is what makes the build reproducible, and it is easy to miss because it is not
next to `Package.swift`.

**If UI logic later needs unit tests**, the alternative is a `SwitchyardUI` library target inside
`YardKit/Package.swift` that depends on SlidingTabs, with the app importing it and the CLI not. That
keeps everything in SwiftPM and testable in CI. Do not do it pre-emptively — one target with no tests
in it is not worth the indirection — but it is the shape to reach for when the first view needs a
test.

## Expected behavior

- [ ] SlidingTabs added to the **app target** in `Switchyard.xcodeproj`, by tag, as a remote package:
      `https://github.com/brennanMKE/SlidingTabs`, from `1.0.0`.
- [ ] **Not** added to `YardKit/Package.swift`. Verify: `cd YardKit && swift build` must still work
      with no network and no SlidingTabs anywhere, and `otool -L` on the built `switchyard` binary
      must show no SlidingTabs.
- [ ] `Package.resolved` is committed — find its real path rather than assuming; for an Xcode-managed
      package it is not beside `Package.swift`.
- [ ] A clean clone into a fresh directory builds without SlidingTabs present as a sibling. Test it
      by actually cloning to a temp path and building, not by reasoning about it.
- [ ] The MIT attribution is recorded wherever third-party licenses are listed.
