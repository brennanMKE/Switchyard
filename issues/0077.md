## Description

Tab chrome comes from [SlidingTabs](https://github.com/brennanMKE/SlidingTabs) — MIT, same author,
macOS 15+. `SlidingTabBar` is generic over `Identifiable` and takes a chip `ViewBuilder`, so
reordering and the "+" affordance come with it rather than being rebuilt.

Depend on it **by tag**, not by local path. Batty uses `.package(path: "../../SlidingTabs")`, which
is frictionless while both repos sit on one machine but means a public clone of Switchyard cannot
build. Switchyard is public and MIT, and #0076 puts it in CI.

## It must not go in `YardKit/Package.swift` — corrected 2026-08-06

The original wording said "in the package manifest". That would be wrong, and the reason is the
project's most important constraint.

`Package.swift` declares the CLI as depending on `YardKit`, so a SlidingTabs dependency added there
is inherited by `switchyard` — a command-line tool that renders no views, linking a SwiftUI tab bar
it can never use.

The reason is simply that the CLI is a **remote control**: the app has the functionality and the
views, and the CLI drives it over XPC. UI belongs to the app target.

*(An earlier version of this note justified the same conclusion by claiming the CLI must run headless
in CI and over SSH. That requirement was never real — see guide §4's correction. The conclusion
stands; the reasoning was wrong.)*

**SlidingTabs is a dependency of the app target**, added to `Switchyard.xcodeproj` as a remote package
— which is where `WindowView` lives per guide §4's tree. Pin it by tag there; an Xcode package
reference takes a version rule just as a manifest does, so nothing about "by tag, not by path" is
lost.

`Package.resolved` for an Xcode-managed dependency lives under
`Switchyard.xcworkspace/xcshareddata/swiftpm/Package.resolved` (or the project's equivalent path).
**Commit it** — that is what makes the build reproducible, and it is easy to miss because it is not
next to `Package.swift`.

**If UI logic later needs unit tests**, the alternative is a `SwitchyardUI` library target inside
`YardKit/Package.swift` that depends on SlidingTabs, with the app importing it and the CLI not. That
keeps everything in SwiftPM and testable in CI. Do not do it pre-emptively — one target with no tests
in it is not worth the indirection — but it is the shape to reach for when the first view needs a
test.

## Expected behavior

- [ ] SlidingTabs added to the **app target** in `Switchyard.xcodeproj`, by tag, as a remote package:
      `https://github.com/brennanMKE/SlidingTabs`, from `1.0.0`.
- [ ] **Not** added to `YardKit/Package.swift`. Verify: `cd YardKit && swift build` must still work
      with no network and no SlidingTabs anywhere, and `otool -L` on the built `switchyard` binary
      must show no SlidingTabs.
- [ ] `Package.resolved` is committed — find its real path rather than assuming; for an Xcode-managed
      package it is not beside `Package.swift`.
- [ ] A clean clone into a fresh directory builds without SlidingTabs present as a sibling. Test it
      by actually cloning to a temp path and building, not by reasoning about it.
- [ ] The MIT attribution is recorded wherever third-party licenses are listed.

## Planning update — 2026-08-17. The literal `project.pbxproj` edit, so this is transcription.

Structural work converges in one round when the edit is **pasted** and fails repeatedly when it has to
be **designed** — that is the lesson #0129 established. So here is the edit, read out of this
project's own `project.pbxproj` at `HEAD`.

**Verified on the remote, 2026-08-17:** `git ls-remote --tags https://github.com/brennanMKE/SlidingTabs`
returns `0ed59a08dd644619cb75a32c746f25606cbc9ec9  refs/tags/1.0.0`. The tag exists; this needs network.

### Three insertions, and nothing else

The file uses object ids of the form `26BA4480 3025CBFE 00DDB2E9`. **Invent two new 24-hex ids** that
do not appear anywhere in the file — check with `grep -c` before using them — and keep them consistent
across all three sites below. The placeholders `AAAA…` and `BBBB…` mark where each goes.

**1. A new section, beside the existing `XCLocalSwiftPackageReference` section** (which is at the
`/* Begin XCLocalSwiftPackageReference section */` marker):

```
/* Begin XCRemoteSwiftPackageReference section */
		AAAAAAAAAAAAAAAAAAAAAAAA /* XCRemoteSwiftPackageReference "SlidingTabs" */ = {
			isa = XCRemoteSwiftPackageReference;
			repositoryURL = "https://github.com/brennanMKE/SlidingTabs";
			requirement = {
				kind = upToNextMajorVersion;
				minimumVersion = 1.0.0;
			};
		};
/* End XCRemoteSwiftPackageReference section */
```

**2. One line in the project's `packageReferences` list**, which today reads:

```
			packageReferences = (
				26BA44803025CBFE00DDB2E9 /* XCLocalSwiftPackageReference "YardKit" */,
			);
```

Add `AAAAAAAAAAAAAAAAAAAAAAAA /* XCRemoteSwiftPackageReference "SlidingTabs" */,` as a second entry.

**3. A product dependency, and its reference on the app target.** In the
`XCSwiftPackageProductDependency` section, beside the existing `YardGit`/`YardKit`/`YardUI` entries:

```
		BBBBBBBBBBBBBBBBBBBBBBBB /* SlidingTabs */ = {
			isa = XCSwiftPackageProductDependency;
			package = AAAAAAAAAAAAAAAAAAAAAAAA /* XCRemoteSwiftPackageReference "SlidingTabs" */;
			productName = SlidingTabs;
		};
```

Note the `package = …` line: the **local** package's product dependencies omit it, a remote one
requires it. Then add `BBBBBBBBBBBBBBBBBBBBBBBB /* SlidingTabs */,` to the **`Switchyard` app
target's** `packageProductDependencies`, which currently lists `YardGit` and `YardKit`. Add it to no
other target — not `BrokerAgent`, not either test target.

**Confirm the product name before pasting.** `SlidingTabs`'s own `Package.swift` names its library
product, and the `productName` above must match it exactly. Fetch the tag and read the manifest;
if it differs, use the real name and say so.

### What must not happen

- **Not in `YardKit/Package.swift`.** The CLI depends on `YardKit`, so a dependency added there is
  inherited by a command-line tool that renders no views. Verify: `cd YardKit && swift build` still
  succeeds, and `grep -c SlidingTabs YardKit/Package.swift` returns **0**.
- **`Package.resolved` is committed.** For an Xcode-managed package it is at
  `Switchyard.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` — **find the real
  path after resolving** rather than assuming, and `git add` it explicitly, since it sits outside the
  paths anyone thinks to look at.
- **Xcode rewrites `project.pbxproj` while it has the project open.** If a build succeeds but the file
  looks different from what was written, that is why. Verify with `xcodebuild`, not by re-reading.

  resolved rather than being ignored.
- **Prove the app can actually use it**: add `import SlidingTabs` to one existing app-target file,

- A clean clone into a temp directory builds. Actually clone and build it — the whole point of pinning
  by tag rather than by path is that a machine without a sibling checkout can build, and reasoning

- Record the MIT attribution wherever third-party licenses are listed; if no such file exists yet,
