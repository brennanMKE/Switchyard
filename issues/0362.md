## Description

Two branch-position operations from GitUp's context menu (#0359): **Rebase Current Branch onto
Here (⌃R)** — replay the current branch's commits onto the selected node — and **Set Tip of
Current Branch Here (⌃T)** — move the branch ref to the selected commit without replaying
(hard-reset semantics for the branch pointer).

Rebase is the rewrite pipeline's natural generalization (#0060's decision): the current branch's
commits after the fork point are a commit list; replaying them onto a new base is the same
`cherry-pick` walk `Rewrite` already performs, with the branch ref moved once at the end. No
`git rebase -i`, no sequencer state — the #0060 decision applies directly.

Set-tip is the deliberate history-loss operation: the ref moves, the old commits become
unreachable. It must be the most guarded operation in the engine — journal checkpoint first, the
pre-state fully recoverable, and the typed refusal set covering "target not on any branch",
detached HEAD, and the tip-equals-target no-op.

## Expected behavior

- [ ] `yard rebase-onto <commit>` replays the current branch's unique commits onto the node via
      the rewrite pipeline; conflicts exit 8 resumable; auto-checkpoint, exactly undoable.
- [ ] `yard set-tip <commit>` moves the branch ref transactionally (`update-ref --stdin`) inside
      one checkpoint; the pre-state is restorable by `yard undo` with nothing lost.
- [ ] Both refuse typed before mutation: detached HEAD, target not an ancestor-or-parallel of
      the branch, no-op when the tip already matches.
- [ ] Signed commits stay signed through the replay (explicit `-S`).
- [ ] Both appear as #0359 context-menu items with the disabled states mirroring the refusals.

## Notes

The rebase walk shares `Rewrite`'s core (#0063) — this issue generalizes its replay target from
"the same branch" to "an arbitrary base". Set-tip is small but the most dangerous: its issue
weight is in the guards, not the code.

### Items

`CommitAction.rebaseOnto` and `.resetBranch` go in #0361's group, after Merge:

| Item | Title | Shortcut |
|---|---|---|
| rebaseOnto | `Rebase “main” onto Here` | ⇧⌘R |
| resetBranch | `Reset “main” to Here…` | **none, deliberately** |

- **"Reset" instead of "Set Tip".** It is the word git users already attach to "move my branch to
  that commit". It is written fresh here, not taken from GitUp's title.
- **No shortcut on the reset.** It is the one operation that takes commits off a branch, so it must
  never be a single keystroke away. #0359 records this allocation.
- **Rebase has no ellipsis and no confirmation.** It preserves content and is journaled, like #0359's
  reorder. **Reset always confirms**, hence its ellipsis.

Reachability is `LocalReachability.oids(in:from:)` from #0358, bounded by the window like every
other rule. A false "enabled" falls through to the engine's typed refusal and the failure alert.

### Reset confirmation — the copy is the guard

A reset is irreversible from the user's point of view until undo is reachable from the app
(#0359's question), so the dialog must say exactly what leaves the branch. Compute it with this
pure helper:

```swift
// YardKit/Sources/YardUI/RefManagement.swift (new; #0363 adds RefNameProblem to the same file)

import YardGit

/// #0362: what resetting the current branch to `target` takes off it.
public nonisolated struct BranchResetImpact: Equatable, Sendable {
    /// Commits reachable from `head` but not from `target`, newest first,
    /// within the loaded window. They leave the branch; another ref may
    /// still hold them.
    public let removed: [String]

    /// True when a removed commit has a parent outside the window, so more
    /// commits may be removed than the window shows -- say "at least".
    public let isLowerBound: Bool

    public init(removed: [String], isLowerBound: Bool) {
        self.removed = removed
        self.isLowerBound = isLowerBound
    }

    public static func make(rows: [GraphRow], head: String, target: String) -> BranchResetImpact {
        let byOid = Dictionary(rows.map { ($0.oid, $0) }, uniquingKeysWith: { first, _ in first })
        let fromHead = LocalReachability.oids(in: rows, from: [head])
        let fromTarget = LocalReachability.oids(in: rows, from: [target])
        let removed = rows.map(\.oid).filter { fromHead.contains($0) && !fromTarget.contains($0) }
        let isLowerBound = removed.contains { oid in
            byOid[oid]?.parents.contains { byOid[$0] == nil } ?? false
        }
        return BranchResetImpact(removed: removed, isLowerBound: isLowerBound)
    }
}
```

*Measured* on the fixture `h2 → h1 → base → old`, `t1 → base`, with `old` outside the window.
These are the expected values for a test:

| head | target | removed | isLowerBound |
|---|---|---|---|
| h2 | t1 (sideways) | [h2, h1] | false |
| h2 | h1 (backwards) | [h2] | false |
| h1 | h2 (forwards) | [] | false |
| h2 | a target outside the window | [h2, h1, base] | true |

The dialog, a `.confirmationDialog` with `titleVisibility: .visible`:

- **Title**: `Reset “main” to <shortOid>?`
- **Message, when `removed` is empty**: "“main” moves forward to “<subject>”. No commits leave the
  branch."
- **Message otherwise**: "<N> commit(s) will no longer be on “main”:". Use "At least <N> commits"
  when `isLowerBound`. Follow with up to three subjects, one per line and truncated to about 60
  characters, then "and <M> more" if there are more. The subjects are looked up in the loaded
  `history` by oid.
- **Buttons**: **Reset Branch** (`role: .destructive`) and **Cancel** (`role: .cancel`). No
  `.keyboardShortcut(.defaultAction)` on the destructive button: Return must not reset.
- **Do not name a recovery command** — none is reachable yet (#0359, *measured*). Once in-app undo
  exists, append "You can undo this with Edit → Undo."

**Uncommitted changes are unspecified.** The Description says "hard-reset semantics for the branch
pointer" but not what happens to the working tree and index when the branch is checked out. The
dialog must state it once the engine pass decides. If the engine refuses a dirty worktree, add
that refusal to the availability table ("Commit or stash your changes first", from
`whereAmI.stagedCount`/`unstagedCount`). This is a question in the planning report.

### While running, and after

- **Progress labels**: "Rebasing…" / "Resetting…", with #0359's busy disabling.
- **Rebase success**: select the new `HEAD` (the rebased tip) and scroll to it. The current branch's
  lane now leaves from the chosen node. Conflicts follow #0359 exactly: the failure alert with the
  conflict sentence, then after refresh the header's "A cherry-pick is in progress", because the
  replay is the cherry-pick walk.
- **Reset success**: select the target commit, now `HEAD`. Removed commits drop out of the graph
  unless another ref still holds them. Refresh in place; never through `ContentView.reload()`.
