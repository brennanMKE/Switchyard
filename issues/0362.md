## Description

Two branch-position operations from GitUp's context menu (#0359): **Rebase Current Branch onto
Here (⌃R)** — replay the current branch's commits onto the selected node — and **Set Tip of
Current Branch Here (⌃T)** — move the branch ref to the selected commit without replaying
(hard-reset semantics for the branch pointer).

Rebase is the rewrite pipeline's natural generalization (#0060's decision): the current branch's
commits after the fork point are a commit list; replaying them onto a new base is the same
`cherry-pick` walk `Rewrite` already performs, with the branch ref moved once at the end. No
`git rebase -i`, no sequencer state — the #0060 decision applies directly.

Set-tip is the deliberate history-loss operation: the ref moves, the old commits become
unreachable. It must be the most guarded operation in the engine — journal checkpoint first, the
pre-state fully recoverable, and the typed refusal set covering "target not on any branch",
detached HEAD, and the tip-equals-target no-op.

## Expected behavior

- [ ] `yard rebase-onto <commit>` replays the current branch's unique commits onto the node via
      the rewrite pipeline; conflicts exit 8 resumable; auto-checkpoint, exactly undoable.
- [ ] `yard set-tip <commit>` moves the branch ref transactionally (`update-ref --stdin`) inside
      one checkpoint; the pre-state is restorable by `yard undo` with nothing lost.
- [ ] Both refuse typed before mutation: detached HEAD, target not an ancestor-or-parallel of
      the branch, no-op when the tip already matches.
- [ ] Signed commits stay signed through the replay (explicit `-S`).
- [ ] Both appear as #0359 context-menu items with the disabled states mirroring the refusals.

## Notes

The rebase walk shares `Rewrite`'s core (#0063) — this issue generalizes its replay target from
"the same branch" to "an arbitrary base". Set-tip is small but the most dangerous: its issue
weight is in the guards, not the code.
