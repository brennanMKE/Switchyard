## Description

**Filed by #0040's review on 2026-08-08, from a mutation the reviewer invented. Companion to
#0181 — same defect shape, different protocol.**

Review replaced the whole of `StagingError.description` with `""` and ran the suite: **all 13 tests
green.** `description` is shipped as public API and asserted by nothing — the string appears zero
times in `StagingTests.swift`.

Measured across the engine, 2026-08-08: **28 files in `YardKit/Sources/YardGit` conform to
`CustomStringConvertible`; 5 test files anywhere assert a `.description`.** Re-measure rather than
trusting those figures.

## Why this matters, and why it is not merely tidiness

An error's `description` is **what an agent reads when a command fails.** It is the difference
between *"repository changed since capture: refs/heads/main was abc123, is def456"* and a bare type
name. The CLI contract says errors are structured, and the message rides in
`{"error":{"message":"…"}}` — so an empty or wrong description is a silent degradation of the one
field a human or agent actually acts on.

Several are load-bearing beyond diagnostics: `WorktreeDisturbance`'s names the worktree path and
branch, `CrossToolGuard`'s names every diverging ref and both values, `JournalRestore`'s
`unrestorableObjects` names each `ref → oid`. That last one already lost its `→` to a
transcription drift that **no test could see**, precisely because nothing asserts the string.

## What this issue must deliver

The point is **not** to assert 28 strings verbatim — that is churn, and it makes every message
change a test change. Deliver instead:

- **A scan, reusing #0181's mechanism** (that issue builds a source-scanning test for
  `ExitClassCarrying`; this should share it rather than duplicate it — say how). It lists
  conformers whose `description` no test exercises, fails with **the missing type names**, and
  supports a reasoned allow-list.
- **Substance assertions for the messages that carry data**, not equality against a full literal.
  For each error whose description interpolates values, assert the **values appear**: the ref name,
  the oid, the path, the worktree. That survives rewording while catching an empty string, a
  dropped interpolation, or a flattened `→`.
- **A mutation row per assertion**: emptying that description, and dropping one interpolated value,
  each observed red.

## Sequencing

**After #0181**, which builds the scanning mechanism. If #0181's design turns out not to generalise
to a second protocol, say so and this issue carries its own scan — but check first, because two
near-identical scanners is exactly the duplication that rots.

## Notes

This is the seventh consecutive finding of the same shape: **the code is right and the evidence is
missing**, found by a reviewer writing a mutation the planner's table lacked. #0176 through #0181
are the others. The general rule is `docs/review-failures.md` check 0b; the specific corollary is
that **a conformance has no behaviour of its own to notice**, so nothing draws attention to its
absence — which is why it needs a structural check rather than another instance-by-instance fix.
