## Description

**`main` is red.** `aForeignEntryRestoresUnderTheOverrideAndLeavesOurPrivateRefsAlone` (#0211's
pinning test, `YardKit/Tests/YardGitTests/JournalRestoreTests.swift:516`) fails **in the full suite
only**, on both ref formats:

```
✘ ...JournalRestoreTests.swift:547:9: Expectation failed: (survivor.exitCode → 1) == 0
✘ ...JournalRestoreTests.swift:548:9: Expectation failed: (survivor.lines.first → nil)
                                                          == (mainProbe → "1b74e9e…")
```

`refs/worktree/probe-main` — the **caller's own per-worktree ref** — does not exist after the
restore. That is the exact failure #0044's decision about carrying per-worktree entries through
`applied` exists to prevent, so this is not a cosmetic test problem.

## Bisected — 2026-08-17, and the shape is the whole clue

Measured in a clean detached worktree (`git worktree add -d`), so nothing about the primary
checkout's state is involved:

| commit | what it is | full suite | this test alone (`--filter`) |
|---|---|---|---|
| `467015c` | immediately before #0214 | **995 pass** | pass |
| `10e87e5` | after #0214 merged | **1002, 4 issues** | **pass** |

So: **#0214 introduced it, it only appears when the whole suite runs, and the test passes in
isolation at the same commit.** #0214's round reported 1002 green in its own worktree, which is
consistent — it is not reliably reproducible, only reliably reproducible *enough*.

`#0214` changed exactly two files: `YardKit/Sources/YardGit/Fixup.swift` and
`YardKit/Tests/YardGitTests/FixupTests.swift`. Neither touches `JournalRestore`,
`WorktreeDisturbance`, or `RefSnapshot`. **So the coupling is not through the source — it is through
what the new tests do while running concurrently**, and finding it is the substance of this issue.

## Where to look first

The assertion that fails says the restore deleted a per-worktree ref, which happens when `applied`
does not carry `current`'s per-worktree entries — i.e. when this branch in `JournalRestore.restore`
is **not** taken:

```swift
allowDifferentWorktree && metadata.worktree.name != context.worktreeName
```

Both operands are worth suspecting: `metadata.worktree.name` comes from the entry written in the
fixture's linked worktree, and `context.worktreeName` from `WorktreeContext.resolve`. If either
resolves differently under load — or if the fixture's linked worktree is not created at all, so both
are nil and compare equal — the override branch is skipped and the recorded snapshot is applied
verbatim, deleting the caller's `refs/worktree/probe-main` as an extra.

**Check the fixture's own setup before assuming the restore is wrong.** `crossWorktreeFixture`
(`JournalRestoreTests.swift`, just above the test) creates the worktree and the probe ref; a silent
failure there produces exactly this symptom with no fault in the code under test. `mainProbe` is
non-nil in the failure output, so the main worktree's ref existed — the question is whether the
*linked* one was created and named as expected.

## Expected behavior

- [ ] The mechanism is **identified and stated**, not worked around. "Added a retry" or "made the
      fixture unique" without saying why closes nothing.
- [ ] The full suite is green on `main`, run **three times**, with the counts pasted.
- [ ] If the fault is in the test or its fixture, the fix must not weaken what the test asserts:
      #0211's whole point is that a cross-worktree restore leaves the caller's per-worktree refs
      alone.
- [ ] If the fault is in `JournalRestore` — a real race in worktree-name resolution — that is a
      **correctness bug in the journal** and needs its own regression test that fails without the fix
      and passes with it.
- [ ] Whatever the cause, say whether other tests share the shape and could fail the same way.

## Notes

**Do not simply mark the test flaky or add a retry.** A restore deleting a sibling's per-worktree ref
is the loss-of-work class this milestone exists to prevent, and a green suite that is green by
retrying is worse than a red one.

**Reproduction:** run the **full** `swift test` in this worktree and read the four issues; then run
`swift test --filter aForeignEntryRestoresUnderTheOverride` and watch it pass. The difference between
those two runs is the entire bug. Do all of it inside the worktree you were given — the bisect above
was run in a throwaway detached worktree by the orchestrator, and nothing in this issue needs one.

The count on `main` at dispatch is **1010**, and it must come back 1010 **passing**, not 1010 with
four issues.

## Invalid — 2026-08-17. The bisect was right about where and wrong about why.

**There is no flake, and #0214 did not cause this.** The `git diff` proves it:

```
$ git log --oneline 467015c..HEAD -- YardKit/Sources/YardGit/JournalRestore.swift
d063764 #0150 Record the work log, resolve, set the baseline to 1010, log the costs
10e87e5 #0214 Record the work log, resolve, set the baseline to 1002
```

Both of those are **my own bookkeeping commits**, made with `git add -A` in the primary checkout, and
neither should have touched a source file at all. `10e87e5` deleted this line:

```swift
+ current.refs.filter { WorktreeContext.isPerWorktree($0.name) }
```

and `d063764` put it back. That line is decision 4's carry-through — the caller's own per-worktree
refs surviving a cross-worktree restore — so with it gone the test failed **deterministically**, which
is exactly what the bisect showed. The "full suite only" reading was wrong: the `--filter` runs that
passed were run against a working tree in which the line had already been restored.

**Where it came from.** The #0044 umbrella review was mutating `JournalRestore.swift` **in the primary
checkout** to check which of #0044's decisions were pinned. Its mutation sat in the working tree while
I ran `git add -A` from the same directory, and my commit took it. The review restored the line, and my
next `git add -A` committed the restoration.

So two rules, and they are mine to keep:

1. **A review that runs mutations works from a scratch copy** — `git archive HEAD` into the scratchpad
   — never in the primary checkout. The review moved to that itself after noticing, which is how this
   was caught at all.
2. **Never `git add -A` in the primary checkout.** Name the paths. The checkout is shared with
   whatever else is running, and `-A` commits somebody else's working state without showing it to you.

`main` is green at **1010**, run twice. Closing this as `wontfix`; the finding it recorded is real
process damage rather than a defect in the code.
