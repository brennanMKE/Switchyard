# 0192 — Pin the hook-install staging cleanup on the failure path

## Description

**Filed by #0178's round-2 review on 2026-08-17, as a gap that round created deliberately and
reported honestly.**

`HookInstall.write` cleans up its staging file on every path out, including a throw:

```swift
        defer { try? fm.removeItem(at: staging) }
```

Nothing pins that. #0178's failure test drives its failure by making the staging path itself
immutable, so under that fixture the staging file *cannot* be removed by design — the removal attempt
is what produces `.failed` in the first place. Round 2 correctly removed the "no staging file"
assertion rather than leave one that could never pass, and said so.

The consequence: deleting the `defer` leaves the whole suite green. A failed install can litter the
hooks directory with `reference-transaction.switchyard-installing` and no test notices. That is
cosmetic rather than dangerous — git ignores a file it does not know — but a stray file beside a hook
is exactly the kind of thing that wastes an hour when someone hits it.

## Expected behavior

- [ ] One test that fails an install **after** the staging file is written, by a route that leaves the
      staging path itself removable, and asserts no staging file remains.
      **The injection is already measured**: mark the **hook** immutable (`FileManager` `.immutable`),
      which lets the copy and the staging write succeed and fails only the final `replaceItemAt`.
      #0178's round 1 used exactly this fixture, and with the `defer` in place the staging file was
      measured absent afterwards; in an earlier prototype without the `defer` it was measured present.
- [ ] Deleting the `defer { try? fm.removeItem(at: staging) }` line turns that test red. Record the
      observation; if it stays green the test is not doing its job.
- [ ] `cd YardKit && swift test` prints a `Test run with N tests` line exceeding the count in
      `docs/test-baseline.txt` by exactly 1.

## Notes

Note the difference between the two fixtures, because it is the whole reason both exist:

- **Immutable staging** — copy succeeds, wrapper write fails, staging is *unremovable*. Pins the
  ordering and the backup rollback. This is #0178's test.
- **Immutable hook** — copy succeeds, staging write succeeds, `replaceItemAt` fails, staging *is*
  removable. Pins the staging cleanup. This is the one to add.

Neither can pin the other's property, which is why #0178 ended up with a gap rather than a mistake.
