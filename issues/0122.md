## Description

The JSON `switchyard` writes has a **different key order on every run of the same binary**. Six
consecutive invocations of `swift run switchyard` produced three distinct orders:

```
{"ok":true,"result":"switchyard 0.0.1","schemaVersion":1}
{"result":"switchyard 0.0.1","schemaVersion":1,"ok":true}
{"schemaVersion":1,"ok":true,"result":"switchyard 0.0.1"}
```

Key order is not semantically significant in JSON, so nothing is *broken*. But the CLI is a product
for agents, and this makes three ordinary things impossible:

- **A golden-file test.** Any assertion comparing output bytes fails at random. #0114's round 1 was
  reviewed against a "byte-identical output" criterion that no implementation could satisfy.
- **Diffing two runs.** An agent comparing `switchyard status` before and after an operation sees
  spurious changes in every field.
- **Caching or hashing a response.** The same state hashes differently each time.

## Givens — verified on `main` 2026-08-07, treat as true

1. `Envelope.encode(to:)` (`YardKit/Sources/YardKit/Envelope.swift:44`) writes its keys through a
   `KeyedEncodingContainer` in a fixed order — `schemaVersion`, `ok`, `result`. **The order it writes
   is not the order that comes out**, because `JSONEncoder` does not preserve insertion order unless
   told to.
2. The fix is `encoder.outputFormatting.insert(.sortedKeys)` at each `JSONEncoder()` construction.
   There are two, both in `CommandLineRunner.swift` (`jsonString`) and one in `Envelope.swift`
   (`EnvelopeFail.write()`) — confirm the exact set with
   `grep -rn 'JSONEncoder()' YardKit/Sources/`.
3. `SchemaEmitter.renderSchema` already uses `.sortedKeys` deliberately, so sorted output is the
   established convention in this package rather than a new one.
4. `#0114` is in flight against `CommandLineRunner.swift` and `Envelope.swift`. **Sequence after it**
   and merge `main` first.

## Expected behavior

- [ ] Every `JSONEncoder` that produces CLI output uses `.sortedKeys`.
- [ ] Key order is identical across runs, and alphabetical: `ok`, `result`, `schemaVersion`.
- [ ] No other change to the output — the same keys with the same values.
- [ ] Tests use **swift-testing** — `import Testing`, `@Test`, `#expect`. Not XCTest.
- [ ] Tests go in `YardKit/Tests/YardKitTests/`. `Tests/YardKit/` is not a declared target path and a
      file there is silently never compiled.
- [ ] **The test file is a deliverable**: `git diff --name-only` must list source *and* test files.
- [ ] `cd YardKit && swift test` prints a `Test run with N tests` line you paste. **`main` reported 276 on 2026-08-07.** Paste the branch's own pre-change baseline too; N must exceed it.

## Tests must be able to fail

**Run the binary more than once in the test and compare.** A single invocation cannot detect
nondeterminism — it produces one order and agrees with itself.

Call `runYard(arguments:)` twenty times and assert every `stdout` is byte-identical to the first. Do
the same for the failure envelope (`runYard(["bogus"])`). Before the change this fails within a few
iterations; after it, never.

**Mutation**: remove `.sortedKeys` from one encoder and confirm the corresponding test fails. Note
that it may take several runs to trip — if it passes once, run it again rather than concluding the
mutation survived, and say how many iterations you used.

Also assert the exact expected order once, so a future change from `.sortedKeys` to something else is
caught rather than merely tolerated.

The production change is six lines and was right immediately. **The tests shipped the exact defect the
issue was about.**

Two of them were written as *mutation tests*: they constructed a local `JSONEncoder` **without**
`.sortedKeys` and asserted its output was **not** alphabetical. Random order lands on alphabetical
roughly one time in six, so they failed 8 of 12 runs — and they touched no production code, so they
would have passed unchanged if `.sortedKeys` were deleted from both real sites. Flaky and inert at
once. The full suite failed **5 of 6** consecutive runs.

**That is this issue's fault, and the wording is now fixed everywhere.** "**Mutation**: remove
`.sortedKeys` and confirm the test fails" reads, to a model, as an instruction to *write a test that
does that*. It means the **reviewer** performs it on production source. `AGENTS.md` now says so
explicitly.

The replacement assertion compares the whole envelope string byte for byte. Comparing
`Array(json.keys).sorted()` to an alphabetical list is a tautology — `sorted()` guarantees it whatever
the encoder produced. The byte comparison catches drift on the **first** run, with no loop and no
chance of a lucky pass. Performed against production source, the real mutation now fails it **5 times
out of 5**, where the round's own versions managed 8/10 and 2/10.

The twenty-iteration loops stay but are a weak second line: `runYard` is in-process, so all twenty
share one process and one `JSONEncoder` seeding. They detected the defect only 2 times in 10. The
exact assertion is the real detector.

Six `range(of:)!` force-unwraps and an `as!` became `try #require`, consistent with #0114.
