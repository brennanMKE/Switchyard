CLAUDE.md.** The binding design below is settled; the pass writes the code and measures it.

## The design — bound by #0044 decision 4 and #0168's decisions

- **Why verbatim application corrupts (measured, #0044):** `for-each-ref` lists the *capture
  worktree's* `refs/worktree/*` and `refs/rewritten/*` under plain names, so worktree A's
  snapshot applied verbatim from worktree B (a) writes A's private refs into **B's** namespace
  and (b) deletes B's own private refs as "extras" — `RefSnapshot.restore` plans deletions from
  the same listing rules as capture, which in B's context enumerates B's private refs.
- **The resolution is filter-and-preserve, not refuse.** #0044 offered either; refusal would
  make the recovery story impossible — a dead agent worktree's entry (recorded worktree pruned,
  #0168's gate says "no longer exists") restored from the main worktree is exactly the case the
  override exists for. Under the override, build the **applied snapshot** as: the recorded
  snapshot's entries whose names are NOT `WorktreeContext.isPerWorktree`, **plus the caller's
  current per-worktree entries** (from #0168 step 3's single capture — they land in the `wanted`
  set, so deletion planning leaves them alone and their updates are no-ops), with the recorded
  `HEAD` applying to the caller — documented, not hidden (#0034 decision 5).
- **The guard stays coherent under the override for free.** #0168 decision 1 made the guard's
  reference the *caller's own* scoped cursor entry — always recorded in the calling worktree —
  so no cross-worktree comparison ever happens; #0044 decision 3's incoherence cannot arise.
- **The gate honors the override in both liveness states**: a live recorded worktree and a
  pruned one both restore under `allowDifferentWorktree: true`; without it, #0168's typed
  refusals stand unchanged.
- **Disturbance and object checks run on the applied snapshot**, not the recorded one — the
  applied one is what `update-ref` will see.

## Partial — 2026-08-09. The filter landed; the override did not.

**Done and merged:** `RefSnapshot.withoutPerWorktreeRefs`, plus the measurement it rests on.
`for-each-ref` lists `refs/worktree/*` and `refs/bisect/*` **only in the worktree that owns them**,
under plain names — verified against a real sibling worktree — so a snapshot is a per-worktree
artifact and applying one elsewhere would both plant those refs and delete the target's own as
"extras". Three mutations red: neutering the filter, a blunt `refs/` strip that would take every
branch with it, and forgetting `refs/rewritten`. 825 → 829.

**Not done: the `allowDifferentWorktree` parameter on `JournalRestore.restore`.** I stopped short
deliberately rather than half-landing it.

The override is not a parameter plus a filter call. #0044 decision 4 and #0168's ordering make it a
behavioural change to the restore flow:

- the worktree gate currently **throws** `differentWorktree` before anything else; under the
  override it must instead proceed and the `Report` must say what was skipped and why;
- `WorktreeDisturbance` must still run on the applied snapshot **regardless** of the override —
  that check answers a question the guard cannot, and bypassing it is how a sibling's checked-out
  branch gets clobbered silently (`update-ref` does that at exit 0);
- the cross-tool guard's reference snapshot is the **cursor's**, not the target's (#0168 decision
  1), and whether that reasoning still holds across worktrees has not been established.

That last point is the reason to stop: it is a design question, not typing. Doing it half-right
would produce a flag that looks safe and is not — and the whole point of this issue is that the
plumbing underneath it fails silently.
