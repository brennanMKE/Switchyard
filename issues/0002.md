## Description

Commit signing is the thing GitUp never implemented and one of Switchyard's reasons to exist, so it
has to be proven before any other code is written. This is a spike, not the real implementation.

libgit2 does not produce signatures — it only attaches them. The shape is
`git_commit_create_buffer` to build the commit content, sign that buffer externally, then
`git_commit_create_with_signature` to write it with the signature in the `gpgsig` header. Git stores
SSH signatures under that same header. Signing itself shells out to `ssh-keygen -Y sign -f <key> -n git`.

## Expected behavior

- [ ] A commit created this way is reported as verified by `git log --show-signature`.
- [ ] The same commit is reported as verified by GitHub after being pushed to a scratch repo.
- [ ] `ssh-keygen -Y verify` round-trips against a throwaway key generated in a temp directory.
- [ ] Finding recorded in `docs/engine-findings.md`.

## Notes

Guide §5 "Signing implementation". **If this fails, stop and escalate** — the project's premise
depends on it.

Use a throwaway key in a temp dir, never a real signing key. Do not touch the user's git config;
set `user.signingKey` and `gpg.format` on the scratch repo only.

## Notes

**Round 1 (2026-08-06): everything verifiable locally passes. One criterion is blocked on Brennan.**

The mechanism works end to end: `git_commit_create_buffer` → `ssh-keygen -Y sign -f <key> -n git` →
`git_commit_create_with_signature` under header `gpgsig`. Verified with a throwaway ed25519 key and
repo in a temp dir — `git log --show-signature` reports
`Good "git" signature for spike@test with ED25519 key SHA256:DYZTl5JaDhb…`, `ssh-keygen -Y verify`
round-trips, and the commit object carries the `gpgsig` header.

**Outstanding:** the GitHub-verification criterion needs a push to a scratch repository under
Brennan's account with an SSH signing key registered there. That is an outward action on his
account, so it was not attempted.

Three findings already captured in `docs/engine-findings.md` for #0036 and #0019:
`gpg.ssh.allowedSignersFile` is required or git calls a valid signature untrusted (making `verify` a
three-state answer); `create_with_signature` writes the object but updates no ref, so the ref move
is the journal's concern; and SSH signatures share the `gpgsig` header with GPG, so format detection
is by content.

This does not block M1 — the local result establishes the mechanism, and GitHub's check is a policy
check on key registration rather than a property of the commit we produce.

## Handoff — the GitHub step, for Brennan

Everything else in this issue passes. The only outstanding criterion is *"the same commit is reported
as verified by GitHub after being pushed"*, and it cannot be done for you: registering an SSH signing
key and pushing to a repository are actions on your account, which `CLAUDE.md` makes a stop
condition. Nothing below creates, revokes or modifies a signing asset — an SSH signing key on GitHub
is an account setting, not a certificate.

**Recommended: use the SSH key you already have.** GitHub tracks authentication keys and signing keys
separately, so a key already registered for auth still has to be added again as a *signing* key. That
is a one-line settings change and creates no new key material.

### Step 1 — add your existing key as a signing key (browser, ~30 seconds)

1. Print your public key: `cat ~/.ssh/id_ed25519.pub` (substitute your key's filename if different).
2. Go to **github.com → Settings → SSH and GPG keys → New SSH key**.
3. Set **Key type** to **Signing Key** — this is the part that matters; the default is Authentication.
4. Paste the public key, give it a title, and save.

### Step 2 — produce a signed commit and push it

Run this as one block. It creates a scratch repo under `/tmp`, configures signing **on that repo
only**, and never touches your global git config:

```sh
KEY=~/.ssh/id_ed25519            # adjust if your key has a different name
D=$(mktemp -d) && cd "$D" && git init -q .
git config user.name  "$(git config --global user.name)"
git config user.email "$(git config --global user.email)"
git config gpg.format ssh
git config user.signingKey "$KEY"
git config commit.gpgsign true
echo "signing check" > README.md && git add README.md
git commit -q -S -m "Verify SSH commit signing end to end"
git log --show-signature -1 | head -5
echo "--- scratch repo is at: $D"
```

You should see `Good "git" signature`. If it says the signature is *untrusted* rather than bad, that
is expected locally without `gpg.ssh.allowedSignersFile` — it does not affect what GitHub reports.

### Step 3 — push it somewhere GitHub can see it

Either push this scratch repo to a new private throwaway repository, **or** simply make one signed
commit on a branch of this repository and push that — a branch here is fine and avoids creating a
repo you then have to delete.

### Why this is worth the five minutes

Guide §5 makes signed commits carrying provenance trailers a differentiator — *"a signed commit
carrying provenance trailers is a meaningfully stronger claim than an unsigned one"*. The local
evidence proves git accepts our signatures. GitHub's badge is what proves the claim is legible to the
people the provenance is *for*, and that is the whole point of #0036 and #0064.

## Verified with Brennan's real key — 2026-08-07

He registered `~/.ssh/id_ed25519` on GitHub as a Signing Key. I then signed a commit with **that key**
in a throwaway repo (his global git config untouched — the scratch repo carried the signing settings
locally):

```
git cat-file -p HEAD | grep gpgsig          →  present
git log --show-signature -1                 →  Good "git" signature for offwhite@gmail.com
                                               with ED25519 key SHA256:NSSbIJ9ghfbmdsa8wOkq…
```

So the mechanism works with the production key, not merely with a throwaway one. Every locally
verifiable criterion now passes.

**It also reproduced the three-state finding** that `docs/engine-findings.md` records and that #0019
depends on. Before `gpg.ssh.allowedSignersFile` was set, the same commit reported:

```
error: gpg.ssh.allowedSignersFile needs to be configured and exist for ssh signature verification
…
No signature
```

The signature was valid the whole time; git simply had no basis to trust the key. **"No signature",
"signature present but the signer is not allowed", and "good signature" are three distinct states**,
and a `verify` command that reports two of them will mislabel the middle one.
