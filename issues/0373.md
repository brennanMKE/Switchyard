## Description

**Decision issue — no implementation.** Brennan, 2026-09-12: settle what "merged" and ahead/behind

### Why git's own answer does not fit

Both repositories land work by squash: Batty has 1 merge commit among the 1,182 reachable from
`HEAD`, and Switchyard has 0 (*measured*, #0358). A squash-landed branch's commits are never
ancestors of `main`, so `git branch --merged main` calls almost every landed branch unmerged.

### Measurements

Run 2026-09-12 with git 2.50.1 on Batty (`/Users/brennan/Developer/brennanMKE/Batty`) and on the
Switchyard primary checkout at `1cd8ba2`. Timings are one wall-clock run each on this machine, in
zsh with `EPOCHREALTIME`. "Per branch, all" is a shell loop running one git process per local branch.

| | Batty | Switchyard |
|---|---|---|
| local branches | 122 | 309 |
| with an upstream set | 2 | 123 |
| upstream reported `[gone]` | 0 | 0 |
| merged by **ancestry** (0 ahead of `main`, `main` itself included) | 4 | 11 |
| merged by **patch equivalence** (`git cherry main <b>` prints no `+` line; `main` excluded) | 4 | 228 |
| merged by **content** (`git merge-tree --write-tree main <b>` yields `main`'s tree; `main` excluded) | 18 | 91 |
| content check cannot answer (merge-tree reports a conflict) | 102 | 215 |
| cost: `for-each-ref --format='%(ahead-behind:main)'`, all branches, one process | 30 ms | 53 ms |
| cost: `for-each-ref --format='%(upstream:track)'`, all branches, one process | 16 ms | 23 ms |
| cost: `git cherry`, per branch, all | 6,069 ms | 40,216 ms |
| cost: `git merge-tree --write-tree`, per branch, all | 2,173 ms | 7,747 ms |

Sample `%(ahead-behind:main)` output (ahead, behind): Batty `issue-0392-cont 6 28`,
`issue/0145 0 144`; Switchyard `chore/work-logs 2 1547`, `issue-0153 16 914`.
`refs/remotes/origin/HEAD` exists in the Switchyard checkout, where `for-each-ref` reports it as a
commit.

### Candidate definitions — "merged"

| # | Definition | For | Against |
|---|---|---|---|
| M1 | **Ancestry** — the tip is reachable from the default branch | git's own meaning; one process, ~50 ms | false for nearly every squash-landed branch (4/122, 11/309) |
| M2 | **Patch equivalence** — every commit on the branch already exists on the default branch as an equal patch | catches squash-landed single-commit branches (228/309 here) | misses a multi-commit branch squashed into one commit (Batty: 4/122); 40 s here, so it needs a background pass or a cache |
| M3 | **Content** — merging the branch would change nothing | catches squash landings of any size | undecidable once the default branch has since touched the same lines (102/121 Batty), so it needs an "unknown" state; 7.7 s here |
| M4 | **Upstream gone** — the branch's upstream was deleted on the remote | cheap; matches a delete-branch-on-merge hosting workflow | says nothing without upstreams (2/122 Batty) or pruned fetches (0 `[gone]` in both) |
| M5 | **Show no merged state**; show staleness (ahead/behind, last commit date) instead | nothing to get wrong | drops the question #0358 asked |
| M6 | **Composite** — M1, else M4, else M3, computed in the background with "unknown" | the best coverage of these candidates | the most code, and three states for the user to read |

### Candidate definitions — ahead/behind

| # | Baseline | For | Against |
|---|---|---|---|
| A1 | the branch's **upstream** (`%(upstream:track)`) | git's meaning, and what `WhereAmI` already reports for `HEAD` | no answer for 120/122 Batty branches |
| A2 | the **default branch** (`%(ahead-behind:<default>)`) | always defined; one process | "ahead" never returns to 0 after a squash landing |
| A3 | upstream when set, otherwise the default branch, with the baseline named in the row | always defined, and git's meaning when it has one | two meanings in one column, so the row must say which |

### Also to decide

1. **Default branch source**: `refs/remotes/origin/HEAD`'s target, a per-repository setting, or the
   literal `main`.
2. **Cost budget**: sidebar-load cost only (M1, M4, A1–A3 are single-process, tens of ms) versus a
   background pass (M2, M3 run seconds to tens of seconds per repository).

### Planner's recommendation (non-binding)

**A3** for ahead/behind, and **M6** (ancestry, else upstream gone, else content, with "unknown") as
a background pass that fills the merged column after the sidebar appears. The default branch is
`origin/HEAD`'s target, falling back to `main`. Reason: the two measured workflows squash, so only
content comparison recognises their landed branches, and it is too slow to block the sidebar.
