## Description

Seven of the nine `YardGitTests` files parameterise over `FixtureRepository.RefFormat.supported()`.
Two do not:

| file | `refFormat` / `reftable` mentions |
|---|---|
| `WorktreeRemoveTests.swift` | **0** |
| `WorktreeStatusTests.swift` | **0** |
| every other test file | 3–14 |

Reftable becomes the default ref format for new repositories in Git 3.0, and CLAUDE.md is explicit
that anything reading `.git/refs/**` returns **nothing at all** on such a repository — not an error,
nothing. A test suite that only ever builds `--ref-format=files` repositories cannot notice.

## This is a coverage gap, not a bug — verified

Both functions were probed against a real reftable repository on 2026-08-07 and **both are correct**:

```
PROBE [reftable] status entries=1 paths=["u.txt"]
PROBE [files]    status entries=1 paths=["u.txt"]
PROBE [reftable] remove success=true before=2 after=1 exists=false
PROBE [files]    remove success=true before=2 after=1 exists=false
```

So this issue adds the parameterisation that keeps them correct. **Do not "fix" either
implementation** — a diff touching `Sources/` is a rejection.

## Givens — verified on `main`, treat as true

1. `FixtureRepository.RefFormat.supported()` returns `[.files]`, plus `.reftable` when the local git
   can create one. Local git is 2.50.1, which supports it — reftable arrived in 2.45.
2. `FixtureRepository.init(refFormat:)` takes the format. The established pattern is a parameterised
   test:

   ```swift
   @Test("…", arguments: FixtureRepository.RefFormat.supported())
   func something(format: FixtureRepository.RefFormat) throws {
       var repo = try FixtureRepository(refFormat: format)
       defer { repo.destroy() }
       …
   }
   ```

   **Copy this from `WhereAmITests.swift` or `CommitLogTests.swift`**, which already do it. Do not
   invent a different shape.
3. Both target files are `YardKit/Tests/YardGitTests/WorktreeRemoveTests.swift` and
   `YardKit/Tests/YardGitTests/WorktreeStatusTests.swift`.
4. A parameterised swift-testing `@Test` counts as **one** test in the summary line regardless of how
   many arguments it runs — verified. So the total may not move even though coverage doubles. Say so
   explicitly rather than reporting a flat count as a failure.

## Expected behavior

- [ ] Every `@Test` in both files is parameterised over `FixtureRepository.RefFormat.supported()` and
      builds its fixture with that format.
- [ ] `git diff -- YardKit/Sources/` is **empty**.
- [ ] `cd YardKit && swift build` succeeds and `swift test` passes. Paste the `Test run with N tests`
      line. **`main` reported 276 on 2026-08-07.** Paste the branch's own pre-change baseline too.
      **The count may be unchanged and that is not a failure here** — see Given 4: a parameterised
      `@Test` counts as one regardless of how many arguments it runs. What must change is that each
      test now executes twice, which is proved by the two checks under "Tests must be able to fail".
      What must change is that each test now runs twice.

## Tests must be able to fail

The count will not prove anything here, so prove it two other ways:

1. **Print the format inside one test** on a scratch run and paste the output showing both `files`
   and `reftable` appearing. Remove the print before finishing.
2. **Mutation**: change `RefFormat.supported()` to return `[.files]` only, re-run, and confirm the
   number of *test cases executed* drops — swift-testing reports this in its verbose output. Restore.

If neither of those can be made to show a difference, the parameterisation is not actually taking
effect and the round has not done its job.

**The reason it converged is that the issue named the trap up front.** A parameterised swift-testing
`@Test` counts as **one** test in the summary line regardless of how many arguments it runs, so the
usual "N must exceed the baseline" criterion could not apply. Stating that, and supplying two
substitute proofs, is what let the round know when it was done:

- both formats printed on a scratch run, in both files
- forcing `RefFormat.supported()` to `[.files]` drops executed cases **78 → 39**, halving all eight

Without those, the round would have had a green suite at an unchanged count and no way to tell success
from having done nothing — which is exactly the shape of #0095's and #0013's failures.

Three of `WorktreeStatusTests`' ten `@Test`s are parameterised, not all ten. That is correct: the
other seven call `WorktreeStatusParser().parse(Data)` on an in-memory buffer and never construct a
repository, so there is no fixture for a ref format to apply to. The reviewer confirmed by reading
them rather than by trusting the count.

`git diff -- YardKit/Sources/` is empty, as the issue required. Both implementations were probed
against a real reftable repository *before* the issue was written and were already correct — this
closed a coverage gap, and a round that "fixed" either would have been wrong.
