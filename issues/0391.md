### Measured refusals and outcomes (`git branch`)

git 2.50.1, 2026-09-12, scratch repository with a linked worktree.

| Situation | git's behaviour | This wrapper |
|---|---|---|
| create a name that exists | exit 128 `fatal: a branch named 'feature' already exists` | `.branchExists(name:)`, before mutation (`rev-parse --verify -q refs/heads/<name>`) |
| create an invalid name (`a b`) | exit 128 `fatal: 'a b' is not a valid branch name` | `.invalidName(name:)`, before mutation (`git check-ref-format --branch <name>`; full refusal table measured in #0363) |
| create at an unknown start point | exit 128 `fatal: not a valid object name: 'nosuch'` | `.unknownRevision(_:)`, before mutation |
| rename onto an existing name | exit 128 `fatal: a branch named 'main' already exists` | `.branchExists(name:)`, before mutation |
| rename the checked-out branch | exit 0; `HEAD` follows (`refs/heads/trunk`) | allowed |
| rename a branch **another worktree** has checked out | **exit 0, and git rewrites that worktree's `HEAD`** (`refs/heads/wtrenamed`) | `.checkedOutInOtherWorktree(name:path:)`, before mutation — see below |
| delete the checked-out branch | exit 1 `error: cannot delete branch 'main' used by worktree at '<path>'` | `.checkedOut(name:)`, before mutation |
| delete a branch another worktree has checked out | exit 1, the same message, **even with `-D`** | `.checkedOutInOtherWorktree(name:path:)`, before mutation |
| delete an unmerged branch with `-d` | exit 1 `error: the branch 'unmerged' is not fully merged` | `.notFullyMerged(name:)` unless `force: true` (`-D`, measured exit 0 `Deleted branch unmerged (was 29917e7).`) |
| delete a branch that does not exist | exit 1 `error: branch 'nosuch' not found` | `.unknownBranch(name:)`, before mutation |

**Why rename is also refused for a sibling's branch** (the coordinator asked for delete; this extends
it). git silently rewrites the sibling worktree's `HEAD`, and guide §11 decision 23 has a restore
leave a live sibling's held branch alone. So undo could not put the sibling back. Flagged as a
recommendation.

**Checked-out detection**: `worktreeList(path:git:)` → `[WorktreeEntry]`, where `branch` is already
the short name with `refs/heads/` stripped (verified in `YardKit/Sources/YardGit/WorktreeList.swift`),
and `path` identifies the worktree. The calling worktree is `WorktreeContext.topLevel`.

**git's "fully merged" is ancestry.** #0373 measured 4 of Batty's 122 branches as merged, because
work lands by squash, so `force: true` is the common path. #0363's UI decides force from its own
reachability, falling back on this refusal.

### Open question — undo of create and rename (decision needed, Brennan)

*Measured from source*: `RefSnapshot.restore` "writes back every ref the snapshot recorded" and
**does not delete refs it did not record**. That is guide §11 decision 20, and
`YardKit/Sources/YardGit/RefSnapshot.swift`'s doc says the same. A checkpoint taken before
`create` does not record the new branch, so **`undo` of a create leaves the branch**. `undo` of a
rename brings the old name back **and leaves the new one**. `undo` of a delete restores the branch
correctly. #0363's "every mutation is exactly undoable" therefore does not hold for create and
rename. Options:

1. **Accept and document** it: undo of a create or rename leaves the new ref.
2. **Record the refs this operation created** in its own journal entry, and let restore delete exactly
   those. This is a narrow exception to decision 20 — it still never deletes refs another actor
   created.
3. Leave create and rename out of the journal. That breaks the one-checkpoint rule.

**Recommendation: 2.** The same gap applies to #0392's tag create. Until it is decided, the test for
create/rename asserts today's behaviour and names this question.

### Surface — `YardKit/Sources/YardGit/Branches.swift` (new, *not compiled*)

```swift
public enum Branches {
    public struct Result: Sendable, Equatable, Encodable {
        public let name: String
        /// The commit the branch points at (after create/rename; before delete).
        public let oid: String
    }

    public static func create(name: String, startPoint: String = "HEAD", at path: String,
                              git: GitProcess = GitProcess(), extraEnvironment: [String: String] = [:]) throws -> Result
    public static func rename(from oldName: String, to newName: String, at path: String,
                              git: GitProcess = GitProcess(), extraEnvironment: [String: String] = [:]) throws -> Result
    public static func delete(name: String, force: Bool = false, at path: String,
                              git: GitProcess = GitProcess(), extraEnvironment: [String: String] = [:]) throws -> Result
}

public enum BranchError: Error, Equatable, Sendable, CustomStringConvertible {
    case invalidName(name: String)
    case branchExists(name: String)
    case unknownBranch(name: String)
    case unknownRevision(String)
    case checkedOut(name: String)
    case checkedOutInOtherWorktree(name: String, path: String)
    case notFullyMerged(name: String)
}
```

All `BranchError` cases map to `.repositoryError`. Each operation runs its `git branch` invocation
inside `JournalCheckpoint.around`, with operation names `branch-create`, `branch-rename` and
`branch-delete`. Every refusal except `.notFullyMerged` is checked before the checkpoint.
`.notFullyMerged` comes from git's `-d` (exit 1, message measured above), which is why `-d` runs
inside the checkpoint.

## Expected behavior

- [ ] `Branches.create`, `rename` and `delete` each run inside one journal checkpoint; `delete` is
      exactly undone by `JournalUndo.undo`, and create/rename undo behave as the open question's
      decision says (today: option 1, asserted).
- [ ] Every refusal in the table is typed. Those marked "before mutation" write no journal entry, and
      delete and rename refuse a branch checked out in this or another worktree.
- [ ] Tests live in `YardKit/Tests/YardGitTests/BranchesTests.swift` (with a linked-worktree fixture);
      `swift test` prints `Test run with N tests`.
