## Description

**Finding 4 of the M1 milestone review, eleventh pass, 2026-08-18.** `wt where` reports the **wrong
worktree name** when the repository's own path contains `worktrees/`, and nothing detects it.

`YardKit/Sources/YardGit/WorktreeContext.swift:103`, dropping `options: .backwards`: survived the **full
suite**.

**Measured against a real linked worktree under `…/worktrees/repo`:**

| search | resulting name |
|---|---|
| forward | `repo/.git/worktrees/wt1` |
| backward | `wt1` |

`worktreeName` reaches the wire at `WorktreeWhere.swift:74`, so this is **`wt where`'s output**, not an
internal detail. `grep backwards Tests/` returns **zero hits** — the `.backwards` exists precisely for
this case and nothing holds it there.

**A repository living under a directory called `worktrees` is not exotic**: anyone who keeps their
checkouts in `~/worktrees/` hits it.

## Expected behavior

- [ ] A named test asserting `worktreeName` for a linked worktree whose **repository path itself
      contains a `worktrees` component** — the fixture must place the repository under such a directory,
      not merely name the worktree that way.
- [ ] **Verify the fixture actually reproduces the ambiguity**: with a forward search the name would come
      back containing a `/`. Assert the clean name, and consider asserting it contains no `/` at all,
      which is the invariant.
- [ ] **Mutation:** drop `options: .backwards` at `WorktreeContext.swift:103`. The new test must redden.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, above the count in `docs/test-baseline.txt`.
