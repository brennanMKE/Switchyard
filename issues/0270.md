## Description

**Finding 3 of the M1 milestone review, fifth pass, 2026-08-18.** `verify`'s `signer` (`%GS`) and `key`
(`%GK`) are only ever asserted **`nil`** out of `SignatureVerification.run`, so the extraction of
`fields[1]`/`fields[2]` from the `\u{01}`-delimited line is untested.

```swift
// SignatureVerification.swift:90
["log", "-1", "--format=%G?", revision, "--"]
// was: ["log", "-1", "--format=%G?\u{01}%GS\u{01}%GK", revision, "--"]
```

Full suite: **no** `SignatureVerificationTests`, `SigningWireTests` or `CommitCreate*` test failed.

**What is pinned, and why it is not enough.** The pure mapping is covered —
`SignatureVerificationTests.swift:150-157` feeds `parse` populated strings — and
`SigningWireTests.swift:84-90` pins the encoding of a hand-built value, its own docstring calling itself
*"HAND-BUILT, the one non-run fixture in this file"*. But nothing runs `run` against a commit where git
reports a signer or a key. The only `run`-derived assertions are `result.signer == nil` /
`result.key == nil` (`SignatureVerificationTests.swift:49-50`).

**The existing comment claiming this needs a real signing key is wrong, and that was measured.** A fake
`gpg.program` suffices, and this project already installs one — `installFakeGpg` in
`CommitCreateGPGTests`. Measured, git 2.50.1, against a crafted `gpgsig` commit:

```sh
# fakegpg -- git invokes it as: --keyid-format=long --status-fd=1 --verify <tmp> -
#!/bin/sh
echo "[GNUPG:] NEWSIG"
echo "[GNUPG:] GOODSIG DEADBEEFCAFE1234 Fixture <f@example.invalid>"
echo "[GNUPG:] VALIDSIG ABCDEF0123456789ABCDEF0123456789ABCDEF01 2026-01-01 1700000000 0 4 0 1 8 00 ABCDEF0123456789ABCDEF0123456789ABCDEF01"
echo "[GNUPG:] TRUST_ULTIMATE 0 pgp"
exit 0
```

```
$ git -c gpg.program=./fakegpg log -1 --format='FLAG=[%G?] SIGNER=[%GS] KEY=[%GK]' <sha> --
FLAG=[G] SIGNER=[Fixture <f@example.invalid>] KEY=[DEADBEEFCAFE1234]
```

No key material, no keyring, no network.
