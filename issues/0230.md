## Description

**Filed by the third #0044 umbrella review, 2026-08-17.** #0044 decision 3 says, verbatim:

> the worktree gate (its step 2) must run before the guard (its step 4). #0168's current step order is
> correct and may not be reordered.

**Nothing pins it.** Measured in a clean-room `git archive HEAD` copy: moving the whole step-2 gate
block (`guard metadata.worktree.name == context.worktreeName || allowDifferentWorktree else { … }`)
from before step 3 to immediately before step 5 leaves the suite entirely green —

```
✔ Test run with 1002 tests in 76 suites passed after 51.108 seconds.
```

This is the **third** review to notice it. The first recorded it inside decision 3's own text ("no test
pins the order") and deferred it; it is the same defect class as #0203 and #0210, both of which were
filed and fixed. A stated criterion with no test is a finding.

## Why the order is load-bearing

Decision 3's reason is **error quality**, not safety: a cross-worktree attempt must report
`JournalRestore.Error.differentWorktree` — which names both worktrees and whether the recorded one
still exists — rather than a `CrossToolGuard.Error.repositoryChanged` divergence list the caller
cannot act on.

The two existing gate tests survive the reorder because both run from the **main** worktree with an
empty scoped chain, so the cursor is nil and the guard is skipped either way. Their names claim more
than they assert, which is why the reorder is invisible.
