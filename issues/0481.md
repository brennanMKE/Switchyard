## Description

#0475 fixed `HunkParser`, which split git output on the Character `"\n"`. Swift treats `"\r\n"` as
a single grapheme cluster, so a CRLF file's lines merged into one and swallowed later files. The
#0474 planner noted that `Blame.swift` may have the same bug; it was not measured. A line whose
first scalar is a combining mark would also be misread by `line.first`.

**This is an umbrella.** The audit is below, and each affected parser is its own child with the
literal edit, a test, and the measured before and after. It resolves when every child resolves.

### The two failure shapes, measured with `swift` 6 on 2026-09-29

1. **CRLF.** `"a\r\nb\r\n".split(separator: "\n").count == 1`. Grapheme rule GB3 joins CR+LF, so a
   `"\n"` Character never matches inside a CRLF line. Only a CR **immediately before** an LF
   matters. A CR anywhere else, or any other control character, splits correctly.
2. **Combining mark after a non-control character.** `"+\u{301}x".first == "+"` is false,
   `"+\u{301}x".hasPrefix("+")` is false, and `"summary \u{301}x".hasPrefix("summary ")` is false.
   `"a \u{301}b".split(separator: " ").count == 1`. The mark joins whatever **printable**
   character sits before it: a diff marker, or a space separator. It never joins a control
   character (GB4/GB5): `"\t\u{301}x".hasPrefix("\t")` is true, and splitting on `"\u{0}"` or
   `"\u{01}"` is always safe.

**The fix, in every child:** split and match on `unicodeScalars`, not on Characters. Each line keeps
its trailing `"\r"`, as #0475 does.

### Where CR-before-LF can reach a parser at all

Measured with git 2.54.0:

- **File content can.** It reaches `diff`, `blame`, `range-diff` bodies and conflict sides.
- **Commit messages can**, when made with `--cleanup=verbatim` or `commit-tree`, or imported. The
  default `strip` cleanup removes the CR.
- **Paths without `-z` cannot.** git C-quotes control characters whatever `core.quotePath` says.
- **Ref names cannot.** `check-ref-format` forbids control characters.
- **Reflog and stash subjects cannot.** git folds whitespace in a reflog message.
- **Oids, counts and dates cannot.**

## The audit — every Character-split or Character-prefix parser of git output in `YardKit/Sources`

Found with `grep -rnE 'split\(separator: "\\n"|\.lines|\.first|hasPrefix|split\(separator: " "'`
over `YardKit/Sources` on `main` at `b39dd314`. Each affected parser was reproduced with a failing
test in the planning worktree `../sy-plan-0481` before it was changed.

### Affected, but not planned to the code here: #0488

These files are being written or changed by the line-staging issues #0476–#0480 right now, so an
edit planned against today's `main` would conflict. They are filed as **#0488**, to be planned after
#0476 and #0479 merge.

- `YardGit/LineStaging.swift` (#0476, new). Its planned code reads `hunk.body[index].first` and
  `raw.first` as the marker. That is shape 2: a `+\u{301}x` line would not be selectable or
  stageable.
- `YardUI/DiffLineSelection.swift` (#0479, new). It uses `hunk.body[line].first`. Same shape.
- `YardUI/FileDiffView.swift:107`, `DiffLineView.marker` is `line.first`. Same shape, but it only
  changes the tint of a line.
- `YardUI/SplitCommitSheet.swift:181`, the preview filter `hasPrefix("+")`. Same shape, but it only
  affects the preview.

### Not affected, and why

| parser | why it is safe |
|---|---|
| `GitProcess.Output.lines` (`GitProcess.swift:84`) | Every caller reads oids, ref names, `true`/`false`, remote names or `notes list` pairs. None can hold CR-before-LF (see above). Changing it would change no test. |
| `CommitLog.parse(output:)` record and field splits | They split on `"\u{0}"` and `"\u{01}"`, which are control characters and never join a cluster. |
| `BranchStatus.parse`, `BranchTipDates.parse`, `JournalObserved.list`, `JournalRebuild`, `JournalRestore`, `JournalCheckpoint`, `ReviewNotes.list` | `for-each-ref` / `ls-tree` / `notes list` output. Ref names, oids and dates only. The tab splits are split on a control character. |
| `RevListParser.parse` (`LaneAssignment.swift:154`) | `rev-list --parents` prints oids only. |
| `RefSnapshotSerialization.init(serialized:)` | Switchyard's own format of ref names and oids. |
| `WhereAmI` counts (`stash list`, `ls-files -o`, `diff-index --name-status`) | Paths without `-z` are C-quoted, and stash subjects are whitespace-folded. The `-z` counts go through `countNULSeparatedPaths` on bytes. |
| `RerereForget`, `WorktreePrune`, `WorktreeRepair`, `classifyWorktreeAddFailure`, `RemoteOperations` (YardUI) | These read stderr prose. Each matched line ends in fixed text or a closing quote, never in a CR from user data. |
| `SignatureVerification.detectFormat` | It reads the commit header block, which git writes LF-only. The `"\n\n"` cut is Foundation's `components(separatedBy:)`, which is not Character-based. |
| `RerereResolution.lines(of:)` | It already splits on the byte `0x0A`. |
| `PostRewrite`, `WorktreeSnapshot`, `Rerere`, `WhereAmI.countNULSeparatedPaths` | They split `Data` on bytes. |
| `HunkParser.HunkBuilder.consumeCombined` (`@@@`) | It reads Characters, but #0342's conjunction in `wantsMoreBody` also needs a status-character marker. So an `@@@` header can never be swallowed, and a missed count has no visible effect. |
| `CommitChangesView` `FileChangeKind.of`, `CommitDetailView` trailer tail | They split header text or a message that `CommitLog` has already parsed. The header lines are git's, LF-only. The message tail only decides whether to hide the trailers a second time. |
