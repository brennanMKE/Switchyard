## Description

**Observed, not yet diagnosed — needs a planning pass before any dispatch.** Found while planning
#0555, on its large-history fixture (`scripts/uitest-fixtures/make-large-history-fixture.sh`, in
#0555: 6,002 commits, 1,000 tags; History loads the newest 5,000, `large-main`'s commits 5999-5991
and everything below 5990 fold).

What the planning VM runs showed (debug build, guest, `-uiTestRealSurfaces`), in both a baseline
over `main` at `1def86dc` and with #0552-#0554 applied — so it is not caused by that work:

1. **⌘G.** Type `rel-5994` in the filter → the match bar says "1 match" (the commit is
   `large commit 5994`, inside a fold that typing opens) → `app.typeKey("g", modifierFlags:
   .command)` → the Detail pane never showed `large commit 5994` within 30 s (two runs). Clicking
   that row right after selected it at once. In one run where `needle` (20 matches) had been typed
   first and then replaced by `rel-5994`, ⌘G left **`large commit 5875` — the first `needle`
   match — selected**, which suggests the shortcut stepped through a stale match list. #0402's
   spike makes the same ⌘G step on the small fixture and passes.
2. **↓/↑.** After clicking the `large commit 5994` row (selected, headline shown), `app.typeKey(
   .downArrow, modifierFlags: [])` did not select `large commit 5993` within 30 s. No existing spike
   presses an unmodified arrow, so it is unknown whether this is specific to the large fixture or
   to how the row click leaves keyboard focus (the filter field had focus before the click).

Hypotheses for the planning pass (none verified): the match bar's `.keyboardShortcut("g")` Button
keeps an action closure from an earlier `body` (`CommitHistoryView.matchBar`/`step`); `step`'s
`focus` opening a fold changes the layout under the selection; clicking a node's invisible target
does not make the map (`BranchMapView`'s `.focusable()` scroll view) first responder, so the arrows
go to the search field.

**Assumed meanwhile:** #0555's spike does not drive ⌘G or the arrows, and #0551's work goes ahead —
this is not a performance defect.
