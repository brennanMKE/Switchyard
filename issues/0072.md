## Description

Open question in guide §11: how much uncommitted worktree state to snapshot, and what `undo`
promises when it did not capture everything.

Refs and index are cheap. Worktree state is not always cheap. The reasonable default is to snapshot
the worktree only for operations that would disturb it, and to record in `captured` which parts were
taken — but "reasonable default" is not a decision, and `undo` making a promise it cannot keep is
the worst outcome available.

## Expected behavior

- [ ] Policy written down: what is captured, for which operations, and why.
- [ ] The size threshold or heuristic (if any) is specified, not left to implementation taste.
- [ ] What `undo` reports when capture was partial is specified exactly.
- [ ] Guide §11 updated to settled and §7 updated to match.

## Notes

Guide §11 open question 2, git internals §3. Should be settled before #0027 is implemented.

## Fix

`docs/journal-capture-policy.md` settles it: **capture everything, always, except ignored files**,
with the entry recording what was taken so `undo` reports honestly instead of implying fidelity it
never had. Guide §11 moves this from open to settled.

The asymmetry decides it — over-capturing costs objects `gc` later reclaims; under-capturing costs
the user's uncommitted work. "Snapshot only when the operation would disturb the worktree" was
rejected because it is a *prediction*, and a rebase that was expected to replay cleanly touches the
worktree the moment it conflicts.

Excluding ignored files is what makes "always" affordable: cost is bounded by changed tracked files
plus untracked non-ignored files, not by the size of `node_modules`.

## Verification

Empirically established on git 2.50.1, in a throwaway repo with one tracked modification and one
untracked file:

| Command | Parents | Untracked captured |
|---|---|---|
| `git stash create --include-untracked` | 2 | **no** |
| `git stash create -u` | 2 | **no** |
| `git stash push -u` | 3 | yes |

Also confirmed that ignored files are excluded from `stash create` output entirely.

## Gotchas

**The design doc was wrong, and dangerously so.** It stated that `git stash create
--include-untracked` "produces a commit object holding everything uncommitted". It does not —
`stash create` silently ignores the flag. Had #0027 been implemented against that sentence, every
journal entry would have claimed to capture the worktree while dropping every untracked file, and an
agent's newly written not-yet-added source file is exactly an untracked file. The doc now carries the
correction inline, and #0027 requires a round-trip test for an untracked file specifically.
