## Description

**Child of #0160, split 2026-08-17.** The other half of rewrite persistence: when the rewrite was
`switchyard`'s **own** (`Decision.isOwnInvocation == true`), the mapping attaches to the **in-flight
journal entry** for the operation that ran it, rather than becoming an observed entry (#0220).

This is why #0043 routes rather than skips: for `switchyard`'s own rebases the `post-rewrite` hook is
the **only** source of the old→new mapping. Nothing else sees it.

## The mechanism, and it already exists

#0160's note said identifying the in-flight entry from inside a hook is "a real mechanism to design".
It is smaller than that, because of the order the checkpoint runs in:

`JournalCheckpoint.around(operation:at:command:agent:git:_:)` writes the entry **first** and then runs
the body (`JournalCheckpoint.swift`, the `around` implementation — read it). So the entry's id exists
before any git subprocess starts, and `JournalCheckpoint.checkpoint` returns it.

So: **`around` exports the id to its body's git invocations through the environment**, and the hook arm
reads it back. `GitProcess.environment(adding:)` is already the single place environment is assembled,
and the hook already relies on an environment marker to recognise its own transactions — that marker is
the precedent, and this is a second variable beside it, not a new mechanism.

Name it explicitly rather than reusing the own-invocation marker: the marker answers "is this ours",
this answers "which entry". Both are needed and conflating them would make an entry-less own operation
indistinguishable from a foreign one.

**Read the existing marker's name and plumbing before writing anything** — `GitProcess.swift` and
`ReferenceTransaction`'s own-invocation check — and use the same spelling convention. State what you
found.

## The mechanism, measured — 2026-08-17

**The existing marker**, read from source rather than remembered:

```swift
// GitProcess.swift:18
public static let markerVariable = "SWITCHYARD_YARD_INVOCATION"
// GitProcess.swift:196, inside environment(adding:)
env[markerVariable] = "1"
for (key, value) in extra { env[key] = value }   // extraEnvironment wins
```

So every invocation already carries "this is ours", and `extraEnvironment` is merged **after** it.
Name the new one **`SWITCHYARD_JOURNAL_ENTRY`**, beside it, carrying the entry id's `description`.
Two variables, not one: the marker answers *is this ours*, this answers *which entry*, and conflating
them makes an own operation that took no checkpoint indistinguishable from a foreign one.

**The part that needs a real decision, and here it is.** `JournalCheckpoint.around` currently takes a
`git: GitProcess` and calls `body()` with **no arguments** — so the body closes over whatever
`GitProcess` its caller already had, and `around` has no way to hand it a different one. Three ways
to export the id, and only one is safe:

- **Change `around`'s body to receive the git process** — `_ body: (GitProcess) throws -> T` — where
  `around` constructs one carrying the entry id and passes it in. Call sites (`Staging.commitHunks`,
  `Fixup.run`, and whatever else uses `around`) use the parameter instead of the captured value.
  **Do this one.** It is explicit, it scopes the id to exactly the body, and it is a compile error at
  every call site that forgets — which is the property that matters.
- Threading `extraEnvironment` through every call inside every body: same effect, far more edits, and
  silent when one is missed.
- `setenv` around the body: process-global mutable state in a suite that runs seventy suites in
  parallel. **Do not.** It would leak the id into unrelated concurrent git invocations, and the
  resulting test failures would be non-deterministic.

`GitProcess` gains the id as an initialiser parameter defaulting to `nil`, merged into the environment
next to the marker. Keep it a stored property rather than a mutating setter — `GitProcess` is a
`Sendable` struct and should stay one.

  the git invocations its body runs.

## Expected behavior

- [ ] `JournalCheckpoint.around` makes the in-flight entry id visible to git subprocesses it runs, and
      only for the duration of the body.
- [ ] A `Decision` with `isOwnInvocation == true` and a readable entry id attaches its ordered mapping
      to **that** entry's metadata. No observed entry is created — #0220 asserts the same boundary from
      its side.
- [ ] An own invocation with **no** entry id in the environment (an operation that took no checkpoint)
      does something stated and tested — the honest options are "record nothing" and "fall back to an
      observed entry". Pick one, say why, and test it. Silently losing the mapping is not acceptable;
      neither is inventing an entry.
- [ ] Attaching must not rewrite the entry's other fields. The metadata is already written; this adds a
      field to it. Say how the existing anchor contents are preserved — the id, the snapshot commit and
      the guard refs must come back byte-identical, and a test must assert that.
- [ ] The totality invariant holds: a failed attach never produces a non-zero hook exit (#0043, #0191).
- [ ] `cd YardKit && swift test` prints `Test run with N tests` where **N is greater than** the count in
      `docs/test-baseline.txt` at dispatch (966 on 2026-08-17). State the delta.
- [ ] A test drives a **real** `switchyard`-run rewrite end to end, not a synthesised `Decision`: run an
      operation that rebases inside `JournalCheckpoint.around`, and assert the entry it wrote carries
      the mapping. `Fixup.run` (#0039) is exactly such an operation and is the natural fixture.

## What this issue does not decide

A **dropped** commit appears in no mapping line at all — measured, absence is the representation
(#0043). Naming drops explicitly needs the pre-rewrite commit set from the entry's snapshot, and that
comparison belongs to whoever consumes the mapping (#0064 `rewrite-diff`), not to the writer. Store the
mapping as git reported it.
