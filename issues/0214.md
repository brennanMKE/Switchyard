## Description

**Split out of #0039 on 2026-08-17.** #0039 fixes up the **staged index** into an ancestor commit. This
issue adds the other half of guide §6's `fixup`: take an **existing commit** — `HEAD` by default — and
squash it into an older ancestor.

Different mechanism, which is why it is a separate issue. #0039 creates the `fixup!` commit with
`git commit --fixup=<target>`, so git writes the subject. Here the commit already exists and must be
re-labelled: rewrite its message to `fixup! <target subject>` (or use `git commit --amend --fixup`, or
build the todo list directly), then autosquash. Only the autosquash step is shared.

## Expected behavior

- [ ] `Fixup.run(source:target:…)` where `source` defaults to `HEAD` and must be a descendant of `target`.
- [ ] Refuses when `source` is not a descendant of `target`, and when `source == target`.
- [ ] Refuses when the index is dirty — otherwise the staged changes are silently swept into the rebase.
      #0039's `.nothingStaged` guard is the mirror image of this one; state which error each is.
- [ ] The same conflict, signing, and checkpoint behaviour #0039 measured — reuse its code paths rather
      than a second copy.

### The mechanism, measured during this planning pass

```
$ git commit --amend --fixup=<target> --no-edit
[main dfcd979] fixup! c2
$ git log --format='%h %s' -2
dfcd979 fixup! c2
7fded85 c3
$ git rebase --autosquash <target>^      # exit 0
$ git show --stat --format='%s' HEAD~1
c2
 f2.txt | 1 +
 f4.txt | 1 +
```

So `git commit --amend --fixup=<target> --no-edit` **rewrites `HEAD`'s message in place** to
`fixup! <target's subject>` while keeping its content, and the ordinary autosquash then folds it. That
is the whole mechanism — no message parsing, no `commit-tree`, no todo-list construction.

`--no-edit` is required: without it git opens an editor. `GitProcess` pins `GIT_EDITOR=false`, so
omitting it would fail rather than hang, but pass it anyway and say why.

### The refusal that has to exist, and here is the measurement that proves it

```
$ printf "y\n" > extra.txt && git add extra.txt
$ git commit --amend --fixup=HEAD~1 --no-edit    # exit 0
$ git show --stat --format='%s' HEAD
fixup! c2
 extra.txt | 1 +
 f3.txt    | 1 +
```

**A dirty index is silently swept into the amended commit.** `extra.txt` was never meant to be part
of it. So the "refuses when the index is dirty" criterion is not defensive tidiness — without it this
command silently commits staged work the caller did not offer. Refuse with a **new** case:

```swift
case indexNotClean(paths: [String])   // -> ExitClass.repositoryError
```

mirroring `CommitHunksError.indexNotClean(paths:)` in `Staging.swift`, which exists for the same
reason. Read `git diff --cached --name-only` exactly as `commitHunks` and `Fixup.run` already do.

**This is the mirror image of #0039's `.nothingStaged`**, and the issue asks you to say which is
which: `Fixup.run` fixes up **the index** and so requires it non-empty; this mode fixes up **a
commit** and so requires it empty. State that in the doc comment — the pair is confusing precisely
because the two errors look like the same check with the sense flipped.

### The API

```swift
extension Fixup {
    /// Squashes an existing commit into an older ancestor.
    ///
    /// - Parameter source: the commit to fold in. Defaults to `HEAD`; only
    ///   `HEAD` is supported in this issue — folding a commit that is not the
    ///   tip needs an interactive todo list and is a different mechanism.
    public static func run(
        source: String = "HEAD",
        target: String,
        signing: CommitCreate.Signing = .config,
        at path: String,
        git: GitProcess = GitProcess(),
        extraEnvironment: [String: String] = [:]
    ) throws -> Fixup
}
```

**Only `source == HEAD` in this issue.** Say so in the doc comment and throw for anything else rather
than silently doing something else — a non-tip source needs a todo list built by hand, which is #0062
and #0063's territory. If that makes the `source` parameter look premature, keep it anyway: it names
the concept the caller is asking for and makes the refusal explicit.

Guards, in order: `source` resolves; `target` is an ancestor of `source` (`merge-base --is-ancestor`,
read with `capture`, exit 0 means ancestor — measured in #0039); `source != target`; the index is
clean. Then `git commit --amend --fixup=<target> --no-edit` + `CommitCreate.arguments(for: signing)`,
then the **same** rebase step `Fixup.performFixup` already runs, including the `--root` probe and the
conflict-versus-signing classification. **Factor that step out and call it from both** rather than
copying it; a second copy of the classification is a second place for the exit codes to drift.

### Tests — `YardKit/Tests/YardGitTests/FixupTests.swift`, beside the existing seven

- **Happy path**: four commits on separate files, fold `HEAD` into `HEAD~2`; the target commit gains
  the source's file, the log is one shorter, no `fixup!` subject survives.
- **Dirty index refused**: stage an unrelated file, expect `.indexNotClean(paths:)`, and assert
  `HEAD` is unchanged **and the staged file is still staged** — the failure must not consume it.
- **`source == target`** refused.
- **Non-descendant `source`** refused (a sibling branch's tip).
- **Undo**: `JournalUndo` returns `HEAD` and the branch tip to their pre-call oids, exactly as
  #0039's undo test does.
- **A conflict** leaves the rebase resumable and throws `.blockedOnConflicts` — reuse #0039's fixture
  shape, which conflicts because every commit rewrites the same line.

**Mutation to run and report:** delete the clean-index guard and confirm the dirty-index test goes
red. That is the one guard this issue exists for.
