## Description

Register the embedded launch agent as a login item so launchd owns the Mach service name.

**`SMAppService.status` can disagree with launchd.** Drive repair from an actually-failed broker
call, at most once per launch, and never from the reported status — a status-driven repair loop
was a real source of confusion in RemoteControl.

## Expected behavior

- [ ] Registers on first launch and surfaces the "Requires approval" state with a link to Login Items.
- [ ] Repair is triggered by a failed broker call, not by `status`, and runs at most once per launch.
- [ ] The absence of an approval prompt is treated as success, not as a missing step.
- [ ] UI shows Mach service name, login-item status, endpoint registration, and client count.

### Two files, and the split is about what `swift test` can reach

**`Switchyard/AgentRegistrar.swift`** (new, app target) — wraps
`SMAppService.agent(plistName: ServiceNames.agentPlistName)`. #0046 already embeds
`co.sstools.Switchyard.broker.plist` into `Contents/Library/LaunchAgents/`, and `plistName` is
resolved relative to that directory, so it is a bare filename and never a path.

**`YardKit/Sources/YardKit/RepairGate.swift`** (new, library target) — the once-per-launch rule,
extracted so it has tests. `SMAppService` itself cannot be exercised unattended: calling `register()`
in a test would enrol a real login item on this machine and outlive the run. **No test in this issue
may call `register()`, `unregister()`, or `repair()`.** The registrar is verified by building; the
rule that decides *whether* to repair is verified by tests.

```swift
/// Allows an action at most once for the lifetime of the process.
///
/// Repair is driven by an actually-failed broker call, never by
/// `SMAppService.status` — the two genuinely disagree after a `launchctl
/// bootout`, and a status-driven repair loop was a real source of confusion in
/// RemoteControl. A failed call is evidence; a status is an opinion.
public final class RepairGate: @unchecked Sendable {
    public init() {}
    /// True exactly once, however many times or from however many queues it is
    /// called. XPC error handlers fire on their own queues, so this is reached
    /// concurrently and the check must be atomic, not a plain `Bool` read.
    public func claim() -> Bool
    public var hasClaimed: Bool { get }
}
```

Back it with an `NSLock` (or `OSAllocatedUnfairLock`), matching `EndpointRegistry` in
`XPCProtocols.swift:56`, which chose a lock over an actor for exactly this reason and says why.

### Port from `../../RemoteControl/RemoteControl/AgentRegistrar.swift` — MIT, same author

Take `registerIfNeeded()`, `repair()`, `refreshStatus()`, `openLoginItemsSettings()`, and the
`SMAppService.Status.label` / `.isOperational` extension close to verbatim, with two substitutions:

- **`os.Logger`, not RemoteControl's `MessageLog`.** `Logger(subsystem: ServiceNames.logSubsystem,
  category: "agent")`, matching `AppXPCServer.swift:25`. Interpolate with `privacy: .public` for
  anything a human needs to read in `/usr/bin/log stream` — and note `log` is a zsh builtin, so the
  full path is required when checking by hand.
- **`ServiceNames.machServiceName`** wherever it reads `ServiceNames.broker`.

Keep the three behaviours whose comments explain a real trap, and keep the comments:

1. **`register()` throwing is not necessarily failure** — registering an already-registered service
   throws. Re-read the status and treat `.enabled` as success.
2. **`repair()` unregisters first, unconditionally**, and tolerates the unregister throwing. Without
   that, `registerIfNeeded()` short-circuits on a `.enabled` status that launchd does not share and
   the app can never repair itself.
3. **`.requiresApproval` is a first-class outcome, not an error** — surface it with the System
   Settings → General → Login Items & Extensions wording and the
   `SMAppService.openSystemSettingsLoginItems()` affordance.

### Wiring — this is criterion 2, and it is the substance of the issue

`AppDelegate.applicationDidFinishLaunching` calls `registerIfNeeded()` **before**
`server.registerWithBroker()`; launchd cannot own the Mach service name until the agent is registered.

`AppXPCServer` gains a `RepairGate` and a repair callback. In the broker connection's **error
handler** — the `@Sendable` closure at `AppXPCServer.swift:80`, which is where a *failed call* is
actually observed — claim the gate and, only if the claim succeeds, hop to the main actor and call
`repair()` followed by one more `registerWithBroker()`. Nothing may consult `service.status` to
decide this.

**"The absence of an approval prompt is treated as success."** macOS does not always prompt; a
registration that lands `.enabled` with no user interaction is the normal path on a machine that has
approved this bundle before. Do not add a wait-for-approval state, and do not block launch on it.

### Tests — `YardKit/Tests/YardKitTests/RepairGateTests.swift`

- One claim succeeds; the second and third return false; `hasClaimed` flips exactly once.
- **Concurrent claims yield exactly one winner.** Race a `TaskGroup` of ~100 claims and assert the
  count of `true` results is 1. This is the assertion that would fail against a plain `Bool`, which
  is the mistake the type exists to prevent — so it is the one that must not be skipped.
- A fresh gate is independent of another gate.

Three tests, one small type. That is deliberate: everything else in this issue is verified by the app
building and by #0054's manual script, and pretending otherwise would mean a test that calls
`SMAppService`.
