## Description

**Finding 3 of #0160's fourth umbrella review, 2026-08-17.** Three behaviours in `attachRewrite` that
nothing pins. Each was measured by deleting it and running the full suite green at 1044.

**1. The own/foreign seam is pinned on one side only.** Deleting
`guard decision.isOwnInvocation else { return nil }` from `attachRewrite` leaves **all 1044 tests
green**. Its mirror in `JournalObserved.record(_ decision:)` **is** pinned, by
`anOwnInvocationDecisionWritesNothing`.

Without a pin, a regression lets a **foreign** rewrite both attach to whatever entry the file names
**and** be recorded as observed — double-recorded, and a foreign mapping misattributed as ours. That is
precisely the distinction `Metadata.kind` exists to keep, and #0220's own boundary assertion is what
made it safe.

**2. Environment-wins precedence is unpinned.** Inverting `entryID ?? inFlightEntryID(...)` so the file
beats the environment leaves the suite green. The precedence is deliberate — a scoped `GitProcess`
means the operation is running *right now*; the file is the fallback for when it is not.

**3. Removing the file after a successful attach is unpinned.** Deleting the
`try? fileManager.removeItem(atPath: pendingPath)` leaves the suite green. A slot that outlives its
successful attach is exactly the stale-file hazard #0253 and #0254 are about.

## Expected behavior

- [ ] A test that reddens when the own-invocation guard is removed from `attachRewrite` — a **foreign**

- [ ] A test that reddens when the precedence is inverted: both an environment id and a file present,

- [ ] A test that reddens when the post-attach removal is dropped: after a successful attach the file
