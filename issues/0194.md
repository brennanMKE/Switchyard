## Description

**Filed by the M1 milestone review, 2026-08-17, against M1 exit criterion 4** — *"The response
schemas are documented and versioned (#0026)."*

#0026 shipped a real artifact: `YardKit/Schemas/README.md` with a versioning policy and
breaking-change rules, a generator, and `SchemaGoldenTests` with a four-way drift gate. What it does
not contain — and what the emitter has no field to express — is **any of the thirteen payload shapes
criteria 1 and 2 name**.

- `YardKit/Schemas/` holds exactly two files, `noop.json` and `switchyard.json`. Neither is an M1
  command.
- Every generated success shape is `"result": {"optional": true, "schema": "<schemaName>"}`
  (`SchemaEmitter.swift:64`) — a self-reference describing no field, no type, no enum.
- `CommandSpec` (`CommandSpec.swift:9-13`) carries `name`, `summary`, `flags`, `exitCodes` and
  `schemaName`. There is **no representation of a payload shape to emit**, so registering `whereami`
  in M3 would document its fifteen fields as `{"schema": "whereami"}`.

**The load-bearing part is the contradiction with the delivered artifact's own promise.**
`Schemas/README.md`'s "What `schemaVersion: 1` covers" lists *"Each command's result payload shape,
named by its `schemaName`"* as part of the version-1 guarantee, and its breaking-change rules turn on
*"removing or renaming any key an agent can currently read, in the envelope **or in a payload**"* —
rules over payload keys that no artifact records.

**No milestone currently owns the payload contract.** #0026 deferred it in its own text (*"the M1 read
commands arrive in the registry with M3's wiring"*), but that is #0026's claim, not a recorded
decision: guide §9 and §11 decision 11 moved only *CLI reachability* to M3, and M3's criterion asks
only that `schema` emit one file per command — which today's emitter satisfies while documenting
nothing.

The seventeen `YardWireTests` files do pin every payload byte-exactly, which is the substance. What is
missing is a **published, versioned artifact an agent can read**.

## Expected behavior — pick one of two, and record which

**(a) Make criterion 4 true as written.** `CommandSpec` gains a payload-shape field; the thirteen
shapes are expressed in it; the generated files carry real field lists; and the `YardWireTests`
literals are bound to the generated files so the two cannot drift. This is the larger change and it
needs its own planning pass.

**(b) Narrow the criterion, honestly.** Record a decision in guide §9/§11 that M1 criterion 4 covers
the **envelope frame only**, assign the payload contract to a **named M3 criterion**, and correct
`Schemas/README.md`'s two payload-key promises in the same change.

- [ ] One of (a) or (b) is chosen and the choice is recorded in guide §11, not just in this issue.
- [ ] If (b): `Schemas/README.md` no longer promises payload coverage it does not provide, and M3's
      checklist in guide §9 carries the payload criterion explicitly.
- [ ] If (a): `swift test` prints a `Test run with N tests` line exceeding the count in
      `docs/test-baseline.txt`, and the drift gate covers the new files.

**The review's own recommendation was (b)** — cheap and honest — with the note that *"the current

## The gap is now visible on a real command — 2026-08-17

```json

  "ok" : true,
  "result" : {
    "optional" : true,
    "schema" : "whereami"
  },
  "schemaVersion" : 1

```

**`WhereAmI` has fifteen fields and the schema names none of them.** `"schema": "whereami"` points at

shapes now has a real command to be measured against, and **(b)** narrowing M1 criterion 4 to the
envelope frame now has to say, in the guide, that the payload contract lands in whichever milestone
owns it — with twelve more commands about to generate twelve more files of exactly this shape.

## Decided — option (a), guide §11 decision 21. Planned 2026-08-17.

**Brennan picked (a): build the payload schemas.** Against the milestone review's own recommendation

has to catch up.

### The scope problem, and how this issue avoids being unbuildable

The criterion names **thirteen** payload shapes, but only three commands are in `CommandRegistry.all`
today — `switchyard`, `noop`, `whereami` — and a schema cannot be generated for a command that is not
registered. The other twelve arrive with their own wiring issues (#0225–#0228 and the rest of #0115's
table).

So this issue delivers **the mechanism and the first real shape**, and makes supplying a shape part of
what wiring a command means. It is one deliverable, not thirteen:

- `CommandSpec` gains a payload-shape field.
- `SchemaEmitter` renders it instead of the self-reference.
- `whereami` supplies a real one, and its generated file carries its fifteen fields.
- The `YardWireTests` literal for `WhereAmI` is **bound to the generated file**, so the two cannot
  drift.
- **#0115's per-command pattern gains a step**: a command lands with its payload shape or it does not
  land. Add it there, so #0225–#0228 pick it up.

### What the field looks like

Today, `SchemaEmitter.swift:64`:

```swift
"success": [
    "ok": true,
    "result": ["optional": true, "schema": schemaName],   // names the file it is already in
    "schemaVersion": EnvelopeSchema.v1.rawValue,
],
```

`CommandSpec` (`CommandSpec.swift:8-21`) carries `name`, `summary`, `flags`, `exitCodes`,
`schemaName` — and nothing that could hold a shape.

**Design it yourself, and state the choice in the type's doc comment.** The requirements, in priority
order:

1. It must express what an agent needs to read a payload without guessing: **field name, type,
   whether it is optional, and for an enum its cases**. `WhereAmI` exercises all four —
   `branch: String?`, `ahead: Int?`, `hasConflicts: Bool`, `headOID: String` (the **7-character short**
   form, which is exactly the kind of fact a schema cannot express and a description must).
2. **Absent means absent.** `Envelope` omits a nil `result` rather than emitting `null`, and
   `WhereAmI`'s optionals encode the same way — the schema has to say so, or an agent will expect
   `null`.
3. It must be **declarative data**, like the rest of `CommandSpec`: no behaviour, no reflection over
   `Mirror`, nothing that runs at emit time. A hand-written shape that drifts from the type is a real
   risk — which is what the binding in the next section is for.
4. Nested objects can wait. `WhereAmI` is flat. If a later command needs nesting, that is that
   command's issue; **say in the doc comment that it is not supported yet** rather than half-building
   it.

### The binding, which is the part that stops this rotting

A hand-written schema and a hand-written wire literal can drift from each other **and** from the type.
`YardWireTests` already pins `WhereAmI`'s encoded bytes. Bind the two: the wire test reads the
generated `whereami.json`, extracts the payload field names, and asserts they are **exactly** the keys
in the encoded JSON — no more, no fewer.

That single assertion is what makes the schema true rather than decorative, and it is the criterion's
real content. A mutation must prove it: **add a field to the schema that the type does not encode, and
confirm the wire test reddens.** Then remove a field from the schema and confirm it reddens the other
way.
