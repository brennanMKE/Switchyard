# 0354 — Broker launch-agent registration fails silently; the app never says why

| | |
|---|---|

## Description

Measured 2026-09-11 during the first real demo attempt: the app runs (Xcode Debug build), its
bundle is complete (`Contents/Library/LaunchAgents/co.sstools.Switchyard.broker.plist` present,
`BrokerAgent` binary present, all three identifiers matching `ServiceNames`), but **launchd has no
`co.sstools.Switchyard.broker` service** — `launchctl print gui/$(id -u)/co.sstools.Switchyard.broker`
returns "could not find service". Every CLI command therefore exits 3 (`app_unavailable`): the app
has no broker to register its endpoint with.

`AgentRegistrar.registerIfNeeded()` uses `SMAppService.agent(plistName:)` and logs status
transitions and failures at info/error under subsystem `co.sstools.Switchyard` — but the failure
never reaches the user: the transport pane showed nothing actionable, and the demo died at exit 3
with no diagnosis. Two suspected causes, both known SMAppService failure classes:

1. **Approval pending** — SMAppService agents can sit unapproved in System Settings → General →
   Login Items & Extensions until the user allows them.
2. **Ad-hoc signing rejection** — SMAppService is documented to reject ad-hoc/"Sign to Run Locally"
   builds in common configurations; a Debug build from Xcode may be exactly that.

**Batty ships the identical mechanism successfully** (`Embed Broker` build phase + SMAppService,
`docs/xpc/`), so the mechanism is proven on this machine — the difference to find is in what Batty
does around registration (diagnostics, status surfacing, or signing) that Switchyard does not.

## Expected behavior

- [ ] Registration either succeeds or surfaces a **typed, user-visible status** naming the failure
      (approval required / signing rejected / launchd error) — never a silent no-op.
- [ ] The transport pane (or the Settings surface, #0352) shows the broker's registration state
      and offers the repair action when it is not healthy.
- [ ] The failure is diagnosable from the app's own UI, not only from `log show`.
- [ ] A passing end-to-end check exists: app running → `launchctl print` shows the service →
      `switchyard ping` succeeds. Recorded in `scripts/verify-install.md`'s successor.

## Planning pass — 2026-09-11, to code level. One round.

**The Batty delta, found by reading its source** (`BattyKit/Sources/BattyKit/Settings/BrokerAgentController.swift`,
MIT — adapt with the notice retained): Batty wraps `SMAppService.agent` in a controller that (a)
maps `SMAppService.Status` through a **pure, tested four-state function** — `notRegistered`
(`.notRegistered`/`.notFound`), `requiresApproval`, `enabled`, `unknown` — (b) captures
`lastErrorDescription` on every failed `register()`/`unregister()` for the UI, and (c) treats
SMAppService status as **registration belief, never health**: `.enabled` has been observed while
launchd had no service (post-`bootout`), so only a round-trip ping may claim the broker is
reachable. Switchyard's `AgentRegistrar` logs status labels but surfaces none of this to the user —
which is exactly the 2026-09-11 demo failure.

**Round 1 — the state machine, the surfacing, the diagnosis:**
- `Switchyard/BrokerAgentController.swift` (NEW, adapted from Batty's, notice retained): the
  four-state mapping as a pure function over `SMAppService.Status` (all cases + `@unknown default`),
  the controller wrapper (`register`/`unregister`/`status`/`lastErrorDescription`), and the doc
  comment carrying Batty's measured warning: status is belief, ping is health.
- `Switchyard/AgentRegistrar.swift` (EDIT): route registration through the controller; on failure
  capture the error and publish the state instead of only logging it.
- `Switchyard/TransportStatusBridge.swift` + `YardKit/Sources/YardUI/TransportStatus.swift` (EDIT):
  the transport pane gains the registration state (`requiresApproval` → "approve in System
  Settings → Login Items & Extensions"; `notRegistered` + lastError → the error text + Repair) and
  its "reachable" claim comes from a real broker ping round-trip, never from SMAppService status.
- `SwitchyardTests/` (NEW file): the mapping table (every `SMAppService.Status` → state), the
  error-capture behavior, and the ping-gated health rule — swift-testing, no `@testable` if that
  target's rule requires it.
- **The diagnosis itself is user-visible after this round**: Brennan relaunches the app and the
  pane names the actual state. If `requiresApproval` → the System Settings path (his action). If
  register fails with a signing error → **Rule 2 hard stop**: report the exact error text, hand
  him the menu path, never touch signing settings.
- Manual scenario appended to `scripts/verify-install.md`'s successor set: launch → pane shows
  state → approve/repair → `launchctl print` shows the service → `switchyard ping` succeeds.
- **Verification**: `cd YardKit && swift test` — **N greater than 1710**; state the delta.
  `xcodebuild build … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` → `** BUILD SUCCEEDED **`.
