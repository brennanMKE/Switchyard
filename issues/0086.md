## Description

A pure function that turns a `CommandSpec` into help text. No I/O, no printing, no argument parsing —
it takes a spec and returns a `String`, which is what makes it testable.

## Expected behavior

- [ ] New file `YardKit/Sources/YardKit/HelpRenderer.swift`. Touch nothing else except its test file.
- [ ] `func renderHelp(for spec: CommandSpec) -> String` — pure, `nonisolated`, no side effects.
- [ ] Output includes the command name, the summary, every flag with its help text, and every exit code with its meaning.
- [ ] Flags render as `--long` or `-s, --long`, and `<argument>` is appended **to whichever of those
      two forms applies** when the flag takes one. These are two prefix forms plus an independent
      suffix, not three mutually exclusive cases. All four combinations must render correctly:
      `--verbose`, `-v, --verbose`, `--output <PATH>`, and `-o, --output <PATH>`.
- [ ] A test asserts the rendered text contains every flag long name and every exit code number from a hand-built spec.
- [ ] A test renders a flag that has **both** a short name and an argument — `FlagSpec(long: "output",
      short: "o", argument: "PATH", ...)` — and asserts the line contains `-o, --output <PATH>`.
      This exact shape is the canonical example in `CommandSpecTests.swift` from #0085.
- [ ] A test asserts rendering is deterministic — same spec in, identical string out, called twice.
- [ ] Tests use **swift-testing** — `import Testing`, `@Test`, `#expect`. Not XCTest. Every other
      test file in this package uses swift-testing, and `swift test`'s summary line counts only
      swift-testing tests.
- [ ] `cd YardKit && swift build` succeeds, and `swift test` prints a `Test run with N tests` line
      you paste. **N must be greater than 83**, the count on `main` before this change. If N is
      still 83, your tests are not in the run being counted.

## Notes

Split out of #0010. Blocked by #0085.

Return a `String`; do not print. A function that writes to stdout cannot be asserted against.

**Target placement:** `yard` is an `executableTarget`, so `@testable import yard` does **not** link in
SwiftPM — anything that needs unit tests must live in the `YardKit` library target. This was found
the hard way on #0085, whose round burned itself discovering the link error. Only `main.swift` and
code that genuinely cannot be unit-tested belong in `Sources/yard/`.

## Review — round 1 was rejected

Round 1 exited 0 after 125s and landed both files at the right paths with no scope violations. Two
things were wrong.

**1. `<argument>` is dropped whenever a flag also has a short name.** `renderFlagLine` is an
if/else-if chain in which the short-name branch short-circuits the argument branch:

```swift
if let short = flag.short {
    return "-\(short), --\(flag.long)"      // <argument> silently dropped
} else if let argument = flag.argument {
    return "--\(flag.long) <\(argument)>"
}
```

Rendering `FlagSpec(long: "output", short: "o", argument: "PATH", ...)` produced `-o, --output`
instead of `-o, --output <PATH>`. That is the canonical example from #0085's own tests, so it is not
a corner case.

The tests did not catch it because they are split so that **no test ever constructs a flag with both
a short name and an argument** — one test uses `short: "v", argument: nil`, another uses
`short: nil, argument: "PATH"`. Each half of the criterion passes alone; their conjunction, which is
the only case that exposes the bug, is untested. Fix the code *and* add that test.

**2. The tests were written in XCTest, so they are invisible in the count.** The round pasted
`Test run with 54 tests in 6 suites` and claimed it was "8 new + 46 existing". It was not: deleting
both new files and re-running gives the same `54 tests in 6 suites`. The eight tests really did run
and really did pass — on the XCTest channel, which that summary line does not count. Rewrite them in
swift-testing so the number the criterion asks for actually measures the work.

Neither failure was a defect in this issue's original wording, but the issue was thin: it never named
the test framework. It does now, and the count criterion now has a baseline to exceed.

Round 1: exit 0, 125s. Both files landed at the specified paths with no scope violations, and the
code was mostly right — rejected on the flag-rendering conjunction and on the test framework.

The reviewer caught the second issue by **deleting the new files and re-running the suite**, getting
the identical `Test run with 54 tests in 6 suites`. That is the check worth keeping: a count is only
evidence if removing the work changes it.

Round 2: exit 0, 302s, accepted. 92 tests, up from 83, and
`swift test --filter HelpRenderer` accounts for exactly the nine new ones — so the increase is real
rather than asserted. `renderFlagLine` now builds the short prefix and the long/argument suffix as
independent decisions, which is a structural fix rather than a special case for the failing shape.

The reviewer proved the fix by building a probe and rendering all four flag forms — **and ran it
against round 1's committed code first**, confirming it reproduced the dropped `<PATH>`. A test that
has never been seen to fail proves less than one that has.

Filed in `docs/review-failures.md`. Two checks came out of round 1: `AGENTS.md` Rule 8 requires
swift-testing, and the preflight warns when a test-count criterion states no baseline to exceed.
