# 0285 — WorktreeContext.resolve truncates a path containing a newline

| | |
|---|---|
| **Status** | in-progress |
| **Module** | YardGit |
| **Milestone** | M1 |
| **Platform** | macOS |

## Description

**Found by #0284's round, one layer below the bug it was sent to fix, and hit directly rather than
inferred.** `WorktreeContext.resolve` reads `git rev-parse` output through `.lines` / `.lines.first`,
so **a worktree whose own path contains a newline gets its `topLevel` and `gitDir` truncated.**

The round hit this while building #0284's fixture: its first draft resolved `yardWhere` from *inside* a
linked worktree whose directory name embedded a newline, and it failed with

```
fatal: cannot change to '.../wt-has': No such file or directory
```

— **the `-C` argument `WorktreeContext` handed back was already truncated before `yardWhere` ever saw
it.** It redesigned the test to resolve from the untainted main worktree instead, and left
`WorktreeContext.swift` alone because it was outside #0284's scope. That was the right call and this is
the follow-up.

**This is the same class as #0284**, one layer down and with a wider blast radius: `WorktreeContext` is
resolved once per invocation and **every path lookup in the engine goes through it** (`CLAUDE.md`, the
`WorktreeContext` rule). A truncated `topLevel` is not a wrong answer from one command — it is a wrong
`-C` for everything that follows.

## Expected behavior

- [ ] `WorktreeContext.resolve` stops splitting `rev-parse` output on newlines. **`git rev-parse` has
      no `-z`**, so the fix is not the same one #0284 used — measure what is available before choosing.
      Two candidates worth testing rather than reasoning about:
      - **One `rev-parse` call per value** (`--show-toplevel` alone, `--git-dir` alone), so the whole
        output *is* the value and there is nothing to split. Costs extra subprocesses per resolve.
      - **`-z` on the enclosing command** where one exists, or `--path-format=absolute` combined with a
        single-value call.
      **Say which you chose and what you measured**, including the subprocess cost if you take the
      one-call-per-value route — `WorktreeContext.resolve` runs on every invocation and this is the
      engine's hot path.
- [ ] A test with a newline in the **current** worktree's own path, asserting `topLevel` and `gitDir`
      come back whole. `WorktreeListTests.newlineInPathRoundTrips` and #0284's
      `newlineInLinkedWorktreePathDoesNotCorruptParsing` are the models for the fixture.
- [ ] **Mutation:** restore the `.lines` read. The new test must redden.
- [ ] **Five sites, measured — the issue does not make you find them.** `grep -n "\.lines" WorktreeContext.swift`:
      `:55` (`dirs.lines.count >= 2`), `:58` (`gitDir = canonicalize(dirs.lines[0])`), `:59`
      (`commonDir = canonicalize(dirs.lines[1])`), `:70` (`top.lines.first`), `:142` (`out.lines.first`),
      `:193` (`out.lines.first`). **`:55-59` is the worst of them**: it reads a *two-value*
      `rev-parse --git-dir --git-common-dir` by index, so a newline in the first value does not merely
      truncate it — it shifts `commonDir` onto the wrong line entirely.
- [ ] **Check the rest of the file the way #0284's round checked its own** — every other `.lines` or
      `.lines.first` on `rev-parse` output in `WorktreeContext.swift`. Name what you converted and what
      you left. A partial fix here is worse than none, because `WorktreeContext` is what everything else
      trusts.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.

`YardKit/Sources/YardGit/WorktreeContext.swift` and

## Notes

**Milestone M1** — `WorktreeContext` is M1 ground (guide §9: worktrees are in M1 deliberately, because
every path lookup goes through it and retrofitting means auditing every call site).

**This is a production defect, not a coverage gap.** Unlike #0276-#0283 it changes behaviour.

**A newline in a path is not a hypothetical the project invented for tests** — `WorktreeList` already
carries `-z` and a round-trip test for exactly this, and #0284 has just extended it to `WorktreeWhere`.
This issue finishes the sweep at the layer underneath both.
