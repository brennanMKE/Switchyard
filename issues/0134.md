## Description

Apply #0129's settled wire pattern (Decisions 1–8) to the worktree mutation results:

| type | source file |
|---|---|
| `WorktreeAddResult`, `WorktreeAddError` | `YardKit/Sources/YardGit/WorktreeAdd.swift` |
| `WorktreeRemoveResult`, `WorktreeRemoveError` | `YardKit/Sources/YardGit/WorktreeRemove.swift` |

Both results are already `Sendable`. **The error-object rule (#0129 Decision 5) lands here**: an
error enum with associated values encodes as an object with a stable `code` string plus a
`message` — both properties already exist (`WorktreeAddError.code` / `.description`,
`WorktreeRemoveError.code` / `.description`), so the explicit `encode(to:)` reuses them rather
than inventing strings. Uniform shape across every case of one enum; whether structured detail
fields (e.g. `branchInUse`'s `holderPath` / `holderIsMainWorktree`, `unclean`'s `paths`) ride
alongside `code`/`message` is decided and pinned at planning time — an agent that must act on the
holder should not have to parse it out of `message` prose.

Traps: the results' computed `success` / `refusal` / `lockReleased` / `hadToForce` are not
encoded (Decision 7); a nil `error` is omitted, never `null` (Decision 4), so a success payload
simply has no `error` key — pin both a success and a refusal literal.
