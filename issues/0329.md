## Description

**Measured 2026-08-18.** `gitStatus`'s payload **changes shape** under `status.renames=false` or
`diff.renames=false` — one entry becomes two, and `originalPath` disappears.

`gitStatus` (`YardKit/Sources/YardGit/WorktreeStatus.swift:422`) pins `status.showUntrackedFiles` and
nothing else about renames. Measured, git 2.50.1, a fixture with one staged `git mv old.txt new.txt`:

```
# user config: status.renames=false, diff.renames=false
engine vector as it stands today:
  1 A. N... 000000 100644 100644 000…000 1c99002b… new.txt
  1 D. N... 100644 000000 000000 1c99002b… 000…000 old.txt

with -c status.renames=true added:
  2 R. N... 100644 100644 100644 1c99002b… 1c99002b… R100 new.txt
  old.txt
```

So `WorktreeStatus.entries` goes from **one** `R`-with-`originalPath` entry to **two** entries, `A`
and `D`, purely from the user's `~/.gitconfig`. An agent diffing two `status` payloads across two
machines sees a change that is not in the repository.

**`true` is the value to pin because it is git's own default** (`status.renames` falls back to
`diff.renames`, which defaults to true), so pinning it **preserves today's behaviour exactly** and
changes only what happens under a non-default user config. Verified that a command-line `-c` beats a
repository-config setting: with `status.renames=false` in `.git/config`, the pinned vector still
reports `2 R.`.

**Update the comment block above the vector while you are there.** It currently reads *"`color.ui`,
`core.quotepath` (under `-z`), and `status.relativePaths` were measured to leave this output
byte-identical, so they are not pinned here"* — that list was measured on a fixture with **no rename
in it**, which is exactly why `status.renames` was not in it. Say so; the next reader needs to know
the enumeration was fixture-bounded, not exhaustive.

**Not a contradiction with `listHunks`' unconditional `--no-renames`, and do not "fix" that.** The two
answer different questions: `status` *describes* the worktree, where a rename is the truthful
description; `hunks` must emit a patch `git apply` accepts, and a rename header is not that. #0296's
shape — two functions describing the *same field* differently — does not apply.
