## Description

**Sibling of #0337.** That issue makes the engine runnable; this one makes it worth running.

`YardKit/Sources/YardCommands/EngineCommands.swift` is 67 lines and its `switch` has **one case**,
`whereami`, while the engine behind six more criterion-1 functions and the whole `wt` group exists and
is tested. Each missing command is an adapter of roughly the size of the existing `runWhereAmI` —
call the engine function, wrap the result in `Envelope(result: EncodableResult(...))`, encode, and map
a thrown error to `EnvelopeFail` with the right `ExitCode`.

**The engine entry points, with their files, all verified present 2026-08-18:**

| command | function | file |
|---|---|---|

## Expected behavior

- [ ] Each command above is a case in `runEngineCommand`'s `switch`, each delegating to a
      `private func run…` in the shape of the existing `runWhereAmI`.
- [ ] **Read-only commands only.** `wt new`, `wt rm`, `wt gc` and `wt repair` mutate a repository and
      are **out of scope** — a demo harness that can delete a worktree is a demo harness that will.
      Say in the report that you left them out.
- [ ] **Arguments that the engine function requires get parsed; everything else is refused.**
      `hunks` needs an area (`--staged` / `--unstaged`), `verify` needs a revision, `log` takes a
      range. An unparseable argument returns the `usage` exit code and a structured error, **never a
      default guess** — guide §6.
- [ ] A test per command in `YardKit/Tests/YardCommandsTests/`, asserting the **exit code** and that
      the payload parses as a `schemaVersion: 1` envelope with the expected top-level key. Not merely
      that output is non-empty.
- [ ] One test that a **bad argument** to `hunks` returns the `usage` code, not `success` with an
      empty payload — guide §9 M1 criterion 3 is exactly this shape and it has been violated before
      (#0287).
- [ ] `swift run yard-engine <each command>` against this repository, with the **actual output pasted
      into the report** — one line each is enough. That is the deliverable a human looks at.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, above the count in `docs/test-baseline.txt`.

## The files

`YardKit/Sources/YardCommands/EngineCommands.swift` and `YardKit/Tests/YardCommandsTests/`.

## Notes

**Milestone M3. Blocked on #0337** — without its executable there is no way to run what this adds.

**The adapters are the M3 CLI's real content, not throwaway.** When the XPC layer lands, the app calls
`runEngineCommand` on its side of the connection; only the transport changes. So write them as
production code, not as demo scaffolding.

**Do not widen `EngineCommands.swift` into a command framework.** Guide §11 has command metadata as
data driving `--help` and the skill (#0010, `wontfix` as written, but the idea stands). A `switch`
with nine cases is the right amount of structure for nine cases.
