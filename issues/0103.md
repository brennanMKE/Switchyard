# 0103 — Replace the Homebrew libgit2 dependency with a vendored binary

| | |
|---|---|
| **Status** | open |
| **Module** | Build / YardGit |
| **Milestone** | M3 |
| **Platform** | macOS |
| **First seen** | 2026-08-06 |

## Description

`YardKit` reaches libgit2 through `Sources/Clibgit2`, a SwiftPM `systemLibrary` target with
`pkgConfig: "libgit2"`. That resolves against Homebrew, which is fine for development and **cannot
ship**.

This is not a theoretical concern. Measured on a real Xcode build of the app target on 2026-08-06:

```
otool -L Switchyard.debug.dylib
    /opt/homebrew/opt/libgit2/lib/libgit2.1.9.dylib (current version 1.9.6)
```

An absolute load command into `/opt/homebrew`. An app distributed with that runs only on a machine
with Homebrew libgit2 installed at exactly that path — so, effectively, this machine. It is not a
build failure, so CI will never catch it; it is a launch failure on someone else's Mac, and the first
person to see it will be a user.

`docs/engine-findings.md` calls this "route B: vendored / prebuilt — the shipping route, not yet
built". This issue is that route.

## Scope

Both the app target and the embedded CLI link libgit2, so both are affected. #0050 covers *embedding*
the CLI in the bundle and is a different problem.

## Why not just copy the dylib into the bundle

The obvious fix — copy `libgit2.1.9.dylib` into `Contents/Frameworks/` and rewrite its load command —
does not work, and the reason is one `otool` call away:

```
otool -L /opt/homebrew/opt/libgit2/lib/libgit2.1.9.dylib
    /opt/homebrew/opt/llhttp/lib/libllhttp.9.4.dylib
    /opt/homebrew/opt/libssh2/lib/libssh2.1.dylib
    …CoreFoundation, Security, libz, libiconv, libSystem
```

Homebrew's libgit2 is itself linked against **two more Homebrew dylibs by absolute path**. Copying
one file leaves those dangling; copying all three means recursively chasing a dependency tree that
belongs to somebody else's build configuration, rewriting every load command with
`install_name_tool`, and re-signing each one. And the result still carries whatever flags,
optimisations and transitive dependencies Homebrew happened to choose.

## Licensing — this is allowed, and it matters here

**libgit2 is GPLv2 *with a linking exception*.** The exception is explicit:

> In addition to the permissions in the GNU General Public License, the authors give you unlimited
> permission to link the compiled version of this library into combinations with other programs, and
> to distribute those combinations without any restriction coming from the use of this file.

So an MIT-licensed Switchyard may link libgit2, statically or dynamically, and ship the result. The
GPL still governs *modification and redistribution of libgit2 itself* — so if the build ever patches
libgit2, those patches are GPLv2 and must be published. Pin an unmodified upstream version and this
stays simple.

This is unrelated to the GitUp clean-room rule. GitUp's *own source* is GPLv3 and off limits; libgit2
is a third-party dependency both projects consume.

## What GitUp does — the answer to "is there a known-good shape for this"

Checked directly, and it is unambiguous. GitUp vendors **static** libraries inside `.xcframework`s:

```
GitUpKit/Third-Party/
    libgit2.xcframework/macos-arm64_x86_64/libgit2.a   ← static, universal arm64 + x86_64
    libssh2.xcframework  libssl.xcframework  libcrypto.xcframework  libsqlite3.xcframework
    rebuild-libgit2.sh   rebuild-libssh2.sh   …
```

Every piece of the picture:

- **Static `.a`, not a dylib.** Nothing to embed in `Contents/Frameworks/`, nothing to sign
  separately, no `@rpath`, and no way to fail at launch on a machine that lacks it. The failure mode
  this issue exists to prevent becomes structurally impossible rather than merely fixed.
- **Universal** (`arm64` + `x86_64`) in one slice, which is what an `.xcframework` is for.
- **Built from source via CMake**, driven by a `rebuild-*.sh` script, with the built artefact
  checked into the repo — so a clone builds without CMake or Homebrew present.
- **From a maintained fork**, tracking an upstream branch, so patches are rebased deliberately rather
  than accumulated.
- **They vendor libssh2 and OpenSSL too**, which confirms the transitive-dependency problem above is
  real and not hypothetical.

Their `UPDATING-LIBGIT2.md` documents the refresh process. **Read it for the shape, do not copy the
scripts** — they are GPLv3 like the rest of GitUp. Write ours independently; the approach is not
copyrightable, the script text is.

## Expected behavior

- [ ] libgit2 is built from source for `arm64` and `x86_64` and packaged as a **static** library in
      a universal `.xcframework`, checked into the repo and produced by a documented, repeatable
      script. Static, not dynamic — see the GitUp section above for why that removes the failure mode
      rather than relocating it.
- [ ] Any transitive dependency that would otherwise resolve to Homebrew is vendored the same way or
      designed out. Decide explicitly whether SSH transport and HTTPS are needed in M1; if libgit2 is
      configured without them, `libssh2` and OpenSSL are not needed at all, which is a large
      simplification worth taking if the CLI shells out to `git` for network operations anyway —
      and `CLAUDE.md` says it does.
- [ ] `YardKit/Package.swift` uses `binaryTarget` (or a vendored static lib) instead of the
      `systemLibrary` + `pkgConfig` route. `Sources/Clibgit2`'s module map survives if it is still
      needed for the C shim.
- [ ] `otool -L` on the built app dylib shows **no path under `/opt/homebrew` or `/usr/local`**.
      Paste the output. This is the criterion that matters — the build succeeding proves nothing,
      because it already succeeds today.
- [ ] The same check passes for the built `switchyard` binary.
- [ ] `cd YardKit && swift build && swift test` still passes, and the count does not fall.
- [ ] The libgit2 version is pinned and recorded, so a rebuild is reproducible.
- [ ] The build script does not require Homebrew to be installed.

## Notes

Blocked by nothing technically, but it is only worth doing once the app target exists (#0045) so both
consumers can be verified at once.

**Do not solve this with `install_name_tool` on a Homebrew dylib.** See the section above: it is not
one file, it is a dependency tree belonging to someone else's build configuration.

libgit2 builds with CMake, which SwiftPM cannot drive — that is the whole reason this is a separate
piece of work rather than a `Package.swift` edit.
