## Description

The branch/tag management legs of GitUp's context menu (#0359): **Add Tag… (T)**,
**Create Branch… (B)**, **Edit Local Branch "main" (→)** — rename, delete, set upstream.
Switchyard's engine reads refs extensively (`wt list`, `graph`, the sidebar's branch list) but
creates none of them: there is no tag creation, no branch create/rename/delete, anywhere.

These are ref operations, so the journal's ref-snapshot machinery covers undo — but the guards
differ per operation: deleting a branch with unmerged commits is data loss (GitUp confirms;
Switchyard should refuse without `--force` and journal the deletion when forced), renaming a
checked-out branch must move `HEAD`'s symref, and tag creation can be lightweight or annotated
(and signed — `git tag -s` shells out to the same signing path).

## Expected behavior

- [ ] `yard tag <name> <commit>` (annotated and lightweight), `yard branch create <name>
      [<start>]`, `yard branch rename <old> <new>`, `yard branch delete <name> [--force]`,
      `yard branch upstream <name> <upstream>` — all non-interactive, all typed-refusal-first.
- [ ] Deleting the checked-out branch, deleting an unmerged branch without `--force`, renaming
      onto an existing name, and creating a tag that exists are typed refusals touching nothing.
- [ ] Every mutation auto-checkpoints and is exactly undoable (ref snapshots already cover
      branch/tag state — verify, don't assume).
- [ ] The sidebar's branch list (#0358) gains the management affordances; the context menu
      (#0359) gains the items.

## Notes

The ref-management primitives (`update-ref --stdin`, symref handling) exist for the journal;
this issue is the user-facing surface over them.
