## Description

Mac App Store or direct distribution. This is baked in early because it decides sandboxing, and
sandboxing has **two** concrete consequences, not one:

1. The Mach service name must be prefixed with an app-group identifier, changing the naming scheme
   throughout.
2. The state directory diverges — `~/.local/state/switchyard/` from a sandboxed app resolves to
   `~/Library/Containers/co.sstools.Switchyard/Data/.local/state/switchyard/`, silently disagreeing
   with what `yard` sees from a shell.

Two processes reading different journals while both believe they are reading the same one is a bug
that would take a long day to find.

## Notes

**Analysis complete 2026-08-06; the decision itself is Brennan's, so this stays `open`.**
`docs/distribution.md` sets out the case.

**Recommendation: direct distribution, unsandboxed, Developer ID signed and notarized.**

The deciding argument is not a list of inconveniences, it is that sandboxing removes the
differentiator. `review --wait` requires a CLI outside the container talking to an app inside it —
`/usr/local/bin` is outside the container, the privilege escalation #0051 relies on is unavailable,
and a sandboxed Mach service name is reachable only within the app group. An App Store build would
be a graphical git client with no CLI, which is the half that already exists elsewhere.

The state-directory divergence is the specific hazard worth naming: sandboxed,
`ServiceNames.stateDirectory()` resolves inside the container while `yard` resolves the real
`~/.local/state/switchyard/`. Nothing errors — the app and the CLI simply never see each other's
data, and no test catches it unless it runs the app sandboxed and the CLI unsandboxed simultaneously.

Guide §1 already lists sandboxing under non-goals; this is the evidence for keeping it there.

Left for Brennan: the decision, and the Developer ID plus notarization work, which per `CLAUDE.md`
is his to run through Xcode's Distribute App flow.

## Decision — 2026-08-06

**Brennan chose direct distribution: unsandboxed, Developer ID signed and notarized.** Not the Mac
App Store.

The reasoning in `docs/distribution.md` stands as written. The deciding factor is that a sandboxed
build cannot install a CLI to `/usr/local/bin`, cannot publish a Mach service an external process can
reach, and runs hooks outside its container's grants — so the App Store build would be a graphical
git client with no agent surface, which is the half that already exists elsewhere.

Recorded as settled decision 5 in guide §11. What this settles concretely:

- `ServiceNames.machServiceName` keeps its unprefixed form — no Team ID prefix.
- `stateDirectory()` stays as written, and the app and CLI genuinely share it. The silent divergence
  described in `distribution.md` cannot happen.
- #0074's release script targets Developer ID plus notarization, not an App Store upload.

**Archives, notarization and DMG creation remain Brennan's**, through Xcode's Distribute App flow,
per `CLAUDE.md`. Nothing here creates or modifies a signing asset.
