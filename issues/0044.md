## Description

**This is an umbrella issue.** Re-authored 2026-08-08: the original single issue mixed decisions,
enforcement, and criteria that other issues have since absorbed. This pass settles the worktree
semantics of undo (below, every fact measured), splits the remaining engine work into **#0172**
(per-worktree chain scoping) and **#0173** (sibling-checkout disturbance refusal) — both
code-complete, compiled, run, and mutation-tested on a scratch copy of `main` (`73dead0`, from
`git archive`) — and records the binding requirements the #0168/#0169/#0170 planning passes must
pick up. Opus reviews this umbrella when its children resolve; it is never dispatched itself.

The premise: two agents in two worktrees is the intended usage. `HEAD` is per-worktree;
`refs/heads/*` is shared (with `refs/bisect/`, `refs/worktree/`, `refs/rewritten/` per-worktree
despite the prefix); journal anchors are shared, so every worktree sees one entry list (#0028,
`anchorsAreSharedAcrossWorktrees`); and every entry records its worktree (#0155's
`worktree: {name, path}`, name = `WorktreeContext.worktreeName`, nil for the main worktree).
Getting the shared/per-worktree split wrong loses someone's work — silently.

## Decisions — settled at this pass, binding on the children and on #0168/#0169/#0170

### 1. The journal is per-repository; the undo chain is per-worktree

`JournalChain` (#0166, merged) resolves the cursor from the entry list alone and **considers
worktree not at all** — as a pure order-replay it cannot. Left that way, the chain would be
repository-wide, and in a two-agent repository that is wrong twice over:

- Agent A's `undo` would target agent B's newest entry — which the restore gate (#0034
  Decision 5, enforced in #0168 step 2) then *refuses*, because the entry's recorded worktree is
  not A's. A repository-wide chain plus a per-worktree restore gate deadlocks the normal case.
- Agent B writing an ordinary checkpoint would reset the repository-wide cursor to present and
  truncate agent A's live redo run mid-undo. One agent's routine work would destroy the other's
  traversal state.

So: **the cursor, undo target, redo target, and truncation rule are all evaluated per-worktree**,
over the subsequence of entries recorded in the calling worktree. The journal's storage, listing,
and anchor namespace stay repository-wide — `journal` shows everything from anywhere; only the
*walk* is scoped. A single-worktree repository degenerates exactly to #0166's semantics
(pinned by test `singleWorktreeJournalMatchesTheUnscopedChain`).

**What it costs.** `JournalChain.State.protectedIDs` is per-scope, but pruning (#0033/#0170) is
repository-wide — so the protected set handed to `JournalPrune` must be the **union of every
live worktree's protected ids** (#0172's `protectedIDs(of:live:)`). And the scoping key is the
worktree **name**: a re-created worktree reuses its name and inherits the dead chain's cursor.
Accepted, documented in the type: the first checkpoint written in the new worktree resets its
cursor to present, and every restore re-checks reality through the cross-tool guard regardless.

### 2. Undo refuses to disturb a sibling's checkout — because git's plumbing will not

What git actually does when `refs/heads/agent-branch` is checked out in a sibling worktree
(measured 2026-08-08, git 2.50.1, **identical on `files` and `reftable`**):

| command from the main worktree | result |
|---|---|
| `git checkout agent-branch` | `fatal: 'agent-branch' is already used by worktree at '<path>'` — **exit 128** |
| `git branch -f agent-branch <oid>` | `fatal: cannot force update the branch 'agent-branch' used by worktree at '<path>'` — **exit 128** |
| `git branch -d agent-branch` | `error: cannot delete branch 'agent-branch' used by worktree at '<path>'` — **exit 1** |
| `git update-ref refs/heads/agent-branch <oid>` | **exit 0, silent** — the sibling's checkout is now inconsistent with its own `HEAD` (`git -C <wt> status` immediately shows phantom staged changes) |
| the same `update-ref --stdin` transaction form `RefSnapshot.restore` uses | **exit 0, silent** — same wreckage |
| `git update-ref -d refs/heads/agent-branch` | **exit 0, silent deletion** |

So git enforces branch exclusivity in porcelain and not in plumbing — and restore is plumbing.
**Switchyard adds the refusal at the engine layer**: before applying a snapshot, #0173's
`WorktreeDisturbance.requireUndisturbed(by:in:)` names every sibling worktree whose checked-out
branch the snapshot would move or re-create, and throws (`ExitClass.repositoryError`,
6) while any exists. The original issue said *warn* by name; the engine **refuses** by name —
a warning printed beside a completed clobber helps nobody, and the force path is M3's
human-authorization decision, exactly as with the cross-tool guard (#0031 Decision 5).

**Corrected 2026-08-17 (#0250): this sentence said "move, delete, or re-create" until guide §11
decision 20** made `RefSnapshot.restore` stop deleting refs at all — it now emits `update` only
for refs its snapshot recorded (`RefSnapshot.swift:206-208`), and nothing else, so a restore
cannot delete a sibling's branch any more. The decision's behaviour did not change: the "delete"
case in the table above (`git update-ref -d`) is still what raw plumbing *can* do, and #0173's
refusal still exists to add exactly the protection porcelain has and plumbing lacks — but a
sibling checkout is disturbed only by having its branch **moved** (rewound or fast-forwarded to
the snapshot's recorded oid) or **re-created** (the snapshot recorded an oid for a branch that
does not currently exist), never by deletion. `WorktreeDisturbance`'s type comment and its
`Disturbance.target` doc were corrected the same way by #0244, before this decision's own text
was.

Not disturbances, deliberately: the **calling worktree's own** checked-out branch (moving it is
what restoring one's own checkpoint *is*), and a **detached** sibling (it holds no branch; its
`HEAD` is per-worktree state that shared-ref writes cannot touch — porcelain emits `detached`
with no `branch` attribute, measured).

### 3. What the cross-tool guard compares in a multi-worktree repository

The guard (#0031, merged) diffs the **union** of recorded and current ref names plus `HEAD`, and
both sides come from `RefSnapshot.capture` in one `WorktreeContext`. Two measured facts scope it:

- A sibling's commit moves the shared `refs/heads/<branch>` and **is** caught from any worktree
  (#0031's `sharedRefMovedFromASiblingWorktreeIsReported`). The sibling's `HEAD` is not in the
  report — it is per-worktree state, invisible to this context's capture.
- `for-each-ref` lists the **current worktree's** per-worktree refs under their plain names —
  `refs/worktree/*`, `refs/rewritten/*` — and not a sibling's (measured 2026-08-08: a
  `refs/worktree/probe-main` written in the main worktree appears in the main worktree's
  `for-each-ref` and not in the linked worktree's, and vice versa; identical on reftable). So
  **a capture is a per-worktree artifact**: two worktrees with identical shared refs capture
  different snapshots.

Consequence, binding on #0168's ordering: **the worktree gate (its step 2) must run before the
guard (its step 4)**. #0168's current step order is correct and may not be reordered.

**The reason stated here is superseded — corrected 2026-08-17 by the umbrella review.** It originally
read: *"comparing a snapshot captured in worktree A against a fresh capture in worktree B reports
divergences (`HEAD`, any per-worktree refs) that no tool ever made."* Under the merged code that
comparison **cannot occur at any ordering**, because #0168 decision 1 made the guard's reference the
**scoped chain cursor's** snapshot (`JournalRestore.swift:265-269`) — always an entry recorded in the
*calling* worktree — so both sides of the diff always come from the caller's context. #0175 records
this too ("#0044 decision 3's incoherence cannot arise").

**The order is still load-bearing, for a different reason: error quality.** A cross-worktree attempt
must report `differentWorktree`, naming both worktrees and whether the recorded one still exists, not
a `repositoryChanged` divergence list the caller cannot act on. Note that **no test pins the order** —
the two gate tests run from the main worktree with an empty scoped chain, so the cursor is nil and the
guard would be skipped either way. Worth a row if #0168 is ever reopened.

And the disturbance check answers a question the guard cannot: the guard asks *"did refs move
behind the journal's back since the reference snapshot was taken"*; #0173 asks *"would applying
the **target** snapshot wreck a sibling's checkout"*. A rewind of a sibling's branch can be
refused by either (the sibling's move trips the guard; the target diff trips the disturbance),
but only the disturbance refusal **names the worktree** — and it must run on the target snapshot
in every restore path, **including when the guard is bypassed** (`bypassGuard` skips the guard,
never the disturbance check; the M3 force surface decides separately whether a human may skip
both). Binding on #0168's re-authoring.

### 4. Cross-worktree restore (`allowDifferentWorktree`) must filter per-worktree refs

Because capture includes the capture-worktree's `refs/worktree/*` and `refs/rewritten/*`
(Decision 3), applying worktree A's snapshot from worktree B verbatim would (a) write A's
per-worktree refs into **B's** private namespace, and (b) delete B's own per-worktree refs as
"extra" — `RefSnapshot.restore` plans deletions from the same listing rules as capture, which in
B's context enumerates B's private refs. Same-worktree restore round-trips them correctly (the
namespaces coincide); only the override path corrupts. **Binding on #0168's planning pass:**
under `allowDifferentWorktree`, drop recorded entries in `WorktreeContext.isPerWorktree`
namespaces and exclude those namespaces from deletion planning — or refuse outright when the
snapshot carries any. Either resolution needs a test; the measured basis is above.

### 5. A deleted worktree: honest refusals, expiring protection

An agent's worktree directory vanishes without `git worktree remove` constantly. Measured
(2026-08-08, git 2.50.1): the administrative entry survives — `git worktree list --porcelain`
still lists the worktree with its `branch` attribute plus
`prunable gitdir file points to non-existent location`; `git rev-parse worktrees/<name>/HEAD`
and `--symbolic-full-name` still resolve; `git checkout <its-branch>` from the main worktree
**still refuses, exit 128**; and `git update-ref` still silently moves its branch. The claim
outlives the checkout until `git worktree prune`.

Policy, in three parts:

- **Disturbance refusal keeps firing** for a prunable holder — matching git's own porcelain —
  with `prunable: true` in the report and the release path named in the error text
  (`git worktree prune`). #0173 delivers and tests this. Honesty over clever recovery: the
  engine does not prune on the caller's behalf.
- **Chain protection expires with the worktree.** `protectedIDs(of:live:)` (#0172) unions only
  the worktrees the caller names as live; a deleted worktree's cursor and redo tail become
  ordinary prunable history. The prune composition (#0170) derives `live` from `worktreeList`
  minus prunable entries, resolving each surviving path's `worktreeName` — binding on #0170's
  planning pass.
- **The restore gate reports the death.** When an entry's recorded worktree no longer exists,
  #0168's worktree-gate error must say so — recorded name and path, plus "no longer exists" —
  rather than only "not the calling worktree". `worktree.path` in the metadata is for exactly
  this message; it is never dereferenced. Binding on #0168's planning pass.

### 6. `refs/rewritten/*` mid-rebase: already captured, in the right scope

Measured 2026-08-08: `for-each-ref` enumerates `refs/rewritten/*` and `refs/worktree/*` of the
current worktree under their plain names (both formats), so `RefSnapshot.capture` **already**
carries them and same-worktree restore already round-trips them — per-worktree, in the worktree
the rebase runs in, which is the correct scope. The original checkbox "so the rebase remains
resumable" needs more than refs: sequencer *files* (`rebase-merge/`, `rebase-apply/`,
`sequencer/`) are per-worktree `$GIT_DIR` state that no current issue captures — #0151 owns the
index, #0152 the worktree files, and neither names the sequencer. #0035 lists mid-rebase
sequencer state as a round-trip case and will fail without an owner; flagged in this pass's
report as a backlog gap rather than silently absorbed here.
