## Description

The detail that makes journal restore correct or catastrophic. All pseudo refs such as `HEAD` are
per-worktree; refs under `refs/` are shared — **except** `refs/bisect`, `refs/worktree`, and
`refs/rewritten`, which are per-worktree.

So restoring `HEAD` affects only the worktree the operation happened in, while restoring
`refs/heads/*` affects every worktree. If a sibling worktree has that branch checked out, its
working copy is now inconsistent with its own `HEAD` — silently, unless we say so.

## Expected behavior

- [ ] Entries record the originating worktree; restore refuses from a different one without `--worktree`.
- [ ] The guard checks sibling worktrees' `HEAD` values, read via `worktrees/<name>/HEAD`.
- [ ] `undo` warns **by name** when a restore will disturb another worktree.
- [ ] `refs/rewritten/*` captured when snapshotting mid-rebase, so the rebase remains resumable.
- [ ] Tests use a real linked worktree and assert a `HEAD` restore does not move the sibling.
- [ ] Tests assert a shared-branch restore is detected as affecting the sibling.

## Notes

Git internals §5 "Which refs are shared and which are not". Blocked by #0031, #0034.

This is the highest-risk correctness area in the journal. Two agents in two worktrees is the
intended usage, so getting the shared/per-worktree split wrong loses someone's work.
