## Description

**Proposal 1 of the M1 milestone review, 2026-08-17**, filed as an ordinary issue because it is a real
latent gap rather than a criterion violation.

`ExitClassWireTests.gitProcessFailureCasesAreRepositoryErrors` enumerates **two** of
`GitProcess.Failure`'s cases and pins `#expect(failures.count == 2)`.
`GitProcess.Failure.timedOut(after:arguments:terminationStatus:)` (`GitProcess.swift:51`, added by
**#0239**) is absent from it, and the conformance's doc comment at `GitProcess.swift:419` still reads
*"Both cases"*.

**Behaviour is correct** — the `ExitClassCarrying` conformance returns `.repositoryError`
unconditionally, so `timedOut` already carries the right §6 code. What is wrong is the **guard**: a
hardcoded count that was true when written means the next case added slips through exactly as this one
did.

## Expected behavior

- [ ] The test covers every case of `GitProcess.Failure`, including `timedOut`.
- [ ] **The count stops being a literal.** Derive it, or assert over an exhaustive list the compiler
      checks — a `switch` over a constructed value of each case is the usual trick, since
      `GitProcess.Failure` has associated values and cannot be `CaseIterable`. Say which you chose and
      why it will fail when a case is added.
- [ ] The doc comment at `GitProcess.swift:419` says "Both cases" and is now wrong; fix it.
- [ ] Mutation: add a throwaway fourth case to `GitProcess.Failure` and confirm the test fails to
      compile or fails at runtime — **that** is the property being bought. Remove it afterwards and say
      what happened.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.

## Work log

- **Round 1 — 2026-08-17, Sonnet subagent, 130,776 tokens, 10m32s, accepted.** A private
  `gitProcessFailureCaseLabel` switching over the enum with **no `default`**, plus a shared samples
  array; the original test split into one asserting every case is covered and one asserting each maps
  to `.repositoryError`. The stale *"Both cases"* doc comment on the conformance is fixed too.
- **The reasoning for not reusing the existing coverage machinery is right and worth keeping:**
  `ExitClassCoverageTests`/`DescriptionCoverageTests` scan source text to answer *"does every
  conformer **type** have a registry row"*, across many enums. This is about **cases within one enum**,
  which neither source scanning nor `CaseIterable` can reach — an enum with associated values cannot
  conform. The compiler is the only thing that can enforce it.
- **Review.** 1040 green with `main` merged in. I added a fourth case myself: `swift build` still
  succeeds — the production module is fine — and `swift test` **fails to compile** at
  `ExitClassWireTests.swift:136` with `error: switch must be exhaustive`. A guard that fails the build
  is stronger than any runtime count, which is exactly what this issue was asking for.
