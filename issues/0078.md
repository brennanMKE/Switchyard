# 0078 — Implement the multi-window model

| | |
|---|---|
| **Status** | open |
| **Module** | Switchyard |
| **Milestone** | M3 |
| **Platform** | macOS |
| **First seen** | 2026-08-06 |

## Description

Multiple windows from the start, as in Batty: `WindowGroup(for: WindowID.self)` with a `WindowID`
value type, each window owning its own set of repository tabs.

Two traps are already documented by Batty's `BattyApp.swift` (tracked there as Batty issue 0251), and **Switchyard is
more exposed to the second** because it has both a `switchyard://` URL scheme and XPC waking the
app:

1. **The phantom second window.** `WindowGroup(for:)` needs a `defaultValue` returning a `WindowID`
   already seeded in app state. Without it SwiftUI's first content window creates a second runtime,
   and CLI-delivered work lands in the invisible one while the visible window sits empty.
2. **External events spawning stray windows.** `.handlesExternalEvents(matching: Set())` must be on
   **every** scene. When the content group declines a URL open, SwiftUI falls back to the next scene
   that accepts external events — including a Help window — and opens that instead.

## Expected behavior

- [ ] `WindowGroup(for: WindowID.self)` with a `defaultValue` returning the pre-seeded window id.
- [ ] Cmd-N opens a second window with its own independent tab set.
- [ ] `.handlesExternalEvents(matching: Set())` on every scene, including Settings and any Help window.
- [ ] A `switchyard://` open with the app already running opens **no** new window — verified by counting windows before and after.
- [ ] The same, verified for an XPC-triggered activation.
- [ ] Closing one window does not disturb another window's tabs.

## Placement — settled 2026-08-07

Every view and everything around it goes in **`YardKit/Sources/YardUI/`**, the package target created
by **#0126**. Not in the Xcode project.

The Xcode project keeps only the `@main` `App` type, the asset catalog, `Info.plist`, entitlements,
`SMAppService` registration, and the embedded `switchyard` binary.

**Why it matters for this issue specifically:** a view in the app target can only be exercised by a UI
test, and UI tests cannot run under CLI-driven `xcodebuild` on this machine — the runner times out
enabling automation mode without Accessibility rights. Anything built here would ship untested. In
`YardUI` it is reachable from `swift test`.

`YardUI` sets `.defaultIsolation(MainActor.self)`, so views are main-actor isolated exactly as they
are in the app target today.

Tests go in `Tests/YardUITests` and import **without** `@testable`, so they see what the app sees.
