# 0078 — Implement the multi-window model

| | |
|---|---|
| **Status** | open |
| **Module** | Switchyard |
| **Milestone** | M3 |
| **Platform** | macOS |
| **First seen** | 2026-08-06 |

## Description

Multiple windows from the start, as in Batty: `WindowGroup(for: WindowID.self)` with a `WindowID`
value type, each window owning its own set of repository tabs.

Two traps are already documented by Batty's `BattyApp.swift` (tracked there as Batty issue 0251), and **Switchyard is
more exposed to the second** because it has both a `switchyard://` URL scheme and XPC waking the
app:

1. **The phantom second window.** `WindowGroup(for:)` needs a `defaultValue` returning a `WindowID`
   already seeded in app state. Without it SwiftUI's first content window creates a second runtime,
   and CLI-delivered work lands in the invisible one while the visible window sits empty.
2. **External events spawning stray windows.** `.handlesExternalEvents(matching: Set())` must be on
   **every** scene. When the content group declines a URL open, SwiftUI falls back to the next scene
   that accepts external events — including a Help window — and opens that instead.

## Expected behavior

- [ ] `WindowGroup(for: WindowID.self)` with a `defaultValue` returning the pre-seeded window id.
- [ ] Cmd-N opens a second window with its own independent tab set.
- [ ] `.handlesExternalEvents(matching: Set())` on every scene, including Settings and any Help window.
- [ ] A `switchyard://` open with the app already running opens **no** new window — verified by counting windows before and after.
- [ ] The same, verified for an XPC-triggered activation.
- [ ] Closing one window does not disturb another window's tabs.

## Placement — settled 2026-08-07

Every view and everything around it goes in **`YardKit/Sources/YardUI/`**, the package target created
by **#0126**. Not in the Xcode project.

The Xcode project keeps only the `@main` `App` type, the asset catalog, `Info.plist`, entitlements,
`SMAppService` registration, and the embedded `switchyard` binary.

**Why it matters for this issue specifically:** a view in the app target can only be exercised by a UI
test, and UI tests cannot run under CLI-driven `xcodebuild` on this machine — the runner times out
enabling automation mode without Accessibility rights. Anything built here would ship untested. In
`YardUI` it is reachable from `swift test`.

`YardUI` sets `.defaultIsolation(MainActor.self)`, so views are main-actor isolated exactly as they
are in the app target today.

Tests go in `Tests/YardUITests` and import **without** `@testable`, so they see what the app sees.

## Planning update — 2026-08-17. Where the split falls, and the two traps verbatim from Batty.

The placement note above is right about views and slightly too broad about *this* issue: a
`WindowGroup` is a `Scene` inside the `@main App` type, and the `App` type lives in the Xcode project
by decision 10. So this issue lands in two places, and the line between them is what makes it
testable at all:

- **`YardKit/Sources/YardUI/WindowID.swift` and `WindowState.swift`** — the `WindowID` value type
  (`Hashable`, `Codable`, `Sendable` — `WindowGroup(for:)` requires all three) and the observable
  store that owns the window list, seeds the first id, and hands out per-window tab state. **All the
  behaviour is here**, reachable from `swift test`.
- **`Switchyard/SwitchyardApp.swift`** — the scenes. Declarations only: no logic that a test would
  want to reach.

### The two traps, from `../../Batty/Batty/BattyApp.swift` (MIT, same author — copyable)

Batty's comments name both root causes precisely; they are reproduced here so the round does not have
to reconstruct them.

**1. The phantom second window.** `WindowGroup(for:)`'s `defaultValue` must return a `WindowID`
**already seeded in the store**:

```swift
WindowGroup(for: WindowID.self) { $windowID in
    ContentView(windowID: windowID)
} defaultValue: {
    AppStateStore.shared.initialWindowID
}
```

Batty's own comment: *"so that SwiftUI's first content window reuses the existing runtime rather than
creating a phantom second one. A phantom second runtime causes `batty <path>` sessions to land in
`windows[0]` (the phantom) while the visible window shows an empty `windows[1]`."* Switchyard is more
exposed to this than Batty was, because CLI-delivered work arrives over XPC and would land in the
invisible window.

**2. Stray windows from external events.** `.handlesExternalEvents(matching: Set())` goes on
**every** scene — the content group, any Help window, and Settings. Batty's comment on the Help
window is the one that explains why it is not enough to put it on the content group: *"When the
content `WindowGroup` above stops volunteering for `batty://` opens, SwiftUI otherwise falls back to
the next scene that does accept external events — this Help window — and opens it."*

Cmd-N and `openWindow(value:)` are internal SwiftUI actions and are **unaffected** by
`handlesExternalEvents`; only OS-delivered URL opens are suppressed. So criterion 2 (Cmd-N opens a
second window) and criterion 4 (a `switchyard://` open adds no window) are not in tension.

### What can be tested, and what cannot

**Testable in `YardUITests`, and this is the deliverable:**
- The store seeds exactly one window at init, and `initialWindowID` returns **that** id — the phantom
  trap expressed as an assertion rather than a comment.
- Adding a window yields an independent tab set; mutating one window's tabs leaves the other's
  unchanged (criterion 6, and it needs no window at all to assert).
- Removing a window leaves the others intact, and removing the last one is defined behaviour — say
  which.
- `WindowID` round-trips through `Codable`, since `WindowGroup(for:)` persists it.

**Not testable here, and it must not be faked:** criteria 4 and 5 count real windows after a real URL
open and a real XPC activation. `XCUIApplication` cannot run under CLI-driven `xcodebuild` on this
machine (CLAUDE.md), so **write them as scenarios in #0054's script** and say so in the report. A test
that asserts "no extra window" by inspecting a store rather than `NSApp.windows` is asserting
something else.

### Verification

- `cd YardKit && swift build && swift test` — `Test run with N tests`, **N greater than** the count in
  `docs/test-baseline.txt` at dispatch (960 on 2026-08-17).
- `xcodebuild build -project Switchyard.xcodeproj -scheme Switchyard -destination 'platform=macOS'
  CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` prints `** BUILD SUCCEEDED **`.
- **Do not launch the app.** #0125 owns the launch smoke test and #0054 owns the manual window counts.
- Mutation: remove the `defaultValue` seeding (return a fresh `WindowID()` instead) and confirm the
  seeding test goes red. If it does not, the test is asserting the store's initialiser rather than the
  property the trap is about.

**`YardUI` sets `.defaultIsolation(MainActor.self)`** — a package target does not inherit the app's
`SWIFT_DEFAULT_ACTOR_ISOLATION`, so a type moved across that boundary silently changes isolation.
