## Description

**Finding 5 of the M1 milestone review, fifth pass, 2026-08-18, and the third time this suite has cost a
session real work.** `AppConnectionTests` times out under full-suite parallel load, non-deterministically.

**Measured across seven full-suite runs in one review, with no source change relevant to it, two were
red — both entirely inside this one suite:**

| run | failures |
|---|---|
| 1 (pristine baseline, before any mutation) | `requireAppFailsFastWithoutLaunching()` — *"expected error of type AppConnectionError, but "timed out after 60.0s" of type CLIError was thrown instead"*. **Re-run in isolation: passed in 0.001 s.** |
| 3 | **nine** — `brokerUnreachableMapsToExitCodeTwo`, `launchIfNeededFalseDoesNotLaunch`, `requireAppFailsFastWithoutLaunching`, `requestReplyOverAnAnonymousEndpointRoundTrips`, `appTerminatedMapsToExitCodeFive`, and all four cases of `"perform round-trips runYard's bytes exactly"` — every one `timed out after 60.0s` |

**The deadline has already been raised once for this** (#0240, 2026-08-17), and the file carries a
comment at lines 120-129 explaining why. It is still not enough, and raising it again is not obviously
the fix: **the failure mode is not a slow reply, it is the whole suite starving at once.**
`brokerUnreachableMapsToExitCodeTwo` is documented as measuring 0.000 s and still timed out at 60 s.

**The cost is not the red run, it is the ambiguity.** The reviewer had to discount nine failures by hand
to score an unrelated finding, and CLAUDE.md's rule that one green run is not evidence exists because of
this suite.

## Expected behavior

- [ ] **Diagnose before changing anything.** Establish *what* starves — whether the tests are waiting on
      a real XPC round trip, a `Task.sleep`, a GCD queue with no thread available, or a listener that
      never gets scheduled. Report the finding even if the fix turns out to be small; a third deadline
      bump with no diagnosis is what this issue exists to avoid.
- [ ] **Reproduce it deliberately** rather than waiting for it. Two concurrent full suites is the
      condition that produced it before (#0240), and it is reproducible in one foreground command:
      `( cd ../other-worktree/YardKit && swift test > A.log 2>&1 ) & swift test > B.log 2>&1; wait`.
      **Never background a single suite and wait for a notification** — `AGENTS.md` Rule 7.
- [ ] **Then fix the cause.** If the tests genuinely need an isolated executor, or serialization
      (`.serialized`), or to stop sharing a Mach service name across cases, do that. Raising the
      timeout again is acceptable **only** with a measurement showing the wait is bounded and merely
      long — say so explicitly if that is the conclusion.
- [ ] The fix is demonstrated by **ten consecutive full-suite runs** under the two-concurrent-suites
      condition, all green. Paste the count line from each. One green run is not evidence here; that is
      the whole subject.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.
