## Description

`WorktreeContext.resolveRef(_:inWorktree:git:)` builds a name with
`refName(_:inWorktree:)` — `worktrees/<name>/<ref>` or `main-worktree/<ref>` — and runs
`git rev-parse --verify --quiet` on it. That prefix syntax addresses a worktree's **per-worktree** ref
space only. Handed a shared ref it resolves nothing, `rev-parse` exits 1, and `resolveRef` returns
`nil` — which is the same answer it gives for a ref that genuinely does not exist.

So a caller asking "what commit is worktree `lw`'s branch at" gets `nil`, forever, for a branch that
exists.

## Measured against real git, 2026-08-07 — treat as verified

From the main worktree of a repository with a linked worktree `lw` on branch `lb`:

| query | exit | result |
|---|---|---|
| `worktrees/lw/HEAD` | 0 | resolves |
| `worktrees/lw/refs/bisect/good` (created inside `lw`) | 0 | resolves |
| `worktrees/lw/refs/worktree/mine` (created inside `lw`) | 0 | resolves |
| `worktrees/lw/refs/heads/lb` | **1** | **nothing** |
| `worktrees/lw/refs/tags/v1` | **1** | **nothing** |
| `main-worktree/refs/heads/main` | **1** | **nothing** |

And the ground truth underneath it, `git rev-parse --git-path` from inside `lw`:

```
HEAD                 …/.git/worktrees/lw/HEAD        ← per-worktree
refs/bisect/bad      …/.git/worktrees/lw/refs/…      ← per-worktree
refs/worktree/x      …/.git/worktrees/lw/refs/…      ← per-worktree
refs/rewritten/y     …/.git/worktrees/lw/refs/…      ← per-worktree
refs/heads/lb        …/.git/refs/heads/lb            ← COMMON
refs/tags/v1         …/.git/refs/tags/v1             ← COMMON
refs/remotes/o/m     …/.git/refs/remotes/o/m         ← COMMON
```

This is the split CLAUDE.md warns about, and the code applies the per-worktree prefix to **all** of
it.

A shared ref is visible from every worktree under its plain name — `git rev-parse refs/heads/lb`
works from anywhere in the repository. That is the correct route for those refs.

## Givens — verified on `main`, treat as true

## Tests must be able to fail

Build a real fixture: a repository with a linked worktree on its own branch, a tag, and — created
**from inside the linked worktree** — `refs/bisect/good` and `refs/worktree/mine`. That last detail
matters: a per-worktree ref created from the main worktree lives in *main's* space and will not
resolve under `worktrees/<name>/`, so a fixture that gets it wrong tests nothing.

Assert every row of the table above, both the resolving and the non-resolving cases.

**Run these three mutations and report each individually.** A green suite is not evidence — every
rejected round in this project had a green suite.

| # | mutation | required |
|---|---|---|
| 1 | make `isPerWorktree` return `true` for everything (the current behaviour) | the `refs/heads/…` test FAILS |
| 2 | make `isPerWorktree` return `false` for everything | the `HEAD` and `refs/bisect/…` tests FAIL |
| 3 | classify `refs/worktree/` as shared but keep the rest | only that one test FAILS |

Mutation 1 restores exactly today's code, so it is the direct proof this issue's defect is covered.
Mutation 3 proves the classification is a set rather than a single prefix check.

Also assert that a genuinely absent ref still returns `nil` in both branches — otherwise the routing
could turn every miss into a hit.

## Why the existing tests do not catch it

`WorktreeContextTests.swift` exercises `resolveRef` and `refName` **only with `HEAD`** — lines 110,
114, 119, 120 and 127. `HEAD` is the one ref for which the prefix works, so every assertion passes and
the shared-ref case has never been tried. Adding a `refs/heads/…` case is the whole of the coverage
gap.
