## Description

Brennan, 2026-09-27, on the host, with `main` at `997fb348`: *"I just tried to open another path
and selected Batty but it actually change to this project instead. That is strange and very
broken."*

How the app was launched: `build/Switchyard-997fb348-dirty.app` (Release, from `make-release.sh`),
started with `open -n … --args -uiTestRepository /Users/brennan/Developer/brennanMKE/Git/Switchyard
-uiTestRealSurfaces`. The repository he opened was `/Users/brennan/Developer/brennanMKE/Batty`, an
ordinary repository whose `git rev-parse --git-common-dir` is `.git`.

**Leading hypothesis, not verified.** `ContentView.repositoryPath(window:tabs:fallback:)`
(`YardKit/Sources/YardUI/ContentView.swift` ~line 254) returns `fallback` whenever the window's
`tabIDs` is empty. `fallback` is `initialRepositoryPath`, which comes from the launch argument, and
every window the app creates gets it. The #0416 open flow may present a new or empty window that
falls back to the launch repository (Switchyard) instead of showing Batty. A second possibility is
that `place(_:)` fills the launch window, whose `tabIDs` is empty because it shows the path only
through the fallback, and the visible window is a different one.

The bug must also be checked with a **normal launch**, no launch arguments, then opening two
repositories in turn. That is how a person uses the app.

## Expected behavior

- [ ] Reproduced first, in the VM, with both launch styles; the planner records which of them fail.
- [ ] After File ▸ Open (or the toolbar's Open) picks repository B, B shows in a window. The launch
      repository or fallback never shows in place of B.
- [ ] The launch-argument repository seeds the launch window's model (a real tab) rather than
      acting as a per-window fallback, or equivalent. The planner decides from evidence.
- [ ] A VM UI test opens a second repository after launch and asserts its name is what is shown.
      The test fails on current `main`.
