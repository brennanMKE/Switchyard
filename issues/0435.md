## Description

Brennan, 2026-09-27, on the host, with `main` at `997fb348`: *"I just tried to open another path
and selected Batty but it actually change to this project instead. That is strange and very
broken."*

How the app was launched: `build/Switchyard-997fb348-dirty.app` (Release, from `make-release.sh`),
started with `open -n … --args -uiTestRepository /Users/brennan/Developer/brennanMKE/Git/Switchyard
-uiTestRealSurfaces`. The repository he opened was `/Users/brennan/Developer/brennanMKE/Batty`, an
ordinary repository whose `git rev-parse --git-common-dir` is `.git`.

**Leading hypothesis, not verified.** `ContentView.repositoryPath(window:tabs:fallback:)`
(`YardKit/Sources/YardUI/ContentView.swift` ~line 254) returns `fallback` whenever the window's
`tabIDs` is empty. `fallback` is `initialRepositoryPath`, which comes from the launch argument, and
every window the app creates gets it. The #0416 open flow may present a new or empty window that
falls back to the launch repository (Switchyard) instead of showing Batty. A second possibility is
that `place(_:)` fills the launch window, whose `tabIDs` is empty because it shows the path only
through the fallback, and the visible window is a different one.

The bug must also be checked with a **normal launch**, no launch arguments, then opening two
repositories in turn. That is how a person uses the app.

## Root cause (read from `main` at `4ea94528`, then reproduced in the VM, see VM results)

The leading hypothesis was right, and narrower than "every window gets the fallback": **only a
`-uiTestRealSurfaces` launch builds `ContentView` without a window model.**

`Switchyard/SwitchyardApp.swift`, the `WindowGroup(for: WindowID.self)` content, lines 71-73:

```swift
if Self.uiTestRealSurfaces {
    ContentView(initialRepositoryPath: path)      // no `window:` argument
} else {
```

The ordinary branch (line 86) passes `window: WindowStore.shared.windowState(for: windowID.wrappedValue)`.
This branch passes nothing, so `ContentView.window` is `nil` in **every** window of such a launch.
`ContentView.repositoryPath(window:tabs:fallback:)` (`YardKit/Sources/YardUI/ContentView.swift`
lines 254-262) then returns `fallback`, the launch path, because `window?.tabIDs.first` is `nil`:

```swift
guard let tabID = window?.tabIDs.first, let tab = tabs.tab(for: tabID) else {
    return fallback
}
```

The sequence Brennan hit:

1. `SwitchyardApp.init()` calls `RepositoryOpener.open(path: <Switchyard>)` →
   `RepositoryTabs.openInWindow` → `WindowStore.place(_:)`, which puts the Switchyard tab in
   `windows[0]`. The model is right.
2. The launch window renders `ContentView(initialRepositoryPath:)` with `window == nil`. It shows
   Switchyard through the fallback, not through the model. With `window == nil`, its `onAppear`
   never calls `noteShown` and its `onChange(of: appearsActive)` never sets `activeWindowID`.
3. File ▸ Open… Batty: `chooseAndOpen` → `openInWindow` → `place`. `activeWindowID` is `nil`, so
   "current" is `windows[0]`. It holds Switchyard, so `place` creates a new `WindowState` holding
   Batty, and `WindowPresenter.present` opens a window for its id. The model is right again.
4. SwiftUI builds that new window's content through the same branch:
   `ContentView(initialRepositoryPath: <Switchyard>)`, `window == nil`, fallback. It shows
   **Switchyard**. Batty's tab is in the model and no view reads it.

A plain launch (no arguments) takes the `else` branch, passes `window:`, and is not affected. The
VM runs below measure both launch styles.

**Why this is a real-user bug and not only a harness bug:** Brennan launches the Release app with
`-uiTestRepository … -uiTestRealSurfaces` to get a repository open at start, so for him this *is*
the app. Every VM spike that uses `launchWithFixtureRepository()` or `launchWithMapFixture()` runs
this branch. None of them opened a second repository, so none could see the bug.

### Decision (recorded here): delete the per-view fallback, and fix the call site

Expected behavior 3 of the original filing asked for the launch repository to seed the launch
window's model "or equivalent". It already does (step 1). The defect is that a second, per-view
path to a repository exists at all. So:

- `ContentView` loses `initialRepositoryPath`, and `repositoryPath(window:tabs:fallback:)` loses
  `fallback`. A window shows only what its `WindowState` holds. A view with no model shows "No
  repository open". Nothing can show a repository by going around the model.
- The `-uiTestRealSurfaces` branch passes the window model, exactly like the ordinary branch.

Both halves are needed. With only the first, the real-surfaces launch would show nothing, and
every real-surfaces VM spike would fail loudly. With only the second, the fallback would stay in
place as a trap for the next caller.

### Unit tests and the mutations that kill them

The defect is app-target wiring in `SwitchyardApp.swift`, which `swift test` cannot reach. So
**no unit test fails on `main` except by not compiling**: both call `repositoryPath(window:tabs:)`,
which does not exist there. The unit layer pins what it can:

- `contentViewShowsTheWindowModelsRepository` (rewritten): a view with no window model shows
  `nil`, even when a repository is open elsewhere. **Measured:** mutating `repositoryPath`'s
  `return nil` to `return tabs.tabs.first.map { $0.context.topLevel ?? $0.context.commonDir }`
  (a fallback to any open repository) fails it on two expectations (lines 188 and 190).
- `launchRepositoryThenSecondOpenEachShowTheirOwn` (new) runs the app's launch sequence: open A
  before any scene, let the `defaultValue` name the launch window, then open B. It ends with the
  launch window showing A and the presented window showing B. **Measured in the planning
  worktree:** mutating `idForWindowWithoutValue()` to always `return addWindow().id` fails it on
  three expectations (lines 212, 220 and 224). Dropping the `if current.tabIDs.isEmpty` guard in
  `place(_:)`, so the tab replaces the current window's repository, fails it on two (220 and 224).

The VM test is the one that fails on `main`.

test uses the menu and not that button.
