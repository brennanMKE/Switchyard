## Description

**Filed by #0170's review on 2026-08-08, from a mutation the reviewer invented rather than one in
the table.**

#0170 decision 3 states that id-bearing rebuild defects — `missingSnapshotCommit`,
`missingMetadata`, `anchorNotACommit` — **fold into the listing as items in id order**, carrying
their defect. The whole point is that a listing which silently omits a broken entry hides exactly
the state an agent needs to diagnose.

**Nothing tests it.** Review deleted the entire id-bearing fold from `recover`, replacing those
three cases with `break`, and ran the full suite: **712 tests, green.** A second mutation removing
`records.sort` is green for the same reason — no fixture ever creates an id-bearing rebuild defect,
so the sort is a no-op in every existing test.

`JournalList` has no other consumer, so nothing else in the suite could have caught either.

## The consequence in plain terms

A repository whose snapshot commit was garbage-collected would **list as though the entry never
existed.** An agent asking "what happened to my journal?" gets a clean, shorter list instead of an
entry marked defective — the failure mode #0030 chose skip-and-report specifically to avoid.

The decode-failure half of decision 3 *is* covered, by M6 and by
`metadataWhoseIdDisagreesWithItsAnchorIsADefectNotAChainEntry`. Only the rebuild-defect half is
bare.

## What this issue must deliver

- A fixture that produces each of the three id-bearing rebuild defects. #0030's own tests build
  them, so the construction is known and need not be re-derived: `update-ref` accepts a blob for a
  ref in a custom namespace (`anchorNotACommit`), and deleting the snapshot commit's loose object
  yields `missingSnapshotCommit` — with the object path resolved through
  `git rev-parse --git-path`, never string-built onto `.git/`.
- Assertions that each appears **as an item**, in **id order**, with its defect set and
  `position == nil` — not merely that no error was thrown.
- **A mutation row per assertion**, each observed red. Specifically, the two mutations that are
  currently green must both go red: deleting the id-bearing fold, and removing `records.sort`.
- Parameterise over both ref formats.

Expected: **+1 to +3 tests**.

## Also fix, while here

`#0170`'s Expected behavior carries an unsatisfiable presence criterion:
`grep -cF 'JournalWorktreeScope.protectedIDs'` is specified to print `1` but prints **2** — the
mandated file contains the string in a doc comment as well as at the call site. The expected count
was written from memory rather than measured. The round flagged it correctly and it did not affect
the outcome, but it is the class of defect that costs a round when it is load-bearing.

## Notes

Fifth consecutive issue where the code was right and the evidence was missing — after #0176,
#0177, #0178 and #0179. In every one the gap was found by a reviewer writing a mutation the
planner's table lacked. `docs/review-failures.md` check 0b is the rule; the recurring shape is
that **a mutation table drifts toward the code paths the tests already exercise**, so the untested
path is precisely the one no row perturbs.
