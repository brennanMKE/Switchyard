## Description

**Finding of #0044's fifth umbrella review, 2026-08-17. A restore silently destroys the work of a
sibling worktree that is stopped mid-rebase or mid-bisect.**

Decision 2 excludes *"a **detached** sibling (it holds no branch; its `HEAD` is per-worktree state that
shared-ref writes cannot touch)"*. **That basis is false in exactly the case decision 6 is about.** A
worktree stopped mid-rebase or mid-bisect **does** hold a branch — git keeps it in
`rebase-merge/head-name` or `BISECT_START` — and git's own porcelain honours the claim. But
`git worktree list --porcelain` reports that worktree as `detached` **with no `branch` line**, and
`WorktreeDisturbance.disturbances` reads only that attribute
(`WorktreeDisturbance.swift:120-121`), so the sibling falls out at the first `guard`.

**Measured, git 2.50.1** — sibling stopped at an `edit` in `git rebase -i HEAD~2` on `agent-branch`:

| from the main worktree | result |
|---|---|
| `git checkout agent-branch` | `fatal: 'agent-branch' is already used by worktree at '<path>'` — exit **128** |
| `git branch -f agent-branch main` | `fatal: cannot force update the branch 'agent-branch' used by worktree at '<path>'` — **128** |
| `git branch -d agent-branch` | `error: cannot delete branch 'agent-branch' used by worktree at '<path>'` — **1** |
| `git worktree list --porcelain` | `HEAD <oid>` / `detached` — **no `branch` attribute** |
| `git for-each-ref --format='%(worktreepath)' refs/heads/agent-branch` | **empty** — the atom shares the same blind spot, so it is not an alternative source |
| `cat "$(git rev-parse --git-path worktrees/agent-a/rebase-merge/head-name)"` | `refs/heads/agent-branch` |

Identical for bisect, with the branch in `BISECT_START`.

**Established against the engine**, by four probes: `disturbances` returns `[]` and `requireUndisturbed`
does not throw for a mid-rebase sibling whose branch the snapshot would move; the same for mid-bisect;
and **end to end**, `JournalRestore.restore` from present is **not refused**, rewinds
`refs/heads/agent-branch`, and the sibling's `git rebase --continue` then fails with
`error: could not update refs/heads/agent-branch` / `cannot lock ref … is at <ours> but expected
<theirs>`. **The agent's rebased commits are off the branch and its rebase cannot finish.**

The hole is reachable in exactly the paths decision 2 exists to cover: the cross-tool guard is skipped
at present (nil cursor) and under `bypassGuard`, so the disturbance check is the only protection there.

## Expected behavior

- [ ] `disturbances` learns a sibling's branch from its **sequencer state** when porcelain reports it
      detached: `rebase-merge/head-name`, `rebase-apply/head-name`, and `BISECT_START`.
- [ ] Resolve those through **`WorktreeContext.path(for:)`** — `path(for: "worktrees/<name>/rebase-merge/head-name")`
      — never by concatenating onto `.git/` (CLAUDE.md). That call already resolves correctly for a
      named sibling.
- [ ] **`rebase-merge/head-name` holds a full ref name; `BISECT_START` holds a short one.** Normalise,
      and say how.
- [ ] A **prunable** sibling needs no new handling — its directory is gone, so there is no rebase left
      to protect, and decision 5's prunable rule already covers the branch claim. Confirm that rather
      than assuming it.
- [ ] Tests: a mid-rebase sibling is named as a disturbance; a mid-bisect sibling is named; a genuinely
      detached sibling (no sequencer state) is **still** not a disturbance —
      `aDetachedSiblingHoldsNoBranchAndIsNeverDisturbed` must keep passing, since that is the case the
      exclusion is actually for.
- [ ] Mutation: drop the sequencer lookup and confirm the two new tests redden while the detached test
      stays green.
- [ ] Decision 2's exclusion text in `issues/0044.md` is corrected — it currently states the false
      basis, and stale decision text is what produced #0244 and #0250.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.

## Notes

Parent **#0044**, decision 2 — and this is a **data-loss** path, not a refusal-quality one.

**Interaction with #0251, which is with Brennan.** Fixing this *widens* #0251: a rebasing sibling
becomes one more holder that can permanently block the caller's undo. The **detection** half is
independent — a sibling mid-rebase does hold a branch whatever we decide to do about it — so implement
detection and refuse as decision 2 already says. If #0251 later replaces refusal with something
narrower, it applies to this holder uniformly.

## Round 2 — wire the restore path (2026-08-18)

**Round 1 fixed the pure function and said plainly that it had not fixed the bug.** It was right:
`JournalRestore.restore` never calls the enriching overload. `YardKit/Sources/YardGit/JournalRestore.swift:296`
reads

```swift
        let worktrees = try worktreeList(path: base, git: git)
```

and that raw list feeds **both** consumers — `detachingHeldHead` at line 322 and the four-argument
`disturbances(restoring:current:worktrees:callerPath:)` at line 374. So the data-loss path this issue
measured is still open on `main`.

`WorktreeDisturbance.withSequencerBranches(_:in:git:)` is already `public` and already tested. The
change is one call:

```swift
        // #0256: porcelain reports a sibling stopped mid-rebase or mid-bisect
        // as `detached` with no `branch` line, though it does hold one. Both
        // consumers below need that filled in -- the head-detach transformation
        // and step 5's disturbance check -- so it is enriched once, here.
        let worktrees = WorktreeDisturbance.withSequencerBranches(
            try worktreeList(path: base, git: git), in: context, git: git)
```

### Expected behavior — round 2

- [ ] `JournalRestore.swift:296` enriches the list exactly as above. Nothing else in that file changes.
- [ ] **End-to-end test, in `YardKit/Tests/YardGitTests/JournalRestoreTests.swift`:** a sibling worktree
      is stopped at an `edit` in `git rebase -i` on `refs/heads/agent-branch`; the caller restores an
      entry whose snapshot would move that branch. Since **guide §11 decision 23** (#0251) landed, the
      right outcome is no longer a refusal — restore **succeeds**, `report.leftAlone` names
      `refs/heads/agent-branch`, and the branch is **unmoved**. Assert all three.
- [ ] **The claim that makes it a data-loss test:** after the restore, the sibling's
      `git rebase --continue` **succeeds**. Before this change it failed with
      `error: could not update refs/heads/agent-branch` / `cannot lock ref … is at <ours> but expected
      <theirs>`, which is the agent's commits going off the branch. Assert the continue's exit status,
      not just the ref value — that is the difference between testing the mechanism and testing the harm.
- [ ] **A mid-bisect sibling too**, at least to the `leftAlone` assertion. The continue half is
      rebase-specific.
- [ ] **`detachingHeldHead` sees the enrichment as well**, which is a second behaviour change from the
      same line: when the restored `HEAD` names a branch a **mid-rebase** sibling holds, `HEAD` now
      detaches at the recorded oid instead of adopting it (#0211, decision 16). Add a test, and say
      whether you think detaching is right here — it is the same reasoning as a live ordinary sibling,
      but it is a real behaviour change and should not land unnoticed.
- [ ] **Mutation:** revert line 296 to the raw `worktreeList(...)`. The new restore tests must redden
      while `aMidRebaseSiblingIsNamedAsADisturbance` (round 1's, on the pure function) stays **green** —
      that pair is the whole point, since round 1 was green with the bug live.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.

### Why this was not caught in planning

The issue named `WorktreeDisturbance.swift` and its tests, and the round obeyed that scope exactly as
instructed. **The planning defect was naming files instead of naming the call path** — the measured
probes in the Description ran against `JournalRestore.restore`, so the fix had to reach it, and nothing
in "The files" said so. Recorded in `docs/review-failures.md` as a `spec-defect`.
