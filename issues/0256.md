## Description

**Finding of #0044's fifth umbrella review, 2026-08-17. A restore silently destroys the work of a
sibling worktree that is stopped mid-rebase or mid-bisect.**

Decision 2 excludes *"a **detached** sibling (it holds no branch; its `HEAD` is per-worktree state that
shared-ref writes cannot touch)"*. **That basis is false in exactly the case decision 6 is about.** A
worktree stopped mid-rebase or mid-bisect **does** hold a branch — git keeps it in
`rebase-merge/head-name` or `BISECT_START` — and git's own porcelain honours the claim. But
`git worktree list --porcelain` reports that worktree as `detached` **with no `branch` line**, and
`WorktreeDisturbance.disturbances` reads only that attribute
(`WorktreeDisturbance.swift:120-121`), so the sibling falls out at the first `guard`.

**Measured, git 2.50.1** — sibling stopped at an `edit` in `git rebase -i HEAD~2` on `agent-branch`:

| from the main worktree | result |
|---|---|
| `git checkout agent-branch` | `fatal: 'agent-branch' is already used by worktree at '<path>'` — exit **128** |
| `git branch -f agent-branch main` | `fatal: cannot force update the branch 'agent-branch' used by worktree at '<path>'` — **128** |
| `git branch -d agent-branch` | `error: cannot delete branch 'agent-branch' used by worktree at '<path>'` — **1** |
| `git worktree list --porcelain` | `HEAD <oid>` / `detached` — **no `branch` attribute** |
| `git for-each-ref --format='%(worktreepath)' refs/heads/agent-branch` | **empty** — the atom shares the same blind spot, so it is not an alternative source |
| `cat "$(git rev-parse --git-path worktrees/agent-a/rebase-merge/head-name)"` | `refs/heads/agent-branch` |

Identical for bisect, with the branch in `BISECT_START`.

**Established against the engine**, by four probes: `disturbances` returns `[]` and `requireUndisturbed`
does not throw for a mid-rebase sibling whose branch the snapshot would move; the same for mid-bisect;
and **end to end**, `JournalRestore.restore` from present is **not refused**, rewinds
`refs/heads/agent-branch`, and the sibling's `git rebase --continue` then fails with
`error: could not update refs/heads/agent-branch` / `cannot lock ref … is at <ours> but expected
<theirs>`. **The agent's rebased commits are off the branch and its rebase cannot finish.**

The hole is reachable in exactly the paths decision 2 exists to cover: the cross-tool guard is skipped
at present (nil cursor) and under `bypassGuard`, so the disturbance check is the only protection there.

## Expected behavior

- [ ] `disturbances` learns a sibling's branch from its **sequencer state** when porcelain reports it
      detached: `rebase-merge/head-name`, `rebase-apply/head-name`, and `BISECT_START`.
- [ ] Resolve those through **`WorktreeContext.path(for:)`** — `path(for: "worktrees/<name>/rebase-merge/head-name")`
      — never by concatenating onto `.git/` (CLAUDE.md). That call already resolves correctly for a
      named sibling.
- [ ] **`rebase-merge/head-name` holds a full ref name; `BISECT_START` holds a short one.** Normalise,
      and say how.
- [ ] A **prunable** sibling needs no new handling — its directory is gone, so there is no rebase left
      to protect, and decision 5's prunable rule already covers the branch claim. Confirm that rather
      than assuming it.
- [ ] Tests: a mid-rebase sibling is named as a disturbance; a mid-bisect sibling is named; a genuinely
      detached sibling (no sequencer state) is **still** not a disturbance —
      `aDetachedSiblingHoldsNoBranchAndIsNeverDisturbed` must keep passing, since that is the case the
      exclusion is actually for.
- [ ] Mutation: drop the sequencer lookup and confirm the two new tests redden while the detached test
      stays green.
- [ ] Decision 2's exclusion text in `issues/0044.md` is corrected — it currently states the false
      basis, and stale decision text is what produced #0244 and #0250.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.
