# 0050 — Embed and sign the switchyard binary in the app bundle

| | |
|---|---|

## Description

A Run Script phase builds `yard` with `swift build` and copies it to `Contents/Resources/bin/yard`,
then signs it. Embedded via a script phase, **never as a product dependency** — RemoteControl
documents why.

## Expected behavior

- [ ] One `--arch` per Xcode arch, so a universal app produces a universal CLI.
- [ ] Scratch path under `DERIVED_FILE_DIR`, so an Xcode build does not fight a `swift build` running in a terminal.
- [ ] SwiftUI preview builds skip the phase.
- [ ] Embedded binary is signed separately from the bundle, and both verify.
- [ ] The embedded binary runs and reports a real version.

### The one thing that must not be done

> **Do not add the CLI's executable *product* as an Xcode `XCSwiftPackageProductDependency` on the app
> target.**

RemoteControl's doc calls this "the one that will cost you a day": an executable product in the app's
build graph breaks `Bundle.module` resolution under the `xcodebuild` test runner, and every test in
that bundle then dies with `unable to find bundle named …`. `swift test` does **not** reproduce it, so
it is introduced easily and attributed slowly. Use a **Run Script** phase; the executable never enters
Xcode's graph.

### The script, to be added as a Run Script phase on the `Switchyard` target

Transcribe it. It is adapted from the doc and every line in it has a stated reason there.

```bash
set -euo pipefail

# SwiftUI preview builds re-run script phases; nothing here is needed for one.
if [ "${ENABLE_PREVIEWS:-NO}" = "YES" ] && [ -n "${PREVIEW_FRAMEWORK_PATHS:-}" ]; then
    echo "note: skipping CLI embed for preview build"
    exit 0
fi

PACKAGE_DIR="$SRCROOT/YardKit"

case "$CONFIGURATION" in
    Release) SWIFT_CONFIG=release ;;
    *)       SWIFT_CONFIG=debug ;;
esac

# One --arch per Xcode arch, so a universal app gets a universal CLI.
ARCH_FLAGS=""
for arch in $ARCHS; do
    ARCH_FLAGS="$ARCH_FLAGS --arch $arch"
done

# Scratch path under DERIVED_FILE_DIR rather than the package's .build, so an
# Xcode build does not fight a `swift build` running in a terminal.
SCRATCH="$DERIVED_FILE_DIR/yardkit"

BUILD_ARGS="--package-path $PACKAGE_DIR --scratch-path $SCRATCH \
            --configuration $SWIFT_CONFIG $ARCH_FLAGS --product switchyard"

xcrun swift build $BUILD_ARGS
BIN_DIR="$(xcrun swift build $BUILD_ARGS --show-bin-path)"

DEST_DIR="$BUILT_PRODUCTS_DIR/$CONTENTS_FOLDER_PATH/Resources/bin"
mkdir -p "$DEST_DIR"
cp -f "$BIN_DIR/switchyard" "$DEST_DIR/switchyard"

# Xcode does not sign a Mach-O that a script phase drops into the bundle, and an
# unsigned nested binary breaks the bundle seal. Unsigned builds must keep
# working, so this is guarded rather than unconditional.
if [ "${CODE_SIGNING_REQUIRED:-YES}" != "NO" ] && [ -n "${EXPANDED_CODE_SIGN_IDENTITY:-}" ]; then
    codesign --force --sign "$EXPANDED_CODE_SIGN_IDENTITY" \
        --options runtime --timestamp=none "$DEST_DIR/switchyard"
else
    echo "note: code signing disabled; embedded CLI left unsigned"
fi
```

Declare the phase's **output path** so Xcode tracks the file:

```
$(BUILT_PRODUCTS_DIR)/$(CONTENTS_FOLDER_PATH)/Resources/bin/switchyard
```

`--show-bin-path` is called with the *identical* arguments on purpose — SwiftPM's output directory
depends on configuration and arch flags, and asking it is what keeps Debug, Release and universal
builds all working.

### Signing — read this before touching anything

The `codesign` line above **signs with an identity Xcode has already resolved** (`$EXPANDED_CODE_SIGN_IDENTITY`).
It creates nothing, revokes nothing, and does not run at all in the unsigned builds this project uses
by default. That is the whole of this issue's contact with signing.

**Do not** pass `-allowProvisioningUpdates`, do not change `CODE_SIGN_STYLE`, `CODE_SIGN_IDENTITY`,
`DEVELOPMENT_TEAM` or `PROVISIONING_PROFILE_SPECIFIER`, and do not run a signed build to "check". If
any signing stop-word appears — `No signing certificate ... found`, `its private key is not installed
in your keychain`, `errSecInternalComponent`, `User interaction is not allowed` — **stop, do not
retry, and report**. CLAUDE.md's Code signing section is not advisory.

### Verification — and the trap that makes the obvious check useless

Build unsigned:

```
xcodebuild build -project Switchyard.xcodeproj -scheme Switchyard -destination 'platform=macOS' \
  CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO
```

Then, against `$BUILT_PRODUCTS_DIR/Switchyard.app` (find it with `-showBuildSettings`):

1. **The file exists**: `ls -l "$APP/Contents/Resources/bin/switchyard"`.
2. **It runs**: `"$APP/Contents/Resources/bin/switchyard" --version` prints `switchyard 0.0.1` and
   exits 0. Reporting the *host app's* version instead is #0219; `0.0.1` is the correct output today.
3. **No `@rpath`**: `otool -L "$APP/Contents/Resources/bin/switchyard" | grep @rpath` prints **nothing**.
   A CLI that inherits an `@rpath` load command cannot resolve it from two levels below
   `Contents/Frameworks/` and dies with `Library not loaded` — a bug that shipped in the sibling
   project because its verification checked architecture with `file` instead of running the binary.
   `switchyard` depends only on `YardKit`, which links nothing, so this should be clean; report the
   full `otool -L` output either way.
4. **`codesign -v --deep --strict "$APP"` proves nothing about this binary** and must not be cited as
   if it did. A Mach-O under `Contents/Resources/` is sealed as a *resource*; `--deep` descends into
   nested code only. The embedded CLI can be entirely unsigned and that command still reports the
   bundle valid. On an unsigned build there is nothing to check here at all — say so rather than
   running a command whose success is meaningless.

`cd YardKit && swift test` must still print `Test run with 924 tests` — this issue adds no package
code, and a changed count means the script phase is doing something it should not.

### Sequencing note

The phase runs `swift build` on every app build, so an app build now depends on the package building.
That is intended, and it is why the criterion above re-runs the package suite.
