## Description

Open the three-way merge UI for a conflicted path, block, and return the resolution. The interactive
counterpart to `yard conflicts` (#0017), and the place where a human's judgment gets captured once
and reused by `rerere` (#0065).

## Expected behavior

- [ ] Renders in the **Detail pane** of the conflicted repository's tab, routed through #0084 — not in a detached window.
- [ ] Renders ours, base, and theirs from the blob IDs #0017 reports.
- [ ] Resolution is written to the index and returned as structured data.
- [ ] Handles add/add, delete/modify, and rename conflicts, not only content conflicts.
- [ ] Exit 3 when the app is unavailable; exit 8 when conflicts remain unresolved on return.
- [ ] Cancelling leaves the conflicted state untouched, not half-resolved.

### The interaction design (what Brennan is signing off)

**The Detail pane becomes the resolution surface for the repository's conflicts.** When
`resolve --interactive --wait` arrives for a repository, its tab routes through #0084 and the Detail
pane switches to the resolution view: one conflicted path at a time, the paths listed as a vertical
stack of resolution cards (newest conflict kind first), each card showing **ours / base / theirs**
from #0017's stage blobs side by side, rendered with the existing #0082 diff machinery — not a new
renderer.

**Per-path resolution vocabulary** (what the human can do to each conflicted path):

| kind | choices |
|---|---|
| content (`UU` etc.) | **Use ours** · **Use theirs** · **Edit merged** — a text editor seeded with the file's conflict-marked content; what the human saves is what stages |
| add/add (`AA`) | **Use ours** · **Use theirs** · **Edit merged** (seeded with ours' content) |
| delete/modify (`DU`/`UD`) | **Keep the deletion** · **Keep the modification** · **Edit merged** (seeded with the surviving side) |
| rename (`*` conflicts involving a path move) | **Take ours' path+content** · **Take theirs'** — the round documents exactly which porcelain kinds reach this card; a kind the engine cannot resolve is presented read-only with an explanation rather than a fake choice |

Every card also carries an optional **note to the agent** (free text, per path). A path is marked
resolved when the human presses the card's **Stage resolution** button — the engine applies it
(write the chosen/edited content to the working file, `git add` the path — one path per action,
individually undoable through #0027's checkpoint machinery). **Nothing is staged until the human
presses the button on that card.** The human can stage some paths and leave others conflicted.

**Submit** (the sheet-level action) ends the blocking request: the reply carries every path's
resolution as structured data — path, kind, what was chosen, the edited content when edited, the
note — and the CLI re-runs `conflictedFiles` after the reply: **conflicts remaining → exit 8
(`blockedOnConflicts`, which is what that code exists for); all resolved → exit 0**. **Cancel**
(the sheet-level discard) stages nothing, touches nothing, and returns **exit 7** — a considered
human decision, same vocabulary as `ask`'s decline. Timeout (`--timeout N`, default 3600) →
**exit 10**; app unavailable → **exit 3** (`launchIfNeeded: false`); app quits mid-resolve →
**exit 5**. Resolve's blocking semantics are #0055's, inherited whole — including `timedOut = 10`.

**Untrusted content rule**: ours/theirs/base blobs are rendered as text with conflict markers
visible, never interpreted; the seeded editor is plain text.

### The wire and the rounds

- **Round 1 (headless-testable)**: `ResolveRequest`/`ResolveReply`/`ResolveOutcome` wire types in
  YardKit (the #0055 pattern; `ResolveReply` carries per-path `PathResolution` entries);
  `PendingResolveStore` (keyed by commonDir, ONE pending per repo — a second `resolve --wait`
  supersedes, the review semantics; the queue is `ask`'s distinction); `AppServiceProtocol`
  `performResolve`; the CLI arm (`resolve` in `CommandRegistry.all`: `--wait` required, `--timeout`,
  `<pathspec>` optional — default all conflicted paths; exits 0/3/5/7/8/10); the **engine apply
  half**: `ResolveApply.apply(path:resolution:in:)` in YardGit — write content (from a stage blob or
  edited text) + stage the path, checkpointed; the serving body resolves the conflict list
  engine-side (like #0055's diff resolution) and delivers ours/base/theirs blob contents to the
  store. Tests: wire bytes, round-trip, exit 3/5/8/10, apply paths per kind on real fixture
  conflicts (content, add/add, delete/modify), cancel-stages-nothing.
- **Round 2 (the pane)**: the resolution cards in YardUI on the #0055 sheet pattern (value-driven
  model, per-tab presentation, untrusted-content rule), the Detail-pane presentation binding, blob
  rendering reusing #0082. Tests assert every state through the model.
- **Round 3**: `scripts/verify-resolve.md` (UNRUN manual scenarios: the four kinds end to end,
  cancel-stages-nothing, conflicts-remain → exit 8, timeout), polish, and the Expected-behavior
  sweep.
