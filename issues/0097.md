## Description

Wrap `git worktree repair` for the moved-directory case — reestablishing the links between a main
worktree and its linked worktrees after either end has been moved.

## Givens — verified on `main`, treat as true

1. `YardKit/Sources/YardGit/WorktreeContext.swift` provides `WorktreeContext.resolve(...)` plus
   `topLevel: String?` (nil in a bare repo), `gitDir`, `commonDir`, `worktreeName: String?`,
   `isLinkedWorktree`, `isBare`, and `path(for:git:)`. Use it; do not resolve paths yourself.
2. **`WorktreeContext` does not expose the main worktree's path.** If you need it, take the **first**
   `worktree <path>` line of `git worktree list --porcelain` — that entry is the main worktree from
   any worktree in the repo. Verified from inside a linked worktree. Do not derive it by trimming
   `/.git` off `commonDir`; that breaks on bare repos and on a `.git` file pointing elsewhere.
3. `YardKit/Sources/YardGit/FixtureRepository.swift` provides — verified by reading it, these are
   the real signatures:

   ```swift
   public func addWorktree(named name: String, branch: String) throws -> URL   // returns the path
   public func addWorktree(path targetDir: String, branch: String) throws -> URL
   public mutating func build(_ commits: [Commit]) throws
   public func destroy()
   ```

   `addWorktree` **returns the worktree URL** — move that, and keep the returned value so the test
   can name both the old and the new path. `repo.oids` is populated only by `build(_:)`;
   force-unwrapping it for anything else traps and aborts the whole suite, which cost #0112 a round.
4. **Every shell-out goes through `GitProcess`** (`YardKit/Sources/YardGit/GitProcess.swift`). Do not
   construct `Process` directly — the boundary is centralised there so it stays testable, and
   libgit2 does not run hooks.
5. **Never build a path by concatenating onto `.git/`.** Resolve through `git rev-parse --git-path`
   or `WorktreeContext`. Reftable repositories have no `.git/refs/**` at all and return nothing
   rather than erroring.

## Probed 2026-08-07 against real repositories — read this before writing the test

The 2026-08-06 note says asserting "status fails before repair" would be wrong. It is wrong. Here is
what to assert instead, measured rather than reasoned.

**1. A moved worktree looks exactly like a deleted one, from the main worktree.** After
`git worktree add ../w1` then `mv ../w1 ../w1-moved`, `git worktree list --porcelain` run from the
main worktree reports the **old** path:

```
worktree /…/w1                                        ← the OLD path, which no longer exists
HEAD 282a573…
branch refs/heads/w1
prunable gitdir file points to non-existent location
```

**That is the assertion for "broken":** the porcelain still names the old path and carries a
`prunable` line. Not `status`, which exits **0** from inside the moved directory, because its own
`.git` file still points at the administrative directory.

**2. `git worktree repair <new-path>` writes its report to stderr, exit 0:**

```
repair: gitdir incorrect: /…/main/.git/worktrees/w1/gitdir
```

Verified by redirecting each stream separately — `git worktree repair … 2>/dev/null` prints
**nothing at all**. `GitProcess.Output.text` and `.lines` are **stdout only**, so a round parsing
them reports "nothing repaired" for every input, including a successful repair. Use
`Output.standardError`. This is the single most likely way to lose a round on this issue.

**3. After repair, the porcelain names the new path and the `prunable` line is gone.** That is the
assertion for "fixed".

**4. Repair is idempotent, and silence is meaningful.** Running it again exits 0 and prints
**nothing**. So "which links were repaired" is derived from the `repair: ` lines on stderr, and an
empty result means *nothing needed repairing* — not failure. Do not map empty output to an error.

**5. The order that destroys data.** `git worktree prune` reaps a merely-moved worktree, and
afterwards `git worktree repair <new-path>` fails with exit 1:
`error: unable to locate repository; .git file does not reference a repository`. The directory
survives on disk, orphaned. **Repair before prune, never after.** #0096 is where the opt-in gate for
pruning lives; this issue only needs to not make the situation worse.

## The three invocation positions, concretely

Expected behavior asks for all three. They are not the same call:

| position | command | what it fixes |
|---|---|---|
| from the main worktree, naming each moved path | `git -C <main> worktree repair <newpath>…` | the admin `worktrees/<name>/gitdir` reverse pointer |
| from inside a moved worktree, no arguments | `git -C <moved> worktree repair` | the same reverse pointer, for that worktree |
| from the main worktree after **the main repo itself** moved | `git -C <main> worktree repair` | each linked worktree's own `.git` file |

The last one is the case the other two do not cover, and it is the one a test is most likely to skip.
Cover at least the first two; if you cover only two, say which you left out and why.

### Verified `git worktree` behaviour — probed 2026-08-06, still true

Run against a real repo with a linked worktree, not read from the man page.

- **`git worktree remove <path>` refuses a dirty worktree with exit `128`** and the message
  `fatal: '<path>' contains modified or untracked files, use --force to delete it`.
  `--force` then succeeds. "Dirty" includes untracked files, not just modifications.
- **`git worktree prune -v`** prints one line per reaped entry:
  `Removing worktrees/<name>: gitdir file points to non-existent location`, and the entry disappears
  from `git worktree list --porcelain`.
- **`git worktree repair <path>`** prints `repair: gitdir incorrect: <path-to-admin-gitdir-file>`.

**The counter-intuitive one, and the reason it is written down:** after a linked worktree is *moved*
on disk, `git -C <new-path> status` **still exits 0**. The worktree keeps working from the inside,
because its own `.git` file still points at the administrative directory. What breaks is the
*reverse* pointer — the `worktrees/<name>/gitdir` file in the main repository still names the old
location. So a test asserting "status fails before repair" would be **wrong**, and would pass or fail
for reasons unrelated to the code under test. Assert on the administrative state, or on an operation
run from the main repository, not on `status` from inside the moved worktree.

### I was wrong in round 1: the implementation is not correct

Round 1's review said the source was right and must not change. **It was right only because position 3
was never exercised.** Round 2 added it, and it fails — correctly.

`mainRepoMovedLinkedWorktreeIsPrunableThenRepaired` asserts `!reports.isEmpty` and gets `[]`, because
**git uses a different message when the main repository moves.** Measured:

```
position 1 — the linked worktree moved:
  repair: gitdir incorrect: …/m/.git/worktrees/wm/gitdir

position 3 — the MAIN repo moved:
  repair: .git file broken: …/w1
```

`WorktreeRepair.repairReportPrefix` hardcodes `repair: gitdir incorrect:`, so `parseReport` drops the
line even though a real repair happened. **This is a source change, and the round-1 instruction to
leave the source alone is superseded.**

Note the payload also changes meaning: `gitdir incorrect` reports the **administrative gitdir file**,
`.git file broken` reports the **linked worktree's own path**.

### The complete message set, read from git's source — do not guess at it

`git/builtin/worktree.c:1437`:

```c
static void report_repair(int iserr, const char *path, const char *msg, void *cb_data)
{
    if (!iserr) fprintf_ln(stderr, _("repair: %s: %s"), msg, path);
    else      { fprintf_ln(stderr, _("error: %s: %s"), msg, path); *exit_status = 1; }
}
```

and the three `msg` values, all of them, from `git/worktree.c`:

| line | msg |
|---|---|
| 685 | `.git file broken` |
| 914 | `gitdir unreadable` |
| 924 | `gitdir incorrect` |

**So parse structurally, not by whitelist.** A stderr line beginning `repair: ` is a report; split the
remainder on the first `": "` into a reason and a path. That covers all three today and anything git
adds later. A line beginning `error: ` is a failure, and git exits 1 in that case.

`GitProcess` already sets `LC_ALL=C` (`GitProcess.swift:193`), so these strings are guaranteed
English — no locale handling is needed.
