## Description

Guide §11 decision 44, the wiring. After this issue:

- **`ContentView` holds `@State historyIndex`** and assigns it only where `history` and `sidebar`
  are assigned: `reload()` (reset to `.empty` with the others, then from the load) and
  `refreshAfterMutation(select:)`. Both call #0553's `loadRepositoryWindow(at:)` instead of the
  six sequential awaits, so the index is built off the main actor and every value lands on one
  main-actor turn. **Never assigned from `body`** (swift-guidance's observation rule: view
  construction is pure). `reloadSidebarAfterForget()` still assigns `sidebar` alone and leaves the
  index as it is: a rerere forget touches the rr-cache, never a ref.
- **`CommitHistoryView` takes `index: HistoryIndex` (required, no default)** and its `body` reads
  `index.matches(query:)`, `index.entriesByOid` and `index.chipsByOid` instead of building them —
  O(1) per render instead of #0552's measured 42-46 ms release / 731-770 ms debug (plus 118-154 ms
  while a filter query is typed). Required so that a caller that forgets it does not compile; the
  `#Preview` builds its own.

`CommitHistoryView.body` re-runs whenever `ContentView.body` does, because `ContentView` passes it
fresh closures (`menuStates`, `perform`, `onOpenChanges`, the selection `Binding`) that SwiftUI
cannot compare — so a click, an arrow key, or a filter keystroke paid the whole rebuild. (That
re-run frequency is inferred from the code, not instrumented; the per-render cost is measured.)

What the user sees change: nothing on a small repository; on a large one the filter stops lagging
behind typing, the arrow keys stop stuttering, and a repository opens and refreshes after every
mutation in about a third of the time (0.62-0.68 s → 0.20-0.21 s on git/git, #0553).

The reads `reload()` made one at a time used to let the header appear before History on a slow
repository; now every pane appears together, about 0.2 s after the spinner on git/git. The
`summary = nil` spinner at the start of `reload()` is unchanged.
