## Description

**Finding of #0160's eighth umbrella review, 2026-08-18, which overturned three prior passes'
"unreachable" verdict — with a measurement rather than a re-reading.** A mid-rebase `amend` under the
**`--apply`** backend double-records a rebase, violating bullet 3.

`YardKit/Sources/YardGit/JournalObserved.swift:243-245`:

```swift
guard decision.source == .amend else { return false }
let rebaseMergePath = try context.path(for: "rebase-merge", git: git)
return fileManager.fileExists(atPath: rebaseMergePath)
```

Passes 5, 6 and 7 each recorded this as a proposal on the grounds that *"`git rebase --apply` never
amends internally."* **That is true and it is not what bullet 3 says.** The criterion is about
*mid-rebase `amend` invocations*, not about who raises them — and **a user's own `git commit --amend`
during a stopped `--apply` rebase raises one**, after which git's final `rebase` invocation repeats the
pair.

**Measured, git 2.50.1**, plain shell with a logging `post-rewrite` hook and no Switchyard involved.
Pre-rewrite side branch `c3=57652de`, `c4=1f992a2`, `c5=de9bed1`; conflicting `git rebase --apply main`,
resolve, `--continue`, stop on `c4`, then `git commit --amend` instead of `--continue`, then
`git rebase --skip`:

```
--- source=amend
   rebase-apply live
     27fcaba90b17e1bad3c791626bc845198144db84 f3ba37267b67f4ce491f95a8c15032c7368ed4b2
--- source=rebase
   rebase-apply live
     57652de56065bea16e96b6ca0f6a65fe5e0e1433 27fcaba90b17e1bad3c791626bc845198144db84
     1f992a2ae239115e474a4a943f377a6dbfa4a876 f3ba37267b67f4ce491f95a8c15032c7368ed4b2
     de9bed145ab4feef7a5cc57703d5dd36afcbd6cd 5f2e3e290c34dadc8dec5e72ffad9217ca6e5139
```

`27fcaba` is an intermediate commit **that never existed in the pre-rewrite history** — the exact class
the issue's Description names — and the authoritative invocation repeats `→ f3ba372`.

**Reproduced against production code** by a throwaway probe driving the same fixture:

```
UMB8: isMidRebaseAmend=false firstRecord=Optional(01M0AGJF4R44GJZQNBGED9HWTB) observedCount=2
✘ (observed.count → 2) == 1
```

**Two observed entries for one rebase.** That is bullet 3's failure, verbatim.

## The fix, and the discriminator it needs — both measured

Widen the probe to the `rebase-apply` layout, but **not indiscriminately**:

| state | marker file |
|---|---|
| `git am` | `rebase-apply/applying` |
| `git rebase --apply` | `rebase-apply/rebasing` |

**Keying on `rebasing` does not suppress a legitimate amend during a `git am`**, which has no final
`rebase` invocation to repeat the pair — so `am`'s amend really is its own event and must keep
producing its own observed entry.

The review applied exactly that as mutation M8: **the full existing suite stayed green (1094/78)** while
the probe flipped to `isMidRebaseAmend=true, observedCount=1`. **Nothing pins the current
rebase-merge-only behaviour** — `aMidRebaseAmendDoesNotProduceItsOwnObservedEntry` creates `rebase-merge`
by hand and never exercises the other layout.

## Expected behavior

- [ ] `isMidRebaseAmend` returns true for a stopped **`--apply`** rebase, keyed on
      `rebase-apply/rebasing`, resolved through `WorktreeContext.path(for:)`.
- [ ] **`git am` still produces its own observed entry.** A test for that case, keyed on
      `rebase-apply/applying` being present and `rebasing` absent — otherwise the fix trades one
      double-record for a silent drop.
- [ ] A test reproducing the measured scenario end to end: conflicting `--apply` rebase, stop, user
      `git commit --amend`, then the final rebase invocation — **one** observed entry, not two.
- [ ] **Mutation 1:** revert to `rebase-merge` only. The new test must redden.
- [ ] **Mutation 2:** widen to *any* `rebase-apply` (drop the `rebasing` discriminator). The `git am`
      test must redden. That pairing is what shows the discriminator earns its place.
- [ ] **Both doc comments are corrected.** `isMidRebaseAmend`'s and
      `aMidRebaseAmendDoesNotProduceItsOwnObservedEntry`'s each call `rebase-merge` *"git's own signal
      that a rebase is in progress"*, which is true only of the merge backend.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, above the count in `docs/test-baseline.txt`.

## Notes

**Parent #0160**, bullet 3. **Blast radius is the foreign path only** — `attachRewrite`'s
`guard decision.isOwnInvocation` keeps an own operation's slot from being consumed by a user's manual
amend, and a rebase continuation is a new process carrying no marker. The harm is a **spurious observed
entry carrying a bogus old oid** beside the authoritative one.

**Worth recording as a lesson about reviews, not just about this bug:** three passes reached the same
wrong conclusion because they each re-examined the *argument* ("git never amends internally under
`--apply`") instead of the *criterion*. The eighth pass asked what the criterion actually said, then
went and measured. A proposal that survives three passes unchanged is a candidate for that treatment,
not evidence it was right.
