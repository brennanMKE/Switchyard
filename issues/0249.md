## Description

**Finding 4 of #0044's fourth umbrella review, 2026-08-17.** #0044 **decision 6** states:

> `for-each-ref` enumerates `refs/rewritten/*` … so `RefSnapshot.capture` **already** carries them and
> same-worktree restore already round-trips them.

**Nothing pins it.** Adding `!name.hasPrefix("refs/rewritten/")` to the skip in
`RefSnapshot.listDirectRefs` leaves the suite **fully green**.

The three places that mention `refs/rewritten` in tests all miss it: `PerWorktreeRefFilterTests`
builds synthetic `RefSnapshot` values rather than capturing, and `WorktreeResolveRefSharedRefTests`
exercises `WorktreeContext.resolveRef` rather than capture. So the claim "capture already carries
them" is asserted nowhere.

Same class as **#0203**, **#0210** and **#0230** — a stated criterion with no test — and the third
instance of it in this umbrella.

`refs/rewritten/*` matters because it is **per-worktree despite the `refs/` prefix** (CLAUDE.md), and
it is what an interrupted rebase uses to remember its mapping. A capture that silently dropped it would
lose exactly the state a mid-rebase checkpoint exists to preserve.

Writing a per-worktree ref by hand needs `git update-ref` against the **worktree's own** `$GIT_DIR` —
`WorktreeContext.path(for:)` and `WorktreeContext.refName(_:inWorktree:)` are the tools; never build the
path by string concatenation.
