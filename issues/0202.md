## Description

**Found by the #0034 umbrella review, 2026-08-17, and nearly triggered by #0188 the same day.**

`JournalRestore.worktreeCommit(of:at:git:)` (`YardKit/Sources/YardGit/JournalRestore.swift:426-435`)
identifies the worktree snapshot commit **positionally**:

```swift
return parents.count > 1 ? parents.last : nil
```

It is correct today only because of the order two unrelated lines happen to appear in
`JournalCheckpoint.writeEntry`: `keepAliveParents(of: snapshot, ...)` first, then
`keepAlive.append(worktree.commit)` last. **Nothing states that as a contract and nothing tests it.**

#0188 came within one line of breaking it: its pasted change appended `sequencer.keepAlive` *after* the
worktree commit, which would have made `parents.last` a sequencer oid. That line was removed for a
different reason — tree oids cannot be commit parents at all — so this stayed latent by luck rather than
by design. The next keep-alive addition has the same trap waiting.

**Why it fails silently.** A wrong `worktreeCommit` does not throw. `JournalRestore` would try to apply
the wrong commit as a stash, or find nothing to apply, and the honest report would say `worktree` was
restored. The tests that would notice compare worktree bytes, and they only run in the round-trip suite.

## Expected behavior

- [ ] The worktree snapshot commit is identified by something **stable**, not by position. Options, in
      the order I would try them: read it from the entry's own metadata (`captured.worktree == .stash`
      already records *that* it exists, so the oid could ride alongside); or name it in the anchor tree
      as its own entry the way `index` and `untracked` are; or, cheapest, keep the positional read but
      make the contract explicit and enforced — a comment plus a test that appends a second keep-alive
      oid and asserts the worktree commit is still found.
- [ ] Whichever is chosen, a test that **fails under the #0188-shaped mutation**: append an extra
      keep-alive commit after `worktree.commit` in `writeEntry` and confirm the worktree still round
      trips. That mutation is the whole point of the issue.
- [ ] `cd YardKit && swift test` prints a `Test run with N tests` line exceeding the count in
      `docs/test-baseline.txt` by exactly 1.

## Notes

Prefer the smallest change that removes the positional coupling. This is not an invitation to redesign
the anchor's parent list — #0028 settled that parents are the keep-alive set, and that is fine; the
defect is only that one reader infers *meaning* from a position within it.

Sequence after **#0200**, which adds captures to the restore flow's `writeEntry` call and will touch the
same lines. Doing them in the other order means writing this test twice.
