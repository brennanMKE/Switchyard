## Description

**Proposal C from #0160's fourteenth umbrella pass.** `YardKit/Sources/YardGit/JournalCheckpoint.swift:504`
trims whitespace from the in-flight entry-id file's contents. **The trim can never matter**: `around`'s
catch is the file's only writer, and it writes `entry.id.string` with no trailing newline. Deleting the
`trimmingCharacters` call leaves the full suite green (1135 tests, 80 suites) — measured.

**Why this is worth a change rather than a note.** An untested defensive call reads as protection
against an input that can occur, and the next reader will preserve it, extend it, and eventually write
a test that asserts it. Guide §11 **decision 24** already narrowed this file's reachable states
sharply — the id now lives inside the sequencer directory, which git deletes on both finish and abort —
so this is the second dead guard that decision left behind (#0292 removed the first, the
unparseable-file cleanup).

## Expected behavior

- [ ] The `trimmingCharacters` call at `JournalCheckpoint.swift:504` is **deleted**, with a comment on
      the read saying the writer is `around`'s catch and it writes no trailing newline — so a future
      reader knows the omission is deliberate.
- [ ] **Before deleting, confirm the premise yourself**: `grep` the whole package for every writer of
      that file and show there is exactly one. If you find a second writer, **stop and say so** — the
      trim is then load-bearing and this issue is wrong.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, at or above the count in `docs/test-baseline.txt`.
- [ ] **No new test.** There is nothing to assert about a deletion whose whole justification is that
      no input reaches it; the verification is the premise check plus the green suite. Say that
      explicitly in the report rather than inventing a test that passes either way.
