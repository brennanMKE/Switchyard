## Description

This is why worktrees are in M1 rather than a later milestone. Every git path resolution in the
codebase has to go through one context object, and adding it later means auditing every call site
that ever touched a git path — the definition of a retrofit nobody finishes.

`WorktreeContext` is resolved once per invocation and holds the worktree path, `$GIT_DIR`,
`$GIT_COMMON_DIR`, and the worktree id. In a linked worktree, `.git` is a *file* containing a
`gitdir:` pointer, `$GIT_DIR` is `<main>/.git/worktrees/<name>`, and `$GIT_COMMON_DIR` is
`<main>/.git`. Which one a given path uses depends on the ref name, so it cannot be guessed.

## Expected behavior

- [ ] Context resolved via `git rev-parse --git-dir --git-common-dir --show-toplevel`, never by string concatenation.
- [ ] Correct in the main worktree, in a linked worktree, and in a bare repository.
- [ ] Per-worktree refs of another worktree are reachable via `worktrees/<name>/HEAD` and `main-worktree/HEAD`.
- [ ] Tests build a real linked worktree and assert `$GIT_DIR` and `$GIT_COMMON_DIR` differ as documented.
- [ ] Grep confirms no `.git/` string concatenation anywhere in the package.
