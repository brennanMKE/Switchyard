## Description

**Found by the second #0044 umbrella review, 2026-08-17, and measured in a scratch repository.**

`RefSnapshot.restore` applies `head` first, as a plumbing `symref-update HEAD <target>`. Under
`allowDifferentWorktree` (#0175) the applied head is `recorded.head` — the **foreign** worktree's HEAD,
normally symbolic to the branch that worktree still has checked out. `WorktreeDisturbance.disturbances`
inspects only `refs/heads/*` **oid** changes; it never looks at the head being applied.

So a restore silently produces a state git itself refuses to create. Measured, git 2.50.1:

```
git checkout agent-branch
  -> fatal: 'agent-branch' is already used by worktree at ...   exit 128

update-ref --stdin   symref-update HEAD refs/heads/agent-branch
  -> exit 0, silent

git worktree list
  -> BOTH worktrees now listed as [agent-branch]

git commit   (in the caller)
  -> moves agent-branch; the sibling immediately reports `## agent-branch` with `M f`
```

That last line is precisely the wreckage #0044 decision 2's `update-ref` row was measured against —
arriving one ordinary commit later instead of at restore time.

**A test currently pins the dual-claim state as correct**:
`aForeignEntryRestoresUnderTheOverrideAndLeavesOurPrivateRefsAlone` asserts `after.head == recorded.head`
against a **live** linked worktree still holding `agent-branch`.

## Two bounds on the severity, both verified — read these before sizing the work

- **It is not new with #0175.** Measured: caller stands on `feature`, checkpoints, moves off; a sibling
  then checks out `feature`; the caller restores its **own** checkpoint — same-worktree, no override —
  and the plumbing symref write produces the same dual claim at exit 0. This is a gap in decision 2 and
  in `WorktreeDisturbance`, not a defect the override introduced. The override makes it routine rather
  than rare.
- **The dead-agent recovery case #0175 exists for is unaffected.** A pruned recorded worktree holds
  nothing, so adopting its HEAD is correct and desirable. **Any fix must key on a *live* holder, not on
  the override.**

## The interpretive question, stated so it can be overruled

#0044 decision 2's operative sentence enumerates "**move, delete, or re-create**", and a HEAD retarget
does none of those at the instant of restore. This is filed as a decision-2 extension because of
decision 2's own stated premise — *"git enforces branch exclusivity in porcelain and not in plumbing …
Switchyard adds the refusal at the engine layer"* — and because row 1 of its own measured table is this
case. **If Brennan reads decision 2 strictly by its three verbs, this is a proposal rather than a
finding**, and the right resolution is a recorded decision rather than code.

Note also that **#0034 decision 5** settled "`HEAD` applies to the calling worktree — documented, not
hidden" without considering the exclusivity collision, and #0034 is closed. Whichever way this goes,
that sentence needs a pointer to the answer.

## Decision and planning update — 2026-08-17. Detach, and it keys on liveness.

**Settled as guide §11 decision 16**, in Brennan's absence and on the same terms as decision 14:
reversible, flagged in the guide, taken on measurement. **Detach rather than adopt**, keyed on a
**live** (non-prunable) sibling holding the branch. The interpretive question above is answered by
extending decision 2's premise rather than its three verbs; the guide entry states the case for
overruling it, and if Brennan reads decision 2 strictly this issue closes `wontfix` and the guide entry
becomes a scope clarification.

Detaching, not refusing, because a refusal would break the dead-agent recovery path #0175 was built
for — and the recorded commit is reached either way. Only the symref is given up, and only when
somebody else is standing on it.

### The code, and where it goes

**`YardKit/Sources/YardGit/WorktreeDisturbance.swift`** gains a pure function beside `disturbances`.
Pure over the same three inputs, so it is testable with no repository at all — which is how
`disturbances(restoring:current:worktrees:callerPath:)` is already written:

```swift
/// The snapshot to apply, with `HEAD` detached when its branch is checked out
/// by a live sibling.
///
/// Returns the branch that was given up, or nil when nothing changed, so the
/// caller can say what it did rather than doing it silently.
public static func detachingHeldHead(
    in snapshot: RefSnapshot,
    worktrees: [WorktreeEntry],
    callerPath: String?
) -> (snapshot: RefSnapshot, detachedFrom: String?)
```

Rules, in order:

1. `snapshot.head` must be `.symbolic(target:)`; a `.detached` head is returned unchanged.
2. Some entry in `worktrees` must have `prunable == false`, a canonicalized `path != callerPath`, and
   `"refs/heads/" + branch == target`. Canonicalize with `WorktreeContext.canonicalize`, exactly as
   `disturbances` does — `/var` and `/private/var` are one directory and comparing raw paths silently
   never matches.
3. The oid comes from `snapshot.refs` under that name. **If the snapshot does not carry the branch,
   return it unchanged** and let the existing checks speak: fabricating a detached head from an oid the
   snapshot never recorded would be inventing state.

**`YardKit/Sources/YardGit/JournalRestore.swift`** applies it. The insertion point is exact: `applied`
is built at the `let applied: RefSnapshot = allowDifferentWorktree && …` expression, and step 5 calls
`worktreeList(path: base, git: git)` a few lines later. Hoist that call into a `let worktrees` above
`applied`, pass it to both, and apply the transformation to `applied` **before** step 5 — so the
disturbance check runs against the snapshot that will actually be written, which is what step 5's own
comment says it is for.

### The test that pins the bug

`YardKit/Tests/YardGitTests/JournalRestoreTests.swift:514`,
`aForeignEntryRestoresUnderTheOverrideAndLeavesOurPrivateRefsAlone`, asserts `after.head ==
recorded.head` against a **live** linked worktree still holding `agent-branch`. It currently asserts
the dual claim is correct, so it must change: the head becomes `.detached(oid:)` at the branch's
recorded oid, and the assertion about private refs is unaffected. Do not delete the test — change the
head expectation and say in the report what it asserted before.

### Tests to add — `WorktreeDisturbanceTests` for the pure function, `JournalRestoreTests` for the flow

- **Live sibling holds the branch** → head detached at the recorded oid, `detachedFrom` names the ref.
- **Pruned sibling holds the branch** → unchanged, still symbolic. This is the case #0175 exists for
  and it is what stops the fix from breaking dead-agent recovery.
- **The caller itself holds the branch** → unchanged. The caller is never its own disturbance and must
  never detach itself.
- **`.detached` head in** → returned unchanged, `detachedFrom` nil.
- **Branch absent from the snapshot's refs** → unchanged.
- **The same-worktree case**, which #0211 measured and which is not about the override at all: caller
  stands on `feature`, checkpoints, moves off; a sibling checks out `feature`; the caller restores its
  own checkpoint. Assert the head comes back detached, not dual-claimed. **This is the test that proves
  the fix is not keyed on `allowDifferentWorktree`**, and it is the one to write first.
- **End to end**: after such a restore, `git worktree list` shows the branch claimed **once**. Assert
  it by counting the worktree records naming that branch — the wreckage in the reproduction above is
  visible exactly there.
