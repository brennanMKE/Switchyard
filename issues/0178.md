## Description

**Filed by #0041's review on 2026-08-08. Two behaviours that are correct in the shipped code and
unguarded by any test.**

#0041 landed `HookInstall` with chaining: an existing foreign hook moves to `.switchyard-chained`
and the wrapper runs it, propagating its exit status. Review confirmed the chaining itself is well
covered — a mutation that overwrites instead of chaining turns three test functions red. These two
paths are not.

## 1. A non-executable pre-existing hook

#0041's Given 7 asserts the wrapper's `[ -x "$chained" ]` test preserves git's own semantics: git
does not run a non-executable hook, so neither should the wrapper. **No test covers it.**

Review wrote a temporary probe and **the behaviour is correct** — the bytes are preserved at
`.switchyard-chained`, the non-executable mode survives the rename, and the hook does not run. So
this issue is about evidence, not a fix. Make that probe a permanent test.

Assert all three: contents preserved, mode bits preserved through the rename, and the chained hook
does **not** execute. The third is an absence assertion, so **mutate the fixture** — make the hook
executable — and confirm the test goes red. Otherwise it passes for free.

## 2. The rename-then-write window is not atomic

`moveItem` followed by `write` means that if the write fails after the rename, the foreign hook
sits at `.switchyard-chained` with no wrapper in place — **the user's hook silently stops running**
until #0158 restores it.

It surfaces as `.failed(...)` rather than silently succeeding, so it is visible to a caller. But it
is untested, and the window is real.

Decide and record which this is:

- **acceptable and documented** — the failure is reported, and recovery is #0158's job; or
- **worth closing** — write the wrapper to a temporary path and rename it into place last, so the
  foreign hook is never without a wrapper.

If the second, the ordering becomes: write wrapper to temp → move foreign hook aside → rename temp
over the hook path. Measure what that costs and whether any window remains.

Either way this issue must leave a test that drives a failure **after** the rename and asserts what
the caller observes and what state the hook directory is left in.

## Planning update — 2026-08-08, authored in-context

**Scoped to item 1.** The rename-then-write atomicity question (item 2) is a *decision* plus a test
and stays open in the filing above; this pass delivers the non-executable guard, which is pure
evidence against already-correct code.

### Givens — read from the merged source

1. The wrapper tests the chained hook twice, at `HookInstall.swift:101` and `:106`, both
   `[ -x "$chained" ]`. Git does not run a non-executable hook, so neither should the wrapper —
   that is the behaviour to pin.
2. `chainedSuffix` is `".switchyard-chained"` (`HookInstall.swift:62`), and install **renames** the
   foreign hook to that path.
3. `writeHook(_:in:content:mode:)` already takes a **mode**, defaulting to `0o755`. A
   non-executable foreign hook is `mode: 0o644` — no new helper needed.
4. `loggerHook(to:)` appends to a log file, which is how the existing chaining tests observe whether
   the chained hook ran. The same helper gives the negative observation: **the log must not exist.**

### The trap this test must avoid

"The chained hook did not run" is an **emptiness assertion**, and it passes for free if the hook was
never going to run for some unrelated reason — a wrong path, a broken fixture, an install that
failed. So the test must also prove the *positive* half in the same fixture: the bytes and the mode
survive the rename. And the mutation row must be a **fixture** mutation — make the hook executable —
because no production change distinguishes "correctly did not run" from "never installed properly".

## Change 1 — `YardKit/Tests/YardGitTests/HookInstallTests.swift`, append one test

Append at file scope, alongside the other `@Test func`s — this file's tests are top-level, not
inside a struct. **Match the surrounding file.**

```swift
/// Git does not run a non-executable hook, so the wrapper's `[ -x "$chained" ]`
/// tests must not either (#0041 Given 7 asserted this and nothing covered it).
///
/// The negative half — "it did not run" — passes for free if the hook was
/// never going to run anyway, so the positive half is asserted in the same
/// fixture: the bytes and the non-executable mode both survive the rename.
/// The mutation for this is a FIXTURE mutation; see the table.
@Test func aNonExecutableForeignHookIsPreservedButNeverRun() throws {
    var repo = try FixtureRepository()
    defer { repo.destroy() }
    try repo.build([.init("a")])
    let log = repo.url.appendingPathComponent("theirs.log").path
    let hooks = try hooksDirectory(repo)
    let body = loggerHook(to: log)
    try writeHook("reference-transaction", in: hooks, content: body, mode: 0o644)

    let reports = try installReports(repo)
    #expect(reports.first?.outcome == .chained)

    // Positive half: the foreign hook survived the rename, byte-for-byte and
    // mode-for-mode.
    let chained = hooks + "/reference-transaction" + HookInstall.chainedSuffix
    #expect(try String(contentsOfFile: chained, encoding: .utf8) == body)
    let mode = try #require(
        FileManager.default.attributesOfItem(atPath: chained)[.posixPermissions] as? NSNumber)
    #expect(mode.intValue & 0o111 == 0, "the non-executable bit must survive")

    // Negative half: a ref transaction runs the wrapper, and the chained hook
    // must stay silent because git would not have run it either.
    let result = try updateRef("refs/heads/probe", in: repo)
    #expect(result.exitCode == 0)
    #expect(!FileManager.default.fileExists(atPath: log),
            "a non-executable chained hook must not be executed")
}
```
