# 0141 — No engine failure mode carries the exit code from guide section 6

| | |
|---|---|
| **Status** | open |
| **Module** | YardGit, YardKit |
| **Milestone** | M1 |
| **Platform** | macOS |
| **First seen** | 2026-08-07 |

## Description

**M1 exit criterion served (guide §9, criterion 3):** "Every failure mode returns a structured error
**carrying the exit code from §6** — not a trap, and not a success value with empty fields."

Found by the M1 milestone review, 2026-08-07. The engine's failure modes are structured — every
`YardGit` function throws a typed error (`WorktreeAddError`, `WorktreeRemoveError`,
`WorktreeListError`, `GitProcess.Failure`, the parser `Failure` enums, …) and the refusal-carrying
result types encode `code`/`message` objects, all wire-tested. But **no production code anywhere
associates any engine failure with a §6 exit code.** Verified by grep: `YardGit` contains no
reference to `ExitCode`, `EnvelopeErrorCode`, or the codes 6/8/9; the only `exitCode` values it
carries are git's own process exits (e.g. `WorktreeAddError.unknownFailure(code: 128, …)`), which
are not §6 codes.

The §6 system lives complete but unconnected on the other side of the package: `ExitCode` and
`EnvelopeErrorCode` in `YardKit/Sources/YardKit/` map one-to-one (`repository_error` → 6,
`blocked_on_conflicts` → 8, `signing_failed` → 9, …). `YardGit` and `YardKit` are mutually
independent targets in `YardKit/Package.swift` (only `YardWireTests` and `YardUI` see both), so
today there is no place where `WorktreeRemoveError.unclean` is declared to be a 6, or a signing
failure a 9 — when M3 registers commands, every mapping would have to be invented at wiring time,
per command, which is how the codes drift.

The 2026-08-07 rewrite of M1's checklist (§11 decision 11) deliberately kept this criterion in M1
while moving binary reachability to M3 — the mapping is engine-contract work, not CLI work.

## Expected behavior

Every `YardGit` failure mode has a declared §6 exit-code association, tested. Where the mapping
lives — an engine-side enum mirroring the §6 labels, a mapping layer in the target that will host
registration, or a `YardKit`-side `Error`-to-`EnvelopeErrorCode` bridge — is a planning decision;
whichever shape is chosen, a test must pin each engine error's §6 code so M3 registration is a
mechanical wrap rather than a per-command judgment call.

(Planning pass to author to code level before dispatch, per the workflow. If planning concludes the
mapping's home materially changes the architecture, that is a stop-condition-3 question for
Brennan first.)
