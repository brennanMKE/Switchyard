## Report

Brennan, 2026-10-05:

> I created a docs2 branch and added a file. Then changed back to main and used Merge Into Current
> Branch on the commit on the docs2 branch. It created a new commit on the main branch but no file
> change.

## Root cause — measured, not guessed

**Git is right. The window is wrong.** The merge does exactly what it should. The Detail pane never
shows a merge commit's files, so a correct merge looks like an empty commit.

### 1. Reproduced in the VM through the real UI, asserting git state

This was a throwaway spike in a detached planning worktree, run with `scripts/run-ui-tests-vm.sh`
on 2026-10-05 against `main` at `7ff8d880`. It is the basis for #0578's spike. The fixture was
built with git commands: `merge-main` has one commit (README.md). `docs2` branches from it and adds
`docs.md`. The fixture is checked out on `merge-main`, with two shapes. In **ff**, `main` has no
commit of its own. In **diverged**, `main` has its own commit (`main.txt`). The spike selected
docs2's commit in History, chose Commit ▸ Merge into Current Branch, then ran `/usr/bin/git`
from the test runner:

| check | ff | diverged |
|---|---|---|
| `rev-list --parents -n1 HEAD` | merge, parents = old HEAD `cd5f840`, docs2 tip `3db9667` | merge, parents = old HEAD `66fa99f`, docs2 tip `37a5410` |
| `ls-tree -r --name-only HEAD` | `README.md`, `docs.md` | `README.md`, `docs.md`, `main.txt` |
| `diff --name-status HEAD^1 HEAD` | `A docs.md` | `A docs.md` |
| `docs.md` in the working tree | yes | yes |
| `status --porcelain` | empty | empty |
| journal | one `refs/switchyard/journal/…` entry | one entry |
| **Detail pane** | **"Merge commit diffs are not shown yet."**, no `docs.md` | **same** |

Screenshots: `issues/0575/0575-ff-merge-detail-pane-on-main.png` and
`0575-diverged-merge-detail-pane-on-main.png`. After the merge, `RewriteSelection` selects the new
merge commit, which is chain index 0. The pane then shows the merge subject, the note, and no files.
That is the report, word for word: "a new commit on the main branch but no file change."

The same holds at engine level. A probe test in the planning worktree derived the request through
`CommitActionRequest.make(for: .merge, …)` from real `graphRows` and `BranchOwnership.owners`. It
got `.merge(branch: "docs2")` in both shapes, then called `performCommitAction`. The resulting git
state matched the table above.

### 2. Candidates ruled out, with the evidence

- **The journal restoring the worktree or index after the merge.** Ruled out. `docs.md` is on disk,
  `status` is clean, and `ls-tree HEAD` has it. `JournalCheckpoint.around` writes its entry
  **before** the body runs and restores nothing on success.
- **Wrong merge target (the commit's parent, `HEAD`, or the commit instead of its branch).** Ruled
  out. The request is `.merge(branch: "docs2")`, and the merge's second parent is docs2's tip.
- **The merge running in the wrong directory or worktree.** Ruled out. HEAD in the opened repository
  moved to the merge.
- **`--no-ff` against an already-merged ref.** Ruled out. `Merge.walk` refuses that case with
  `.alreadyUpToDate` before touching anything, and here the merge was created.
- **A stale refresh.** Ruled out. The merge row appears and is selected. The empty file list comes
  from the next cause, not from stale data.

### 3. The cause: two layers both decline to show a merge's files

1. **`YardKit/Sources/YardUI/CommitDetailView.swift`, `diffContent`.** `if isMerge {
   Text("Merge commit diffs are not shown yet.") }`. Every merge commit takes this branch, before
   `files` is even read.
2. **`YardKit/Sources/YardGit/Hunks.swift`, `commitDiffArguments`.** It runs
   `diff-tree --root -p --cc`. `--cc` is the combined diff: it prints only what differs from
   **every** parent. A clean merge's files each match one parent, so the output is empty. Measured
   on git 2.54.0 for both shapes: `--cc` gives 0 bytes, and `--diff-merges=first-parent` gives
   exactly `docs.md`. So removing the note alone would only change the message to "This commit
   introduced no changes." That is still the bug. The `Show Changes` window (`CommitChangesView`)
   loads through the same `loadCommitDiff` and is empty for the same reason.

`--cc` was a deliberate choice (b0f68d13, #0341). Its doc comment says so: the combined diff is "the
honest verdict 'this merge introduced no changes of its own'". That answers a reviewer's question.
It is not what a person looking at their history asks after a merge, which is "what did this merge
bring in?" The answer to that is the **first-parent diff**, the same thing
`git diff <merge>^1 <merge>` prints (measured: `A docs.md` in both shapes).

## Why this got through

Every layer had tests and every test was right about its own claim. `MergeTests` proves the merge.
`CommitActionMenuTests` proves the menu rule and request. `HunksTests` pins `--cc`'s empty output
for a clean merge **as intended**. `CommitDetailView` was never tested on a merge at all. Nothing
ran the app's own path, the commit menu → `performCommitAction` → refresh → Detail pane, and then
compared git with the window. That gap is plan workstream C. #0579 makes it a preflight check.

## Observed, not in scope

- **The branch map does not draw the merge's second-parent edge.** In both screenshots the merge
  commit sits on `merge-main`'s lane with no line to `docs2`'s lane, and `docs2` is not dimmed as
  merged (#0430). So a merge looks like an ordinary commit on the map as well as in the Detail
  pane. This is decision 29's design ("one connector per branch") and needs no fix to resolve this
  report. It is noted for workstream C and Brennan (question 2 below).
