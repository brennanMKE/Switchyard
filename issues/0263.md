## Description

**Finding 1 of #0044's sixth umbrella review, 2026-08-18.** Decision 2's #0256 correction names three
sources for a sibling's held branch — `rebase-merge/head-name`, `rebase-apply/head-name`, and
`BISECT_START`. **Two of the three are pinned by tests. The third is not.**

`✔ Test run with 1062 tests in 78 suites passed after 60.381 seconds.` — **SURVIVED.**

**The case is real, measured on git 2.50.1** with the `--apply` backend stopped on a conflict:

| probe | result |
|---|---|
| `cat "$(git rev-parse --git-path worktrees/wt/rebase-apply/head-name)"` | `refs/heads/agent-branch` |
| `git worktree list --porcelain` | `HEAD <oid>` / `detached` — **no `branch` line** |
| `git branch -f agent-branch main` from the main worktree | `fatal: cannot force update the branch 'agent-branch' used by worktree at '…'` — exit **128** |

**Why nothing catches it.** `aMidRebaseSiblingIsNamedAsADisturbance` and
`aMidRebaseSiblingIsLeftAloneAndItsRebaseContinueSucceeds` both drive `git rebase -i`, which uses the
**`rebase-merge` backend exclusively**. No test in the suite reaches `rebase-apply` at all, so removing
that element — or mistyping it — ships green, and the consequence is the one #0256 measured: the
sibling's branch is rewound and its `rebase --continue` fails with `cannot lock ref`.

**Third instance of one failure shape**: an enumerated member of a set a decision names, where the
siblings are pinned and one is not. #0249 was `refs/rewritten`; #0257's first half was `refs/bisect`;
this is `rebase-apply`.
