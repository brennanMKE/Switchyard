## Description

**Split out of #0038 on 2026-08-17**, which was five deliverables. This is the hunk-selected half of
`switchyard commit`: commit only the changes in a named hunk set, rather than whatever happens to be
staged.

Both halves already exist and this issue composes them:

- **`Staging.stageHunks(ids:at:git:)`** (#0040, merged) stages by stable hunk id, resolving ids against
  a fresh listing inside the call and throwing on an unknown or stale id **before** anything is applied,
  so a partial stage is not a reachable state.
- **`CommitCreate.run`** (#0036, merged; #0038 adds trailers) commits the staged index by shelling out
  to `git commit`, so hooks run.

## The question this issue has to answer, because composing them naively is wrong

**What happens to changes that were already staged when `--hunk` is given?** `stageHunks` adds to the
index; it does not clear it. So a caller with unrelated staged work would silently get that work in the
commit too — the opposite of what asking for specific hunks means.

Three options, and this issue must pick one and record why:

- **Refuse** when the index is not clean and `--hunk` was given, naming what is staged. Safest, and
  consistent with the project's habit of refusing rather than guessing.
- **Commit only the named hunks** by building the commit from a temporary index, leaving the caller's
  staged work untouched in the real one. Most useful, most machinery.
- **Document that `--hunk` adds to the index** and commit everything staged. Cheapest, and the one most
  likely to surprise an agent.

**Measure before choosing**: `git status --porcelain=v2` in a fixture with something staged, then
`stageHunks`, then read the index again. The answer should be in this issue before the option is.

## Measured — 2026-08-17. The staged-work question is answered; the decision is not.

`stageHunks` is `git apply --cached` of the selected patch (`Staging.swift:56`), which is **additive**:
it stages the patch and touches nothing else in the index.

Measured in a scratch repository rather than inferred from the flag's name:

```
git add A.txt                 # unrelated work, staged by the caller
git apply --cached b.patch    # what stageHunks does, for B.txt only
git diff --cached --name-only
A.txt
B.txt
```

**So composing `stageHunks` with `CommitCreate.run` naively commits the caller's unrelated staged work
along with the named hunks** — the opposite of what asking for specific hunks means, and silent.

## Decision — refuse, and say what is staged

Recorded here rather than left to the round, because it is a product-surface choice and the round should
not be inventing one mid-implementation. Taken 2026-08-17 in Brennan's absence, reversible, flagged.

**Refuse when `--hunk` is given and the index already holds unrelated changes**, naming the staged
paths in the error. Reasons, in order:

- **It matches what the project does everywhere else.** `WorktreeDisturbance` refuses rather than
  warns; the worktree gate refuses; `CrossToolGuard` refuses. Guide §7's principle is that an agent
  gets a structured refusal it can act on rather than a surprise it cannot see.
- **The temporary-index alternative is real but not yet earned.** Building the commit from a scratch
  index would let both coexist, and it is what a GUI eventually wants — but it needs `GIT_INDEX_FILE`
  plumbing and interacts with the conflicted-index rule (CLAUDE.md: `git write-tree` refuses an
  unmerged index). That is its own issue if a caller ever needs it, and refusing now does not foreclose
  it: a refusal can become a behaviour later, whereas a silent commit cannot be taken back.
- **Documenting "`--hunk` adds to the index" was the third option and is the worst of the three**: it
  is correct, cheap, and precisely the kind of footnote nobody reads before losing a commit's contents.
