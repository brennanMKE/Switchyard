# 0224 — A metadata rewrite can leave the journal cache stale

## Description

**Filed while reviewing #0221 on 2026-08-17.** `JournalMetadataCache` (`#0155`) caches each entry's
`JournalEntryMetadata` **verbatim**, keyed by anchor ref, in a file under `commonDir`. #0221 added
`JournalAnchor.updateMetadata`, which **rewrites an entry's metadata blob in place** — the first
operation in the codebase that changes an entry after it is written.

Nothing is broken today: `grep` finds no engine caller of `JournalMetadataCache` at all — it is built
and unwired. That is exactly why this is filed now rather than discovered later.

**When the cache is wired, a rewrite that does not update the cached row makes the attached mapping
invisible on the fast path** — the reader takes the cache, sees the pre-attach metadata, and reports
no rewrite mapping. #0064 (`rewrite-diff`) is the consumer that would silently return nothing.

## Expected behavior

- [ ] Whoever wires `JournalMetadataCache` into the read path also updates the cached row when
      `JournalAnchor.updateMetadata` changes an entry — or documents, in the cache's own file, that a
      rewrite invalidates it and how a reader detects that.
- [ ] The cache `Row` stores `snapshotRef` (a ref name, not an oid), so the ref itself stays valid
      across a rewrite. **The staleness is in the embedded `metadata`, not in the ref** — say so where
      a reader will find it, because the ref surviving is exactly what makes the staleness quiet.
- [ ] A test that attaches a rewrite mapping and then reads through the cache sees the mapping.
- [ ] Rebuilding from refs (#0030) already recovers from any staleness; confirm that and state it, so
      the remedy is known rather than rediscovered.

## Notes

Blocked by nothing; **do it in whichever issue wires the cache**, and close this one as a duplicate if
that issue covers it. Filed so the interaction is visible in the queue rather than living only in
#0221's review.

Related: #0155 (the cache), #0221 (the rewrite), #0064 (the consumer), #0030 (rebuild from refs).

## Re-milestoned M2 → M3 — 2026-08-17

Nothing reads `JournalMetadataCache` today — `grep` finds no engine caller at all — so there is no
test this issue could write that would fail, and no behaviour it could change. The deliverable is a
**constraint on whoever wires the cache into the read path**, and that work is not in M2: the cache
exists to make journal reads cheap at the scale the app and the CLI create in M3.

Keeping it open in M2 would block a milestone on work that belongs to a later one, which is the
pattern guide §11 decision 17 just corrected elsewhere. Moved rather than dragged.

**It stays a real issue**, not a note: the interaction is genuinely easy to miss, because the ref
survives a rewrite and only the metadata embedded in the cached row goes stale — so a reader sees a
valid-looking row with the mapping absent.
