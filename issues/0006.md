## Description

Everything shareable lives in the package, so the package comes first and the app target is added
later. Four products: the `YardGit` engine library, the `YardKit` library (XPC protocols, message
types, `ServiceNames`, `CLIInstaller`), the `yard` executable, and tests.

The layering rule is the point: the app target should end up owning only SwiftUI views, agent
embedding, `SMAppService` registration, and presentation. Anything with logic worth testing lives
here. RemoteControl's retrospective names putting the installer in the app target by default —
rather than by decision — as a mistake that had to be undone later.

## Expected behavior

- [ ] `YardKit/Package.swift` declares `YardGit`, `YardKit`, `yard`, and a test target.
- [ ] libgit2 is wired in per the #0001 decision and one call links and runs.
- [ ] `swift build && swift test` pass from `YardKit/`.
- [ ] `YardGit` does not import `YardKit` — the engine must not depend on the XPC layer.

## Notes

Guide §4 "The layering rule". Blocked by #0005.

`YardGit` must stay usable with no app, no XPC, and no launch agent — that constraint is what makes
the CLI work in CI, over SSH, and in headless agent runs.

## Fix

Created the package with five targets: `Clibgit2` (systemLibrary), `YardGit`, `YardKit`, the `yard`
executable, and two test targets. `YardGit` depends only on `Clibgit2`; `YardKit` depends on
`YardGit`; `yard` depends on both.

## Verification

`swift build` clean, `swift test` — **4 tests in 2 suites passed**. `swift run yard` prints
`yard 0.0.1 (libgit2 1.9.6)`, which proves the systemLibrary target linked rather than merely
compiled.

The layering guard was verified by deliberately breaking it: adding `import YardKit` to
`YardGit.swift` made `yardGitDoesNotImportYardKit()` fail with
`Expectation failed: !((trimmed → "import YardKit").hasPrefix(...))`, and reverting restored green.
A guard that has never failed is not known to work.

## Gotchas

**The package platform had to be `.macOS(.v26)`, not `.v15`.** Homebrew's libgit2 is built for
macOS 26, so declaring v15 produced a linker warning on every build. v26 also matches the app
target's existing `MACOSX_DEPLOYMENT_TARGET = 26.5`.

`swift build` needs `PATH=/opt/homebrew/bin:$PATH` to find `pkg-config`, per #0001. This will need
handling in CI (#0076) and the Xcode run-script phase (#0050), both of which run with a reduced
environment.
