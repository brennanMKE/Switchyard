## Description

The Changes view (guide §11 decisions 30 and 34) stages, unstages and discards whole files and whole
hunks. A hunk often mixes a change you want in this commit with one you do not: a fix and a stray
debug line, three lines apart. Today the only way to split them is a terminal (`git add -p` and its
`e` editor). #0437 deferred line staging as its question 5 and #0467 deferred line discard as its
question 6.

**Guide §11 decision 35** is the design. In short: in the selected file's diff, click a changed line
to select it, shift-click to extend, ⌘-click to toggle, or drag across lines. While a hunk has a
selection its header buttons read **Stage Lines** (or **Unstage Lines**) and **Discard Lines…**. The
engine builds a patch holding only the selected `+`/`-` lines and applies it with the same `git
apply` the hunk actions use: `--cached` to stage, `--cached --reverse` to unstage, `--reverse` to
discard. Each is one journal entry, so Edit ▸ Undo Stage / Undo Unstage / Undo Discard work
unchanged.

**A prerequisite bug came out of the measurement.** `HunkParser` splits `git diff` output on the
`"\n"` **Character**, and Swift reads `"\r\n"` as one Character. A CRLF file's hunk body therefore
parses as one line, its line counts are never consumed, and it swallows every file listed after it.
Measured on `main` (2026-09-29): a CRLF `a.txt` changed beside an LF `b.txt` lists as `["a.txt"]`
only, with a body of `[" a\r\n-b\r\n+B\r\n c\r\ndiff --git a/b.txt b/b.txt", "index …", …]`. That is
visible today (the Changes view shows no diff for `b.txt`), and line selection cannot work on a
CRLF file without the fix. #0475 fixes it first.

## Questions for Brennan (the plan assumed an answer to each; none blocks a child)

1. **One hunk at a time.** Assumed: a selection lives in one hunk, and the buttons are the hunk's
   own, retitled. Selecting across hunks (or files) would need a toolbar-level Stage Selection and a
   multi-hunk patch; `selectLinePatch` builds one hunk. Cheap to add later if wanted.
2. **Clicking a context line clears the selection.** Assumed: yes, as clicking empty space does.
   Shift- and ⌘-clicks on context do nothing.
3. **Keyboard.** No arrow-key or Escape handling in this pass. Assumed: later, with the rest of the
   Changes view's keyboard story.
4. **CLI.** `stageLines`/`unstageLines`/`discardLines` are public engine functions, but no
   `switchyard` command exposes them. Body indices are a poor contract for an agent (they are only
   valid for one listing); an agent can already send an edited patch through `stagePatch`. Assumed:
   no CLI surface.
5. **A mode change rides along.** Staging any line of a file whose mode also changed stages the mode
   change too, exactly as Stage Hunk does today (the patch carries the file's header). Assumed:
   acceptable.
6. **Discard Lines… always asks**, even for one line (decision 34's rule). Assumed: yes.

### Noted, not measured and not filed (the priority section holds engine hardening)

- Other parsers split git output on the `"\n"` Character, e.g. `Blame.swift:139`
  (`text.split(separator: "\n", …)`). If `git blame --porcelain` prints file content with CRLF, the
  same joined-line bug could apply there. Not measured.
- `HunkParser` reads a line's marker with `line.first`, a `Character`. A body line whose content
  starts with a combining mark (`+` followed by U+0301) is one grapheme and would not compare equal
  to `"+"`. Not measured; rare.
