# 0342 — Decide what commitDiff should return for a merge commit

## Description

**`commitDiff` returns nothing for a merge commit**, and the detail pane will therefore show a merge
as having changed nothing. Measured by #0341's round and asserted in
`commitDiffOfAMergeCommitIsEmpty`: `git diff-tree --root -p --no-commit-id <merge>` prints **no output,
exit 0**, because `diff-tree` does not pick a parent to diff against without `-m`, `-c` or `--cc`.

That is correct plumbing behaviour and a **product gap**: a user clicking a merge commit in the History
pane sees an empty detail pane, which is indistinguishable from "this commit changed nothing".

## The options, none of which is obviously right

- **`-m`** — diff against **each** parent in turn, so an n-parent merge produces n diffs. Truthful and
  complete; the pane needs a way to show "versus parent 1 / versus parent 2".
- **`--cc`** — the *combined* diff, showing only hunks that differ from **all** parents. This is what
  `git show` does for a merge by default, so it is what a user coming from the command line expects.
  It is also the smallest useful thing: for a clean merge it is empty, which is honest.
- **`--first-parent -m`** — diff against parent 1 only. Simple, and what most GUIs show, but it
  silently hides what came from the other side.

**`--cc`'s output is not the same shape** — combined diffs use `@@@ … @@@` headers with one column per
parent, and `HunkParser` has never seen one. Whichever option wins, check what the parser does with it
before assuming it just works.
