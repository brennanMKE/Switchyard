## Description

**Merge into Current Branch… (⌃M)** from GitUp's context menu (#0359): merge the selected
branch into the current one, non-interactively. Switchyard has no merge operation — the resolve
UI (#0057) exists for conflicts but nothing in the engine *starts* a merge.

This is the first operation that creates merge commits, which the journal's machinery already
anticipates (`SequencerSnapshot`, `commitDiff`'s `--cc` handling for clean merges, the
mid-rebase-amend dedup). The new engine surface is the merge itself: find the merge base, run
`git merge --no-ff`/`--ff-only` per intent, surface conflicts as the resumable state the resolve
UI already consumes.

## Expected behavior

- [ ] `yard merge <branch> [--ff-only|--no-ff]` merges into the current branch; the default
      intent is explicit, never git's silent fast-forward guess.
- [ ] Auto-checkpoint; undo restores exactly (including dropping a merge commit).
- [ ] Conflicts exit 8 with the resumable merge state; the resolve UI (#0057) can complete it.
- [ ] The merge commit message is settable non-interactively; signing per the explicit-`-S` rule.
- [ ] Refusals typed before mutation: already-up-to-date, unrelated histories (refuse unless
      `--allow-unrelated` is a stated intent), unmerged index.

## Notes

The context-menu item disables when the node is on the current branch — the UI state mirrors
these typed refusals (#0359's pattern).

### Where the user starts a merge

1. **History context menu and menu bar → Commit**: `CommitAction.merge`, in a group with #0362's two
   items, shortcut ⇧⌘M (allocated by #0359). The title names what is being merged, chosen from the
   node's #0367 chips:
   - exactly one **local** branch chip that is not `HEAD`'s → `Merge “feature” into “main”…`
   - otherwise exactly one **remote** chip → `Merge “origin/feature” into “main”…`
   - otherwise → `Merge This Commit into “main”…`
   Several local branches at one node read as the commit form. Picking one silently would merge
   under a name the user did not choose.
2. **Sidebar**: a `.contextMenu` on each Branches and Remotes row, `Merge into “main”…`. It is absent
   on the row for the current branch. The row already names the source, so the title does not.

Both open the same sheet. The ellipsis is earned: the sheet asks for the intent and the message.

### Availability (after #0359's busy and in-progress checks; outside `rewriteReason`)

| Disabled when | Reason text | Mirrors |
|---|---|---|
| `HEAD` is detached (`whereAmI.branch == nil`) | "Check out a branch to merge into" | UI rule: "the current branch" does not exist. Confirm in the engine pass. |
| the node is reachable from `HEAD` in the window, `HEAD`'s own commit included | "Already merged into “main”" | the typed already-up-to-date refusal |
| an unmerged index | #0359's "There are unresolved conflicts — finish or abort it first" | the typed unmerged-index refusal, already covered by `operationInProgress` |

Unrelated histories cannot be seen from a 100-row window, so the item is never disabled for them.
The engine's typed refusal arrives as the failure alert. The sheet does **not** offer an
allow-unrelated option — that is a question for Brennan, not a sheet control.

### The merge sheet

Title: `Merge “feature” into “main”` — the menu title without the ellipsis.

- **Intent**, a `Picker` with `.pickerStyle(.radioGroup)`, the macOS control for two mutually
  exclusive options:
  - **Create a merge commit** (`--no-ff`) — selected by default.
  - **Fast-forward only** (`--ff-only`) — disabled, with the secondary line "“main” has commits that
    “feature” doesn’t", when `HEAD` is not reachable from the target:
    `!LocalReachability.oids(in: rows, from: [targetOid]).contains(whereAmI.rawHead)`. When
    `rawHead` is outside the loaded window, leave it enabled and let the engine refuse.

  The sheet always sends exactly one of the two flags. That is the Expected behavior's "intent is
  explicit, never git's silent fast-forward guess", made visible.
- **Message**: a multi-line field pre-filled with git's own default wording, *measured* from
  `git merge --no-ff --no-edit`:
  - `Merge branch 'feature'` for a local branch
  - `Merge remote-tracking branch 'origin/feature'` for a remote-tracking branch
  - `Merge commit '<full oid>'` for a bare commit

  The field is disabled while Fast-forward only is selected, since no merge commit is made. Keeping
  git's wording means the history reads the same as a command-line merge.
- **Signing**: no control. The engine applies the explicit `-S` rule, and a per-merge toggle would
  contradict it.
- **Buttons**: **Cancel** (`.cancelAction`, Esc) and **Merge**
  (`.keyboardShortcut(.return, modifiers: .command)`, as #0359's message editor: plain Return belongs
  to the message field).

No separate confirmation. The sheet *is* the confirmation, and the merge is journaled.

### While merging, and after

- **Progress label**: "Merging…", with #0359's busy disabling and no Cancel.
- **Success**: select the new `HEAD` — the merge commit, or the target commit after a fast-forward —
  and scroll it into view. The graph then shows the side lane converging into the current branch's
  lane: a hollow merge ring from #0365, with the curve in the side branch's colour. That shape is
  the visual confirmation the merge happened.
- **Conflicts** (exit 8): alert "Couldn’t Finish Merge", with `CommitActionFailure`'s conflict
  sentence. The refresh then makes the header read "A merge is in progress" (`WhereAmI.isMidMerge`
  exists), and every rewrite and merge item disables with that sentence. Handing off to the resolve
  pane (#0057) is the same open question #0359 records: `ResolveCenter` receives panes only from CLI
  `resolve --interactive` requests.
