# 0123 — The app crashes on launch: libgit2 cannot be loaded

| | |
|---|---|
| **Status** | in-progress |
| **Module** | app / YardGit |
| **Milestone** | M1 |
| **Platform** | macOS |
| **First seen** | 2026-08-07 |

## Description

**The app does not start.** Launching it from Xcode dies in dyld before any code runs:

```
dyld[45106]: Library not loaded: /opt/homebrew/opt/libgit2/lib/libgit2.1.9.dylib
  Referenced from: …/Switchyard.app/Contents/MacOS/Switchyard.debug.dylib
  Reason: … code signature in '/opt/homebrew/Cellar/libgit2/1.9.6/lib/libgit2.1.9.6.dylib'
          not valid for use in process: mapping process and mapped file
          (non-platform) have different Team IDs
```

There are **two** faults, and the second is the one that matters — fixing only the path would not
help.

## Measured on `main` 2026-08-07 — treat as verified

**1. The app links an absolute Homebrew path.** `otool -L` on the built binary:

```
/opt/homebrew/opt/libgit2/lib/libgit2.1.9.dylib (compatibility version 1.9.0, current version 1.9.6)
```

That comes from `Package.swift`'s `Clibgit2` target, which uses `pkgConfig: "libgit2"` with
`providers: [.brew(["libgit2"])]`. The path is baked in at link time and points outside the bundle.

**2. Even at the correct path, macOS refuses to load it.**

```
$ codesign -dv /opt/homebrew/Cellar/libgit2/1.9.6/lib/libgit2.1.9.6.dylib
Signature=adhoc
TeamIdentifier=not set
```

The app is signed with a Team ID; the Homebrew dylib is ad-hoc signed with none. macOS will not map a
non-platform library with a different Team ID into a signed process. **So no amount of path fixing
works — the library has to be signed with the app.**

**3. The bundle embeds nothing.** `Contents/Frameworks` does not exist. The rpath is already right,
though — `@executable_path/../Frameworks` is present in the load commands, so an embedded dylib whose
install name is `@rpath/libgit2.…dylib` would be found.

**4. Nothing in the shipping engine uses libgit2.** The only symbols referenced anywhere are
`git_libgit2_version`, `git_libgit2_init` and `git_libgit2_shutdown`, all in
`YardKit/Sources/YardGit/YardGit.swift`, and the only callers are two lines in
`YardKit/Tests/YardGitTests/YardGitTests.swift`. Every command built so far — `whereami`, `log`,
`status`, and all four `wt` subcommands — shells out through `GitProcess`.

`YardGit.swift`'s doc comment also still describes the abandoned "works without the app / CI / SSH"
premise that CLAUDE.md records as corrected on 2026-08-06.

## Two ways to fix this, and they are not equivalent

**Option A — drop the libgit2 dependency for now.** `YardGit.swift` is M0 spike residue; CLAUDE.md
says the spike code was to be deleted once `docs/engine-findings.md` was written. Removing the
`Clibgit2` dependency, that file, and its two tests makes the app launch immediately, with no signing
work and no build-system change. **Nothing loses functionality, because nothing uses it.**

**Option B — vendor and embed libgit2.** The real fix, tracked as **#0103**. It is required before any
command actually needs libgit2 (object database, diff, blame, merge per guide §3), and it involves a
binary artifact, an install-name rewrite to `@rpath`, a copy-files build phase, and signing the dylib
with the app.

**This issue is Option A.** It exists because the app is broken *now* and B is not a small change.
#0103 stays open and becomes a prerequisite for the first command that needs libgit2.

## Givens — verified, treat as true

1. `YardKit/Package.swift` declares `.systemLibrary(name: "Clibgit2", path: "Sources/Clibgit2",
   pkgConfig: "libgit2", providers: [.brew(["libgit2"])])`, and `YardGit` lists `"Clibgit2"` in its
   `dependencies`.
2. `YardKit/Sources/Clibgit2/` contains `module.modulemap` (which does `link "git2"`) and `shim.h`.
3. `YardKit/Sources/YardGit/YardGit.swift` is the **only** file importing `Clibgit2`.
4. `YardKit/Tests/YardGitTests/YardGitTests.swift:15,17` call `YardGit.initialize()` and
   `YardGit.shutdown()`. Those are the only callers in the package or the app.
5. `main` reported **312** tests on 2026-08-07.

## Expected behavior

- [ ] The `Clibgit2` target, its `Sources/Clibgit2/` directory, and `YardGit`'s dependency on it are
      removed from `Package.swift`.
- [ ] `YardKit/Sources/YardGit/YardGit.swift` is deleted, along with the two tests that call it.
- [ ] `otool -L` on the built app binary shows **no** `/opt/homebrew` path. Paste the output.
- [ ] **The app launches.** Build it unsigned and run it; report that it reaches the UI rather than
      dying in dyld. This is the criterion — a successful build is not evidence, because the failure
      happens at load time, not compile time.
- [ ] `cd YardKit && swift build && swift test` — paste the `Test run with N tests` line. The count
      will **drop** by however many tests are deleted; state the before and after and which tests went.
- [ ] The unsigned app build still succeeds:
      `xcodebuild build -project Switchyard.xcodeproj -scheme Switchyard -destination 'platform=macOS'
      CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO -quiet`

## Tests must be able to fail

There is no new behaviour to test — this is a removal. The evidence is:

1. **`otool -L` shows no Homebrew path.** Paste before and after.
2. **The app launches.** Paste the first line of `/usr/bin/log stream --predicate 'subsystem ==
   "co.sstools.Switchyard"'` or a screenshot-equivalent statement that the window appeared. If it
   still dies in dyld, the round has failed however green the suite is.
3. `grep -rn 'Clibgit2\|git_libgit2' YardKit/ Switchyard/` returns **nothing**.

Do **not** delete any test that does not call into `YardGit`'s libgit2 wrapper. The count must drop by
exactly the number of tests removed, and the round must name them.

## Notes

Surfaced the moment the app target linked `YardGit` for the first time (`adba141`). Before that,
nothing in the app referenced the engine, so libgit2 was never loaded and the crash could not happen.

**The verification that accepted `adba141` was insufficient** — it compiled and linked a probe and
concluded "the app can now use the engine". A dyld failure occurs at launch, not at build, so a green
build proved linkage and said nothing about loadability. See `docs/review-failures.md`.
