# 0140 — whereAmI returns a success value with empty fields on a non-repository

## Description

**M1 exit criterion served (guide §9, criterion 3):** "Every failure mode returns a structured error
carrying the exit code from §6 — not a trap, and not a success value with empty fields."

Found by the M1 milestone review, 2026-08-07, by running the engine — measured, not read:

```
whereAmI(path: <empty temp directory>)
→ WhereAmI(branch: nil, upstream: nil, ahead: nil, behind: nil, isMidRebase: false,
  isMidMerge: false, isMidCherryPick: false, stashCount: 0, untrackedCount: 0,
  unstagedCount: 0, stagedCount: 0, hasConflicts: false, conflictCount: 0,
  headOID: "", rawHead: "")
```

That is the criterion's exact forbidden shape: a success value with empty fields. Compare
`worktreeList` on the same non-repository path, which throws a structured
`WorktreeListError`: `could not list worktrees: fatal: not a git repository (or any of the parent
directories): .git`.

The cause is in `YardKit/Sources/YardGit/WhereAmI.swift`: `whereAmI` swallows the first failing
probe (`try? git.run(["rev-parse", "HEAD"] …)` falls back to `""`) and every subsequent field guard
degrades to `nil`/`0` on non-zero exit, so a non-repository is indistinguishable from an empty
repository on a fresh branch. #0124 knew this — its mutation table row 1 says dropping the
`WorktreeContext.resolve` gate "would return exit 0 with empty fields" — but #0124 put the gate in
the command-registration layer and moved to M3 with §11 decision 11, leaving the engine function
itself without the gate. This is the between-issues gap the milestone review exists to catch.

## Expected behavior

`whereAmI` on a path that is not inside a git repository throws a structured error (the
not-a-repository failure mode), and a test pins it. An empty-but-real repository still returns the
legitimate empty-state value. Other read functions' non-repo behavior worth a quick audit in the
same planning pass, but this issue's deliverable is `whereAmI`.
