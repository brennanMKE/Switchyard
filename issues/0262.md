## Description

**Found while reviewing #0259, 2026-08-18, and measured twice — once by that round and once
independently.** `unstagedCount` counts files whose changes are **staged**, so it does not mean what
`YardKit/Schemas/whereami.json` says it means.

`YardKit/Sources/YardGit/WhereAmI.swift:250-258`:

```swift
    // Unstaged: `diff-index HEAD --name-status` lists entries with unstaged
    // changes, one per line. Each line is a file in modified state.
    let unstagedCount: Int = {
        guard let out = try? git.capture(
            ["diff-index", "--name-status", "HEAD"], workingDirectory: path),
```

`git diff-index HEAD` compares **HEAD to the working tree**. A file that is staged and then left alone
still differs from HEAD in the working tree, so it is listed. What an agent means by "unstaged" — and
what `git diff` reports — is **index vs working tree**.

**Measured, git 2.50.1**, in a repository with one file staged and the working tree matching the index:

| command | output |
|---|---|
| `git diff --name-only` (true unstaged) | *empty* |
| `git diff-index --name-status HEAD` | `M  f.txt` |
| `git diff-index --cached --name-status HEAD` | `M  f.txt` |

So a repository with three staged files and nothing else modified reports `unstagedCount: 3`,
`stagedCount: 3`. The schema at `YardKit/Schemas/whereami.json` describes the field as **"Number of
files with unstaged changes"**, which an agent will read as "work I have not staged yet" — and act on.

**A consequence worth stating**, because it is what surfaced this: `unstagedCount` can never be less
than `stagedCount`, so no fixture can produce a state where it is. #0259's issue text asked for one and
the round correctly reported it as unreachable rather than forcing it.

## Expected behavior

- [ ] `unstagedCount` counts files differing between the **index and the working tree**. The probe
      becomes `git diff --name-only` (or `diff-files`), not `diff-index HEAD`. Say which you chose and
      why; `diff-files` does not detect a file deleted from the working tree in every configuration, so
      **measure rather than assume** — the existing `conflictCount` comment two blocks below records
      exactly this kind of finding and is the standard to match.
- [ ] The doc comment above the probe is corrected — it currently asserts the wrong thing, which is how
      this survived review.
- [ ] `YardKit/Schemas/whereami.json`'s description for `unstagedCount` is checked against whatever
      the field now means, and adjusted only if it no longer matches. Do not weaken the description to
      fit the code.
- [ ] **A test with a file staged and the working tree clean** — `unstagedCount == 0`, `stagedCount`
      nonzero. This is the state the current code cannot report, so it is the whole criterion.
- [ ] `asymmetricWorkingTreeCountsReportDistinctValues` in
      `YardKit/Tests/YardGitTests/WhereAmITests.swift` will need its expected values revised: it was
      written against the current behaviour and its 3-staged/4-unstaged pair exists *because* of it.
      Revise it deliberately and say what changed — do not let it silently keep passing.
- [ ] **Mutation:** restore the `diff-index HEAD` probe. The new test must redden.
- [ ] `cd YardKit && swift test` **twice, in the foreground**, both green, above the count in
      `docs/test-baseline.txt`.

## The files

`YardKit/Sources/YardGit/WhereAmI.swift` (lines 250-258), `YardKit/Tests/YardGitTests/WhereAmITests.swift`,
