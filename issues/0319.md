## Description

**Finding 2 of the M1 milestone review, thirteenth pass, 2026-08-18 — a data-loss path with no test that
can fail.** `wt rm` **deletes untracked files without `--force`** under
`status.showUntrackedFiles = no`.

`git worktree remove` honours that config itself. **Measured on plain git 2.50.1**, a worktree containing
one untracked file:

```
--- remove with default config:
fatal: '…/m1-probe3-wtA' contains modified or untracked files, use --force to delete it
REFUSED (expected)

--- remove with showUntrackedFiles=no:
REMOVED — untracked file destroyed
```

**Reproduced through the engine**: `worktreeRemove(at:_:force: false)` returned `error: nil` on a
worktree holding an untracked file, once the config was set on the repository.

**And the reporting degrades with it.** `extractDirtyPaths` (`WorktreeRemove.swift:202`) uses the same
unpinned `status --porcelain=v2 -z`, so even when git *does* refuse, the `paths` list an agent acts on
degrades to `[]` — which is #0300's field, undone by configuration.

## Expected behavior

- [ ] Both `git worktree remove` invocations (`WorktreeRemove.swift:134`, `:162`) and
      `extractDirtyPaths` (`:202`) pass `-c status.showUntrackedFiles=normal`.
- [ ] A named test setting the config, asserting `wt rm` **still refuses** a worktree holding an
      untracked file without `--force`, and that the untracked file **still exists** afterwards. Assert
      the file's survival, not only the refusal — the harm is the deletion.
- [ ] A second assertion that the refusal's `paths` still names the untracked file under that config,
      so #0300's guarantee survives too.
- [ ] **Verify the config bites first**: plain `git worktree remove` under it must destroy the file in a
      scratch repository. The review's recipe is in the Description.
- [ ] **Mutation:** drop the `-c` from the removal invocation. The new test must redden — and it should
      redden by the worktree being **removed**, which is the real failure.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, above the count in `docs/test-baseline.txt`.
