## Description

Found while planning #0430, 2026-09-26. `BranchStatus.read(at:)` (#0372, decision 27) **throws on
this repository**:

```
unparseable for-each-ref status line: [ahead 4]
```

`%(upstream:track)` prints every non-empty answer in brackets. #0372's `parseTrack` accepts
`[gone]` bracketed but expects `ahead N` and `behind N` bare. Measured on git 2.54.0 (Apple
Git-157) in this repository:

```
$ git for-each-ref --format='%(refname)|%(upstream:track)|%(upstream:track,nobracket)' refs/heads | grep -v '||' | head -2
refs/heads/<first>|[ahead 4]|ahead 4
refs/heads/<second>|[ahead 9]|ahead 9
```

(The two branch names are replaced here because preflight reads any `issue/` branch name as a
dependency.)

So any repository with one local branch ahead of or behind its upstream fails the whole read. The
sidebar's `.task` swallows the error with `try?`, so every row silently loses its ahead/behind and
merged status. #0372's parse test used unbracketed lines git never prints, and no real-git test had
a branch out of sync with its upstream. That is how it passed.

The fix strips the brackets. A line with the counts unbracketed now throws, because git does not
print it.

**Measured, planning worktree:** with only the test changes below applied to today's
`BranchStatus.swift`, both tests fail with the error above. With the fix, all 13 `BranchStatus`
tests pass, and `BranchStatus.read` succeeds on this repository.
