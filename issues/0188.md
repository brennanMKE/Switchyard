## Description

**Filed by #0035 on 2026-08-09; re-planned to code level 2026-08-17.** #0174 built
`SequencerSnapshot` — capture and restore of an interrupted rebase, proven by a test that runs
`git rebase --continue` to completion after a wreck-and-restore. **Nothing calls it.**
`JournalCheckpoint` does not capture it, so `JournalRestore` reports `.sequencer` as `.notCaptured`
on every entry, and M2's undo criterion is met for four of its five cases: an unmerged index, a
detached `HEAD`, untracked files and a staged/unstaged mix all round-trip; a mid-rebase sequencer
does not.

This issue is the wiring and its proof. **The wire field it stores into is #0189**, which landed on
2026-08-17 — `captured.sequencer`, its three wire values and the two `SequencerSnapshot.Layout`
mappings are on `main` now.

## Why this is not just "call the function"

**The layout must be persisted, not assumed.** `SequencerSnapshot.Layout`
(`SequencerSnapshot.swift:22`) has two cases — `rebaseMerge = "rebase-merge"` and
`rebaseApply = "rebase-apply"` — and `restore` writes the directory to
`context.path(for: layout.rawValue)`. Recording every capture as `.merge` therefore materialises a
`rebase-apply` state into `rebase-merge`, and the rebase cannot resume. #0189 gives
`captured.sequencer` its `"apply"` wire value and the two total mappings; **use them** —
`.init(snapshot.layout)` on the way in, `captured.sequencer.layout` on the way out.

**`AUTO_MERGE` is a keep-alive concern only.** It holds a tree reachable from no ref, so omitting it
from the anchor's parents leaves a restored entry pointing at an object maintenance may reclaim.
It is *not* a restore concern: `SequencerSnapshot.restore` materialises the directory and never
reads `autoMerge` (verified by reading it — `SequencerSnapshot.swift:93-124`). Passing `nil` for
`autoMerge` when reconstructing the snapshot to restore is therefore correct and needs no lookup.

## The test that is the point

`midRebaseSequencerIsHonestlyReportedAsNotCaptured` **does not do what its name says**: it uses
`FixtureRepository.linear()`, which has no rebase in progress, so it asserts the not-captured path
and would stay green even with this issue's wiring in place. That is why the salvaged implementation
kept the suite at exactly 836 tests and looked fine.

Copy #0174's `repositoryStoppedMidRebase()` helper — `SequencerSnapshotTests.swift:13-38`, which
writes a `shared.txt` both branches edit and lets `git rebase main` stop on the conflict — into
`UndoRoundTripSuiteTests`, then:

1. Replace `midRebaseSequencerIsHonestlyReportedAsNotCaptured` with
   `midRebaseSequencerRoundTripsThroughCheckpointAndRestore`: stop mid-rebase, `checkpoint`, assert
   `entry` metadata has `captured.sequencer == .merge`, wreck the sequencer directory
   (`FileManager.removeItem` on `context.path(for: "rebase-merge")`), prove the wreck took effect
   (`git rebase --continue` exits non-zero), `JournalRestore.restore`, then resolve the conflict and
   assert `git rebase --continue` **exits 0** and `status --porcelain=v2 --branch` contains
   `branch.head side`. Pass `extraEnvironment: ["GIT_EDITOR": "true"]` to both `rebase --continue`
   calls, exactly as #0174 does.
2. Add `midRebaseCheckpointReportsTheSequencerAsRestored`: the same setup, asserting
   `report.notRestored.map(\.piece)` **does not contain** `.sequencer`. This is the honesty half,
   and it is a separate test because a round trip can pass while the report still lies.

| 2 | Record every capture as `.merge` (`sequencer.map { _ in .merge }`) | **GREEN, and that is expected** — the fixture is a merge-backend rebase. State this in the work log rather than claiming a kill: it is why #0189 carries the `.apply` wire test instead. |

| 4 | Skip zero-byte files in the captured tree (the #0174 trap, re-checked at this layer) | **RED** — the rebase does not resume. `git-rebase-todo` when exhausted, `interactive`, and `no-reschedule-failed-exec` are all zero bytes and their existence is the state. |

## Notes

**#0189 has landed**, so `captured.sequencer`, `SequencerCapture.layout` and `SequencerCapture.init(_:)`
all exist on `main`. Note the nesting the round corrected: it is `JournalEntryMetadata.SequencerCapture`,
a **sibling** of `Captured`, not `Captured.SequencerCapture`.

Two lessons from #0171, which wired the index and worktree the same way, apply directly: **do not
locate a keep-alive commit through the code under test** — a helper that reads parents returns a ref
tip when the parent is missing, and the assertion passes for free — and **do not claim a restore
ordering is load-bearing without mutating it.**

An implementation of the source changes exists on `salvage/0188-sequencer-wiring`, produced by an
off-workflow round on 2026-08-12 and never reviewed. Planning has already found three defects in it,
which is why the code above differs: it recorded every layout as `.merge`, it carried a `fatalError`
branch in `JournalRestore`, and its `Captured` had no decode default — measured, that last one broke
every journal entry written before it (`missing key: sequencer`). It is a reference, not a shortcut;
the code pasted above is the target, and it was compiled and run.
