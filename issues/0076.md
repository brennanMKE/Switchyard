## Description

The undo round-trip suite (#0035) is the suite that must never be allowed to go red, which means
something has to notice when it does. CI runs the package tests on every push.

Deliberately excludes anything requiring signing assets — CI must never be able to touch a
certificate, and unsigned builds are both faster and safe.

## Expected behavior

- [ ] `swift build && swift test` in `YardKit/` runs on every push.
- [ ] Unsigned app compile check runs with `CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO`.
- [ ] Both ref formats exercised; the runner's git version is new enough for reftable, or the skip is loud.
- [ ] No CI step touches certificates, provisioning profiles, or keychains.
- [ ] The skill staleness check from #0066 runs here.
- [ ] UI tests are not attempted — they cannot run in this environment.

## Planning update — 2026-08-17. Worth doing now, and one honest risk that may sink it.

**Why now:** on 2026-08-17 `main` went red for about an hour and nothing noticed but a manual run.
Five tests passed three times in a branch worktree and failed on `main` minutes after the squash,
because merging raised the parallel load past what their deadlines tolerated. That is precisely the
class of failure a human reviewer cannot be relied on to catch, and it is what this issue is for.

### The risk, stated before the work rather than discovered during it

This machine, measured today:

```
$ swift --version
Apple Swift version 6.3.3 (swiftlang-6.3.3.1.3 clang-2100.1.1.101)
Target: arm64-apple-macosx26.0
$ sw_vers
ProductVersion: 26.6.1
```

and `YardKit/Package.swift` declares `// swift-tools-version: 6.3` with `platforms: [.macOS(.v26)]`.

**A GitHub-hosted `macos-latest` runner may be on an older macOS and an older Xcode**, in which case
the package will not build there at all — not a flaky failure, a hard one. **Check what the runner
actually provides before writing the rest of the workflow**: a first commit whose entire job is
`swift --version`, `sw_vers` and `xcodebuild -version` is the cheapest possible way to find out, and
its output belongs in this issue.

If the hosted runner is too old, the options are, in order of preference: **pin `runs-on` to a newer
image label** if one exists; **lower the platform floor** only if that is independently correct (it is
not, today — `.v26` was chosen to match the app's deployment target and a Homebrew libgit2 built for
26.0); or **report that hosted CI is not currently possible** and stop. Do not "fix" it by weakening
the manifest — that trades a real constraint for a green badge.

### The workflow — `.github/workflows/package-tests.yml`

Two jobs, and nothing else in this issue:

1. **`package`** — `cd YardKit && swift build && swift test`. This is the one that matters.
2. **`app`** — `xcodebuild build -project Switchyard.xcodeproj -scheme Switchyard -destination
   'platform=macOS' CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO`.

Triggers: `push` on every branch and `pull_request`. Both jobs run unsigned.

**No step may touch a certificate, a provisioning profile, or a keychain**, and the workflow must
contain no `security`, no `codesign`, no `-allowProvisioningUpdates`, and no secrets at all. State
that in a comment at the top of the file, because a future edit is where it would creep in.

**No UI tests.** `-only-testing:SwitchyardTests` if the app tests are run at all; `SwitchyardUITests`
cannot run unattended even locally.

### Both ref formats (criterion 3)

`FixtureRepository` takes a `refFormat` and `RefFormat.supported(git:)` already probes what the local
git can do — read it before inventing a check. If the runner's git is too old for `reftable`, the
suite must **say so loudly** rather than silently testing one format: fail the job, or emit a
`::warning::` line naming the git version. A silent skip is the outcome this criterion exists to
prevent.

### Deferred

**Criterion 5 — the skill staleness check from #0066 — cannot run: `skills/yard/SKILL.md` does not
exist yet and #0066 is open.** Leave it out and say so; adding a step that checks a missing file is a
step that either passes vacuously or fails forever.

## Verification

The workflow is verified by **its own run**, and that run happens on push. So:

- Push the branch, watch the run, and **paste the job output** — the `swift test` line with the count,
  and the `** BUILD SUCCEEDED **`.
- If the run cannot be observed from this environment, say so plainly rather than claiming a green
  build. `gh run list` and `gh run view --log` are available.
- The count the job prints must match `docs/test-baseline.txt` at the time (964 on 2026-08-17).
