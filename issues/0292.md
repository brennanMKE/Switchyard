## Description

**Proposals 1 and 2 of #0160's eighth umbrella review, 2026-08-18.** Two guards in the entry-id
mechanism survive deletion. Neither is a criterion violation; both are decisions nothing would catch
being reverted.

**The deliverable is one sentence: every guard remaining in `around`'s catch and in `inFlightEntryID`
is either pinned by a test or deleted.** Two candidates, measured:

| # | site | mutation | result |
|---|---|---|---|
| 1 | `JournalCheckpoint.swift:340` — `try?` on `SequencerSnapshot.capture` in `around`'s catch | `try?` → `try` | **full suite green** |
| 2 | `JournalCheckpoint.swift:497` — `try? fileManager.removeItem(atPath: path)` in `inFlightEntryID`'s unparseable-file guard | delete the removal | **full suite green** |

**Site 1** is #0286 round 2's work: it guarded all three throwing calls in the block so none can replace
the body's error, and **two of the three have induced-failure tests** —
`aFailedEntryIDWriteDoesNotReplaceTheBodysError` and `aFailedGitPathResolutionDoesNotReplaceTheBodysError`.
The third does not. **The shim already exists**: the `git` shim built for the second of those fails a
single `--git-path` call, and failing the `rebase-merge` lookup instead would induce a `capture` failure
the same way.

**Site 2 is close to dead, and the review said so.** Under guide §11 decision 24 the file dies with the
sequencer directory git owns, so a *stale unparseable* file has almost no way to exist — which is the
same measurement the fourth pass made about `Fixup.clearInFlightFile` before #0253 deleted it.

## Expected behavior

- [ ] **Site 1: pin it.** A test that makes `SequencerSnapshot.capture` fail inside `around`'s catch and
      asserts the body's original error is what `around` rethrows. Extend the existing `git` shim rather
      than writing a third one.
- [ ] **Site 2: decide, and say which.** Either pin it with a test that plants an unparseable file in a
      live sequencer directory, or **delete it** with the argument that decision 24's lifetime makes the
      case unreachable. **Do not do both, and do not leave it as it is** — an unpinned guard that cannot
      be reached is what this issue exists to resolve.
- [ ] **Mutations, one per surviving site**, each reddening its own test and no other. If you deleted
      site 2, say what you ran to convince yourself nothing else depended on it.
- [ ] `cd YardKit && swift test` **twice, in the foreground with an explicit 900000 ms timeout**, both
      green, at or above the count in `docs/test-baseline.txt`.
