# 0401 — Clicking a branch in the sidebar does nothing; it should focus that branch in the graph

| | |
|---|---|
| **Status** | open |
| **Module** | YardUI |
| **Milestone** | M9 |
| **Platform** | macOS |
| **First seen** | 2026-09-22 |

## Description

The sidebar's branch rows are read-only labels. Brennan filtered for `337`, saw `issue/0337` in
the sidebar, and tried to click it: *"it was read-only. I could not click it to make it focus the
branch in the branches view. It is entirely not useful and should be helpful to the user but it is
not."* The screenshot attached to #0399 (`issues/0399/switchyard-batty.png`) shows the filter at
`337` with `issue/0337` as the only sidebar row.

## Steps to reproduce

1. Open a repository with several branches (Batty was used).
2. Click any branch in the sidebar's Branches section, filtered or not.

## Expected behavior

- [ ] Clicking a local branch row (Branches section) or a remote branch row (Remotes section)
      selects that ref's tip commit in the History pane, scrolls the History list so the tip is
      centred, and the Detail pane shows that commit.
- [ ] The clicked row is highlighted as selected in the sidebar until a commit is picked in the
      History list.
- [ ] This works the same while the filter is active.
- [ ] Tag rows stay inert. An annotated tag's `RefSnapshot.Entry.oid` is the tag object, not a
      commit, so tags are out of scope here.

## Actual behavior

Nothing happens. The row has no selection or tap handling (`RepositorySidebarView.swift`,
`branchRow(_:)` and `refRow(_:prefix:systemImage:)`).

## Design (one writer per direction)

- `ContentView` owns the facts: `selectedRef: String?` (the full ref name, e.g.
  `refs/heads/main`) and `historyScrollRequest: HistoryScrollRequest?`.
- The sidebar only reports a click through `onSelectRef`, from its tap gesture, which is an
  event handler. It never writes the History selection itself.
- The History list scrolls only when `historyScrollRequest` changes. A user click inside the list
  changes `selection` but not the request, so the list doesn't jump under the cursor.
- A user pick in the History list clears `selectedRef` (in the existing selection binding's
  setter). Nothing observes `selectedCommit` to write back into the sidebar.

## Files and literal changes

### 1. `YardKit/Sources/YardUI/HistoryScrollRequest.swift` (new file)

```swift
// HistoryScrollRequest.swift
//
// #0401: a one-shot request for the History list to scroll a commit into
// view. Each request carries a fresh `serial`, so asking for the same commit
// twice (clicking the same sidebar branch again after scrolling away) is
// still a change `onChange(of:)` sees.

import Foundation

public nonisolated struct HistoryScrollRequest: Equatable, Sendable {
    /// The commit to scroll to, a full oid.
    public let oid: String
    /// Distinguishes two requests for the same oid.
    public let serial: UUID

    public init(oid: String) {
        self.oid = oid
        self.serial = UUID()
    }
}
```

```swift
    /// #0401: makes a branch or remote row clickable. A tap gesture rather
    /// than a `Button` keeps the row's `Label` text a plain static text,
    /// which the VM UI tests find the row by (`sidebarRow(named:)`).
    private func selectable<Content: View>(_ entry: RefSnapshot.Entry, _ content: Content) -> some View {
        content
            .contentShape(Rectangle())
            .onTapGesture { onSelectRef?(entry) }
            .listRowBackground(
                selectedRef == entry.name
                    ? RoundedRectangle(cornerRadius: 5).fill(Color.accentColor.opacity(0.25))
                    : nil)
    }
```

```swift
import Testing

@Test("two scroll requests for the same commit are distinct, so a repeat click scrolls again")
```
