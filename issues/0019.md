# 0019 — Engine signature verification: `SignatureVerification` in YardGit

| | |
|---|---|
| **Status** | in-progress |
| **Module** | YardGit |
| **Milestone** | M1 |
| **Platform** | macOS |
| **First seen** | 2026-08-06 |

## Description

Add signature verification for a single commit to the engine: a pure `YardGit` function that asks
git what it thinks of a commit's signature and returns a typed result — verification state, signature
format (SSH / OpenPGP / X.509 / none), signer identity, and key — instead of raw `%G?` characters.

This is the engine half only. The `switchyard verify` command surface, its JSON envelope, and its
exit codes are **out of scope** here (see Notes). The deliverable is one new source file and one new
test file:

1. `YardKit/Sources/YardGit/SignatureVerification.swift` — the type and its `run` entry point.
2. `YardKit/Tests/YardGitTests/SignatureVerificationTests.swift` — the tests listed below.

Why it matters: `docs/engine-findings.md` (#0002) establishes that verification is three-valued, not
two-valued — "no signature", "signature present but git cannot establish trust", and "good
signature" are distinct, and an agent that collapses the first two would reject most real
repositories. The measured behaviour below shows git makes this genuinely tricky: **`%G?` prints `N`
both for a truly unsigned commit and for a signed commit git could not check** — the two cases are
distinguishable only by stderr. That distinction is the core of this issue.

## Givens — verified

Everything in this section was executed on this machine on 2026-08-07 with
`git version 2.50.1 (Apple Git-155)`, in throwaway repositories, under a hermetic config
(`GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_SYSTEM=/dev/null`, `LC_ALL=C` — the same environment
the tests will use). `gpg` is not installed on this machine. Do not re-derive these; apply them.

### 1. Measured `%G?` and `git verify-commit` behaviour

On an **unsigned** commit (a plain `git commit` with `commit.gpgsign=false`, exactly what
`FixtureRepository` produces):

```
$ git log -1 --format='[%G?][%GS][%GK]' HEAD --
[N][][]                # exit 0, stderr empty
$ git verify-commit HEAD
# exit 1, stdout empty, stderr EMPTY — no message at all
```

So `verify-commit` cannot distinguish "unsigned" from "bad" by exit code, and prints nothing for
unsigned. That is why the implementation reads `%G?` from `git log` (always exit 0 for a resolvable
revision) rather than shelling to `git verify-commit`.

On a commit carrying a **structurally-valid but cryptographically garbage SSH signature block**
(built with `git hash-object -t commit -w --stdin --literally`; no key involved — see the test
helper below):

```
# gpg.ssh.allowedSignersFile NOT configured:
$ git log -1 --format='[%G?][%GS][%GK]' <sha> --
[N][][]                # exit 0
# stderr: error: gpg.ssh.allowedSignersFile needs to be configured and exist for ssh signature verification

# gpg.ssh.allowedSignersFile configured, pointing at an existing EMPTY file:
$ git log -1 --format='[%G?][%GS][%GK]' <sha> --
[B][][]                # exit 0, stderr empty
```

On a commit carrying a garbage **PGP** signature block, with `gpg.program` set (local config) to a
path that does not exist — the deterministic stand-in for "gpg is absent", measured identical to a
machine with no gpg on PATH except for the message wording:

```
$ git log -1 --format='[%G?]' <sha> --
[N]                    # exit 0
# stderr: fatal: cannot exec '/nonexistent-gpg-for-test': No such file or directory
# (with gpg simply absent from PATH the message is:
#  error: cannot run gpg: No such file or directory — same N flag, same exit 0)
```

On a revision that does not resolve:

```
$ git log -1 --format='%G?' deadbeef
# exit 128, stderr: fatal: ambiguous argument 'deadbeef': unknown revision or path not in the working tree. …
```

**The parse rule that falls out of all four measurements:** `N` with empty stderr means *unsigned*;
`N` with non-empty stderr means *could not check*; every other documented flag maps directly. stderr
is stable English because `GitProcess` already exports `LC_ALL=C` on every invocation.

### 2. Which `%G?` values were produced locally, and which were not

Git documents the full set as `G`, `B`, `U`, `X`, `Y`, `R`, `E`, `N`. Locally produced and measured:
**`N`** (unsigned) and **`B`** (garbage SSH block + existing allowed-signers file). The remaining six
(`G`, `U`, `X`, `Y`, `R`, `E`) require a real signing key, a trust database, or key
expiry/revocation state, and **signing assets must not be created in this project** — so those
states are covered by unit tests of the pure `parse` function on fixed flag input, not by live
repositories. The integration tests assert only the `N`- and `B`-producible paths.

### 3. What `docs/engine-findings.md` says (verbatim quotes)

> **`gpg.ssh.allowedSignersFile` is not optional for verification.** Without it git reports the
> signature as untrusted rather than good — the signature is valid, but git has no basis to trust
> the key. `yard verify` (#0019) must distinguish "no signature", "signature present but signer not
> allowed", and "good signature", which is three states, not two.

and, from the 2026-08-07 re-confirmation with a real key:

> The `allowedSignersFile` behaviour reproduced exactly as recorded below — without it, the same
> valid signature reports as **No signature**, which is why `verify` has three states and not two.

The measurement above shows the mechanism: without the file, `%G?` is literally `N` and only stderr
says why. #0108's `SigningConfig.canVerifySSHSignatures` already encodes the config-side of this;
this issue encodes the verification-side.

### 4. `GitProcess` — the only way to run git (verbatim from `YardKit/Sources/YardGit/GitProcess.swift`)

```swift
public struct GitProcess: Sendable {

    public enum Failure: Error, CustomStringConvertible, Sendable {
        /// `git` ran and exited non-zero. Carries stderr, because a bare exit
        /// code tells whoever hits it nothing.
        case exited(code: Int32, stderr: String, arguments: [String])
        /// `git` could not be launched at all.
        case launchFailed(String)
    }

    public struct Output: Sendable {
        public let standardOutput: Data
        public let standardError: String
        public let exitCode: Int32

        /// stdout decoded as UTF-8, lossily.
        public var text: String

        /// stdout split into lines with the trailing empty element removed.
        public var lines: [String]
    }

    @discardableResult
    public func run(
        _ arguments: [String],
        workingDirectory: String? = nil,
        standardInput: Data? = nil,
        extraEnvironment: [String: String] = [:]
    ) throws -> Output

    public func capture(
        _ arguments: [String],
        workingDirectory: String? = nil,
        standardInput: Data? = nil,
        extraEnvironment: [String: String] = [:]
    ) throws -> Output
}
```

**`run` throws `Failure.exited` on any non-zero exit; `capture` returns whatever happened and never
throws on exit code.** Use `run` here: every git call this issue makes exits 0 on success, and a
failed revision lookup (exit 128) should propagate as the thrown `GitProcess.Failure`. Note that
`run`'s returned `Output` still carries `standardError` — git writes verification *warnings* to
stderr while exiting 0, and that stderr is load-bearing for the parse rule above.

### 6. The existing `SignatureStatus` in `CommitLog.swift` — do NOT reuse it

`YardKit/Sources/YardGit/CommitLog.swift` already parses `%G?`, verbatim:

```swift
/// GPG signature outcome from `git log --format=%G?`. Only the single-character flag matters.
public enum SignatureStatus: String, Sendable {
    /// No signature information present (typically unsigned commits).
    case noSig

    /// Good, but unverified signature.
    case valid     // %G? -> `g`

    /// Verification failed: bad key, tampered message.
    case invalid   // %G? -> `G`

    public init(_ flag: String) {
        let ch = flag.isEmpty ? "n" : String(flag.first.flatMap(Character.init) ?? Character("n"))
        switch ch {
        case "g": self = .valid
        case "G": self = .invalid
        default:  self = .noSig
        }
    }
}
```

**Decision: this issue defines its own vocabulary and does not touch `SignatureStatus`.** The
existing mapping contradicts git's documented and measured behaviour: git emits uppercase `G` for a
*good* signature and never emits lowercase `g` at all (the documented set is `G B U X Y R E N`), so
`SignatureStatus` reports a good signature as `.invalid` and can never produce `.valid`. Reusing it
would import that defect into verification; fixing it is a separate change with its own blast radius
through `CommitLogEntry` and its tests, tracked as a follow-up (see Notes). Do not modify
`CommitLog.swift` in this issue.

## The API to implement

`YardKit/Sources/YardGit/SignatureVerification.swift`, in full:

```swift
// SignatureVerification.swift — typed result of asking git to verify one commit's signature

import Foundation

/// The outcome of verifying one commit's signature, read from
/// `git log -1 --format=%G?%x01%GS%x01%GK <revision> --` plus the commit's raw
/// `gpgsig` header (for format detection, via `git cat-file commit`).
///
/// Three-valued by design (docs/engine-findings.md, #0002): "no signature",
/// "signature present but git cannot check it", and the checked states are all
/// distinct. `%G?` alone cannot express that — it prints `N` both for an
/// unsigned commit and for a signature git could not check (missing
/// gpg.ssh.allowedSignersFile, missing gpg binary) — so `parse` reads stderr
/// too. Reporting only: nothing here signs anything or creates keys.
public struct SignatureVerification: Equatable, Sendable {

    /// Verification state, mapped from git's `%G?` flag plus stderr.
    public enum State: Equatable, Sendable {
        /// `%G?` = `N` with empty stderr: the commit carries no signature.
        case noSignature
        /// `%G?` = `G`: good, trusted signature.
        case good
        /// `%G?` = `U`: good signature, but the key's trust is unknown.
        case goodUntrusted
        /// `%G?` = `B`: bad signature.
        case bad
        /// `%G?` = `X`: good signature that has expired.
        case expiredSignature
        /// `%G?` = `Y`: good signature made by an expired key.
        case expiredKey
        /// `%G?` = `R`: good signature made by a revoked key.
        case revokedKey
        /// `%G?` = `E`, or `N` with a non-empty stderr, or an unrecognized
        /// flag: the signature could not be checked. `reason` is git's stderr
        /// (trimmed), or a fixed fallback when stderr is empty.
        case cannotCheck(reason: String)
    }

    /// Signature format, detected from the raw commit object's signature
    /// header (`gpgsig` or `gpgsig-sha256`), not from config — a repository
    /// can contain commits signed under a different configuration than its
    /// current one.
    public enum Format: Equatable, Sendable {
        /// `-----BEGIN SSH SIGNATURE-----`
        case ssh
        /// `-----BEGIN PGP SIGNATURE-----` (or `PGP MESSAGE`)
        case openpgp
        /// `-----BEGIN SIGNED MESSAGE-----` (gpgsm / X.509)
        case x509
        /// No signature header on the commit at all.
        case none
        /// A signature header whose armor matches none of the above.
        case unrecognized
    }

    public let state: State
    public let format: Format
    /// `%GS` — signer identity as git reports it. `nil` when git printed nothing.
    public let signer: String?
    /// `%GK` — the key git used. `nil` when git printed nothing.
    public let key: String?

    public init(state: State, format: Format, signer: String?, key: String?) {
        self.state = state
        self.format = format
        self.signer = signer
        self.key = key
    }

    /// Verifies the signature on `revision` in the repository at
    /// `workingDirectory`.
    ///
    /// Two git invocations, both through `GitProcess.run` so a bad revision or
    /// missing repository propagates as `GitProcess.Failure`:
    ///
    /// 1. `git log -1 --format=%G?%x01%GS%x01%GK <revision> --` — flag, signer,
    ///    key on stdout (exit 0 even when checking fails); the *why* on stderr.
    /// 2. `git cat-file commit <revision>` — raw object, for format detection.
    ///
    /// - Parameter extraEnvironment: merged over the process environment for
    ///   both invocations. Tests use it to neutralize global and system config
    ///   scope; production callers leave it empty.
    public static func run(
        revision: String,
        in workingDirectory: String,
        git: GitProcess = GitProcess(),
        extraEnvironment: [String: String] = [:]
    ) throws -> SignatureVerification {
        let logOutput = try git.run(
            ["log", "-1", "--format=%G?\u{01}%GS\u{01}%GK", revision, "--"],
            workingDirectory: workingDirectory,
            extraEnvironment: extraEnvironment
        )
        let fields = (logOutput.lines.first ?? "")
            .split(separator: "\u{01}", omittingEmptySubsequences: false)
            .map(String.init)
        let rawCommit = try git.run(
            ["cat-file", "commit", revision],
            workingDirectory: workingDirectory,
            extraEnvironment: extraEnvironment
        )
        return parse(
            flag: fields.count > 0 ? fields[0] : "",
            signer: fields.count > 1 ? fields[1] : "",
            key: fields.count > 2 ? fields[2] : "",
            stderr: logOutput.standardError,
            format: detectFormat(rawCommit: rawCommit.text)
        )
    }

    /// Pure mapping from git's outputs to a result. Exposed internally so the
    /// states that cannot be produced without a real signing key (`G`, `U`,
    /// `X`, `Y`, `R`, `E`) are still unit-tested.
    static func parse(
        flag: String,
        signer: String,
        key: String,
        stderr: String,
        format: Format
    ) -> SignatureVerification {
        let reason = stderr.trimmingCharacters(in: .whitespacesAndNewlines)
        let state: State
        switch flag {
        case "G": state = .good
        case "U": state = .goodUntrusted
        case "B": state = .bad
        case "X": state = .expiredSignature
        case "Y": state = .expiredKey
        case "R": state = .revokedKey
        case "E": state = .cannotCheck(reason: reason.isEmpty ? "signature cannot be checked" : reason)
        case "N": state = reason.isEmpty ? .noSignature : .cannotCheck(reason: reason)
        default:  state = .cannotCheck(reason: "unrecognized %G? flag \"\(flag)\"")
        }
        return SignatureVerification(
            state: state,
            format: format,
            signer: signer.isEmpty ? nil : signer,
            key: key.isEmpty ? nil : key
        )
    }

    /// Detects the signature format from a raw commit object (the text output
    /// of `git cat-file commit`). Looks only inside the header block — the
    /// text before the first blank line — so a message body that *mentions*
    /// `gpgsig` cannot confuse it. Recognizes both `gpgsig` and
    /// `gpgsig-sha256` header names. The armor label decides the format, per
    /// the measurement that git stores SSH and PGP signatures under the same
    /// `gpgsig` header.
    static func detectFormat(rawCommit: String) -> Format {
        let header = rawCommit.components(separatedBy: "\n\n").first ?? rawCommit
        let lines = header.split(separator: "\n", omittingEmptySubsequences: false)
        var signatureLines: [Substring] = []
        var inSignature = false
        for line in lines {
            if line.hasPrefix("gpgsig ") || line.hasPrefix("gpgsig-sha256 ") {
                inSignature = true
                signatureLines.append(line)
            } else if inSignature, line.hasPrefix(" ") {
                // Header continuation lines start with a single space.
                signatureLines.append(line)
            } else {
                inSignature = false
            }
        }
        guard !signatureLines.isEmpty else { return .none }
        let signature = signatureLines.joined(separator: "\n")
        if signature.contains("BEGIN SSH SIGNATURE") { return .ssh }
        if signature.contains("BEGIN PGP SIGNATURE") || signature.contains("BEGIN PGP MESSAGE") {
            return .openpgp
        }
        if signature.contains("BEGIN SIGNED MESSAGE") { return .x509 }
        return .unrecognized
    }
}
```

Implement it exactly as written. The `\u{01}` field separator matches the `%x01` convention
`CommitLog.formatString` already uses.

## The tests to implement

`YardKit/Tests/YardGitTests/SignatureVerificationTests.swift`. Follow the local conventions in
`YardKit/Tests/YardGitTests/SigningConfigTests.swift`: `import Testing`, `@testable import YardGit`,
top-level `@Test` functions, `defer { repo.destroy() }`, and the hermetic environment:

```swift
private let hermetic = ["GIT_CONFIG_GLOBAL": "/dev/null", "GIT_CONFIG_SYSTEM": "/dev/null"]
```

Pass `extraEnvironment: hermetic` on every `SignatureVerification.run` call so the developer's real
global signing config cannot leak into an assertion.

Two helpers, private to the test file — this is how a *signed* commit is produced **without creating
any key**: hand-build the commit object bytes and write them with `git hash-object`:

```swift
/// A structurally-valid, cryptographically garbage SSH signature block.
/// Continuation lines carry exactly one leading space — that is the commit
/// object header-continuation syntax, and it is load-bearing.
private let fakeSSHSignatureBlock = """
gpgsig -----BEGIN SSH SIGNATURE-----
 U1NIU0lHAAAAAWZha2VmYWtlZmFrZQ==
 -----END SSH SIGNATURE-----
"""

private let fakePGPSignatureBlock = """
gpgsig -----BEGIN PGP SIGNATURE-----
 iQFAKEFAKEFAKE=
 =fake
 -----END PGP SIGNATURE-----
"""

/// Writes a commit object whose signature header is `block`, returns its sha.
/// `--literally` skips object validation; the object is real and resolvable.
private func craftedCommit(in repo: FixtureRepository, block: String) throws -> String {
    let tree = try repo.revParse("HEAD^{tree}")
    let ident = "Fixture <fixture@example.invalid> 1700000000 +0000"
    let object = """
    tree \(tree)
    author \(ident)
    committer \(ident)
    \(block)

    crafted signed commit
    """ + "\n"
    let out = try GitProcess().run(
        ["hash-object", "-t", "commit", "-w", "--stdin", "--literally"],
        workingDirectory: repo.url.path,
        standardInput: Data(object.utf8)
    )
    return out.lines[0]
}
```

The tests, by name — engine work runs against **both ref formats**, so the two fixture-backed state
tests are parameterized over `FixtureRepository.RefFormat.supported()`:

1. `unsignedCommitReportsNoSignature(format:)` — `@Test(arguments:
   FixtureRepository.RefFormat.supported())`. One-commit fixture; `run(revision: "HEAD", …)` returns
   `state == .noSignature`, `format == Format.none`, `signer == nil`, `key == nil`.
2. `craftedBadSSHSignatureReportsBad(format:)` — parameterized the same way. Build the fixture,
   `craftedCommit` with `fakeSSHSignatureBlock`, then
   `try repo.writeUntracked(["allowed_signers": ""])` and
   `git config gpg.ssh.allowedSignersFile <repo.url.path>/allowed_signers` (via
   `GitProcess().run(["config", …], workingDirectory: repo.url.path)`). Expect `state == .bad` and
   `format == .ssh` — the measured `[B]` case.
3. `sshSignatureWithoutAllowedSignersFileIsCannotCheckNotNoSignature` — same crafted commit, **no**
   allowed-signers config. Expect
   `case .cannotCheck(let reason) = result.state` with `reason.contains("allowedSignersFile")`, and
   additionally `#expect(result.state != .noSignature)` — this is the three-state distinction, and
   it fails if `run` drops stderr or `parse` ignores it.
4. `missingGpgToolReportsCannotCheckWithOpenPGPFormat` — crafted commit with
   `fakePGPSignatureBlock`; set local config `gpg.program` to
   `/nonexistent-gpg-for-test` (a path that must not exist — measured to produce
   `N` + `fatal: cannot exec …` regardless of whether a real gpg is installed, so this test is
   deterministic on any machine). Expect `.cannotCheck` with `reason.contains("cannot exec")`, and
   `format == .openpgp`. This is the "gpg absent" criterion: the state is reported, not thrown.
5. `unknownRevisionThrows` — `#expect(throws: GitProcess.Failure.self)` around
   `run(revision: "deadbeef", …)`.
6. `flagMappingsMatchGitsDocumentedSet` — pure `parse` calls, one `#expect` per documented flag:
   `G → .good`, `U → .goodUntrusted`, `B → .bad`, `X → .expiredSignature`, `Y → .expiredKey`,
   `R → .revokedKey`, `E → .cannotCheck`, `N` (empty stderr) `→ .noSignature`. This is where the six
   states that need a real key are covered.
7. `flagNWithStderrIsCannotCheckAndCarriesReason` — `parse(flag: "N", …, stderr: "error: …")`
   returns `.cannotCheck` whose reason equals the trimmed stderr.
8. `unrecognizedFlagIsCannotCheck` — `parse(flag: "?", …)` returns `.cannotCheck`.
9. `emptySignerAndKeyBecomeNil` — empty strings map to `nil`; non-empty (`"Fixture
   <fixture@example.invalid>"`, `"SHA256:abc"`) pass through unchanged.
10. `detectFormatRecognizesEachArmor` — `detectFormat` on five literal raw-commit strings: the SSH
    block → `.ssh`, the PGP block → `.openpgp`, a `BEGIN SIGNED MESSAGE` block → `.x509`, no
    `gpgsig` header → `Format.none`, a `gpgsig` header with unrecognizable armor → `.unrecognized`.
11. `detectFormatIgnoresGpgsigTextInMessageBody` — a raw commit whose *body* contains the literal
    line `gpgsig -----BEGIN SSH SIGNATURE-----` but whose header has no signature → `Format.none`.

## Notes

Guide §5 "Signing implementation" and §6; `docs/engine-findings.md` #0002 findings; #0108 landed the
config-reporting half (`SigningConfig`).

**CLI wiring is deliberately absent.** The original draft of this issue included a `switchyard
verify` command and an exit-code-9 rule. Whether the CLI may call `YardGit` directly or must marshal
over XPC to the app-owned engine is the open architectural question behind #0115, and #0124 showed
what wiring built ahead of that decision costs. The command surface, JSON envelope, and exit codes
land in a follow-up once #0115 settles. Nothing in this issue links the CLI to anything.

**What this issue cannot cover without signing assets, stated plainly:** live production of `G`,
`U`, `X`, `Y`, `R`, and `E` requires a real key (and, for `X`/`Y`/`R`, expiry or revocation state).
Creating keys is off limits here — no `ssh-keygen` into `~/.ssh`, no gpg key generation, no keychain
writes — so those states are covered by unit tests of `parse` on fixed flags (test 6), and the live
integration tests cover exactly the measured `N` and `B` paths plus the two stderr-driven
`cannotCheck` paths. End-to-end good-signature coverage becomes possible only in an environment with
a provisioned signing key, which is a human-run check, not a criterion of this issue.

**Follow-up worth filing (not part of this issue):** `SignatureStatus` in `CommitLog.swift` maps
`%G?` incorrectly — git emits uppercase `G` for *good* and never emits lowercase `g`, so
`.valid` is unreachable and good signatures parse as `.invalid`. `CommitLogEntry.signatureStatus`
should eventually be rebased onto this issue's `State`; that migration touches `CommitLogTests` and
is its own change.

The three-state distinction matters: an agent treating "unsigned" as "invalid" would reject most
real repositories — and, per the measurements above, an agent treating "could not check" as
"unsigned" would silently hide every SSH-signed commit in a repository with no allowed-signers file.
