# Response schema contract — version 1

The `.json` files in this directory are the versioned contract for every `switchyard` command's
stdout. One file per command, named `<schemaName>.json`, generated by `renderSchema(for:)` in
`Sources/YardKit/SchemaEmitter.swift` from the same `CommandRegistry` metadata that builds
`--help` and `switchyard schema` — the schema cannot drift from the binary because both are
renderings of one source.

They are generated, committed, and **drift-tested**:
`SchemaGoldenTests.checkedInSchemasMatchEmitter` re-renders every schema from the code on each
`swift test` run and fails on any byte difference, and the companion tests assert that the
envelope shapes declared here match what a real encoded `Envelope`/`EnvelopeFail` actually emits.
A shape change therefore cannot land silently: the suite is red until the file is regenerated,
and the regenerated file's diff is what review reads.

To regenerate after an intentional change:

    SCHEMA_REGENERATE=1 swift test --filter checkedInSchemasMatchEmitter

then commit the changed files in the same commit as the code change that caused them.

## What `schemaVersion: 1` covers

One number, envelope-wide. There are no per-command versions: every envelope from every command
carries the same `schemaVersion`, and an agent checks it once per response. Version 1 promises:

- The envelope keys and types — `schemaVersion` (int), `ok` (bool), `result` (object, success
  only, may be omitted), `error` (object, failure only, with `code`, `message`, and optional
  `hint`).
- The closed set of `error.code` strings, and that each pairs with the process exit status the
  same way `EnvelopeErrorCode.exitCode` does.
- Each command's result payload **is named** by its `schemaName`, and that name is stable.
- Each field of a documented payload — its wire key, JSON scalar type, whether it is optional (see
  below), and, for a closed string enum, its case list — is published in that command's schema
  file, under `envelope.success.result.fields`.

**History, corrected 2026-08-17 and again by #0194:** until #0194, every generated success shape was
`"result": {"optional": true, "schema": "<schemaName>"}` — a self-reference naming no field, type or
enum — because `CommandSpec` had no field that could hold one. #0194 (guide §11 decision 21) added
`CommandSpec.payload`, and `SchemaEmitter` now renders a real field list when a command supplies one.
A command that has not supplied a shape yet — or one with genuinely no payload, like `noop` — still
gets the historical self-reference; see `CommandSpec`'s doc comment in `Sources/YardKit/CommandSpec.swift`
for exactly when each form applies.

The payload bytes are pinned twice over: the `YardWireTests` byte literals pin the exact JSON, and
(for `whereami`, the first command to carry a shape) `WhereAmIWireTests.schemaFieldNamesMatchTheEncodedKeysExactly`
binds the schema file's declared field names back to the type's actual encoded keys, so the two
cannot drift silently.

## What is a breaking change

Breaking — requires bumping the version:

- Removing or renaming any key an agent can currently read, in the envelope or in a payload. For a
  command with a published payload shape (`whereami`, so far), this is enforced by the checked-in
  schema file plus the `YardWireTests` binding above; a command that has not been given a shape yet
  still relies on its `YardWireTests` byte literals alone.
- Changing a key's JSON type, or changing what an existing enum string means.
- Removing an `error.code` string, or changing the exit code it pairs with.
- Making a previously always-present key optional.

Not breaking — the version stays where it is:

- Adding a new optional key to a payload or to the envelope.
- Adding a new command, a new `error.code` string, or a new enum value agents can ignore.
- Text-only changes to `summary`, `help`, or `meaning` strings.

An additive change still fails the drift test and still regenerates the schema file. The version
number is a promise about compatibility, not a hash of the bytes: classifying a change as
breaking or additive is review's job, and the drift test's job is to make sure review sees every
change.

## What happens at version 2

`EnvelopeSchema` gains `case v2 = 2`, every envelope emits the new number simultaneously, and the
version-1 files move to `Schemas/v1/` and freeze — they document what agents pinned to 1 were
promised. There is no dual emission and no negotiation: an agent that reads `schemaVersion: 2`
and only knows version 1 must treat the response as unparseable rather than guess.
